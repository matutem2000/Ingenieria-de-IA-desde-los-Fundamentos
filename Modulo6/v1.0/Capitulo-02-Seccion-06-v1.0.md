# Módulo 6 – Capítulo 02 – Sección 06

## Cierre: elegir el modelo de embedding correcto para el dominio del problema

La elección del modelo de embedding es la decisión técnica con mayor impacto en la calidad de todo el sistema RAG porque establece el techo de lo que el retriever puede lograr: ninguna técnica de búsqueda híbrida, reranking o expansión de queries puede recuperar lo que el embedding ha perdido al proyectar el texto al espacio vectorial. Si el modelo de embedding no captura que "insuficiencia renal crónica estadio 3" y "CKD G3" son sinónimos exactos en el dominio médico, la búsqueda semántica fallará sistemáticamente en ese tipo de queries, y el reranking no puede corregir lo que el retriever no ha recuperado. Esta asimetría entre la importancia de la decisión y el esfuerzo requerido para tomarla bien —un proceso de evaluación sistemático de días, no semanas— es la razón por la que muchos proyectos RAG se lanzan con el modelo de embedding incorrecto: la evaluación interna parece opcional hasta que las métricas de calidad en producción muestran que no lo era.

El proceso de selección correcto sigue cuatro pasos que deben ejecutarse en orden. Primero, construir el dataset de evaluación interno: 100–500 pares (query, [chunk\_ids\_relevantes]) representativos del uso real del sistema, anotados por expertos del dominio si es posible o generados con LLM y validados manualmente para los casos más importantes. Este dataset es el activo más valioso del proceso de selección y se reutilizará en cada iteración del sistema. Segundo, identificar los candidatos razonables a partir del leaderboard de MTEB Retrieval: típicamente 4–6 modelos que incluyen el líder general (actualmente voyage-3 en muchos dominios), el mejor open source (BGE-M3 o nomic-embed-v1.5), el modelo de OpenAI (text-embedding-3-large), y si existe, el modelo especializado en el dominio (voyage-law-2, voyage-finance-2, voyage-code-3). Tercero, ejecutar la evaluación de todos los candidatos sobre el dataset interno con las métricas definidas (Recall@5, NDCG@10, latencia p99) y ordenarlos. Cuarto, seleccionar el modelo que muestra el mejor balance entre rendimiento de recuperación, costo por millón de tokens, latencia y riesgo de lock-in al proveedor.

La consideración del **lock-in** es frecuentemente subestimada en la selección inicial. Los modelos de API como OpenAI text-embedding-3 o Voyage AI voyage-3 pueden ser deprecados por el proveedor, forzando una reindexación completa del corpus; OpenAI deprecated text-embedding-ada-002 en 2024, y los equipos que habían indexado millones de documentos con ese modelo tuvieron que planificar una migración costosa. Los modelos open source como BGE-M3 y nomic-embed-v1.5, alojados en infraestructura propia bajo licencias Apache 2.0, eliminan este riesgo: el modelo siempre está disponible bajo control del equipo, independientemente de las decisiones del proveedor. El precio de este control es la necesidad de infraestructura de serving (una GPU de al menos 8GB VRAM para BGE-M3) y la responsabilidad de gestionar las actualizaciones del modelo.

En producción, el modelo de embedding debe tratarse como un **componente versionado del sistema**: el índice vectorial está acoplado a la versión específica del modelo que generó sus vectores, y cambiar el modelo implica reindexar todo el corpus con el nuevo modelo antes de poder usar el nuevo índice en producción. Esta dependencia de versión debe registrarse explícitamente en los metadatos de cada vector (campo `embedding_model_version` en el payload de Qdrant o Pinecone) para poder auditar qué modelo generó qué parte del índice y coordinar las migraciones correctamente.

## Criterios de selección del modelo de embedding

| Criterio | Opciones a considerar |
|---|---|
| Rendimiento en dominio (Recall@5 en dataset interno) | Evaluate todos los candidatos; diferencias de 5–10 puntos son decisivas |
| Costo por millón de tokens en ingesta | text-embedding-3-small ($0.02) vs. voyage-3 ($0.06) vs. BGE-M3 (self-hosted ~$0.001) |
| Costo por millón de tokens en serving | Mismo cálculo que ingesta, multiplicado por el volumen diario de queries |
| Riesgo de lock-in al proveedor | Open source (cero lock-in) vs. API propietaria (riesgo de deprecación) |
| Latencia de embedding de queries en serving | API: 50–200ms; modelo local GPU: 5–20ms; modelo local CPU: 50–500ms |
| Dimensionalidad y uso de memoria del índice | 256 (MRL truncado) a 3072; impacto directo en el costo de la base vectorial |

> **Nota del Arquitecto**: El criterio de selección más ignorado es la latencia de embedding de queries en tiempo de serving, no en ingesta. Un modelo que tarda 200ms en embedir cada query del usuario añade esa latencia a cada consulta del sistema RAG, impactando directamente la experiencia del usuario. Para sistemas con SLO de latencia total <1 segundo, un modelo de embedding que consume 200ms del presupuesto es un problema desde el día uno.

La selección del modelo de embedding correcta, respaldada por evaluación empírica en el dominio específico, es la inversión técnica de mayor retorno en las primeras semanas de un proyecto RAG. Los capítulos siguientes construyen sobre esta base: el Capítulo 3 analiza las bases de datos vectoriales que almacenan y sirven los embeddings; el Capítulo 4 aborda el chunking que determina qué texto se embide; y el Capítulo 5 desarrolla las estrategias de recuperación que usan los embeddings para encontrar el conocimiento correcto.

*"En cualquier sistema de recuperación de información, la calidad de la representación es el límite superior de la calidad de la recuperación; ninguna mejora algorítmica posterior puede superar la información perdida en la proyección al espacio latente."* — Gerard Salton, pionero de la recuperación de información moderna y creador del modelo vectorial espacial.
