# Módulo 6 – Capítulo 03 – Sección 03

## Criterios de selección: escala, latencia, consistencia y gestión de metadatos

Elegir una base de datos vectorial sin antes definir los requisitos operativos del sistema es una de las decisiones arquitectónicas más costosas de revertir en un proyecto RAG. Un sistema que comienza con Chroma porque era el más simple de integrar con LangChain y llega a producción con 5 millones de vectores enfrenta una migración que implica reindexar todo el corpus, adaptar el código de integración y potencialmente rediseñar el esquema de metadatos. Este costo de migración es evitable si los criterios de selección se definen con rigor antes de elegir: escala de vectores objetivo, latencia p99 admisible en búsqueda, modelo de consistencia de escritura requerido, complejidad de los filtros de metadatos de producción y restricciones de soberanía de datos.

La **escala de vectores** es el criterio más directamente observable. Los sistemas en fase de prototipo raramente superan los 100K vectores; los sistemas en producción a los seis meses raramente están por debajo del millón; los sistemas maduros en organizaciones medianas con corpus documental activo tienen entre 5 y 50 millones de vectores. La regla práctica es planificar para 10x el volumen inicial esperado: si el corpus inicial tiene 100K documentos y cada uno produce 10 chunks, el índice empezará con 1M vectores y crecerá; elegir una plataforma calibrada para el volumen inicial garantiza que será insuficiente en 12–18 meses. Chroma con SQLite es operativamente adecuado hasta aproximadamente 500K vectores; pgvector funciona bien hasta ~5M vectores en RAM; Qdrant y Weaviate self-hosted están optimizados para 1M–500M vectores; Pinecone serverless y Weaviate Cloud escalan automáticamente más allá de ese rango.

La **latencia p99** —no la media ni la mediana— es la métrica operativa crítica para sistemas RAG de producción. La razón es que el percentil 99 determina la peor experiencia que el 1% de los usuarios experimentan en cada momento; para un sistema con 1000 queries por segundo, eso son 10 usuarios simultáneos experimentando la latencia máxima. Qdrant en Rust con gRPC alcanza p99 <10ms para corpus de 1M vectores completamente en memoria. Pinecone serverless puede tener p99 de 100–300ms para colecciones activas y varios segundos para cold starts en colecciones inactivas. pgvector tiene p99 comparable a Qdrant para corpus en RAM, pero se degrada a 50–200ms cuando el índice requiere I/O a disco. Para sistemas con SLO de latencia total <500ms (incluyendo embedding de la query, búsqueda vectorial, reranking y generación), la base vectorial debe contribuir con menos de 50ms en p99.

La **consistencia de escritura** determina cuánto tiempo tarda un documento recién ingresado en aparecer en los resultados de búsqueda. Pinecone serverless tiene consistencia eventual: un vector insertado puede tardar 1–5 segundos en ser consultable. Qdrant y pgvector tienen consistencia sincrónica: un vector insertado con éxito es inmediatamente consultable. Weaviate tiene consistencia configurable (ONE, QUORUM, ALL para escrituras replicadas). Para casos de uso donde el usuario espera ver en los resultados documentos que acaba de cargar (por ejemplo, un sistema donde el usuario sube un contrato y luego lo consulta de inmediato), la consistencia eventual de Pinecone puede producir experiencias de usuario incorrectas que requieren lógica de compensación.

La **gestión de metadatos** es el criterio más frecuentemente ignorado en la selección inicial y el que más frecuentemente causa problemas en producción. En un sistema RAG empresarial real, prácticamente toda consulta tiene algún filtro de metadatos: el asistente legal filtra por cliente, el chatbot de soporte filtra por versión de producto, el sistema de cumplimiento filtra por fecha de vigencia de la regulación. No todas las bases vectoriales tienen el mismo soporte para filtros de alta cardinalidad (donde el filtro elimina más del 90% del corpus) ni para tipos de filtros complejos (rango de fechas, geo-proximidad, pertenencia a conjunto). Qdrant tiene el soporte más completo: tipos ricos (Match, Range, GeoRadius, IsNull, IsEmpty, HasId), operadores anidables (must, should, must\_not equivalentes a AND, OR, NOT) y filtrado pre-ANN que mantiene el recall incluso con filtros muy selectivos.

## Criterios técnicos de selección

- **Escala de vectores**: Chroma y Redis VSS para <500K vectores (prototipado); pgvector para 500K–5M en RAM; Qdrant y Weaviate self-hosted para 1M–500M; Pinecone serverless y Weaviate Cloud para >100M con escalado automático.
- **Latencia p99 objetivo**: Qdrant (Rust, gRPC) tiene la menor latencia p99 para búsqueda local; Pinecone managed tiene latencia variable por cold start; pgvector tiene p99 comparable a Qdrant para corpus en memoria pero se degrada con corpus que no caben en RAM.
- **Consistencia de escritura**: Pinecone serverless: eventual (1–5 segundos); Qdrant y pgvector: sincrónica; Weaviate: configurable por nivel de consistencia; crítico para UX cuando el usuario espera ver documentos recién ingresados.
- **Soberanía de datos**: para documentos confidenciales que no pueden salir de la infraestructura propia, Qdrant, Weaviate self-hosted y pgvector son las únicas opciones; Pinecone y Weaviate Cloud requieren enviar vectores a infraestructura del proveedor.
- **Filtrado de metadatos complejos**: Qdrant implementa filtrado pre-ANN para alta selectividad; Weaviate tiene filtrado nativo con motor de inverted index integrado; pgvector soporta filtros SQL estándar pero ejecuta filtrado post-ANN; Pinecone tiene filtrado con índice acoplado.
- **Multi-tenant**: Qdrant soporta colecciones y namespaces por tenant con aislamiento configurable; Pinecone soporta namespaces dentro de un índice (aislamiento lógico, no físico); pgvector puede usar tablas separadas por tenant con RLS de PostgreSQL.

> **Nota del Arquitecto**: El error de selección más costoso que he visto en proyectos RAG es elegir Chroma para el prototipo con la intención de "migrar después a algo más robusto". La migración nunca es tan simple como parece: el esquema de metadatos de Chroma (un diccionario Python simple) es incompatible con el esquema tipado de Qdrant o Pinecone; las rutas de código que asumen la API de Chroma están distribuidas por todo el sistema; y el reindexado tarda horas que el equipo no tiene en el momento en que la presión de producción obliga a migrar. La decisión correcta: usar pgvector si ya tienes Postgres, o Qdrant si no, desde el primer día.

La definición de los requisitos operativos antes de elegir la base vectorial convierte una decisión potencialmente costosa en una elección técnica metódica. Con la base vectorial elegida correctamente, las secciones siguientes profundizan en sus características operativas más importantes: el filtrado híbrido para combinar búsqueda semántica con filtros de metadatos de negocio.
