# Módulo 6 – Capítulo 07 – Sección 01

## Arquitectura de producción: desacoplamiento de ingesta, índice y serving

La distancia entre un prototipo de RAG que funciona en un notebook de Jupyter y un sistema que atiende 10.000 consultas diarias con latencia p99 <500ms y disponibilidad del 99.5% es exactamente la distancia entre una función Python y un sistema distribuido. El prototipo tiene todo en un solo proceso: el parser, el embedder, el indexador, el retriever y el generador se ejecutan secuencialmente cuando se llama a `qa_chain.invoke(query)`. Esta arquitectura monolítica es perfecta para demostrar el concepto, pero imposible de escalar: la ingesta de un documento nuevo tarda el mismo tiempo que responder una query del usuario, el fallo de cualquier componente tumba todo el sistema, y la demanda variable de recursos de la ingesta compite con la demanda constante de baja latencia del serving.

La arquitectura de producción madura hacia **tres planos desacoplados** que operan de forma independiente y se comunican de forma asíncrona. El **plano de ingesta** (ingest plane) es el pipeline que procesa documentos: recibe documentos crudos desde los sistemas de origen, los parsea, limpia, chunkea, embide y persiste los vectores en la base vectorial. Este plano opera típicamente en ventanas batch (procesamiento nocturno de todos los documentos modificados desde el día anterior) o en streaming event-driven (procesamiento en tiempo real de cada documento modificado). Sus recursos dominantes son CPU para el parsing y la manipulación de texto, y ancho de banda de red para las llamadas a la API de embedding si se usa un modelo managed. El **plano de índice** (index plane) es la base de datos vectorial propiamente dicha: almacena los vectores y metadatos, sirve las búsquedas ANN y mantiene la consistencia del índice. El **plano de serving** (query plane) es el pipeline que procesa las consultas de los usuarios: recibe la query, la embide, ejecuta la búsqueda vectorial, aplica reranking si está configurado, construye el contexto y llama al LLM generador. Sus recursos dominantes son la latencia de respuesta (p99 <500ms es el SLO típico) y la concurrencia de solicitudes simultáneas.

El desacoplamiento de los tres planos tiene consecuencias operacionales inmediatas. La ingesta puede escalarse horizontalmente con workers Kubernetes adicionales durante picos de carga (una reorganización departamental que requiere reindexar 50.000 documentos en una noche) sin afectar la disponibilidad del serving. El serving puede escalarse independientemente para manejar picos de tráfico (fin de mes, cuando más usuarios consultan el sistema de conocimiento) sin aumentar la capacidad de ingesta. El plano de índice puede tener réplicas de lectura dedicadas para el serving, separadas de las instancias de escritura que reciben los vectores del ingest plane, evitando la contención de recursos que degrada la latencia del serving durante la ingesta.

La **interfaz entre los tres planos** debe ser asíncrona y basada en eventos para garantizar que el plano de ingesta no bloquee el plano de serving. Las colas de mensajería (Apache Kafka, AWS SQS, Google Pub/Sub) son el mecanismo estándar: el ingest plane publica eventos `vector_batch_ready` en una cola cuando un lote de vectores está listo para indexar; el index plane consume esos eventos, indexa los vectores y confirma la recepción. Si el index plane está temporalmente degradado, los eventos se acumulan en la cola y el ingest plane puede seguir operando sin conocer el estado del index plane. La misma lógica aplica para los eventos de los sistemas de gestión documental (SharePoint, Confluence) hacia el ingest plane.

## Componentes de la arquitectura desacoplada

- **Ingest plane**: workers de procesamiento escalables horizontalmente (Kubernetes, AWS ECS); orquestados por Apache Airflow, Prefect o AWS Step Functions; throughput típico de 500–5.000 documentos/hora dependiendo del enriquecimiento.
- **Index plane**: base de datos vectorial (Qdrant, Pinecone, Weaviate) con réplicas de lectura para el serving; instancias separadas para escritura (ingest plane) y lectura (query plane); SLA de disponibilidad del 99.9% para las réplicas de lectura.
- **Query plane**: API de serving (FastAPI, gRPC) con instancias escaladas horizontalmente; circuit breakers hacia la base vectorial y el LLM para resiliencia ante fallos; load balancer que distribuye el tráfico entre instancias.
- **Message queue entre planos**: Kafka o SQS como cola de eventos asíncronos; garantiza durabilidad y reintentos automáticos; desacopla los planos permitiendo operación independiente ante degradaciones parciales.
- **Configuration management**: parámetros del pipeline (modelo de embedding, chunk\_size, K del retriever, umbral de reranking) gestionados en HashiCorp Consul, AWS Parameter Store o Kubernetes ConfigMaps; permite cambiar configuración sin redespliegue.
- **Feature flags para A/B testing**: activar/desactivar módulos del pipeline (reranking, HyDE, búsqueda híbrida) por porcentaje de tráfico mediante LaunchDarkly o AWS AppConfig; crítico para experimentos controlados en producción.

> **Nota del Arquitecto**: La decisión de desacoplar los tres planos no debe posponerse "hasta que el sistema escale": los patrones de acoplamiento que se establecen en el prototipo son los más difíciles de cambiar después. Un sistema que empieza con el ingest plane y el query plane en el mismo proceso requiere refactorizarlos completamente cuando el corpus crece y la ingesta empieza a competir con la latencia del serving. Diseñar el desacoplamiento desde el día uno cuesta horas adicionales; refactorizarlo en producción cuesta semanas y genera downtime.
