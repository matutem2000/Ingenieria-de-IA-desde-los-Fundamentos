## Reranking: modelos cross-encoder, Cohere Rerank, BGE Reranker

El retriever —ya sea semántico, BM25 o híbrido— opera con bi-encoders: modelos que codifican la query y el documento por separado, generan un vector para cada uno, y miden la similitud entre esos vectores. Esta arquitectura es eficiente (los vectores de documentos pueden pre-computarse en indexación y solo el vector de la query necesita computarse en tiempo de consulta) pero tiene una limitación fundamental: el modelo nunca ve la query y el documento simultáneamente, por lo que no puede capturar interacciones semánticas finas entre los tokens de ambos textos. El reranking resuelve esta limitación con una segunda etapa de evaluación más precisa pero más costosa: los modelos cross-encoder reciben la concatenación de query y documento como entrada y producen un score de relevancia que captura las interacciones entre todos los tokens de ambos textos.

La **arquitectura cross-encoder** es estructuralmente la misma que la de un modelo BERT de clasificación: recibe la secuencia `[CLS] query [SEP] documento [SEP]` y produce un score escalar de relevancia. La diferencia con el bi-encoder es que la atención cruzada entre los tokens de la query y los del documento permite al modelo capturar relaciones semánticas que son invisibles cuando ambos textos se procesan independientemente. Por ejemplo, si la query pregunta "¿cuál es la dosis máxima?" y el documento menciona "no superar los 3000mg diarios", el cross-encoder puede capturar que "dosis máxima" y "no superar los 3000mg" son semánticamente equivalentes en ese contexto, mientras que un bi-encoder puede asignar scores de similitud bajos porque los tokens superficialmente no se parecen. Esta mayor precisión tiene un costo: el cross-encoder requiere una pasada completa del transformer por cada par (query, documento), lo que hace imposible pre-computar los scores en indexación; el reranking debe ejecutarse en tiempo de consulta sobre el conjunto de chunks recuperados.

El **pipeline two-stage** es el patrón estándar en producción: la primera etapa usa el retriever rápido (vectorial o híbrido) para recuperar top-100 candidatos; la segunda etapa usa el cross-encoder para rerankear esos 100 candidatos y seleccionar los top-5 o top-10 para el contexto del LLM. Este diseño mantiene el Recall@100 de la primera etapa (alta probabilidad de que el documento correcto esté entre los 100 candidatos) mientras eleva la Precision@5 de la segunda etapa (los 5 chunks finales tienen alta probabilidad de ser los más relevantes). La mejora de Precision@5 con reranking es consistentemente de 15–25 puntos porcentuales sobre la primera etapa, lo que justifica el overhead de latencia adicional de 200–500ms que el reranker introduce.

**Cohere Rerank v3** es el modelo de reranking como servicio más utilizado en producción empresarial. La API acepta la query y hasta 1000 documentos, devuelve scores de relevancia normalizados de 0 a 1 para cada documento, y soporta más de 100 idiomas. El precio de $2 por millón de documentos rankeados hace que el reranking de 100 chunks por consulta cueste $0.0002 por consulta —un costo operacional mínimo comparado con el costo de los tokens del LLM generador. Cohere también ofrece un modelo lite a $0.10/millón para casos con presupuesto más ajustado, con una reducción de calidad moderada.

**BGE Reranker v2-m3** (BAAI) es la alternativa open source de referencia: un modelo cross-encoder de 568 millones de parámetros con soporte multilingüe, licencia Apache 2.0, y rendimiento comparable a Cohere Rerank en benchmarks de BEIR. Puede desplegarse en GPU con ~2GB VRAM (una GPU T4 es suficiente) y ejecutar reranking de 100 chunks en ~200ms, eliminando los costos de API y las dependencias externas. Para equipos con restricciones de soberanía de datos o presupuesto de API limitado, BGE Reranker es la primera opción.

**FlashRank** es una librería Python que implementa modelos cross-encoder pequeños (ms-marco-MiniLM-L6-v2, ms-marco-TinyBERT-L6) optimizados para CPU con latencias de 5–20ms para 100 documentos. Es la opción correcta cuando GPU no está disponible en el serving o cuando el presupuesto de latencia es muy ajustado: un reranker de 15ms en CPU añade latencia mínima al pipeline y puede ejecutarse en instancias estándar sin GPU especializada.

## Componentes técnicos del reranking

- **Arquitectura cross-encoder**: entrada `[CLS] query [SEP] documento [SEP]`; atención cruzada entre tokens de query y documento; un score de relevancia por par; O(K) inferencias del modelo por consulta; precisión significativamente superior al bi-encoder pero sin posibilidad de pre-computar.
- **Latencia del reranking**: BGE Reranker en GPU V100: ~200ms para 100 documentos; Cohere Rerank API: 200–500ms para hasta 100 documentos; FlashRank en CPU: 5–20ms para 100 documentos con modelos pequeños; el overhead de latencia siempre es justificado si la mejora de Precision@5 supera los 10 puntos.
- **Pipeline two-stage**: first-stage → top-100 con retriever rápido (vectorial o híbrido); second-stage → top-5/10 con cross-encoder; mantiene Recall@100 de la primera etapa mientras eleva Precision@5 de la segunda; mejora típica de 15–25 puntos en Precision@5.
- **Cohere Rerank v3**: 100+ idiomas; hasta 1000 documentos por llamada; latencia <500ms para 100 docs; precio $2/millón de unidades; modelo lite a $0.10/millón; opción managed para equipos sin GPU dedicada.
- **BGE Reranker v2-m3**: 568M parámetros; Apache 2.0; contexto de 8192 tokens; ~2GB VRAM; latencia ~200ms en GPU T4 para 100 docs; disponible en Hugging Face; desplegable con sentence-transformers o TGI.
- **FlashRank**: librería Python para reranking en CPU; modelos MiniLM y TinyBERT; 5–20ms para 100 docs en CPU; calidad inferior a BGE o Cohere pero suficiente para casos de uso con presupuesto de latencia muy ajustado.

> **Nota del Arquitecto**: El reranking es la optimización de mayor ROI en cualquier sistema RAG porque trabaja sobre los chunks ya recuperados por el retriever y los reordena sin coste adicional de embedding ni de consulta a la base vectorial. En un sistema con Recall@100 de 0.90 pero Precision@5 de 0.45 (de los 100 chunks recuperados, solo 45% de los 5 seleccionados para el LLM son relevantes), añadir BGE Reranker eleva típicamente la Precision@5 a 0.70–0.80. Ese delta de 25–35 puntos en Precision@5 se traduce directamente en mejor faithfulness y answer relevancy del sistema completo.
