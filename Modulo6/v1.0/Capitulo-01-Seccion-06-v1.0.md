# Módulo 6 – Capítulo 01 – Sección 06

## Cierre: RAG como disciplina de ingeniería, no solo integración de APIs

Este capítulo abrió con una pregunta práctica —¿por qué existe RAG?— y terminó con una taxonomía de variantes y un árbol de decisión arquitectónica. Antes de cerrar, es necesario establecer el principio más importante que atraviesa todo el módulo: RAG es una disciplina de ingeniería con la misma complejidad operacional que cualquier sistema distribuido de producción, y tratarlo como una simple integración de APIs es el error que separa los prototipos impresionantes de los sistemas confiables en producción.

La proliferación de frameworks como LangChain, LlamaIndex y Haystack democratizó el acceso a los componentes de RAG: cualquier desarrollador puede construir un sistema que responde preguntas sobre un corpus de documentos en un par de horas. Esta accesibilidad es una fortaleza del ecosistema, pero también generó una falsa impresión: que integrar las APIs es suficiente. En producción, la diferencia entre un prototipo funcional y un sistema confiable radica en las decisiones de ingeniería que los frameworks no toman por el desarrollador. ¿Qué estrategia de chunking es apropiada para los PDFs con layout complejo del corpus? ¿Cómo se detecta que el índice se degradó por documentos actualizados que no fueron reindexados? ¿Cómo se correlacionan trazas entre el retriever y el generador para diagnosticar un aumento de hallucinations? ¿Qué SLO de latencia es adecuado para el caso de uso, y cómo se alerta cuando se viola? Ningún framework responde estas preguntas: las respuestas son responsabilidad del AI Engineer.

Los sistemas RAG de mayor impacto en producción son el resultado de meses de iteración sobre pipelines de evaluación, no de semanas de integración de APIs. El sistema de asistencia de Notion AI, por ejemplo, iteró durante meses sobre la estrategia de chunking específica para las notas de Notion, que tienen una estructura jerarquizada de bloques que los splitters genéricos de LangChain no manejan bien. El equipo de GitHub Copilot invirtió tiempo significativo en el enriquecimiento de metadatos de código (lenguaje, repositorio, archivo, función) que permite filtrar el contexto recuperado al ámbito relevante para el cursor del usuario. Estos equipos no encontraron las respuestas en la documentación de LangChain: las construyeron mediante experimentación sistemática sobre sus datasets de evaluación.

Tratar RAG como una disciplina de ingeniería implica establecer desde el inicio cuatro prácticas que el resto del módulo desarrolla en detalle: datasets de evaluación golden que midan Recall@K y faithfulness antes de cada release, pipelines de CI/CD para el índice que detecten regresiones automáticamente, SLOs de latencia y calidad con alertas calibradas, y procesos de revisión de degradaciones con análisis de causa raíz. Estas prácticas no son opcionales para sistemas que usuarios reales dependen para tomar decisiones; son el mínimo de rigor ingenieril que distingue un sistema de IA confiable de un sistema que funciona "la mayor parte del tiempo".

## Principio rector

RAG no es una integración sino una arquitectura: cada decisión de diseño en el pipeline de ingesta, indexación, recuperación y generación tiene impacto directo y medible en la calidad de las respuestas que los usuarios experimentan. El framework aporta los bloques de construcción; el ingeniero aporta las decisiones que determinan si el sistema funciona bien.

*"La diferencia entre un programador y un ingeniero de software es que el ingeniero sabe que el sistema seguirá ejecutándose mucho después de que él haya terminado de escribir el código."* — Dave Parnas, pionero de la ingeniería de software modular

El Capítulo 2 entra en el primer componente técnico fundamental del sistema RAG: los modelos de embedding, cómo capturan significado semántico, qué modelos están disponibles en 2025, cómo elegir entre ellos para un dominio específico y cómo evaluarlos con métricas reproducibles. La elección del modelo de embedding es, como veremos, la decisión de mayor impacto sobre el techo de calidad de toda la recuperación.
