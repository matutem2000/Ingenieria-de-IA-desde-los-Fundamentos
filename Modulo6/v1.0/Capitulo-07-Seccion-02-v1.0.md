# Módulo 6 – Capítulo 07 – Sección 02

## Pipelines de ingesta escalables: procesamiento en lotes y en streaming

El pipeline de ingesta es el sistema que transforma documentos crudos en vectores indexados. Diseñar este pipeline para escalar —manejar tanto la carga inicial de indexación del corpus histórico como las actualizaciones continuas del corpus de producción— requiere elegir desde el inicio entre dos modos de operación con características muy distintas: el procesamiento batch y el procesamiento streaming. En la mayoría de los sistemas de producción, ambos coexisten: el batch para la ingesta inicial y para actualizaciones periódicas masivas, y el streaming para mantener el índice fresco ante cambios individuales del corpus en tiempo casi real.

El **procesamiento batch** es el modo de operación correcto para la ingesta inicial de corpus históricos y para actualizaciones programadas. Un corpus de 500.000 documentos no puede procesarse en un único proceso secuencial en tiempo razonable: el parsing, chunking, embedding y escritura en el índice de cada documento requiere entre 1 y 10 segundos dependiendo del tamaño del documento y del enriquecimiento aplicado; para 500.000 documentos, eso representa entre 6 y 60 días de procesamiento secuencial. La solución es la **paralelización controlada**: distribuir los documentos entre N workers que procesan en paralelo, respetando los rate limits de las APIs externas (el embedding de texto con la API de OpenAI tiene un límite de 3.000 requests/minuto por defecto, ampliable por acuerdo empresarial). Apache Airflow y Prefect son los frameworks de orquestación más utilizados para pipelines batch de ingesta RAG: permiten definir el pipeline como un DAG (Directed Acyclic Graph) de tareas, gestionar las dependencias entre tareas (el chunking debe completarse antes del embedding, el embedding antes del upsert en el índice), y manejar reintentos automáticos con backoff exponencial para las tareas que fallan transitoriamente.

La optimización del throughput del batch pipeline tiene un punto de complejidad que merece atención específica: los **rate limits de la API de embedding**. OpenAI text-embedding-3 permite enviar hasta 2048 textos en una sola llamada usando el parámetro `input` como array; dividir el batch de chunks en grupos de 2048 y hacer una llamada por grupo es significativamente más eficiente que hacer una llamada por chunk (reduce el overhead de HTTP y de autenticación en un factor de 2048x). Para corpus con modelos de embedding open source (BGE-M3, nomic-embed) hosteados en GPU propia, el throughput está limitado por la capacidad del servidor de inferencia (TGI, vLLM, Triton) y puede optimizarse con batching dinámico que agrupa las llamadas concurrentes del pipeline de ingesta.

El **procesamiento streaming** mantiene el índice fresco ante cambios individuales del corpus con latencia de segundos. El mecanismo de disparo es un sistema de eventos: los conectores de los sistemas de gestión documental (SharePoint webhooks, Confluence webhooks, API de Notion, S3 Event Notifications) publican eventos `document_created`, `document_updated` o `document_deleted` en un topic de Apache Kafka o en una cola SQS. Los consumers del pipeline de ingesta procesan cada evento ejecutando el pipeline completo (parse → chunk → embed → upsert) para el documento afectado. La latencia desde que el documento se modifica hasta que es consultable en el índice es de 5–30 segundos dependiendo del tamaño del documento y la carga del sistema.

La **idempotencia del pipeline** es un requisito crítico en ambos modos. Un pipeline idempotente puede ejecutarse múltiples veces sobre el mismo documento sin efectos secundarios: si el worker que procesa un documento falla después del chunking pero antes del embedding y el orquestador reintenta la tarea, el resultado final debe ser el mismo que si la tarea se hubiera ejecutado una sola vez. El mecanismo de content hashing descrito en el Capítulo 4 garantiza idempotencia a nivel de documento; los `upsert` en la base vectorial (que insertan si el ID no existe o actualizan si ya existe) garantizan idempotencia a nivel de vector; y el tracking store garantiza que los chunks obsoletos se eliminan antes de insertar los nuevos.

## Componentes técnicos del pipeline de ingesta

- **Batch ingestion con paralelismo controlado**: ThreadPoolExecutor o asyncio para paralelizar llamadas a la API de embedding; respetar rate limits con exponential backoff y jitter; optimizar throughput usando el parámetro `input` como array (hasta 2048 textos por llamada en text-embedding-3).
- **Document queue management**: cola de prioridad (Redis Sorted Set, SQS FIFO) para ordenar el procesamiento; priorizar documentos críticos (contratos recientes, comunicaciones urgentes) sobre documentos históricos; gestionar la "presión" de la cola para evitar acumulación indefinida.
- **Idempotencia del pipeline**: content hash para skipear documentos no modificados; upsert en lugar de insert para vectores; delete\_by\_filter antes de insertar chunks actualizados; el pipeline puede ejecutarse múltiples veces sin efectos secundarios.
- **Dead letter queue para documentos fallidos**: documentos que fallan repetidamente (parsing error, timeout de embedding API, error de escritura en índice) → cola separada con el error y el documento; requieren revisión manual o procesamiento con estrategia alternativa (parser alternativo, embedding local como fallback).
- **Stream processing con Kafka**: producers en los sistemas de gestión documental publican eventos de cambio en topics Kafka; consumers del pipeline RAG procesan los eventos con exactamente-una-vez semántica usando Kafka transactions; monitorear el consumer lag como indicador de backpressure.
- **Métricas del pipeline de ingesta**: throughput (documentos/hora), tasa de error (% de documentos fallidos), latencia p99 por etapa (parsing, chunking, embedding, indexing), profundidad de la cola de pendientes, lag de actualización (tiempo desde modificación hasta disponibilidad en índice).

La separación entre batch y streaming, con idempotencia garantizada, permite que el sistema de ingesta opere de forma robusta tanto ante la carga inicial masiva como ante las actualizaciones continuas del corpus de producción.
