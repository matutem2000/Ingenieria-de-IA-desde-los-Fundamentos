# Módulo 6 – Capítulo 08 – Sección 06

## Cierre: las extensiones de RAG amplían el dominio del problema resuelto

Las extensiones del RAG estándar que este capítulo ha presentado —multimodal, sobre datos estructurados, basado en grafos, con herramientas externas— no son variantes experimentales de dudosa utilidad en producción. Son respuestas ingenieriles a limitaciones concretas del RAG vectorial estándar que emergen cuando el sistema se enfrenta a la diversidad real del conocimiento empresarial. Una organización que solo indexa documentos de texto plano ignora el 40–60% de su conocimiento, que reside en tablas de bases de datos, imágenes de manuales, grabaciones de reuniones y presentaciones visuales. Un sistema RAG que no puede responder preguntas sobre datos actuales (precio de acción, estado de pedido, capacidad de inventario) tiene una brecha de utilidad significativa para usuarios de negocio. Estas extensiones no son features adicionales: son la diferencia entre un sistema de consulta de conocimiento limitado y un sistema de asistencia empresarial completo.

El criterio de adopción de cada extensión debe ser empírico y económico. Para cada extensión, el AI Engineer debe responder tres preguntas: ¿cuántos usuarios hacen preguntas que esta extensión resuelve, con qué frecuencia? ¿Cuál es el costo de implementar y operar esta extensión (desarrollo, infraestructura, mantenimiento)? ¿Cuál es la mejora de satisfacción del usuario (medida en las métricas de evaluación) que produce? Solo si el numerador (impacto) supera el denominador (costo) de forma clara, la extensión justifica la inversión. GraphRAG con un costo de construcción 20 veces mayor que el RAG vectorial estándar se justifica cuando el 40% de las queries del sistema son de síntesis global; no se justifica cuando el 95% de las queries son factuales específicas sobre documentos individuales.

El criterio técnico de adopción que complementa el económico es la **medición antes de la decisión**: implementar una versión mínima o un proxy de la extensión, ejecutarla sobre un subset del corpus y las queries más representativas del caso de uso, y medir el delta de calidad en el golden dataset antes de comprometerse a la implementación completa. HyDE se puede prototipear en una tarde y evaluar su impacto en el Recall@5 del dataset de evaluación; el resultado dice si los 500ms de latencia adicional y el costo extra del LLM están justificados. Text-to-SQL se puede prototipear con el esquema de las tablas más relevantes y 10 queries de ejemplo para estimar el porcentaje de queries que genera SQL correcto antes de construir la infraestructura completa de validación y seguridad.

La **adopción incremental** es la estrategia correcta: empezar con el RAG vectorial estándar bien implementado y con evaluación correcta, identificar qué tipos de preguntas el sistema no puede responder o responde mal, y adoptar exactamente las extensiones que resuelven esos casos de uso no cubiertos. Esta estrategia contrasta con la alternativa de construir desde el inicio un sistema con todas las extensiones posibles: ese sistema tiene mayor complejidad operacional, mayor costo de infraestructura, mayor superficie de fallos, y frecuentemente no mejora la calidad de las respuestas para el 80% de las queries que el RAG estándar ya manejaba bien.

Con las extensiones del RAG cubiertas, el módulo puede retomar el camino de la madurez operacional del sistema base. El Capítulo 9 aborda la optimización sistemática del sistema RAG construido: cómo diagnosticar los tipos de errores más frecuentes, cómo optimizar el retriever y el generador de forma independiente, y cómo gestionar el costo operacional a escala.

*"Todo debería hacerse tan simple como sea posible, pero no más simple."* — atribuido a Albert Einstein; en ingeniería de sistemas, la complejidad adicional solo se justifica cuando resuelve problemas reales que la solución más simple no puede resolver.
