# Módulo 6 – Capítulo 08 – Sección 04

## RAG con herramientas: integración de APIs externas en el ciclo de recuperación

El índice vectorial contiene el conocimiento del corpus histórico del sistema: documentos procesados hasta el momento de la última actualización del índice. Pero existen categorías de información que ningún índice estático puede proporcionar: el precio actual de una acción, el estado en tiempo real de un ticket de soporte en Jira, la previsión meteorológica para mañana, el estado de entrega de un pedido. Estas informaciones son dinámicas por naturaleza —cambian continuamente y es imposible indexarlas de antemano— y requieren consulta directa a sistemas externos en tiempo real. El RAG con herramientas extiende el paradigma conectando el ciclo de respuesta del LLM con APIs externas que proveen información en tiempo real, transformando el sistema RAG de un sistema de consulta sobre conocimiento pasado a un sistema de acceso a información del presente.

El mecanismo fundamental es el **function calling** (también llamado tool use en la API de Anthropic o function declarations en la API de Gemini): una capacidad de los LLMs modernos que les permite emitir llamadas estructuradas a funciones externas en lugar de (o además de) generar texto de respuesta. El sistema define las herramientas disponibles con un nombre, una descripción en lenguaje natural de qué hace la herramienta y para qué es útil, y un esquema JSON de los parámetros que acepta. El LLM lee estas definiciones en el prompt del sistema y, cuando determina que necesita información de una herramienta para responder la query del usuario, emite un objeto JSON con el nombre de la herramienta y los valores de los parámetros. El sistema ejecuta la herramienta con esos parámetros, obtiene el resultado, y lo devuelve al LLM como un `tool_result` en el contexto de la conversación. El LLM entonces genera la respuesta final usando tanto los chunks del RAG vectorial como los resultados de las herramientas.

La **composición del conjunto de herramientas** es una decisión de diseño que determina las capacidades del sistema. En un asistente empresarial típico, el conjunto puede incluir: búsqueda vectorial en el índice interno (acceso al corpus documental), consulta a Salesforce CRM (estado actual de cuentas de clientes), consulta a Jira (tickets abiertos y su estado), búsqueda en la web con Tavily o SerpAPI (información pública actualizada), y consulta a servicios internos de la empresa vía API REST. El LLM actúa como un router inteligente que selecciona qué herramienta usar según la naturaleza de la pregunta: "¿qué dice la política de devoluciones?" va al índice vectorial; "¿cuál es el estado del ticket SUPP-1234?" va a la API de Jira; "¿qué dijo el CEO de la empresa X en su última conferencia?" va a la búsqueda web.

El **parallel tool calling** es una optimización de latencia disponible en GPT-4o y Claude 3.5 Sonnet que permite al LLM solicitar múltiples herramientas simultáneamente en una sola inferencia. Para una query como "¿cuál es el precio actual de la acción X y qué dice el último informe anual sobre la estrategia de la compañía?", el LLM puede emitir simultáneamente una llamada a la API de precios de bolsa y una búsqueda vectorial en el índice de informes anuales. El sistema ejecuta ambas herramientas en paralelo, reduce la latencia total respecto a la ejecución secuencial, y proporciona ambos resultados al LLM en una sola respuesta.

La **gestión de errores de herramientas** es un componente que frecuentemente se omite en implementaciones iniciales con consecuencias dolorosas en producción. Las APIs externas fallan: timeouts, rate limits (la API de bolsa puede tener un límite de 5 llamadas por segundo), errores 503 por mantenimiento. El sistema debe implementar: timeouts máximos por herramienta (2–5 segundos) para no bloquear la respuesta al usuario indefinidamente; reintentos con backoff exponencial para errores transitorios; notificación al LLM cuando una herramienta falla, para que genere una respuesta parcial o solicite reformulación ("No pude obtener el precio actual de la acción X. ¿Quieres que responda sobre la información histórica disponible en el corpus?"); y logging de todos los errores para monitoreo.

## Patrones de integración de APIs en RAG

- **Function calling para recuperación dinámica**: definir herramientas con nombre, descripción y esquema JSON; el LLM emite tool\_calls con los argumentos; ejecutar la función real y devolver el resultado como tool\_result; el LLM genera la respuesta final integrando todos los resultados.
- **Tool selection como retrieval routing**: el conjunto de herramientas incluye tanto búsqueda vectorial como APIs externas; el LLM selecciona qué herramienta usar según la naturaleza de la query; sistema natural de routing sin clasificador explícito.
- **Parallel tool calling**: GPT-4o y Claude 3.5 Sonnet soportan múltiples tool\_calls en una sola inferencia; ejecutar en paralelo reduce latencia; especialmente útil para queries que requieren información de múltiples fuentes simultáneas.
- **Gestión de errores**: timeout máximo por herramienta (2–5 segundos); reintentos con backoff para errores transitorios; notificación al LLM de fallos para respuestas parciales informadas; logging de todos los errores para monitoreo.
- **Security boundary para tool execution**: sandbox con permisos mínimos para ejecutar herramientas; validar argumentos generados por el LLM antes de ejecutar (prevención de prompt injection en tool\_calls); loggear todas las ejecuciones para auditoría.
- **Timeout y SLO por herramienta**: definir SLO de latencia por herramienta (búsqueda vectorial: 50ms, API de Jira: 500ms, búsqueda web: 2s); si la herramienta no responde en el tiempo límite, proceder sin su resultado notificando al LLM.

El RAG con herramientas amplía el alcance del sistema a información en tiempo real y a sistemas externos, pero introduce dependencias de APIs externas con sus propios SLAs, rates limits y fallos. Cada herramienta adicional es una dependencia a gestionar y un modo de fallo a diseñar.
