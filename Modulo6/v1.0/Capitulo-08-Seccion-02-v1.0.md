# Módulo 6 – Capítulo 08 – Sección 02

## RAG sobre datos estructurados: Text-to-SQL y NL2API

Hay una clase de preguntas que los usuarios de un sistema de asistencia empresarial hacen con frecuencia y que el RAG sobre documentos de texto no puede responder: "¿cuáles son los 10 clientes con mayor facturación en el último trimestre?", "¿qué empleados tienen más de 5 años de antigüedad y están en el departamento de ventas?", "¿cuántos tickets de soporte se abrieron esta semana con prioridad alta?". La respuesta a estas preguntas no está en documentos indexados sino en bases de datos relacionales, data warehouses o APIs con esquemas definidos. RAG sobre datos estructurados —implementado principalmente como Text-to-SQL o NL2API— extiende el sistema para responder estas preguntas accediendo a los datos en tiempo real.

**Text-to-SQL** es el problema de traducir una pregunta en lenguaje natural a una query SQL correcta y ejecutable. Los LLMs modernos tienen capacidades Text-to-SQL sólidas cuando se les proporciona el contexto correcto: el esquema de la base de datos (nombres de tablas, columnas, tipos, claves foráneas, relaciones), algunas filas de ejemplo de las tablas más relevantes, y opcionalmente 3–5 ejemplos de pares (pregunta, SQL) del dominio específico (few-shot examples). GPT-4o y Claude 3.5 Sonnet alcanzan accuracy del 70–85% en el benchmark Spider (Text-to-SQL estándar) en esquemas de complejidad media con few-shot examples bien elegidos; la accuracy cae al 40–60% para esquemas con más de 50 tablas relacionadas donde el contexto de esquema completo no cabe en el prompt de forma útil.

El **patrón RAG híbrido para Text-to-SQL** resuelve el problema del esquema de base de datos grande mediante una primera etapa de recuperación semántica: antes de generar el SQL, el sistema indexa el esquema de la base de datos como texto (cada tabla y sus columnas como un documento, con descripciones de negocio de las columnas si están disponibles en el diccionario de datos) y usa búsqueda semántica para seleccionar las 5–10 tablas más relevantes para la query específica del usuario. Solo el esquema de esas tablas se incluye en el prompt de generación SQL, reduciendo el contexto de esquema de potencialmente cientos de tablas a las directamente relevantes. Esta estrategia de schema-aware retrieval mejora la accuracy del Text-to-SQL en 15–25 puntos para bases de datos de más de 20 tablas.

El ciclo de **SQL validation y error recovery** es crítico para la usabilidad en producción. El LLM comete errores en el SQL generado con frecuencia (tablas con nombres ligeramente distintos a los del esquema, joins incorrectos, filtros de fecha mal formateados). El pipeline debe: (1) intentar ejecutar el SQL generado en un entorno de solo lectura; (2) si el motor de base de datos devuelve un error, enviar el SQL fallido y el mensaje de error de vuelta al LLM para que genere una versión corregida; (3) repetir hasta 3 veces antes de responder al usuario que no pudo generar una query correcta. Este ciclo de auto-corrección reduce la tasa de errores finales en un 30–50% respecto a un sistema sin recuperación de errores.

La **seguridad en Text-to-SQL** es un requisito que no puede ignorarse. El LLM puede generar queries que el sistema ejecuta en la base de datos: si el usuario de base de datos del sistema tiene permisos de escritura, un LLM manipulado (por ejemplo, a través de prompt injection en la query del usuario) podría generar operaciones INSERT, UPDATE o DROP TABLE que modifiquen o destruyan datos de producción. Las medidas de mitigación son: crear un usuario de base de datos de solo lectura dedicado específicamente para el sistema Text-to-SQL, con acceso restringido a las tablas que el sistema necesita consultar; validar que el SQL generado no contenga operaciones DDL ni DML antes de ejecutarlo (un simple check de keywords prohibidas: DROP, DELETE, UPDATE, INSERT, ALTER, TRUNCATE); y monitorear y loggear todas las queries ejecutadas para auditoría.

**NL2API** aplica el mismo principio a APIs REST: en lugar de generar SQL, el LLM genera la llamada a una API correcta (endpoint URL, parámetros, headers de autenticación) a partir de la pregunta del usuario. La especificación OpenAPI/Swagger del API se usa como contexto para el LLM (los endpoints disponibles, sus parámetros y los tipos de respuesta). El framework ReAct y el mecanismo de function calling (OpenAI tools, Claude tool use, Gemini function declarations) son las implementaciones más comunes: el LLM declara qué función (herramienta) quiere llamar, el sistema la ejecuta y devuelve el resultado al LLM para que genere la respuesta final.

## Técnicas de RAG sobre datos estructurados

- **Schema-aware retrieval**: indexar el esquema de la base de datos como documentos semánticos; buscar las 5–10 tablas más relevantes para la query antes de generar el SQL; reducir el contexto de esquema al subconjunto relevante; mejora accuracy en 15–25 puntos para bases de datos de >20 tablas.
- **Few-shot examples de SQL**: incluir 3–5 ejemplos de pares (pregunta, SQL) del dominio específico en el prompt de generación; elegir ejemplos que cubran los patrones de query más frecuentes (JOINs, GROUP BY, filtros de fecha, subconsultas); diferencia de 10–20 puntos de accuracy en el dominio específico.
- **SQL validation y error recovery**: ejecutar el SQL en entorno de solo lectura → capturar error → enviar error + SQL original al LLM → iterar hasta 3 veces; reduce tasa de errores finales en 30–50%; implementable con un simple try/except que alimenta el error de vuelta al LLM.
- **Seguridad de solo lectura**: usuario de base de datos dedicado con permisos SELECT únicamente; validar que el SQL no contiene palabras clave prohibidas (DROP, DELETE, UPDATE, INSERT, ALTER) antes de ejecutar; loggear todas las queries para auditoría.
- **Caché de queries SQL**: cachear pares (query\_normalizada, SQL\_correcta) para preguntas frecuentes; similar al caching semántico para RAG textual; evita la generación SQL y ejecuta la query cacheada directamente; especialmente útil para dashboards o reportes recurrentes.
- **NL2API con function calling**: definir herramientas con nombre, descripción y esquema JSON de parámetros; el LLM emite tool\_calls con los argumentos correctos; el sistema ejecuta la función real y devuelve el resultado al LLM; GPT-4o y Claude 3.5 Sonnet tienen function calling nativo de alta calidad.

Text-to-SQL es un componente de alta complejidad y riesgo que requiere diseño cuidadoso de la capa de seguridad antes de la implementación. Cuando se implementa correctamente, amplía dramáticamente las capacidades del sistema RAG para responder preguntas sobre datos en tiempo real que ningún sistema de recuperación de documentos puede responder.
