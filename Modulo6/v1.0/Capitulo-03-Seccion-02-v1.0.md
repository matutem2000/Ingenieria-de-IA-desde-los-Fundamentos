# Módulo 6 – Capítulo 03 – Sección 02

## Principales bases vectoriales: Pinecone, Weaviate, Qdrant, Chroma, pgvector

Entre 2021 y 2025, el ecosistema de bases de datos vectoriales pasó de ser un nicho académico a uno de los segmentos de infraestructura de datos de mayor crecimiento. Chroma, Qdrant, Weaviate y Pinecone recibieron financiación colectiva de más de $200 millones en ese período, y pgvector convirtió PostgreSQL en una base vectorial viable para millones de equipos que ya tenían Postgres en producción. Esta proliferación tiene una consecuencia práctica para el AI Engineer: la elección ya no es "¿qué base vectorial usar?" sino "¿cuál es la más adecuada para los requisitos específicos de este sistema?". Esta sección analiza los cinco candidatos más relevantes con el nivel de detalle suficiente para tomar esa decisión.

**Pinecone** es la opción managed más madura del mercado. Su arquitectura serverless desacopla el almacenamiento del cómputo de búsqueda: los vectores se persisten en object storage y las instancias de búsqueda se aprovisiona bajo demanda, permitiendo escalar a más de 1.000 millones de vectores sin gestión de infraestructura. La latencia p99 en Pinecone serverless es de 100–300ms para colecciones activas, con posibles cold starts de varios segundos para colecciones inactivas; la latencia p99 en pods dedicados (Pinecone Inference) baja a 20–50ms. El soporte nativo de filtrado por metadatos —implementado mediante un índice invertido acoplado al vectorial— permite filtros complejos sin degradación del recall. La limitación más significativa de Pinecone es el lock-in: los vectores y metadatos viven en la infraestructura del proveedor, lo que implica que cambiar de Pinecone a otra solución requiere exportar y reindexar todo el corpus.

**Qdrant** es la opción open source que más aceleradamente ganó adopción en producción entre 2023 y 2025. Implementado en Rust, combina performance de bajo nivel con una API REST y gRPC de alta calidad. Su arquitectura de sharding nativo permite distribuir el índice entre múltiples nodos horizontalmente; el soporte de payloads JSON sin límite de esquema permite almacenar metadatos arbitrariamente complejos junto a cada vector. La característica técnica más distintiva de Qdrant es el **filtrado pre-ANN**: en lugar de recuperar K vectores con HNSW y luego filtrar por metadatos (lo que degrada el recall cuando el filtro es selectivo), Qdrant construye dinámicamente un subgrafo del índice que incluye solo los vectores que pasan el filtro y ejecuta la búsqueda ANN sobre ese subgrafo. El resultado es que un filtro de alta selectividad (por ejemplo, user\_id = "UUID-específico" que retiene el 0.01% del corpus) no degrada el recall de la búsqueda. Benchmarks en ann-benchmarks.com muestran que Qdrant con gRPC tiene la menor latencia p99 entre las opciones open source para corpus de 1–100M vectores.

**Weaviate** es la opción con mayor integración nativa de búsqueda híbrida: su motor combina internamente búsqueda vectorial con BM25 sobre el texto de los objetos, con un parámetro alpha que controla el balance entre ambas señales. Los módulos pluggables (text2vec-openai, text2vec-cohere, text2vec-huggingface) permiten delegar la generación de embeddings al propio Weaviate, simplificando la arquitectura pero introduciendo acoplamiento al proveedor de embeddings. Weaviate Cloud Services ofrece un tier gratuito generoso para prototipos, y el clustering distribuido nativo (implementado en Go) lo hace competitivo para corpus de escala enterprise.

**Chroma** fue diseñado explícitamente para prototipado rápido: API Python sencilla, modo in-memory o persistido en disco con SQLite, integración nativa con LangChain y LlamaIndex. Es la opción correcta para las primeras horas de desarrollo de un sistema RAG, pero no está diseñado para corpus de más de un millón de vectores ni para ambientes de producción con requisitos de alta disponibilidad. La transición de Chroma a Qdrant o Pinecone en proyectos que crecen más allá del prototipo es una refactorización común y costosa que se puede evitar eligiendo la base vectorial de producción desde el inicio si el equipo tiene claridad sobre los requisitos de escala.

**pgvector** extiende PostgreSQL con el tipo de datos `vector` y operadores de similitud (`<=>` para coseno, `<->` para L2, `<#>` para producto punto). Para equipos que ya operan PostgreSQL en producción, pgvector es la opción de menor fricción operacional: usa el mismo sistema de backup, replicación, RBAC y monitoreo que el PostgreSQL existente. Su rendimiento con índice HNSW (`CREATE INDEX USING hnsw`) es comparable al de Qdrant para corpus en memoria (hasta ~5M vectores en RAM), pero se degrada notablemente cuando el índice no cabe en memoria porque PostgreSQL hace I/O a disco, mientras que Qdrant tiene gestión de memoria optimizada con mmap y cuantización para corpus más grandes.

## Comparación técnica de bases vectoriales

| Característica | Pinecone | Weaviate | Qdrant | Chroma | pgvector |
|---|---|---|---|---|---|
| Deployment | Managed SaaS | Cloud o self-hosted | Cloud o self-hosted | Embebido o self-hosted | Self-hosted (PostgreSQL) |
| Lenguaje de implementación | Propietario | Go | Rust | Python/Rust | C (PostgreSQL) |
| Filtrado pre-ANN | Sí (índice acoplado) | Sí (motor propio) | Sí (nativo) | No | No |
| Búsqueda híbrida nativa | No (requiere pipeline externo) | Sí (parámetro alpha) | Sí (vectores esparsos SPLADE) | No | No |
| Escala óptima | >100M vectores | 10M-1B vectores | 1M-500M vectores | <1M vectores | <10M vectores en RAM |
| Lock-in | Alto | Bajo | Bajo | Bajo | Nulo |

La base de datos vectorial correcta no existe en abstracto: existe en el contexto de los requisitos específicos del sistema —latencia objetivo, escala del corpus, restricciones de soberanía de datos, capacidad operacional del equipo— que la siguiente sección analiza como criterios de selección estructurados.
