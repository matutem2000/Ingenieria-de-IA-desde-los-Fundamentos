# Módulo 10 – Capítulo 09 – Sección 03

## Optimización de inferencia: batching, caché y selección de modelo por tier de calidad

La optimización del costo de inferencia es el área de mayor impacto económico en la mayoría de las plataformas de IA, porque el costo de inferencia escala linealmente con el volumen de uso mientras que el costo de entrenamiento es puntual. A diferencia de la optimización de entrenamiento —donde la principal palanca es el tamaño del job y el tipo de instancia— la optimización de inferencia opera sobre el ciclo completo de cada request individual, lo que significa que las mejoras se replican automáticamente en todos los requests subsiguientes sin esfuerzo adicional. Las tres estrategias con mayor impacto son el **batching** (agrupar múltiples requests para procesarlos juntos), el **caching** (reutilizar respuestas previas para requests similares), y el **tiering de modelos** (seleccionar el modelo más barato que sea suficientemente bueno para cada tipo de request).

El **continuous batching** (también llamado dynamic batching o in-flight batching) es la optimización más importante para el throughput de modelos self-hosted. Los servidores de inferencia como **vLLM** implementan continuous batching con **PagedAttention** —un mecanismo de gestión del KV cache inspirado en la paginación de memoria de sistemas operativos— que permite procesar múltiples requests simultáneamente sin desperdiciar capacidad de GPU entre la finalización de un request y el inicio del siguiente. El resultado es un aumento del throughput de hasta 23x respecto a servir requests de uno en uno, sin impacto significativo en el TTFT para cada request individual. Triton Inference Server también soporta dynamic batching con `preferred_batch_size` configurable. Para modelos self-hosted de producción, no habilitar continuous batching equivale a operar un avión con la mitad de los asientos vacíos en cada vuelo.

El **tiering de modelos** es la optimización más impactante para costo en aplicaciones que usan APIs externas. El principio es directo: no todos los requests necesitan el modelo más capaz y más caro. Un análisis de las queries de producción de muchas aplicaciones muestra que el 60-80% de los requests son tareas relativamente simples —clasificación, extracción de entidades, resumen de texto corto, generación de respuestas formulaicas— para las cuales un modelo de la tier económica (GPT-4o-mini, Claude Haiku, Gemini Flash) produce resultados de calidad equivalente a una fracción del costo. El modelo de la tier premium (GPT-4o, Claude Opus, Gemini Pro) es necesario solo para el 20-40% de requests que requieren razonamiento complejo, generación creativa de alta calidad, o comprensión de contextos muy largos y complejos. Implementar un clasificador de complejidad de requests —que puede ser tan simple como una lista de palabras clave en el system prompt o tan sofisticado como un modelo de clasificación binaria— y usar ese clasificador para routing en el LLM Gateway puede reducir el costo total de inferencia en un 50-80% con degradación mínima de la calidad percibida.

La **compresión de prompts** es una optimización complementaria para contextos largos: técnicas como LLMLingua o Selective Context reducen el número de tokens en el prompt manteniendo la información relevante mediante extracción o compresión del texto de contexto. Para aplicaciones de RAG con contextos extensos —recuperación de múltiples documentos largos para responder una pregunta— la compresión del contexto puede reducir los tokens de input en un 20-40%, con reducción proporcional del costo. La **quantización** para modelos self-hosted —conversión de los pesos de float32 a INT8 (GPTQ, AWQ) o INT4— reduce los requerimientos de VRAM a la mitad y aumenta el throughput 1.5-2x con degradación de calidad inferior al 2% en la mayoría de las tareas, haciendo posible servir modelos más grandes en el mismo hardware.

## Estrategias de optimización de costos de inferencia

- **Continuous batching (vLLM, Triton):** el motor de inferencia procesa múltiples requests en paralelo con PagedAttention para gestionar el KV cache; aumenta throughput hasta 23x vs serving secuencial; no habilitar continuous batching en modelos self-hosted es equivalente a subutilizar el GPU en un factor grande.
- **Semantic caching en el LLM Gateway:** embeddings + búsqueda vectorial para retornar respuestas cacheadas para prompts similares; efectivo en aplicaciones con consultas repetitivas (FAQ, generación templated); puede reducir costos 30-70% con threshold de similitud bien calibrado (ver Capítulo 07).
- **Model tiering:** clasificar requests por complejidad y enrutar a modelos de diferente tier; los modelos de tier económica cuestan entre 10 y 30 veces menos que los de tier premium con calidad equivalente para el 60-80% de las tareas; el clasificador de complejidad puede implementarse como regla en el gateway.
- **Prompt compression:** técnicas de compresión del contexto (LLMLingua, Selective Context) que reducen tokens de input 20-40% para prompts largos; especialmente relevante para aplicaciones de RAG con contextos extensos y recurrentes.
- **Quantization para modelos self-hosted:** INT8 (GPTQ, AWQ) o INT4 quantization reduce requerimientos de VRAM a la mitad y aumenta throughput 1.5-2x con degradación de calidad < 2% en la mayoría de las tareas; primera optimización a evaluar antes de escalar hardware.

> **Nota del Arquitecto:** La optimización del costo de inferencia no es una tarea única que se hace una vez: es un proceso continuo de perfilado del uso real en producción (qué tipos de requests, qué modelos, qué tamaños de contexto) y calibración de las estrategias de optimización basadas en esos datos. Los datos de producción del LLM Gateway —disponibles en el audit log descrito en el Capítulo 07— son la fuente de información correcta para identificar qué optimizaciones tendrán mayor impacto en el caso de uso específico de la organización.

Las estrategias de optimización de inferencia pueden reducir el costo de operación de una plataforma de IA en un factor de 3x a 10x respecto a una configuración sin optimización, con el caching y el tiering de modelos como las contribuciones más grandes en la mayoría de los casos. La siguiente sección examina cómo estas estrategias se integran con las prácticas de FinOps de la organización para crear un sistema coherente de gestión de costos de IA.
