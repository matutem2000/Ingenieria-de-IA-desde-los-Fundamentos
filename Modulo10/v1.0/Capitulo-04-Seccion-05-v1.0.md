# Módulo 10 – Capítulo 04 – Sección 05

## Data quality: validación y monitoreo de calidad de los datos que alimentan el sistema

La calidad de datos en un sistema de IA no es un estado que se alcanza una vez durante el desarrollo del pipeline y se mantiene automáticamente: es una propiedad que puede degradarse en cualquier momento por razones que van desde bugs en sistemas upstream hasta cambios de comportamiento de los usuarios que producen distribuciones de datos no anticipadas. El monitoreo de calidad de datos es el proceso continuo que detecta estas degradaciones estadísticas antes de que impacten la calidad de los modelos, actuando como la primera línea de defensa del sistema de IA. Esta detección temprana es económicamente decisiva: un problema de calidad de datos detectado en el pipeline antes de llegar al modelo se resuelve en horas; el mismo problema detectado después de que el modelo degradado lleva semanas en producción puede requerir un reentrenamiento de emergencia, una investigación de incidente y comunicación a equipos de negocio.

**Great Expectations** es el framework estándar de la industria para definir y ejecutar validaciones de calidad de datos. Su modelo conceptual es simple pero poderoso: cada dataset tiene un conjunto de "expectations" que son afirmaciones sobre las propiedades que los datos deben satisfacer, y Great Expectations ejecuta esas afirmaciones contra los datos reales y reporta qué expectations pasaron y cuáles fallaron. Las expectations se definen en Python de forma declarativa: `expect_column_values_to_be_between("age", 0, 120)` verifica que todos los valores de la columna `age` estén en el rango esperado; `expect_column_proportion_of_unique_values_to_be_between("user_id", 0.95, 1.0)` verifica que al menos el 95% de los valores de `user_id` sean únicos; `expect_column_distribution_to_match_other("feature_x", reference_dataset)` compara la distribución de `feature_x` contra una distribución de referencia. Estas validaciones se ejecutan automáticamente en cada run del pipeline de datos, y si alguna falla, el pipeline puede detenerse antes de usar datos inválidos para entrenamiento o inferencia.

El monitoreo continuo en producción requiere un enfoque diferente de las validaciones batch del pipeline: en lugar de ejecutar validaciones sobre el dataset completo periodicamente, el monitoreo continuo calcula estadísticas de distribución sobre ventanas deslizantes de datos de producción y las compara contra una distribución de referencia. Los tests estadísticos estándar para este monitoreo son: **Kolmogorov-Smirnov** (KS-test) para variables continuas, que mide la máxima diferencia entre la CDF de la distribución actual y la de referencia; **Chi-squared** para variables categóricas, que mide si la frecuencia de cada categoría es consistente con la distribución de referencia; y **Population Stability Index (PSI)**, que combina ambas distribuciones en un índice scalar con umbrales bien establecidos: PSI < 0.1 indica estabilidad, 0.1–0.2 indica drift moderado que merece atención, y PSI > 0.2 indica drift severo que señala la necesidad de reentrenamiento del modelo.

Una complicación práctica del monitoreo estadístico es el problema de las comparaciones múltiples: si se monitorizan 100 features y se aplica un umbral de significancia de p < 0.05 a cada una, se esperan aproximadamente 5 alertas falsas por ciclo de evaluación incluso si los datos no han cambiado. La corrección de Bonferroni —dividir el umbral de significancia por el número de features monitorizadas— reduce los falsos positivos pero puede hacer que el sistema sea insensible a drift real en datasets con muchas features. Una solución práctica es jerarquizar las features: las features críticas para el modelo (las que tienen mayor importancia en SHAP values o feature importance) se monitorizan con umbrales más sensibles y alertas inmediatas; las features secundarias se monitorizan con umbrales más permisivos o se agregan en un score de drift global.

## Dimensiones de calidad de datos para sistemas de IA

- **Completitud:** porcentaje de valores nulos por columna; alertar si supera el umbral definido (ej. >5% para features críticas, >20% para features secundarias); un aumento repentino de nulos suele indicar un bug en el sistema upstream.
- **Frescura:** tiempo desde la última actualización de las features en el online store; la latencia de materialización se mide y alerta cuando supera el SLO; features desactualizadas pueden degradar el modelo silenciosamente.
- **Distribución:** drift estadístico medido con KS-test (variables continuas, p < 0.05) o Chi-squared (variables categóricas), ejecutado periódicamente comparando datos de producción contra distribución de referencia (el dataset de entrenamiento).
- **Esquema:** validación automática de que el schema (columnas, tipos, cardinalidades) coincide con el contrato definido; cambios de schema se detectan inmediatamente antes de que rompan el pipeline de features.
- **Consistencia referencial:** validación de que los identificadores (user_id, item_id) en los datos de features existen en los sistemas fuente y no hay data corruption por JOINs incorrectos o deletes no propagados.

> **Nota del Arquitecto:** La validación de datos debe ejecutarse en cada etapa del pipeline, no solo al inicio. Datos que entran al pipeline con el schema correcto pueden corromperse en transformaciones intermedias —un join con NULL behavior incorrecto, una agregación con lógica de time window equivocada, un encoding de categorías que produce valores fuera de rango. La detección en la etapa siguiente de la transformación incorrecta, no al final del pipeline, es lo que permite identificar la causa raíz con precisión.

La validación y el monitoreo de calidad de datos son las garantías técnicas de que el sistema de IA recibe inputs correctos. Sin ellas, la calidad de los modelos en producción es un evento aleatorio que depende de que los sistemas upstream no cambien de forma inesperada. La sección de cierre de este capítulo integra el argumento central: la inversión en infraestructura de datos —feature stores, versionado, validación— es siempre rentable cuando se mide correctamente como el costo evitado de incidentes de producción causados por datos de baja calidad.
