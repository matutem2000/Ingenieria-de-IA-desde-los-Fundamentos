# Módulo 10 – Capítulo 02 – Sección 01

## Arquitectura de referencia para una plataforma de IA empresarial

Una arquitectura de referencia responde a una pregunta fundamental: ¿cómo se ensamblan los componentes de la plataforma en un sistema coherente? El Capítulo 01 describió qué hace cada componente por separado; este capítulo responde cómo se conectan entre sí con contratos de API versionados, qué patrón arquitectónico organiza esas conexiones, y cómo esa estructura se convierte en un sistema que múltiples equipos pueden usar simultáneamente sin interferirse. La arquitectura de referencia no es un diagrama aspiracional: es un conjunto de decisiones implementadas, testeadas y documentadas que los equipos pueden adoptar sin tener que redescubrir los mismos problemas de infraestructura.

El patrón más adoptado en la industria organiza la plataforma en cinco **planos funcionales**, cada uno con responsabilidades bien delimitadas y contratos de API explícitos con los planos adyacentes. Este patrón, documentado por empresas como Lyft, Netflix y Meta en sus engineering blogs, tiene la ventaja de que cada plano puede evolucionar de forma independiente sin romper los contratos con los demás, y cada equipo puede ser responsable de uno o varios planos sin necesitar conocimiento completo del sistema.

El **plano de datos** es la base sobre la que opera todo lo demás: ingesta datos de múltiples fuentes (Kafka o Pub/Sub para streaming, Spark o dbt para procesamiento batch), los almacena en formato columnar versionado (Delta Lake o Apache Iceberg sobre S3) que soporta time-travel queries para reproducibilidad de experimentos, y expone features procesadas a través del feature store (Feast o Tecton) con consistencia garantizada entre el almacén offline usado en entrenamiento y el almacén online usado en inferencia. El plano de datos es también donde se materializan los controles de governance sobre los datos: clasificación de sensibilidad, políticas de acceso y retención, y validaciones de calidad que impiden que datos incorrectos propaguen sus errores al resto del sistema.

El **plano de experimentación** orquesta el ciclo de desarrollo de modelos: el cluster de Kubernetes con GPU pools segmentados por prioridad (interactivo para notebooks, batch para training jobs de larga duración), el sistema de tracking de experimentos (MLflow o Weights & Biases) que registra automáticamente hiperparámetros, métricas y artefactos de cada run, y las herramientas de hyperparameter optimization (Optuna o Ray Tune) que automatizan la búsqueda del espacio de configuraciones. Este plano debe ser accesible para los ML Engineers con el menor overhead posible: lanzar un experimento no debería requerir más que especificar el código, los datos y los recursos necesarios.

El **plano de serving** transforma modelos registrados en endpoints de producción: el model server (Triton Inference Server o KServe) gestiona la carga del modelo y el procesamiento de requests, el API Gateway (Kong, AWS API Gateway) aplica autenticación, rate limiting y logging al tráfico entrante, y el sistema de routing (Istio o un componente custom) dirige el tráfico entre versiones del modelo para estrategias de canary, blue-green o A/B testing. Cada equipo consumidor del endpoint percibe un servicio estable y con SLA definido; la complejidad del routing y la gestión de versiones es transparente para ellos.

El **plano de control** es el sistema nervioso de la plataforma: el model registry con webhooks de promoción automática, el orquestador de pipelines con DAGs declarativos (Kubeflow Pipelines o Prefect), la gestión de configuración via GitOps (ArgoCD), y la gestión de secretos (HashiCorp Vault o AWS Secrets Manager). El plano de control es lo que hace que la plataforma sea autónoma: un modelo que pasa los gates de calidad en el registry puede desplegarse automáticamente sin intervención humana porque el plano de control ejecuta la secuencia correcta de operaciones.

El **plano de observabilidad** cierra el ciclo con métricas de sistema en Prometheus, métricas de calidad del modelo en Evidently AI o WhyLabs con drift detection automático, logs estructurados en Elasticsearch para debugging, y traces distribuidos en Jaeger u OpenTelemetry para trazabilidad de requests complejos. Los equipos acceden a dashboards predefinidos en Grafana sin configurar el sistema de métricas manualmente: la observabilidad es el comportamiento por defecto de cualquier servicio que corre en la plataforma.

## Componentes principales de la arquitectura de referencia

- **Data plane:** ingesta streaming (Kafka) y batch (Spark en EMR o Dataproc), almacenamiento en object store con formato columnar versionado (Delta Lake), feature store con consistencia online/offline garantizada.
- **Training plane:** Kubernetes con GPU pools segmentados por prioridad, job scheduling con Volcano o Kueue, distributed training con PyTorch DDP y checkpointing en S3 para tolerancia a fallos.
- **Serving plane:** model server (Triton/KServe) con autoscaling via KEDA, API Gateway con rate limiting y autenticación JWT, routing por canary weight o header-based routing.
- **Control plane:** model registry con webhooks de promoción, pipeline orchestrator con DAGs declarativos, GitOps con ArgoCD, secret management con HashiCorp Vault.
- **Observability plane:** métricas de sistema en Prometheus, métricas de modelo con drift detection, logs estructurados en Elasticsearch, traces distribuidos en Jaeger.

> **Nota del Arquitecto:** La arquitectura de referencia se documenta en el developer portal (Backstage) de la organización, incluyendo los contratos de API entre planos y los criterios de decisión para cuándo usar cada componente. Sin esa documentación, cada equipo nuevo que llega a la plataforma reconstruye el mapa del sistema hablando con personas, en lugar de consultando una fuente de verdad. El costo de mantener esa documentación actualizada es insignificante comparado con el costo de onboarding que se paga cuando no existe.
