# Módulo 10 – Capítulo 06 – Sección 02

## Orquestadores de pipelines: Airflow, Prefect y Kubeflow Pipelines

Los orquestadores de pipelines de MLOps comparten una funcionalidad central —gestionar la ejecución de flujos de trabajo como grafos acíclicos dirigidos (DAGs) con dependencias entre tareas, reintentos automáticos, y registro de ejecuciones— pero difieren significativamente en su modelo de programación, sus primitivas de ejecución y su integración con el ecosistema de ML. La elección del orquestador correcto no es solo una decisión técnica: es una decisión sobre la cultura de desarrollo de pipelines que el equipo quiere adoptar. Un orquestador que prioriza la potencia del operador pero tiene una curva de aprendizaje alta puede resultar en que los ML Engineers delegan toda la gestión de pipelines al equipo de plataforma en lugar de operar sus propios pipelines. Un orquestador con mejor developer experience pero menos flexibilidad puede generar workarounds cuando se enfrentan casos de uso avanzados.

**Apache Airflow** es el orquestador más adoptado en la industria con el ecosistema de operadores más amplio: `KubernetesPodOperator` para ejecutar cualquier tarea en un Pod de Kubernetes, `SparkSubmitOperator` para jobs de Spark, `DatabricksRunNowOperator` para notebooks de Databricks, y decenas más para servicios de AWS, GCP y Databricks. Esta amplitud de integración es su principal ventaja: organizaciones con pipelines de datos heterogéneos (ML + dbt + ETL + análisis) pueden centralizar la orquestación en Airflow sin cambiar de herramienta. Sus debilidades son igualmente bien documentadas: el modelo de programación de DAGs en Python tiene una curva de aprendizaje pronunciada porque el código del DAG se evalúa en el scheduler sin ejecutarse (lo que confunde a los desarrolladores acostumbrados al flujo normal de Python), el testing local es complejo porque requiere un entorno similar al de producción, y los cambios en el código de los DAGs en producción pueden causar comportamientos inesperados si no se gestionan cuidadosamente.

**Prefect** adopta un modelo de programación más cercano al código Python estándar, usando decoradores que transforman funciones normales en tareas y flujos del pipeline: `@task` convierte una función en una tarea con retry logic y logging automático, y `@flow` convierte una función en un flujo orquestable. La diferencia operacional respecto a Airflow es significativa: el testing local de un Prefect flow es trivial porque `if __name__ == "__main__": my_flow()` ejecuta el flujo exactamente como lo haría el orquestador, sin necesidad de emular el comportamiento del scheduler. El modelo de ejecución distribuida de Prefect separa el servidor central de orquestación (Prefect Cloud o self-hosted) de los workers que ejecutan el cómputo donde está disponible (Kubernetes, ECS, Lambda, o simplemente el entorno local del desarrollador). Prefect es la opción que maximiza la experiencia del ML Engineer como operador de sus propios pipelines.

**Kubeflow Pipelines** está diseñado específicamente para ML y se integra de forma nativa con el ecosistema de Kubernetes. Los componentes de un pipeline de Kubeflow son contenedores Docker —cualquier proceso que corre en un container puede ser un step del pipeline— y el pipeline se define en Python con el SDK de KFP (Kubeflow Pipelines), generando automáticamente un YAML de Argo Workflows que Kubernetes ejecuta. La integración nativa con el ecosistema Kubeflow es su diferenciador: Katib para hyperparameter tuning automático, Training Operator para distributed training con PyTorchJob o TFJob, y el Metadata Store (MLMD) para tracking de artefactos son componentes que se integran de forma nativa con los pipelines de KFP. La desventaja es que Kubeflow Pipelines requiere un cluster de Kubernetes dedicado o compartido, y la operación del ecosistema completo de Kubeflow tiene una complejidad operativa significativa.

## Comparación técnica de orquestadores

- **Apache Airflow:** ecosistema más amplio, operadores para decenas de servicios, scheduling basado en cron con backfill nativo; complejidad operativa alta, curva de aprendizaje pronunciada; mejor para organizaciones con múltiples tipos de pipelines de datos, no solo ML.
- **Prefect:** modelo de programación Python puro con decoradores, testing local trivial, UI moderna, deployment flexible (Kubernetes, Docker, Process); menor overhead operativo que Airflow; mejor para equipos que priorizan la experiencia del ML Engineer como operador de sus propios pipelines.
- **Kubeflow Pipelines:** integración nativa con Kubernetes y ecosistema Kubeflow (Katib, Training Operator), componentes reutilizables como contenedores, MLMD para tracking de artefactos; requiere cluster Kubernetes dedicado; mejor para plataformas Kubernetes-first con alto volumen de training jobs distribuidos.
- **Criterio de selección:** Airflow para organizaciones con múltiples tipos de pipelines de datos que necesitan centralización; Prefect para equipos que priorizan developer experience y self-service de ML Engineers; Kubeflow para plataformas Kubernetes-nativas con distributed training como caso de uso central.
- **Testing de pipelines:** independientemente del orquestador elegido, cada step del pipeline debe ser testeable en aislamiento con PyTest; los tests de integración deben ejecutarse contra un entorno de staging con datos sintéticos, no sobre datos de producción.

> **Nota del Arquitecto:** La elección del orquestador determina la cultura de desarrollo de pipelines: priorizar la experiencia del ML Engineer (Prefect) sobre la potencia del operador de datos (Airflow) resulta en mayor adopción y menos pipelines abandonados en favor de scripts ad-hoc. Si los ML Engineers no pueden operar sus propios pipelines sin ayuda constante del equipo de plataforma, el orquestador no está cumpliendo su función habilitadora.

La elección del orquestador es una decisión de largo plazo: migrar de un orquestador a otro después de tener decenas de pipelines en producción es costoso en tiempo de ingeniería y en riesgo operacional. La siguiente sección examina el continuous training —el proceso que cierra el ciclo de MLOps al reentrenar automáticamente los modelos cuando su calidad en producción degrada— y los riesgos específicos de feedback loops autoinducidos que hacen del CT una práctica que requiere diseño cuidadoso.
