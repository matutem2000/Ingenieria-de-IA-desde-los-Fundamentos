# Módulo 10 – Capítulo 06 – Sección 05

## GitOps para MLOps: infraestructura como código y despliegue declarativo

GitOps aplica el principio de que el estado deseado de toda la infraestructura y configuración del sistema se describe declarativamente en un repositorio Git, y un operador automático (ArgoCD, Flux) se encarga de reconciliar continuamente el estado real del cluster con el estado declarado en Git. Este principio, que en el contexto de aplicaciones web convencionales ya es una práctica estándar, adquiere una dimensión adicional en el contexto de MLOps: la versión del modelo que está en producción, los parámetros de scaling del serving layer, y la configuración del pipeline de monitoreo son parte del estado del sistema que debe estar bajo control de versiones con la misma rigurosidad que el código de la aplicación.

En el contexto de MLOps, GitOps cubre tres dimensiones complementarias. La primera es la **infraestructura de la plataforma**: la definición de namespaces de Kubernetes, ResourceQuotas, NetworkPolicies e IngressRoutes se describe en Helm charts o manifiestos de Kustomize que viven en Git. Cuando el equipo de plataforma necesita añadir un nuevo namespace para un equipo de AI Engineering, o aumentar la ResourceQuota de GPU de un equipo, el cambio va por un Pull Request con revisión — no por un `kubectl apply` manual que nadie podrá rastrear después.

La segunda dimensión es la **configuración de los modelos en producción**: los InferenceService de KServe con la versión del modelo, los parámetros de scaling (min/max replicas, GPU resources) y los recursos de CPU/GPU se definen en archivos YAML en el repositorio de configuración (config repo), no se modifican directamente con `kubectl`. Un Helm chart parametrizado acepta `model_uri`, `replicas`, `cpu_limit`, `memory_limit`, `gpu_count` como valores configurables: el CI/CD pipeline de entrenamiento actualiza el `values.yaml` con la nueva versión del modelo cuando ésta pasa los gates de calidad, y ArgoCD aplica el cambio automáticamente. El resultado es que el historial de Git contiene exactamente cuándo, quién y qué versión del modelo fue desplegada en producción, incluyendo el PR de code review que aprobó el cambio.

La tercera dimensión es los **pipelines de MLOps**: las definiciones de los DAGs de Airflow o los Prefect Deployments se versionan en Git y se despliegan automáticamente al mergearse al branch principal. Si un PR introduce un bug en la lógica del pipeline que no fue capturado por los tests, `git revert` es el mecanismo de rollback: el orquestador carga automáticamente la versión anterior del DAG. La separación entre el repositorio de código de entrenamiento y el repositorio de configuración de despliegue (config repo) es una práctica importante: el pipeline de CI actualiza el config repo cuando un nuevo modelo pasa los gates de calidad, creando un Pull Request automático que puede ser revisado y aprobado por un humano antes de que ArgoCD aplique el cambio a producción.

El beneficio de GitOps para MLOps se materializa en el momento de un incidente. Cuando un modelo de producción empieza a comportarse de forma inesperada después de un despliegue, la primera pregunta es "¿qué cambió?". Con GitOps, esa pregunta tiene una respuesta en segundos: el historial del config repo muestra exactamente qué versión del modelo fue desplegada, cuándo, y qué PR la autorizó, incluyendo el comentario del revisor que aprobó el cambio. Sin GitOps, esa misma pregunta requiere investigación en logs de kubectl, conversaciones con el equipo y reconstrucción manual de la secuencia de eventos.

## Aspectos técnicos de GitOps para MLOps

- **Repository structure:** separar el repo de código de entrenamiento del repo de configuración de despliegue (config-as-code); el pipeline de CI actualiza automáticamente el config repo cuando un nuevo modelo pasa los gates de calidad; la separación establece un punto de control auditable.
- **ArgoCD Application:** recurso de Kubernetes que mapea un directorio del repositorio Git a un namespace del cluster, con sync policy (manual para producción, automático para staging) y configuración de pruning de recursos eliminados.
- **Helm charts para modelos:** un chart parametrizado acepta `model_uri`, `replicas`, `cpu_limit`, `memory_limit` como values; el CI actualiza el `values.yaml` con la nueva versión del modelo; ArgoCD detecta el cambio y aplica el sync.
- **Promotion workflow:** el pipeline de entrenamiento crea un PR automático al config repo con la nueva versión del modelo; un humano aprueba el PR (o el proceso es totalmente automatizado para deployments de bajo riesgo); ArgoCD aplica el cambio creando un audit trail completo en Git.
- **Secret management:** los secretos (API keys, credenciales) no se almacenan en Git sino en HashiCorp Vault o AWS Secrets Manager; External Secrets Operator sincroniza los secretos desde Vault al cluster; las referencias a secretos (no los valores) sí viven en Git.

> **Nota del Arquitecto:** El repositorio de configuración de GitOps para MLOps debe ser el único origen de verdad sobre qué versión de qué modelo está en producción. Cualquier cambio manual con `kubectl` que no pase por Git debe considerarse una violación de proceso y un riesgo de auditoría: no porque el cambio sea necesariamente incorrecto, sino porque es invisible para el sistema de trazabilidad y no puede ser reproducido ni revertido de forma controlada.

GitOps provee la trazabilidad, la reproducibilidad y el control de cambios que hacen del despliegue de modelos un proceso confiable y auditable. La sección de cierre de este capítulo sintetiza el argumento central del Capítulo 06: que un pipeline de MLOps bien diseñado no es un lujo sino la precondición para que la mejora continua de modelos sea sostenible a largo plazo.
