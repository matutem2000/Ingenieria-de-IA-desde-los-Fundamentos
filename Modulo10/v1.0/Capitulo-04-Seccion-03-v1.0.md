# Módulo 10 – Capítulo 04 – Sección 03

## Pipelines de datos para LLM: ingestión, limpieza y preparación de datos de entrenamiento

A partir de esta sección, el capítulo cambia de dominio: de los feature stores para modelos de ML clásico a los pipelines de datos para LLMs. Este cambio no es menor. Los feature stores gestionan features estructuradas con latencias de milisegundos para inferencia en tiempo real; los pipelines de datos para LLMs procesan texto no estructurado a escala de terabytes o petabytes para producir corpora de entrenamiento. Las herramientas, las métricas de calidad y los desafíos operacionales son fundamentalmente distintos. Un ML Engineer con experiencia en feature stores para modelos tabulares encontrará que los pipelines de LLM requieren aprender un conjunto de técnicas diferente, aunque el principio subyacente sea el mismo: garantizar que el modelo se entrena con datos de alta calidad.

Los pipelines de datos para LLMs difieren de los pipelines de ML clásico en dos dimensiones: escala y complejidad de las transformaciones. En escala, un corpus de preentrenamiento de un LLM de tamaño medio procesa entre 100 billones y 1 billón de tokens (entre 100B y 1T tokens), lo que implica decenas o cientos de terabytes de texto. Mientras un dataset de ML tabular puede procesarse en horas con Spark sobre un cluster moderado, un corpus de preentrenamiento requiere pipelines distribuidos que corren durante días sobre cientos de nodos. En complejidad de transformaciones, los pipelines de LLM incluyen etapas de limpieza específicas para texto que no tienen equivalente en ML clásico: deduplicación fuzzy con MinHash LSH para detectar documentos parecidos aunque no idénticos, identificación de idioma a nivel de documento con fastText, evaluación de la calidad del contenido mediante clasificadores de perplexidad entrenados sobre texto de referencia de alta calidad, y filtrado de contenido dañino con listas de bloqueo y clasificadores.

El pipeline de datos para **fine-tuning de LLMs** (instruction tuning, RLHF, RLAIF) opera en una escala más manejable —típicamente decenas de miles a pocos millones de ejemplos— pero con requisitos de calidad más estrictos. El dataset de instruction tuning, compuesto por pares prompt/completion, necesita pasar por validaciones de formato (¿el par tiene la estructura de sistema/usuario/asistente correcta?), filtrado de respuestas de baja calidad (respuestas demasiado cortas, respuestas en el idioma incorrecto, respuestas que no siguen el formato esperado), deduplicación exacta (hash SHA256 de la muestra normalizada para eliminar duplicados idénticos que producen overfitting), y opcionalmente verificación de calidad con un modelo juez. El **LLM-as-a-judge** —usar GPT-4 o Claude para evaluar la calidad de cada par de training en una muestra representativa antes de incluirlo en el dataset— es una técnica con costo no trivial pero que puede identificar sistemáticamente respuestas incorrectas, inseguras o de baja calidad que los filtros heurísticos no detectan.

Las herramientas especializadas para este dominio incluyen: `datatrove` de Hugging Face para pipelines de limpieza de texto a escala con componentes reutilizables; `datasets` de Hugging Face para gestión de datasets con caching inteligente que evita recomputar etapas ya completadas; EleutherAI's `lm_datasets` para procesamiento de Common Crawl con filtros pre-calibrados; y Apache Beam sobre Dataflow (GCP) o Spark sobre EMR (AWS) para el procesamiento distribuido de las etapas más computacionalmente intensivas. El formato de almacenamiento para training eficiente es importante: MosaicML MDS (Mosaic Data Shard) y el formato nativo de Hugging Face datasets son los estándares para carga eficiente durante el entrenamiento con acceso aleatorio y sin cuello de botella de I/O.

## Etapas técnicas del pipeline de datos para LLM

- **Ingestión:** descarga y normalización de fuentes heterogéneas (Common Crawl WARC, GitHub, arXiv, Wikipedia dumps) con conversión a formato estándar JSONL con campos `text`, `source`, `timestamp`, `url`; la estandarización del formato es el primer paso de la cadena de calidad.
- **Limpieza de texto:** eliminación de HTML/boilerplate (Trafilatura, Resiliparse), normalización Unicode, detección de idioma (fastText `lid.176.bin`), y filtros heurísticos de calidad (longitud mínima, ratio de caracteres especiales, ratio de tokens alfabéticos).
- **Deduplicación:** exacta por hash del texto normalizado para eliminar copias idénticas; fuzzy con MinHash + LSH (similitud de Jaccard > 0.8 entre documentos) que detecta near-duplicados que la deduplicación exacta no identifica; esta etapa reduce corpora en un 10-40%.
- **Filtrado de calidad:** perplexity scoring con KenLM entrenado sobre texto de alta calidad (Wikipedia), clasificadores de calidad curated vs. web data, y listas de bloqueo de dominios de baja calidad; estas etapas son las que más diferencian la calidad final del corpus.
- **Tokenización y empaquetado:** tokenización con el tokenizer del modelo objetivo, empaquetado en secuencias de longitud fija (2048 o 4096 tokens) con document boundaries marcados, almacenamiento en formato MDS o Hugging Face datasets para carga eficiente durante el entrenamiento sin cuello de botella de I/O.

> **Nota del Arquitecto:** La calidad del corpus de entrenamiento determina más el comportamiento del LLM que la arquitectura del modelo. Una hora invertida en mejorar los filtros de calidad del pipeline —calibrar mejor el umbral de perplexity, añadir un clasificador de dominio específico, refinar la lista de dominios de baja calidad— tiene mayor impacto en el modelo final que una hora ajustando hiperparámetros de entrenamiento. Los equipos que invierten en la calidad del pipeline de datos iterativamente, eval por eval, son los que producen los modelos más consistentemente buenos.

Los pipelines de datos para LLMs requieren infraestructura distribuida, herramientas especializadas para texto a escala, y métricas de calidad distintas de las del ML clásico. La siguiente sección conecta los dos dominios cubiertos en este capítulo con el tema del versionado de datos: tanto los features de ML clásico como los corpora de LLMs necesitan versionado reproducible para garantizar que los experimentos sean comparables y auditables.
