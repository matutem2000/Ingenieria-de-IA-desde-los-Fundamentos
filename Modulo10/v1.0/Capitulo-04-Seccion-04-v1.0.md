# Módulo 10 – Capítulo 04 – Sección 04

## Data versioning: DVC y LakeFS para reproducibilidad de experimentos

El versionado de datos es tan crítico para la reproducibilidad como el versionado del código fuente, pero su implementación es más compleja porque los datasets de ML tienen propiedades que los sistemas de control de versiones de código como Git no pueden gestionar directamente: son binarios de gran tamaño (gigabytes o terabytes), cambian frecuentemente, y necesitan soportar consultas de "dame los datos que existían el 15 de marzo a las 10:00 AM" para reproducibilidad exacta de experimentos. La consecuencia de no tener versionado de datos es concreta: un mismo código de entrenamiento aplicado sobre datos distintos produce modelos distintos, y sin versionado de datos es imposible diagnosticar regresiones de calidad, reproducir experimentos de hace varios meses, ni cumplir con requisitos de auditoría que exigen saber exactamente qué datos de clientes fueron usados en cada modelo. Esta aplicabilidad es transversal a los dos dominios del capítulo: tanto los feature sets para ML clásico como los corpora de LLMs necesitan versionado.

**DVC** (Data Version Control) extiende Git para versionar datasets y modelos de gran tamaño sin introducir los archivos binarios en el repositorio de Git. Su mecanismo es elegante: al ejecutar `dvc add data/train.parquet`, DVC crea un archivo `data/train.parquet.dvc` con el hash MD5 del contenido (el archivo "puntero") y añade el dataset real al `.gitignore`. El puntero se versiona en Git normalmente —`git commit -m "update training dataset"`, `git push`— y el dataset real se almacena en un remote storage configurado (S3, GCS, Azure Blob, SSH) con `dvc push`. Para reproducir exactamente un experimento del pasado, `git checkout <commit-id>` restaura el puntero histórico y `dvc pull` descarga exactamente el dataset que ese commit referencia. DVC también gestiona pipelines de transformación con `dvc.yaml`: cada etapa del pipeline tiene entradas, salidas y comandos declarados, y `dvc repro` ejecuta solo las etapas cuyos inputs han cambiado, similar al comportamiento de `make`.

**LakeFS** adopta un enfoque arquitecturalmente diferente: en lugar de añadir una capa sobre Git, actúa como un sistema de control de versiones Git-like directamente sobre object storage (S3, GCS, Azure Blob) sin necesitar copiar los datos. LakeFS usa content-addressable storage para crear referencias (branches, commits, tags) que apuntan a los mismos objetos subyacentes con costo cero de branching: crear un branch en LakeFS es instantáneo independientemente del tamaño del data lake porque no copia ningún dato, solo crea una referencia. `lakectl commit` crea un snapshot atómico de millones de archivos en milisegundos. `lakectl checkout <commit-id>` restaura exactamente el estado del data lake en cualquier momento del pasado. Esta arquitectura hace que LakeFS sea especialmente adecuado para organizaciones que ya tienen grandes data lakes en S3 y quieren añadir versionado sin migrar los datos existentes.

La elección entre DVC y LakeFS depende del contexto de uso y la escala. DVC está optimizado para repositorios de experimentos individuales o de equipo: funciona bien cuando el dataset de un experimento es el foco del versionado y el data lake completo no necesita ser versionado. LakeFS está optimizado para data lakes organizacionales completos: cuando múltiples pipelines y equipos comparten el mismo data lake y se necesita versionado de todo el estado del lake, no solo de datasets individuales. Muchas organizaciones usan ambos: LakeFS para el data lake y DVC para los datasets de entrenamiento específicos de cada experimento de ML.

## Aspectos técnicos del versionado de datos

- **DVC tracking:** `dvc add` crea el puntero con hash MD5; `dvc push` sube al remote storage; `dvc pull` restaura la versión exacta; el grafo de dependencias de `dvc.yaml` hace que `dvc repro` sea determinista e incremental.
- **DVC pipelines:** `dvc.yaml` define el grafo de transformaciones con inputs, outputs y comandos; `dvc repro` ejecuta solo las etapas cuyos inputs cambiaron, convirtiendo el pipeline de datos en un sistema reproducible y eficiente.
- **LakeFS branching:** cada experimento puede trabajar en su propio branch del data lake (`feature/experiment-42`) con aislamiento completo de las modificaciones hasta hacer merge; múltiples experimentos en paralelo sin riesgo de interferencia.
- **LakeFS commits atómicos:** `lakectl commit` captura el estado de millones de archivos usando content-addressable storage sin copiar datos físicamente; el costo de un snapshot es independiente del tamaño del data lake.
- **Integración con linaje de modelos:** DVC (`dvc.lock` con hashes exactos) y LakeFS (commit SHA del data lake) proveen los identificadores únicos que se registran en el model registry como parte del linaje del modelo, cerrando el ciclo de trazabilidad datos → modelo.

> **Nota del Arquitecto:** Registrar el hash del dataset (DVC) o el commit del data lake (LakeFS) junto con el `run_id` de MLflow en cada experimento crea automáticamente el linaje completo datos-experimento-modelo sin esfuerzo adicional. La clave es hacer este registro automático en el código base del pipeline de entrenamiento, no opcional para cada ML Engineer. La trazabilidad que no es automática no existe en producción.

El versionado de datos es la base técnica de la reproducibilidad: sin él, los experimentos son eventos únicos que no pueden repetirse ni compararse con rigor. La sección siguiente aborda la dimensión continua del problema de calidad de datos: no solo versionar los datos, sino monitorear que su calidad se mantiene en el tiempo y que los pipelines detectan degradaciones antes de que afecten a los modelos en producción.
