## Feast, Hopsworks y Tecton: comparación de soluciones de feature store

Elegir un feature store no es solo una decisión técnica: es una decisión sobre cuánto esfuerzo operativo el equipo de plataforma está dispuesto a asumir a cambio de cuánta flexibilidad y cuánto control. Las tres plataformas más adoptadas en la industria —Feast, Hopsworks y Tecton— tienen posicionamientos suficientemente distintos como para que la elección correcta varíe significativamente según el contexto de la organización. Comparar solo sus listas de features en papel produce conclusiones incorrectas; la comparación útil es la que considera el esfuerzo operativo real, la curva de aprendizaje del equipo, el costo total de ownership, y el tipo de casos de uso que dominan en la organización.

**Feast** (Feature Store, de Gojek, ahora mantenido por la Linux Foundation con contribuciones de Google, Twitter y Tecton) es el feature store open source de referencia y el punto de partida más común para organizaciones que quieren control total sin costo de licencia. Su modelo de programación es declarativo: las features se definen en Python con `FeatureView`, `Entity` y `FeatureService`, y Feast gestiona la materialización al almacén online y las consultas point-in-time para el training. La flexibilidad de Feast viene con un costo: el equipo de plataforma debe gestionar la infraestructura subyacente (Redis para el online store, S3 para el offline store, y el orquestador de materialización). Esta responsabilidad es manejable para equipos con experiencia en Kubernetes que ya operan múltiples servicios, pero puede ser un obstáculo significativo para equipos más pequeños o menos especializados en infraestructura. Feast es la opción correcta cuando la organización tiene ya capacidad operativa de Kubernetes, quiere control total sobre los backends de almacenamiento, y tiene casos de uso batch con ciclos de materialización de horas a días.

**Hopsworks** añade sobre el modelo de Feast un motor de ingesta streaming integrado (Flink) que permite features calculadas en tiempo real con latencias de segundos, feature versioning nativo con `FeatureGroup.insert()` que mantiene el historial de cada versión de las definiciones de features, y una UI rica con estadísticas automáticas de distribución calculadas en cada escritura al feature group. La versión managed (Hopsworks AI en AWS, GCP o Azure) elimina la carga operativa del despliegue y mantenimiento de la infraestructura subyacente, a un costo de licencia que escala con el volumen de datos procesados. Hopsworks es la opción correcta para organizaciones que tienen casos de uso de streaming features (features que requieren información reciente de eventos en tiempo real) y valoran el feature versioning automático que permite reproducir exactamente qué features se usaron en un training específico.

**Tecton** es la opción con el mayor nivel de abstracción operativa y las capacidades más avanzadas para producción a gran escala. Sus diferenciadores son la real-time feature computation con SLA de sub-100ms (usando infraestructura gestionada de Redis y Kafka que Tecton opera internamente), el backfilling automático de features históricas cuando se añade una nueva feature definition (sin necesidad de ejecutar manualmente un job de backfill), y el feature monitoring nativo que detecta drift en las distribuciones de features y alerta antes de que el impacto llegue a los modelos. El costo de Tecton es significativamente mayor que las alternativas open source —con precios enterprise basados en volumen de features y requests— pero para organizaciones donde el equipo de plataforma tiene capacidad limitada para operar infraestructura compleja, el menor esfuerzo operativo puede justificar el diferencial de costo.

## Comparación técnica

- **Feast:** open source (Linux Foundation), deployment self-managed en Kubernetes, soporte para batch y streaming features via Kafka, bajo costo de licencia pero mayor esfuerzo operativo del equipo de plataforma; para organizaciones con capacidad operativa de Kubernetes.
- **Hopsworks:** open source con Enterprise tier managed, motor de streaming Flink integrado, feature versioning nativo con `FeatureGroup.insert()`, estadísticas automáticas de distribución; para casos de uso con streaming features y requisitos de versioning.
- **Tecton:** SaaS propietario, real-time feature computation con SLA de sub-100ms, automatic backfilling de features históricas, feature monitoring nativo; mayor costo pero menor esfuerzo operativo; para organizaciones que priorizan velocidad de adopción y tienen presupuesto para SaaS.
- **Criterio de selección por esfuerzo operativo:** Feast si el equipo puede y quiere operar infraestructura; Hopsworks si se necesita streaming y versioning sin asumir toda la operación; Tecton si la velocidad de time-to-value supera la consideración de costo.
- **Integración con el model registry:** los tres soportan integración con MLflow para registrar automáticamente las features usadas en cada training run como parte de los metadatos de linaje; esto debe configurarse explícitamente, no es automático por defecto.

> **Nota del Arquitecto:** Antes de elegir un feature store, el ejercicio más valioso es identificar los dos o tres casos de uso de ML en producción que más se beneficiarían de él y hacer un proof of concept con la solución candidata sobre esos casos específicos. La comparación de features en la documentación nunca captura el problema de integración real con los sistemas de datos existentes, la curva de aprendizaje del equipo, o los edge cases del caso de uso específico. El PoC de dos semanas ahorra meses de frustración post-adopción.

La elección entre Feast, Hopsworks y Tecton determina cuánto esfuerzo operativo asume el equipo de plataforma, no qué calidad de features pueden servirse. La siguiente sección cambia de dominio: de los feature stores para modelos de ML clásico a los pipelines de datos especializados para LLMs, que operan en escalas y con problemas de calidad fundamentalmente distintos.
