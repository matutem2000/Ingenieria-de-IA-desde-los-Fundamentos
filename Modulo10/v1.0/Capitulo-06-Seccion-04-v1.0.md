# Módulo 10 – Capítulo 06 – Sección 04

## Pipeline testing: validar cada etapa antes de promover a producción

Un pipeline de MLOps sin tests es una caja negra que produce modelos de forma no reproducible: puede funcionar la primera vez que se ejecuta, la décima vez, y fallar en la undécima de formas que nadie puede diagnosticar rápidamente. El testing de pipelines de MLOps adopta las prácticas de testing de software —unit, integration, end-to-end— adaptadas a las características específicas de los sistemas de ML donde los datos no son fixtures estáticos sino distribuciones variables, los modelos tienen comportamiento probabilístico no determinista, y las métricas de calidad tienen umbrales relativos en lugar de valores exactos.

Los **unit tests** en un pipeline de MLOps validan cada función de transformación de datos y feature engineering de forma aislada con inputs sintéticos. La lógica es la misma que en software convencional: si la función `transform_user_age(birthdate)` tiene un bug que produce edades negativas para fechas futuras, ese bug debe detectarse en el unit test antes de llegar al pipeline de entrenamiento. Ejemplos específicos: `assert transform_user_age(birthdate=date(1990,1,1)) == 35`, `assert feature_encoding(category="unknown") == 0` (el valor esperado para categorías fuera del vocabulario de entrenamiento), `assert normalize_text("  hello WORLD  ") == "hello world"`. Los unit tests de pipeline deben ejecutarse en el mismo entorno de CI que los unit tests del código de la aplicación: si requieren GPU, datos de producción, o servicios externos para ejecutarse, no son unit tests efectivos.

Los **integration tests** validan que las etapas del pipeline se conectan correctamente entre sí. Los puntos de integración más críticos en un pipeline de MLOps son: la compatibilidad del schema de output de la etapa de features con el schema de input esperado por el training step (una incompatibilidad aquí solo se detecta en la ejecución real del pipeline si no se testa antes), la compatibilidad del modelo serializado con el formato que el serving layer espera cargar (un modelo guardado en el formato incorrecto o con dependencias de versión incorrectas solo falla cuando se intenta desplegar), y la validez del schema de respuesta del endpoint desplegado contra el schema que la aplicación cliente espera consumir.

Los **model validation tests** son específicos de ML y no tienen equivalente en software convencional. El test más importante es la comparación de métricas offline del modelo candidato contra el modelo champion: `assert accuracy_new >= accuracy_champion * 0.99` con un margen de tolerancia explícito que permita variación estadística sin rechazar mejoras reales. Los **tests de invarianza** verifican que la predicción no cambia significativamente si se perturban features que deberían ser irrelevantes: el modelo de pricing de un producto no debería cambiar su predicción si el `user_id` cambia pero todas las features de comportamiento son idénticas. Los **tests de fairness** verifican que la métrica de calidad no difiere más del umbral permitido entre subgrupos protegidos: si el modelo de scoring tiene accuracy de 92% para usuarios masculinos y 78% para usuarios femeninas, el test de fairness detecta esa disparidad antes de que llegue a producción.

Los **load tests pre-producción** son el último gate antes del despliegue a producción. Locust o k6 ejecutan tráfico sintético contra el endpoint en staging para verificar que el modelo cumple los SLOs de latencia (TTFT, TPOT para LLMs) bajo la carga máxima esperada. El error más común es hacer load tests con carga mucho menor que el pico de producción previsto: si el endpoint en staging se testea con 50 RPS y el pico de producción es 500 RPS, el load test no ofrece ninguna garantía real sobre el comportamiento en producción.

## Tipos de tests en pipelines de MLOps

- **Data validation tests:** Great Expectations ejecutadas automáticamente en el step de ingesta; el pipeline falla con mensaje de error específico si el schema cambia inesperadamente o si la tasa de nulos supera el umbral; los failures deben ser informativas, no genéricas.
- **Feature engineering unit tests:** PyTest que validan cada función de transformación con inputs edge case (valores nulos, strings vacíos, valores fuera de rango, categorías OOV); aislados de infraestructura y ejecutables en CI sin GPU ni servicios externos.
- **Model evaluation tests:** comparación automática de métricas del modelo candidato vs champion; el gate rechaza el modelo si `accuracy_new < accuracy_champion * 0.99` o si cualquier métrica de fairness cae por debajo del umbral definido; gate de calidad, no solo alerta.
- **Serving compatibility tests:** verificar que el modelo serializado puede ser cargado por el serving layer (KServe, Triton) sin errores, y que el endpoint retorna respuestas con el schema correcto para inputs de ejemplo representativos del tráfico real.
- **Load tests pre-producción:** Locust o k6 sobre el staging endpoint verificando que cumple los SLOs de latencia bajo la carga máxima esperada antes de promover a producción; la carga de test debe ser al menos el pico de producción previsto.

> **Nota del Arquitecto:** En un pipeline de MLOps, un test que no puede ejecutarse en el entorno de CI —por depender de datos de producción, GPU cara o servicios externos— no es un test efectivo: siempre se omitirá bajo presión de tiempo. Los tests críticos deben poder ejecutarse en un entorno reproducible y aislado, con datos sintéticos que capturen los casos edge más importantes. La regla práctica: si el test tarda más de 5 minutos en ejecutarse, no se ejecutará en cada PR.

El testing de pipelines de MLOps es la práctica que convierte la confianza intuitiva en el sistema en confianza técnica verificable. Un pipeline bien testeado es uno que el equipo puede desplegar el viernes a las 5pm con la misma serenidad con la que lo desplegaría el martes por la mañana.
