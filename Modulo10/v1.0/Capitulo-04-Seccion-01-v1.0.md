# Módulo 10 – Capítulo 04 – Sección 01

## Feature store: repositorio centralizado de features para modelos de ML y IA

Este capítulo cubre dos dominios de gestión de datos que son distintos pero frecuentemente confundidos: los feature stores para modelos de ML clásico (tabular, recomendación, clasificación) en las primeras cuatro secciones, y los pipelines de datos especializados para LLMs (corpus de preentrenamiento, datos de instruction tuning) en las secciones 03 y 04. Las herramientas, problemas y arquitecturas de cada dominio son parcialmente independientes: Feast o Tecton no aparecen en un pipeline de preprocesamiento de Common Crawl para preentrenamiento de LLMs, y MinHash LSH no tiene relevancia en un feature store de comportamiento de usuarios. Identificar en qué dominio se trabaja antes de elegir herramientas evita la confusión habitual de aplicar soluciones de un dominio al problema del otro.

Un **feature store** resuelve dos problemas críticos de los proyectos de ML a escala. El primero es la duplicación de lógica de transformación de features entre equipos: sin un repositorio central, el equipo de recomendaciones calcula "tiempo_desde_último_purchase" con una implementación en pandas, el equipo de fraude la recalcula con una implementación ligeramente diferente en PySpark, y el equipo de pricing usa una tercera versión en SQL. Las tres implementaciones producen resultados similares pero no idénticos, lo que significa que ningún equipo puede reutilizar el trabajo de los demás con confianza. El feature store permite que la lógica de cálculo se defina una vez con un contrato explícito (nombre, tipo, descripción, owner, TTL) y se reutilice por todos los modelos que la necesiten, eliminando la posibilidad de divergencia.

El segundo problema que resuelve el feature store es el **training-serving skew**: la diferencia entre las features disponibles en entrenamiento y las disponibles en inferencia en producción. Este es uno de los bugs más silenciosos y peligrosos en sistemas de ML: el modelo se entrena con una feature calculada sobre el historial completo de datos, pero en producción esa misma feature se calcula con una lógica ligeramente diferente o con datos de un sistema diferente, produciendo una distribución de valores distinta que el modelo no vio en entrenamiento. El training-serving skew puede degradar la calidad de los modelos de forma significativa sin producir ningún error de sistema: el endpoint responde correctamente, pero las predicciones son silenciosamente peores. El feature store elimina este problema definiendo una única implementación de cada feature que se ejecuta tanto en el contexto de entrenamiento (offline) como en el contexto de inferencia (online).

La arquitectura de un feature store se divide en dos almacenes complementarios. El **almacén offline** —Parquet sobre S3, Delta Lake en Databricks, o BigQuery en GCP— contiene el historial completo de features con point-in-time correctness: la capacidad de recuperar el valor exacto que cada feature tenía en un momento específico del pasado, sin contaminar el set de entrenamiento con información futura que el modelo no habría tenido disponible en producción (data leakage). El **almacén online** —Redis Cluster, DynamoDB, o Bigtable— contiene la versión más reciente de cada feature con latencias de sub-milisegundo para inferencia en tiempo real: cuando una petición de inferencia llega, el serving layer recupera las features del usuario del almacén online en menos de 10ms y las pasa al modelo. La **materialización** es el proceso de pipeline que calcula las features desde las fuentes de datos originales, las escribe al almacén offline, y las sincroniza periódicamente al almacén online según la frecuencia definida (cada hora, diariamente, en streaming continuo).

## Componentes principales de un feature store

- **Feature definitions:** especificación declarativa de cada feature con nombre, tipo (float32, int64, string), descripción, owner, TTL en el almacén online, y transformación de cálculo; el contrato explícito que garantiza reproducibilidad.
- **Offline store:** almacén columnar con historial temporal completo; soporta point-in-time joins para construir training sets sin data leakage usando el timestamp exacto de cada evento de entrenamiento.
- **Online store:** almacén de baja latencia (Redis, DynamoDB) para inferencia en tiempo real; sincronizado automáticamente desde el offline store por un job de materialización programado en el orquestador de pipelines.
- **Feature registry:** catálogo de todas las features disponibles con metadatos, ejemplos y estadísticas de distribución; el punto de descubrimiento que permite a los equipos encontrar features existentes antes de implementar nuevas que ya existen.
- **Materialización:** proceso de pipeline que calcula y escribe las features desde las fuentes de datos al offline store, y luego las sincroniza al online store; la frecuencia de materialización determina la frescura de las features online.

> **Nota del Arquitecto:** El valor de un feature store es fundamentalmente organizacional antes de ser técnico. La reducción del training-serving skew es valiosa, pero el beneficio más duradero es que detiene la proliferación de implementaciones paralelas de las mismas features en equipos distintos. El ROI del feature store se mide en tiempo ahorrado de descubrimiento (¿ya existe una feature de comportamiento del usuario?), en tiempo ahorrado de debugging (¿por qué mi modelo en producción es peor que en training?) y en confianza aumentada en los resultados de los experimentos.

El feature store es el componente de la plataforma que garantiza que los modelos se entrenan con los datos correctos y que la inferencia usa las mismas features que el entrenamiento.
