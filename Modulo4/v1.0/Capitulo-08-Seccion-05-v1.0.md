# Módulo 4 – Capítulo 08 – Sección 05

## Alta Disponibilidad

La alta disponibilidad de un sistema de IA tiene una particularidad que la distingue de la alta disponibilidad de sistemas convencionales: el componente más crítico — el modelo de lenguaje — frecuentemente está fuera del control operativo directo del equipo. Cuando el sistema depende de una API de LLM de terceros, la disponibilidad del sistema está parcialmente limitada por la disponibilidad del proveedor. Diseñar la alta disponibilidad de un sistema de IA significa tanto eliminar los puntos únicos de fallo propios como preparar estrategias de degradación controlada para cuando el proveedor del LLM no está disponible.

**Redundancia multi-proveedor** es la estrategia de alta disponibilidad más robusta para sistemas que usan APIs de LLM comerciales. El sistema configura al menos dos proveedores de LLM como primario y secundario. Bajo operación normal, todas las solicitudes van al proveedor primario. Cuando el circuit breaker detecta degradación del proveedor primario (latencia elevada, tasa de error elevada, o indisponibilidad total), el tráfico se redirige automáticamente al proveedor secundario. Esta estrategia requiere que el sistema esté abstraído del proveedor específico mediante una capa de interfaz uniforme: el mismo prompt debe producir respuestas aceptables en ambos proveedores. La estandarización de comportamiento entre modelos distintos es un desafío de ingeniería de prompts que debe evaluarse cuidadosamente.

**Alta disponibilidad de la base vectorial** se logra mediante replicación: múltiples réplicas del índice vectorial, sincronizadas, con capacidad de servir consultas de lectura desde cualquier réplica. Las principales bases vectoriales gestionadas (Pinecone, Weaviate Cloud) ofrecen alta disponibilidad como característica del servicio. Para bases vectoriales self-hosted, Qdrant soporta replicación distribuida nativa; Weaviate tiene un modo de alta disponibilidad con múltiples nodos; pgvector aprovecha la replicación streaming de PostgreSQL. El compromiso arquitectónico es entre la consistencia fuerte (más costosa en latencia de escritura) y la consistencia eventual (más eficiente pero con ventanas de inconsistencia entre réplicas).

**Despliegues sin interrupción (zero-downtime deployments)** son esenciales para sistemas productivos que operan continuamente. Las estrategias más utilizadas son:

- **Blue-green deployment:** dos entornos idénticos (azul y verde) donde solo uno está activo en cada momento. El nuevo código se despliega en el entorno inactivo, se valida, y el tráfico se cambia instantáneamente. Si hay problemas, el rollback es cambiar el tráfico de vuelta al entorno anterior.
- **Canary deployment:** el nuevo código se despliega gradualmente: primero al 1% del tráfico, luego al 10%, al 50%, y finalmente al 100%. Si las métricas de calidad o de error degradan durante el proceso, el despliegue se detiene automáticamente. Esta estrategia es especialmente valiosa para cambios de prompt o de modelo donde el impacto en la calidad no puede verificarse completamente en un entorno de staging.
- **Rolling deployment:** las instancias del servicio se actualizan de una en una (o en grupos pequeños), manteniendo la mayor parte del tráfico en la versión anterior durante el despliegue. Es la estrategia más sencilla pero requiere compatibilidad hacia atrás entre la versión anterior y la nueva.

**Estrategias de degradación controlada** son el mecanismo que permite al sistema mantenerse útil incluso cuando uno o más componentes están degradados o no disponibles. El diseño de degradación controlada debe ser explícito: para cada componente del sistema, definir qué funcionalidad puede ofrecerse si ese componente no está disponible. Si la base vectorial no está disponible, el sistema puede responder solo con el conocimiento paramétrico del LLM (con advertencia explícita al usuario). Si el LLM principal no está disponible, el sistema puede derivar a un modelo de menor calidad. Si ambos están degradados, el sistema puede derivar todas las consultas a un humano. La degradación controlada es preferible a la indisponibilidad total.

**Recuperación de estado en sistemas de agentes** requiere que el estado de las tareas en curso sea persistido de manera que pueda recuperarse si una instancia falla. El checkpointing periódico del estado del agente — serializado en Redis u otro almacenamiento con alta disponibilidad — permite reanudar tareas interrumpidas desde el último checkpoint sin pérdida de trabajo. LangGraph implementa checkpointing como primitiva nativa de su modelo de ejecución.

**Tests de disponibilidad** deben ejecutarse continuamente, no solo ante incidentes. Synthetic monitoring — solicitudes automáticas periódicas al sistema con respuestas esperadas conocidas — detecta degradaciones antes de que los usuarios reales las experimenten. Los synthetic monitors deben cubrir el flujo completo del sistema, no solo el endpoint de la API, para detectar fallos en componentes internos como la base vectorial o el servicio de reranking.

La alta disponibilidad de un sistema de IA productivo no es una característica que se añade después de construir el sistema: es un conjunto de decisiones de diseño que se toman desde el inicio y que determinan la resiliencia del sistema ante fallos inevitables. Los sistemas de IA que atienden a usuarios en producción fallarán en algún momento; la pregunta es cuán rápido se recuperan y cuánta funcionalidad mantienen durante el fallo.
