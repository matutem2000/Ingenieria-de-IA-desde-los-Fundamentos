# Módulo 4 – Capítulo 07 – Sección 05

## Gobierno y Cumplimiento de Seguridad

El cumplimiento de seguridad en sistemas de IA es el conjunto de políticas, controles técnicos y procesos que demuestran a auditores externos que el sistema maneja los datos y opera dentro de los marcos regulatorios aplicables. Esta sección se enfoca específicamente en el cumplimiento desde la perspectiva de la seguridad técnica: qué controles son necesarios para demostrar que el sistema protege la información y opera de forma responsable con los datos que procesa. El cumplimiento regulatorio organizacional más amplio — AI Act, responsabilidades legales, modelos de riesgo institucionales — se desarrolla en el Capítulo 09.

**Uso responsable de datos de prompt** es un área donde GDPR y CCPA imponen restricciones específicas sobre los sistemas de IA que procesan datos personales. Cuando un usuario interactúa con un sistema de IA y menciona en su consulta datos personales propios o de terceros — el nombre de un cliente, la situación médica de un familiar, información financiera — esos datos pueden enviarse al proveedor del LLM si el sistema usa una API externa. Las organizaciones que procesan datos personales de ciudadanos europeos bajo GDPR deben evaluar si ese envío es compatible con su base legal de tratamiento, si el proveedor del LLM es un subprocesador bajo acuerdo DPA (Data Processing Agreement), y si los datos de prompt son usados para el entrenamiento del modelo del proveedor (algo que la mayoría de los proveedores empresariales permiten desactivar). Estas evaluaciones deben realizarse antes del despliegue, no después.

**Retención controlada de datos de interacción** desde el punto de vista de seguridad implica que los logs de conversaciones deben tratarse con el mismo nivel de protección que la información más sensible que el usuario podría haber compartido en esas conversaciones. Si el sistema puede procesar consultas sobre información médica, financiera o legal, el log completo de esas conversaciones debe estar protegido con el mismo estándar de seguridad que los registros médicos, financieros o legales del sistema. Esto incluye cifrado, control de acceso estricto, auditoría de accesos y política de retención alineada con las obligaciones regulatorias aplicables al dominio.

**Política de uso aceptable** define qué tipos de consultas y usos son permitidos en el sistema. En un sistema de IA empresarial, la política debe especificar: qué categorías de información puede y no puede procesar el sistema (por ejemplo, no procesar número de seguridad social ni datos de tarjetas de crédito), qué tipos de outputs no debe generar el sistema (contenido ilegal, información que facilite actividades dañinas), y qué consecuencias tiene el incumplimiento de la política para el usuario. La política debe estar comunicada al usuario antes del primer uso y debe ser técnicamente reforzada mediante guardrails, no solo declarada en términos de servicio.

**Evaluación de riesgos de seguridad** debe realizarse de manera estructurada antes del despliegue y periódicamente durante la operación. Para sistemas de IA, esto incluye: revisión del perfil de amenazas usando el OWASP LLM Top 10 como guía, pruebas de penetración específicas de prompt injection y jailbreak, evaluación del riesgo de datos que pasan a través del sistema, y revisión de la postura de seguridad de los proveedores externos (APIs de LLM, bases vectoriales, herramientas de agentes). El resultado de la evaluación debe producir un registro de riesgos con las mitigaciones implementadas y los riesgos residuales aceptados explícitamente.

**Monitoreo de comportamiento anómalo** como control de seguridad complementa las alertas de infraestructura descritas en el Capítulo 06. Desde la perspectiva de seguridad, el monitoreo de comportamiento busca patrones que indiquen un ataque en curso: múltiples variantes de la misma consulta que podrían ser intentos de bypass de guardrails, volúmenes de consultas anómalos de una misma IP o usuario que podrían indicar scraping o exfiltración sistemática, o respuestas del sistema que contienen información que no debería estar disponible para el usuario consultante. Estas alertas de seguridad deben ser procesadas por el equipo de seguridad, no solo por el equipo de operaciones.

**Gestión de vulnerabilidades de dependencias** es un control estándar de seguridad de software que aplica igualmente a los componentes de IA. Las versiones de los frameworks de agentes (LangChain, LlamaIndex), las bibliotecas de embeddings, los clientes de las APIs de LLM y las interfaces de bases vectoriales deben monitorearse para vulnerabilidades conocidas y actualizarse según los ciclos de patching de la organización. Las vulnerabilidades en estos componentes pueden crear vectores de ataque que van más allá de las amenazas específicas de IA.

El cumplimiento de seguridad no es una revisión puntual antes del despliegue: es un proceso continuo que acompaña al sistema durante toda su vida operativa. Las amenazas evolucionan, los modelos cambian de comportamiento, los datos del sistema se actualizan, y las regulaciones se refinan. El arquitecto que diseña el sistema pensando en ese ciclo continuo produce sistemas que envejecen bien; el que piensa solo en el despliegue inicial produce sistemas que acumulan deuda de seguridad hasta que un incidente lo obliga a pagarla.
