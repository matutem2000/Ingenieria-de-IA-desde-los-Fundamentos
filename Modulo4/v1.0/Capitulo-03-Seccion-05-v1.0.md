# Módulo 4 – Capítulo 03 – Sección 05

## Operación y Monitoreo

Un sistema RAG que funciona correctamente el día de su despliegue puede degradarse silenciosamente en las semanas siguientes. La base de conocimiento recibe documentos desactualizados que no son retirados. El modelo de embeddings utilizado en producción es deprecado por el proveedor y la versión de reemplazo genera vectores en un espacio diferente, incompatible con los embeddings ya almacenados. El volumen de consultas crece y la latencia de búsqueda supera el umbral aceptable para el usuario. Un nuevo patrón de consultas aparece — preguntas sobre un producto recién lanzado — y el sistema responde con baja relevancia porque esa área del dominio no está bien representada en la base de conocimiento. Sin observabilidad, ninguno de estos problemas es detectado hasta que un usuario se queja.

La operación de un sistema RAG productivo se organiza en torno a cuatro categorías de métricas. Las métricas de latencia miden el tiempo de respuesta del sistema en sus distintas etapas: tiempo de generación del embedding de la consulta, tiempo de búsqueda en la base vectorial (expresado en percentiles P50, P95 y P99), tiempo de reranking si aplica, y tiempo de llamada al LLM. Monitorear cada etapa por separado permite identificar dónde ocurre la degradación cuando la latencia total aumenta. Un aumento en el tiempo de búsqueda vectorial puede indicar que el índice necesita ser optimizado o que el hardware subyacente requiere escalado.

Las métricas de calidad de recuperación son las más difíciles de obtener pero las más valiosas. Requieren un conjunto de evaluación — consultas con respuestas esperadas — sobre el cual se ejecutan periódicamente las métricas RAGAS: context recall, context precision y faithfulness. Cuando estas métricas degradan, el equipo tiene una señal objetiva de que algo en el sistema — la base de conocimiento, el modelo de embeddings, la estrategia de chunking — ha cambiado y necesita atención. Herramientas como Ragas, DeepEval o Phoenix de Arize pueden integrarse como parte de un pipeline de evaluación automatizada que se ejecuta regularmente sobre el sistema en producción.

Las métricas de costo son imprescindibles para la viabilidad económica del sistema. El costo de cada consulta incluye: tokens de embedding de la consulta (típicamente menor), tokens de entrada al LLM (contexto + consulta), y tokens de salida del LLM (respuesta). A medida que el sistema crece en uso, el costo mensual puede crecer de forma no lineal si el contexto promedio por consulta es extenso. Instrumentar el costo por consulta, por usuario o por tipo de consulta permite identificar los patrones de uso más costosos y optimizarlos: reducir el número de chunks, usar un modelo más económico para categorías de consultas simples, o implementar caché semántico para consultas frecuentes.

Las métricas de actualización de conocimiento miden la salud de la base de documentos. ¿Cuántos documentos ingresaron al sistema en las últimas 24 horas? ¿Cuántos documentos tienen más de seis meses sin actualizarse y siguen siendo referenciados en las respuestas? ¿El pipeline de ingesta completó exitosamente la última ejecución? Un documento desactualizado que sigue siendo recuperado con alta frecuencia es una fuente silenciosa de respuestas incorrectas. La política de gestión del conocimiento — cuándo un documento debe ser retirado, archivado o marcado como obsoleto — debe implementarse en el pipeline de ingesta y verificarse con métricas operativas.

La auditoría de consultas sirve tanto propósitos operativos como de cumplimiento. Desde el punto de vista operativo, el análisis de las consultas más frecuentes y de las consultas que producen respuestas de baja calidad (detectadas por feedback del usuario o por métricas de confianza) guía las mejoras del sistema. Una consulta recurrente que siempre produce baja relevancia en la recuperación puede indicar una laguna en la base de conocimiento que debe cubrirse. Desde el punto de vista del cumplimiento operativo, el registro de qué documentos fueron recuperados para responder cada consulta permite demostrar la trazabilidad del sistema ante una auditoría interna.

El stack de herramientas para observabilidad de sistemas RAG en producción incluye plataformas especializadas como LangSmith (profundamente integrado con LangChain), Langfuse (open source, con soporte para trazas distribuidas de pipelines RAG y agentes), y Phoenix de Arize (enfocado en evaluación y drift detection de modelos de IA). Para la infraestructura subyacente, OpenTelemetry con exporters a Jaeger o Grafana Tempo proporciona trazabilidad distribuida que puede combinarse con las métricas específicas de IA.

La operación de un sistema RAG productivo requiere el mismo rigor que la operación de cualquier sistema de software crítico, más la disciplina adicional de gestionar la calidad de un componente estocástico — el modelo de lenguaje — y la frescura de un componente dinámico — la base de conocimiento. El capítulo siguiente amplía esta perspectiva hacia las arquitecturas de agentes, donde el sistema no solo recupera y genera, sino que planifica, decide y actúa.
