# Módulo 4 – Capítulo 03 – Sección 04

## Generación de Respuestas

El contexto recuperado por el retriever no llega directamente al modelo de lenguaje. Entre la capa de recuperación y la generación de la respuesta existe una etapa crítica de ensamblaje y control que determina si el sistema produce respuestas fundamentadas y trazables, o respuestas que mezclan el conocimiento recuperado con el conocimiento paramétrico del modelo de forma indistinguible. Diseñar esta etapa correctamente es lo que separa un sistema RAG de producción de un chatbot con acceso a documentos.

El primer elemento de diseño es la construcción del prompt de generación. El prompt debe instruir explícitamente al modelo sobre cómo usar el contexto recuperado: qué hacer si el contexto no contiene información suficiente para responder la pregunta (declararlo en lugar de inferir), cómo formular la respuesta (en qué formato, con qué nivel de detalle, en qué idioma), y qué restricciones de comportamiento aplican (no especular, no citar fuentes que no aparecen en el contexto). El prompt de sistema de un RAG productivo no es una instrucción genérica de "usa el siguiente contexto para responder la pregunta": es un contrato preciso entre el arquitecto y el modelo sobre cómo debe comportarse ante cada tipo de consulta.

El segundo elemento es el grounding: mecanismos que verifican que las afirmaciones en la respuesta generada están fundamentadas en el contexto recuperado. El grounding puede implementarse de varias maneras. El citation extraction pide al modelo que cite explícitamente el chunk fuente para cada afirmación clave de su respuesta, lo que permite verificar post-hoc si la cita existe y es correcta. El grounding check utiliza un segundo LLM (o el mismo modelo en una llamada separada) para verificar si cada afirmación de la respuesta puede ser inferida del contexto. Plataformas como Azure AI Content Safety o servicios especializados en hallucination detection pueden integrarse como capa de verificación entre el LLM y el usuario final.

El tercer elemento es la gestión de contextos largos. A medida que el número de chunks recuperados aumenta, el contexto que se envía al modelo crece. Los modelos modernos soportan ventanas de contexto extensas (128K, 200K tokens), pero hay dos problemas que el arquitecto debe contemplar. Primero, el costo: el precio de llamada a la API de un LLM se calcula en tokens de entrada más tokens de salida. Un contexto de 50 chunks puede representar 20.000 tokens de entrada en cada consulta, lo que a escala produce costos significativos. Segundo, el fenómeno de "lost in the middle": los modelos de lenguaje tienden a dar más peso a la información al inicio y al final del contexto, ignorando la información en el medio. Con contextos muy largos, chunks relevantes ubicados en el centro pueden ser ignorados efectivamente. La estrategia de diseño es seleccionar el menor número de chunks suficientemente relevantes — típicamente entre 3 y 7 — en lugar de maximizar el contexto.

El cuarto elemento es la trazabilidad de la respuesta. En sistemas empresariales, cada respuesta debe poder rastrearse hasta los documentos fuente que la produjeron. Esto requiere almacenar, junto con la respuesta generada: la consulta original del usuario, los chunks recuperados (con sus identificadores y posición en el ranking), el prompt completo enviado al modelo, y la respuesta generada. Esta traza completa permite auditorías retrospectivas ("¿por qué el sistema respondió X?"), análisis de fallos ("¿qué contexto recuperó cuando generó la respuesta incorrecta?") y mejora continua del pipeline ("¿qué consultas producen contextos irrelevantes con frecuencia?").

Los patrones de diseño para la generación controlada de respuestas incluyen:

- **Respuesta con citas estructuradas:** el modelo genera la respuesta en un formato JSON que incluye la afirmación y el identificador del chunk fuente. La interfaz del usuario puede mostrar las fuentes junto con la respuesta.
- **Respuesta con nivel de confianza:** el modelo evalúa su propia confianza en la respuesta (alta/media/baja) basándose en la relevancia del contexto recuperado. Respuestas con baja confianza pueden ser redirigidas a un humano.
- **Respuesta en dos pasos (verificada):** un primer LLM genera la respuesta y un segundo LLM verifica si cada afirmación está fundamentada en el contexto. Solo las respuestas verificadas se envían al usuario.
- **Escalada a humano:** cuando el sistema detecta que ningún chunk recuperado supera un umbral mínimo de relevancia, el sistema escala automáticamente la consulta a un agente humano en lugar de generar una respuesta con información insuficiente.

La generación de respuestas es el único componente del sistema RAG visible para el usuario final. Todo el trabajo del pipeline de ingesta y la recuperación inteligente culmina en esta etapa. Un sistema que genera respuestas precisas, trazables y honestas sobre su propia incertidumbre construye confianza con el usuario. Un sistema que genera respuestas plausibles pero no fundamentadas destruye esa confianza en cuanto alguien verifica una afirmación incorrecta. La siguiente sección cierra el ciclo con la disciplina de operación y monitoreo que mantiene este nivel de calidad a lo largo del tiempo.
