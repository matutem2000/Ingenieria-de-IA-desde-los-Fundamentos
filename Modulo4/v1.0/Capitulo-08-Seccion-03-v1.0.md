# Módulo 4 – Capítulo 08 – Sección 03

## Balanceo de Carga

El balanceo de carga en sistemas de IA tiene particularidades que lo distinguen del balanceo de carga en aplicaciones web convencionales. En una aplicación web, todas las solicitudes son estadísticamente equivalentes en términos de costo computacional: un request HTTP para obtener el perfil de un usuario cuesta aproximadamente lo mismo que otro. En un sistema de IA, la varianza del costo por solicitud puede ser de varios órdenes de magnitud: una consulta simple con contexto corto puede completarse en 0.3 segundos y consumir 500 tokens, mientras que una consulta compleja con contexto largo puede tardar 8 segundos y consumir 15.000 tokens. Un balanceador que distribuye solicitudes en round-robin sin considerar esa varianza producirá instancias desequilibradas: algunas procesando muchas solicitudes ligeras, otras saturadas por una sola solicitud pesada.

**Balanceo con conciencia de carga** es la estrategia que resuelve este problema. En lugar de distribuir solicitudes en round-robin, el balanceador dirige cada nueva solicitud a la instancia con menor carga actual. En servicios de inferencia, la "carga actual" puede medirse como el número de solicitudes en vuelo, el uso actual de GPU memory, o la longitud total del contexto siendo procesado. vLLM expone métricas de carga a través de su API que un balanceador inteligente puede consumir para tomar decisiones de routing más precisas.

**Enrutamiento por características de la solicitud** es una estrategia más sofisticada donde el balanceador dirige la solicitud no solo según la carga de las instancias sino según las características de la solicitud misma. Por ejemplo:
- Solicitudes que requieren el modelo más potente (por complejidad del razonamiento) se enrutan a instancias con GPUs de mayor clase.
- Solicitudes de inferencia simple (resúmenes, clasificaciones) se enrutan a instancias con modelos más ligeros y económicos.
- Solicitudes de usuarios premium (con SLO de latencia más estricto) se enrutan a un pool de instancias dedicado con capacidad reservada.
- Solicitudes de procesamiento batch (sin SLO estricto de latencia) se enrutan a instancias de menor costo o a capacidad spot de cloud.

**Circuit breaker para APIs de LLM externas** es un mecanismo de protección específico para sistemas que dependen de APIs de modelos de lenguaje de terceros. Las APIs de LLM pueden experimentar degradación o indisponibilidad parcial: respuestas lentas, errores de rate limit, o errores de servidor. Un circuit breaker monitorea la tasa de éxito de las llamadas a la API y, cuando detecta una degradación significativa, "abre el circuito" — deja de enviar solicitudes al proveedor degradado — y redirige el tráfico a un proveedor alternativo o a una respuesta de degradación controlada (como un mensaje que indica que el servicio está temporalmente indisponible). Las implementaciones comunes incluyen la biblioteca `resilience4j` para Java, `pybreaker` para Python, o el circuit breaker integrado en service meshes como Istio o Envoy.

**Caché semántico como mecanismo de reducción de carga** reduce el número de solicitudes que llegan al servicio de inferencia. Un caché semántico almacena las respuestas generadas para consultas anteriores y, cuando una nueva consulta es semánticamente similar (no necesariamente idéntica) a una consulta en caché, devuelve la respuesta almacenada sin invocar al LLM. Esto es especialmente efectivo para sistemas con distribución de consultas concentrada: cuando el 20% de las preguntas genera el 80% del tráfico. GPTCache y Langchain's SemanticCache son implementaciones de referencia. El umbral de similitud para considerar dos consultas "equivalentes" debe calibrarse cuidadosamente: demasiado permisivo produce respuestas incorrectas para consultas que son similares pero no equivalentes; demasiado estricto produce tasas de hit de caché demasiado bajas para justificar la complejidad.

**Gestión de cola y prioridades** permite que el sistema mantenga servicio de calidad para los usuarios prioritarios incluso bajo alta demanda. Una cola de prioridades asigna capacidad de procesamiento según el SLO del usuario (premium vs. estándar) o según la urgencia de la solicitud (sincrónica vs. batch). La separación de pools de recursos — instancias dedicadas para usuarios premium, instancias compartidas para tráfico estándar — garantiza que la alta demanda de usuarios estándar no impacte la latencia de usuarios con requisitos estrictos.

**Sticky sessions para sistemas de agentes** son necesarias cuando el estado del agente se mantiene en memoria de la instancia (en lugar de externalizarse completamente). En este caso, el balanceador debe dirigir todas las solicitudes de la misma sesión a la misma instancia del agente. Session affinity mediante cookies o headers de sesión es el mecanismo estándar. Sin embargo, la arquitectura más robusta es la que externaliza completamente el estado del agente (a Redis u otro almacenamiento externo), eliminando la necesidad de sticky sessions y permitiendo el escalado stateless.

El balanceo de carga bien diseñado es invisible para el usuario: el sistema responde con latencia consistente independientemente de qué instancia procesa cada solicitud. Cuando el balanceo falla, el síntoma más frecuente no es un error explícito sino una degradación de latencia que afecta solo a algunos usuarios — los que el balanceador está dirigiendo a instancias saturadas.
