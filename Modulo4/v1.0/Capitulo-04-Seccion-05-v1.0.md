# Módulo 4 – Capítulo 04 – Sección 05

## Casos de Uso Empresariales

Las arquitecturas de agentes producen valor real cuando se aplican a problemas que comparten características específicas: tareas que requieren múltiples pasos de razonamiento con herramientas, donde el camino exacto no puede determinarse de antemano, y donde el costo de la automatización parcial es sustancialmente menor que el costo de la intervención humana en cada paso. Fuera de esas características, un agente añade complejidad sin beneficio neto. La evaluación honesta de cuándo un agente es la solución correcta es una de las decisiones más valiosas que puede tomar un AI Architect.

**Automatización de procesos de análisis e investigación** es el caso de uso donde los agentes producen el retorno más claro. Un agente de investigación de mercado puede recibir el nombre de un competidor, buscar información actualizada en la web, analizar sus publicaciones recientes, comparar precios y características con el catálogo propio, y producir un informe estructurado. Este proceso, que un analista humano realizaría en varias horas, puede automatizarse en minutos con un agente que combina búsqueda web, capacidad de lectura de documentos y síntesis estructurada. El patrón Planner-Executor es frecuentemente la elección correcta para este caso, dado que los pasos son conocidos de antemano y pueden paralelizarse.

**Soporte y resolución de tickets técnicos** es un caso de uso donde los agentes pueden reducir significativamente el volumen de tickets que requieren intervención humana. Un agente de soporte puede recibir una descripción de problema, consultar la base de conocimiento interna (mediante RAG), verificar el estado de sistemas relacionados mediante herramientas de monitoreo, ejecutar scripts de diagnóstico estándar, y resolver el ticket o escalarlo con información de contexto enriquecida. El patrón ReAct es adecuado aquí porque el diagnóstico es exploratorio: el agente no sabe de antemano qué pasos seguirá hasta examinar los síntomas. Los límites de autonomía son críticos en este caso: el agente debe poder diagnosticar sin restricciones, pero solo ejecutar acciones de remediación dentro de un conjunto aprobado.

**Asistencia en el desarrollo de software** ha producido algunos de los casos de uso de agentes más visibles del mercado. Herramientas como GitHub Copilot Workspace, Devin y Claude Code son implementaciones de agentes que pueden recibir una descripción de tarea, explorar el código existente, planificar los cambios necesarios, implementarlos, ejecutar las pruebas y corregir los fallos detectados. El patrón Reflection es especialmente valioso aquí: el agente evalúa el código generado antes de entregarlo, ejecutando el linter, las pruebas unitarias y verificando el cumplimiento de convenciones. La capacidad de ejecutar código en un sandbox controlado es la herramienta más poderosa — y la más peligrosa si no está correctamente aislada.

**Procesamiento documental empresarial** es un caso de uso de alto volumen y alto impacto. Un agente de procesamiento de contratos puede recibir un contrato en PDF, extraer las cláusulas relevantes, compararlas con plantillas estándar, identificar desviaciones, clasificarlas por riesgo, y generar un resumen para revisión del equipo legal. Lo que requeriría horas de lectura humana puede realizarse en minutos. Los agentes de procesamiento documental son frecuentemente más simples que otros casos de uso: el objetivo está bien definido, los pasos son predecibles (Planner-Executor), y el output es un documento estructurado que un humano siempre revisa antes de usar.

**Gestión de workflows complejos de negocio** es el caso de uso más ambicioso y el que requiere mayor madurez arquitectónica. Un agente de onboarding de clientes puede coordinar la solicitud de documentos, validar la información contra bases de datos externas, crear cuentas en múltiples sistemas, enviar comunicaciones personalizadas y monitorear el progreso hasta la activación. Este caso requiere el patrón Supervisor-Workers (múltiples sistemas involucrados), gestión robusta de estado (el proceso puede durar días), integración con sistemas de terceros, y mecanismos claros de intervención humana cuando el agente encuentra situaciones fuera de su competencia.

Los casos donde los agentes no son la solución correcta son igualmente importantes. Si la tarea tiene un proceso perfectamente determinístico, un workflow tradicional (Airflow, Prefect, Luigi) es más confiable, predecible y económico que un agente. Si la tarea puede resolverse con una sola llamada al LLM (una consulta de RAG, una transformación de texto), añadir un agente solo añade latencia y costo. Si el dominio es de altísimo riesgo (cirugía, transacciones financieras a gran escala, sistemas de control críticos), la autonomía de un agente puede ser inaceptable independientemente de su calidad.

La evaluación del caso de uso correcto para un agente debe realizarse antes de cualquier decisión técnica sobre herramientas, modelos o frameworks. El arquitecto que responde "usaremos un agente" antes de entender las características del problema está repitiendo el error de elegir tecnología antes de entender el problema — el primero de los errores frecuentes descritos en el Capítulo 01.
