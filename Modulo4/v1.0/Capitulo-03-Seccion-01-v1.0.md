# Módulo 4 – Capítulo 03 – Sección 01

## Arquitecturas RAG en Producción

El patrón Retrieval-Augmented Generation que el lector conoce desde el Módulo 3 describe cómo un modelo de lenguaje puede enriquecer su respuesta con información recuperada de una fuente externa. Sin embargo, la perspectiva del Módulo 3 es la del pattern: un mecanismo de context engineering que enseña al modelo a usar información relevante. La perspectiva de este capítulo es la del arquitecto: el sistema completo que rodea a ese patrón para que funcione de manera confiable, económicamente viable y auditable en un entorno de producción real.

La diferencia es sustancial. Un RAG de prototipo puede construirse en unas pocas horas: se cargan algunos documentos PDF, se generan embeddings con una biblioteca como `sentence-transformers`, se almacenan en un vector store local como ChromaDB, y se conecta la recuperación a la API de un LLM. Ese sistema puede funcionar correctamente para una demo con veinte documentos y cinco usuarios simultáneos. Un RAG productivo enfrenta preguntas completamente distintas: ¿cómo se actualiza la base de conocimiento cuando los documentos cambian? ¿qué sucede cuando el vector store tiene un millón de fragmentos y la latencia de búsqueda supera los dos segundos? ¿cómo se garantiza que un usuario no puede recuperar documentos que pertenecen al tenant de otro cliente? ¿cómo se detecta que la calidad de las respuestas ha degradado después de una actualización del modelo de embeddings?

Responder esas preguntas requiere pensar el sistema RAG como un ecosistema de componentes coordinados, cada uno con sus propias responsabilidades, interfaces y métricas. Este capítulo descompone ese ecosistema en cuatro dominios: el pipeline de ingesta (que transforma documentos en conocimiento recuperable), la capa de recuperación inteligente (que identifica el contexto más relevante para cada consulta), la generación de respuestas (que combina ese contexto con el modelo de lenguaje de manera controlada), y la operación y monitoreo continuo (que mantiene el sistema saludable y auditable a lo largo del tiempo).

Los cinco principios de diseño que atraviesan cada dominio son:

- **Diseño desacoplado:** cada componente del pipeline RAG debe poder reemplazarse o actualizarse sin reconstruir el sistema completo. El modelo de embeddings puede cambiar; la base vectorial puede migrarse; el LLM puede rotarse entre proveedores. Si cada componente tiene una interfaz clara, esos cambios son operaciones de mantenimiento, no proyectos de reingeniería.
- **Escalabilidad diferenciada:** el pipeline de ingesta (batch, tolerante a latencia) y el pipeline de consulta (tiempo real, sensible a latencia) tienen perfiles de carga completamente distintos y deben escalarse de forma independiente. Combinarlos en el mismo servicio produce cuellos de botella innecesarios.
- **Seguridad de la información:** los documentos que ingresan al sistema de recuperación frecuentemente contienen información sensible. El control de acceso debe implementarse en múltiples capas: en la base vectorial (filtrado por metadatos de autorización), en el pipeline de ingesta (clasificación de sensibilidad por documento) y en la generación de respuestas (instrucciones explícitas al modelo sobre qué información puede citar).
- **Calidad del conocimiento:** la precisión de las respuestas de un sistema RAG depende más de la calidad del proceso de ingesta que de la sofisticación del modelo de lenguaje. Documentos mal particionados, embeddings generados sobre texto sucio o una estrategia de chunking inadecuada para el tipo de documento son errores que ningún modelo puede compensar.
- **Costos operativos monitorizados:** cada consulta a un sistema RAG tiene un costo compuesto: búsqueda en la base vectorial, llamada a un posible reranker, y llamada al LLM con un contexto que puede ser extenso. Sin instrumentación de costos por consulta, el sistema puede escalar en uso y producir facturas impredecibles.

> **Nota del Arquitecto:** La trampa más frecuente en proyectos RAG es optimizar el modelo de lenguaje cuando el problema real está en la ingesta o en la recuperación. He visto equipos cambiar de GPT-4o a Claude 3 Opus pensando que el problema era el modelo, cuando la causa raíz era que sus documentos estaban particionados en chunks de 50 tokens — demasiado pequeños para proporcionar contexto suficiente. Antes de cambiar el modelo, mida la calidad de recuperación: ¿el contexto que llega al LLM es el correcto? Si no lo es, el modelo más avanzado del mercado no mejorará la respuesta.

Las secciones siguientes desarrollan cada uno de estos dominios con la especificidad técnica que requiere una decisión de arquitectura: herramientas concretas, criterios de selección, casos de uso y los fallos característicos de cada capa.
