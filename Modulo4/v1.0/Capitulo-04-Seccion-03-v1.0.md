## Memoria y Estado del Agente

La diferencia entre un agente que completa tareas simples y un agente capaz de gestionar procesos de negocio complejos que se extienden en el tiempo es su capacidad de mantener estado. Un agente sin gestión de estado es, en esencia, un pipeline: recibe una entrada, ejecuta una secuencia de pasos y produce una salida. Un agente con gestión de estado puede retomar una tarea interrumpida, adaptar su comportamiento basándose en interacciones previas, y acumular conocimiento sobre su dominio de operación entre sesiones. Diseñar la capa de estado es una de las decisiones arquitectónicas más importantes y menos discutidas en las arquitecturas de agentes.

El problema central de la gestión de estado en agentes LLM es la tensión entre la naturaleza sin estado de los modelos de lenguaje y la necesidad de continuidad en el tiempo. Cada llamada al LLM es independiente: el modelo no "recuerda" conversaciones previas a menos que esa información se incluya explícitamente en el prompt. Esto significa que todo el estado que el agente necesita debe ser serializado, almacenado externamente y deserializado en cada iteración del bucle de razonamiento.

El estado de un agente productivo se organiza en tres capas con diferentes características de persistencia y acceso:

**Estado de sesión (efímero, duración de una tarea):** incluye el objetivo de la tarea actual, el plan inicial si existe, el historial de acciones y observaciones de la sesión, y cualquier variable de trabajo creada durante la ejecución. Este estado vive típicamente en memoria durante la ejecución y se serializa a un almacenamiento persistente solo si la tarea puede interrumpirse y reanudarse. Redis o una base de datos clave-valor con TTL corto son opciones naturales para este nivel. Cuando el historial de sesión crece y amenaza con superar la ventana de contexto del modelo, la estrategia de compresión progresiva — resumir bloques del historial más antiguo mientras se mantiene el detalle del historial reciente — permite gestionar la longitud sin perder el hilo de la tarea.

**Estado de usuario o entidad (persistente, duración indefinida):** incluye el perfil del usuario, sus preferencias, el historial de interacciones relevantes anteriores, y cualquier información que el agente deba recordar entre sesiones distintas. Por ejemplo, un agente de soporte que ha resuelto un problema técnico específico para un usuario debe recordar esa solución si el mismo problema reaparece semanas después. Este estado se almacena en una base de datos relacional o documental y se recupera al inicio de cada sesión para el usuario correspondiente. La gestión de privacidad de este estado — qué se retiene, por cuánto tiempo, quién puede acceder — es un requisito no funcional que debe definirse antes del despliegue.

**Memoria semántica (persistente, acceso por similitud):** cuando el volumen de conocimiento acumulado por el agente supera lo que puede incluirse en el contexto de cada llamada, se usa una base vectorial como memoria semántica. El agente puede escribir en esta memoria ("aprendí que el cliente X prefiere respuestas breves con ejemplos de código") y recuperar información relevante al inicio de cada sesión o cuando el razonamiento lo requiere. Esta arquitectura permite que el agente "aprenda" sin reentrenamiento del modelo subyacente.

La gestión del estado en agentes de larga duración requiere resolver dos problemas adicionales. El primero es la coherencia: cuando una tarea es interrumpida (por un timeout, un error o una pausa deliberada) y reanudada en una nueva sesión, el agente debe recuperar exactamente el estado en que se encontraba. Esto requiere checkpointing explícito: serializar el estado completo en puntos definidos del proceso, de forma que la recuperación sea posible sin reejecutar los pasos anteriores. Frameworks como LangGraph implementan checkpointing nativo para grafos de agentes, permitiendo reanudar exactamente desde el último checkpoint. El segundo problema es la consistencia en sistemas multiusuario: si el mismo agente gestiona tareas para múltiples usuarios simultáneamente, el aislamiento del estado entre usuarios es un requisito de seguridad crítico.

> **Nota del Arquitecto:** El estado de un agente es un activo que debe gobernarse como cualquier otro dato de negocio. He visto sistemas de agentes que acumulan memoria indefinidamente sin políticas de retención, produciendo perfiles de usuario que contienen años de conversaciones. Aparte del problema de privacidad, esto degrada la calidad del contexto: el agente recibe tanta información sobre el usuario que sus respuestas pierden foco. Una regla práctica es diseñar la memoria del agente con la misma disciplina con que se diseña una base de datos: esquema explícito, política de retención, control de acceso y proceso de purga.

La correcta gestión del estado es lo que convierte a un agente en un sistema de producción robusto. Sin ella, cada sesión comienza desde cero, desperdiciando el contexto acumulado y forzando al usuario a repetir información. Con ella, el agente puede operar como un colaborador que recuerda, aprende y mejora con el tiempo.
