## Recuperación Inteligente

La calidad de un sistema RAG se decide, en gran medida, en la capa de recuperación. El modelo de lenguaje solo puede generar una respuesta tan buena como el contexto que recibe. Si el retriever entrega los chunks equivocados — porque la consulta y el documento relevante tienen vocabularios distintos, o porque la búsqueda por similitud semántica no captura el matiz exacto de la pregunta — el modelo generará una respuesta incorrecta con aparente confianza. Este fenómeno se conoce como "alucinación contextual": el modelo no inventa información de la nada, sino que interpreta de manera incorrecta el contexto que le fue entregado. El retriever es, por tanto, el componente cuya calidad más directamente determina la calidad del sistema.

La estrategia de recuperación más simple — y la más ampliamente adoptada en prototipos — es la búsqueda por similitud semántica: se genera el embedding de la consulta y se buscan en la base vectorial los N chunks más cercanos en el espacio vectorial. Esta búsqueda densa captura relaciones semánticas bien: una consulta sobre "reducción de costos operativos" puede recuperar documentos que hablan de "optimización de gastos" aunque no compartan ninguna palabra. Sin embargo, la búsqueda densa tiene un punto débil: falla en recuperar términos técnicos específicos, identificadores, nombres propios o términos de dominio que no aparecen con frecuencia en el corpus de preentrenamiento del modelo de embeddings.

La búsqueda híbrida resuelve este problema combinando búsqueda densa con búsqueda dispersa (sparse). La búsqueda dispersa más utilizada es BM25, un algoritmo probabilístico basado en frecuencia de términos que recupera documentos que contienen exactamente las mismas palabras de la consulta. La combinación de ambas búsquedas se realiza mediante Reciprocal Rank Fusion (RRF): cada chunk recibe una puntuación basada en su posición en el ranking de cada búsqueda, y las puntuaciones se combinan para producir un ranking final. El resultado es un retriever que captura tanto la relevancia semántica como la relevancia léxica, cubriendo los puntos ciegos de cada enfoque individual.

El reranking es el segundo mecanismo de mejora de calidad. Después de recuperar un conjunto inicial de N chunks (típicamente entre 20 y 50), un modelo de reranking ordena ese conjunto según la relevancia específica para la consulta. Los modelos de reranking más utilizados son cross-encoders: a diferencia del bi-encoder que genera embeddings independientes para la consulta y el documento, el cross-encoder procesa la consulta y el chunk juntos, capturando interacciones entre ellos que el bi-encoder no puede ver. Herramientas como Cohere Rerank, el modelo BGE-Reranker de BAAI, o los modelos de reranking de Jina AI son ampliamente utilizados en sistemas productivos. El resultado final es un conjunto reducido — típicamente entre 3 y 10 chunks — de alta relevancia, que reduce el contexto enviado al LLM y mejora la calidad de la respuesta.

El filtrado por metadatos es el tercer mecanismo, y el más importante para implementar control de acceso y relevancia contextual. La mayoría de las bases vectoriales productivas soportan filtrado por metadatos: Pinecone, Weaviate, Qdrant y pgvector permiten combinar búsqueda por similitud con filtros estructurados sobre campos como fecha, departamento, nivel de confidencialidad o tenant. Esto permite implementar RAG multi-tenant donde cada usuario solo puede recuperar documentos de su organización, o RAG con control de vigencia donde documentos obsoletos son excluidos automáticamente de la recuperación.

La selección de la base vectorial para producción depende de varios factores:

- **Pinecone:** servicio gestionado, alta disponibilidad garantizada, escalado automático, ideal para equipos que no quieren gestionar infraestructura de base de datos. Costo predecible pero más alto que alternativas open source.
- **Weaviate:** open source con opción gestionada, soporta búsqueda híbrida nativa (dense + BM25), módulos de reranking integrados, escalado horizontal mediante sharding. Adecuado para equipos con capacidad operativa de base de datos.
- **Qdrant:** open source de alto rendimiento, optimizado para filtrado por payload, excelente soporte de búsqueda híbrida, API REST y gRPC. Opción preferida para escenarios on-premise con requisitos de latencia estrictos.
- **pgvector:** extensión de PostgreSQL, integra búsqueda vectorial en una base de datos relacional existente. Ideal cuando el equipo ya opera PostgreSQL y quiere mantener un único sistema de base de datos. No escala tan eficientemente como las soluciones nativas para grandes volúmenes.
- **Chroma:** base vectorial embebida, excelente para desarrollo local y sistemas pequeños. No es una opción de producción para escala significativa.

La evaluación sistemática de la capa de recuperación es una práctica arquitectónica obligatoria. El framework RAGAS (Retrieval-Augmented Generation Assessment) proporciona métricas específicas: context recall (¿qué porcentaje del conocimiento relevante fue recuperado?), context precision (¿qué porcentaje del contexto recuperado es realmente relevante?), faithfulness (¿la respuesta generada está fundamentada en el contexto recuperado?) y answer relevancy (¿la respuesta responde a la pregunta formulada?). Estas métricas deben medirse periódicamente sobre un conjunto de evaluación representativo del uso real del sistema.

La capa de recuperación inteligente no es un componente estático. A medida que el corpus crece, la distribución de consultas cambia o el modelo de embeddings mejora, los parámetros del retriever — número de chunks recuperados, pesos de la búsqueda híbrida, modelo de reranking — deben reevaluarse.
