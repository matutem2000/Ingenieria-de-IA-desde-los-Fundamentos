# Módulo 4 – Capítulo 03 – Sección 02

## Pipeline de Ingesta

El pipeline de ingesta es el cimiento invisible de un sistema RAG. Es el proceso que transforma documentos en bruto — PDFs, páginas web, registros de bases de datos, transcripciones de reuniones, manuales técnicos — en fragmentos de conocimiento indexados y recuperables con precisión. Cuando las respuestas de un sistema RAG son imprecisas o irrelevantes, la causa más frecuente no es el modelo de lenguaje sino un pipeline de ingesta mal diseñado: documentos procesados con demasiado ruido, particionados con una estrategia que destruye el contexto, o indexados con un modelo de embeddings inadecuado para el dominio.

El primer paso del pipeline es la extracción de texto. Aunque parece trivial, extraer texto de documentos empresariales reales es un problema no trivial. Un PDF generado digitalmente puede extraerse con herramientas como `pdfplumber` o `pypdf` con alta fidelidad. Un PDF escaneado requiere OCR (como Tesseract o AWS Textract) con sus errores de reconocimiento asociados. Un documento Word puede contener tablas anidadas que pierden su estructura en la extracción plana. Una página web contiene navegación, anuncios y contenido de otras secciones que contamina el conocimiento relevante. El arquitecto debe definir, para cada tipo de fuente, el proceso de extracción específico y los controles de calidad del texto resultante.

El segundo paso es la limpieza y normalización. El texto extraído frecuentemente contiene artefactos: números de página, encabezados repetidos en cada página del PDF, caracteres especiales, saltos de línea irregulares dentro de párrafos, y fragmentos de código HTML. Antes de generar embeddings, este ruido debe eliminarse porque los vectores resultantes representarán tanto el contenido relevante como el ruido, degradando la calidad de la recuperación. La limpieza debe ser determinista y reproducible: si el pipeline se ejecuta dos veces sobre el mismo documento, debe producir el mismo texto limpio.

El tercer paso es el particionado o chunking, que es probablemente la decisión de mayor impacto en la calidad del sistema RAG. Un chunk es el fragmento de texto que se almacena como unidad recuperable. Existen cuatro estrategias principales:

- **Fixed-size chunking:** divide el texto en fragmentos de N tokens con un solapamiento de M tokens entre fragmentos consecutivos. Es simple de implementar y predecible, pero puede partir oraciones o párrafos a la mitad, perdiendo coherencia semántica.
- **Semantic chunking:** utiliza cambios en la similitud semántica del texto para identificar fronteras naturales entre ideas. Produce chunks más coherentes pero requiere un paso adicional de análisis y es más costoso computacionalmente.
- **Parent-child documents:** genera dos niveles de chunks: un chunk "hijo" pequeño (alta precisión de recuperación) y un chunk "padre" más amplio (contexto completo para el LLM). La recuperación se realiza sobre los chunks hijos, pero el contexto que se envía al modelo incluye el chunk padre. Esta estrategia es especialmente efectiva para documentos técnicos densos.
- **Late chunking:** genera embeddings del documento completo antes de particionarlo, preservando el contexto global en cada chunk. Es una técnica emergente particularmente efectiva para documentos narrativos donde el contexto de una sección depende de secciones anteriores.

El cuarto paso es la generación de embeddings. El modelo de embeddings determina cómo se representan los chunks en el espacio vectorial y, por tanto, qué tan bien la búsqueda por similitud recupera contenido relevante. Los modelos de embeddings más utilizados en sistemas productivos incluyen `text-embedding-3-large` de OpenAI para alta calidad general, `BGE-M3` de BAAI para soporte multilingüe, y `nomic-embed-text` para escenarios on-premise. La elección del modelo de embeddings debe evaluarse con el corpus específico del sistema, porque el rendimiento varía significativamente según el dominio.

El quinto paso es el almacenamiento en la base vectorial, que se analiza en detalle en la sección de recuperación. Sin embargo, es importante señalar que el pipeline de ingesta debe almacenar junto con cada vector sus metadatos: identificador único del documento fuente, fecha de creación y última modificación, propietario o departamento, nivel de confidencialidad, y cualquier dimensión de filtrado que será necesaria en la recuperación. Los metadatos son la clave para el control de acceso y el filtrado contextual.

> **Nota del Arquitecto:** El pipeline de ingesta debe diseñarse como un proceso idempotente y diferencial. Idempotente significa que ejecutar el pipeline dos veces sobre el mismo documento no crea duplicados en la base vectorial. Diferencial significa que el pipeline detecta qué documentos han cambiado desde la última ejecución y solo reprocesa los modificados. Sin estas propiedades, el pipeline no puede ejecutarse de forma automatizada sobre un corpus que se actualiza continuamente sin degradar la base de conocimiento.

El pipeline de ingesta bien diseñado es la inversión de mayor retorno en un sistema RAG. Mejoras en la calidad del proceso de extracción, limpieza y chunking típicamente producen mejoras de calidad en las respuestas finales que superan a las producidas por cambiar el modelo de lenguaje.
