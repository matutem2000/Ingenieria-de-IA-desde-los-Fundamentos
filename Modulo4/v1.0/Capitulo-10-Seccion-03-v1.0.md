# Módulo 4 – Capítulo 10 – Sección 03

## Abstracción de Modelos

El componente más volátil de cualquier sistema de IA moderno es el modelo de lenguaje. Los proveedores actualizan sus modelos con frecuencia, nuevos competidores entran al mercado con capacidades distintas, los modelos open source alcanzan paridad con los modelos comerciales en dominios específicos, y los precios cambian. Un sistema que depende directamente de un proveedor o modelo específico queda atrapado en esas decisiones originales: cambiar de modelo se convierte en un proyecto de reingeniería en lugar de una decisión de operación.

La abstracción de modelos es la práctica de diseñar el sistema de manera que el modelo de lenguaje sea un componente reemplazable detrás de una interfaz estable. La aplicación no llama directamente a la API de OpenAI o de Anthropic: llama a una interfaz de modelo (Model Interface o AI Gateway) que internamente dirige la solicitud al proveedor configurado. Cambiar de proveedor es cambiar la configuración del gateway, no modificar el código de la aplicación.

**Interfaz unificada de modelo** define el contrato que la aplicación usa para interactuar con cualquier modelo de lenguaje, independientemente del proveedor o del protocolo específico de la API. Esta interfaz incluye: cómo se especifican los mensajes (system prompt, mensajes de usuario y asistente), cómo se configuran los parámetros de generación (temperatura, max_tokens, top_p), cómo se gestionan las herramientas (tool definitions y tool calls), y cómo se procesa la respuesta (streaming vs. completa, extracción de contenido y metadatos). La interfaz de OpenAI (Chat Completions API) se ha convertido en el estándar de facto que la mayoría de los proveedores y frameworks soportan, lo que facilita la portabilidad entre proveedores.

Las implementaciones de abstracción de modelos más utilizadas en producción incluyen:

- **LiteLLM:** librería Python open source que proporciona una interfaz unificada sobre más de 100 proveedores de LLM (OpenAI, Anthropic, Google, Cohere, modelos de Hugging Face, Ollama para modelos locales). Con una sola línea de configuración, el sistema puede cambiar entre proveedores. LiteLLM también gestiona fallbacks automáticos, retry con backoff, y tracking de costos por proveedor.
- **AI Gateway empresariales:** soluciones como Portkey AI, Kong AI Gateway, o Cloudflare AI Gateway que añaden funcionalidades de gateway sobre la abstracción básica: rate limiting, caching de respuestas, enrutamiento por carga, logging centralizado, y control de costos. Son la elección para organizaciones con múltiples equipos que necesitan governance centralizada sobre el acceso a los modelos.
- **Abstracción a nivel de framework:** LangChain y LlamaIndex proporcionan abstracciones de modelo dentro de sus ecosistemas. El LLM es configurado como un objeto con la interfaz del framework, y cambiar de proveedor es cambiar el objeto de configuración. La limitación es que la abstracción funciona solo si todo el sistema está construido sobre el mismo framework.

**Abstracción del modelo de embeddings** es igualmente importante. El modelo de embeddings determina el espacio vectorial en que vive el índice de la base de conocimiento. Cambiar el modelo de embeddings sin re-indexar toda la base de conocimiento produce resultados incorrectos: los vectores de los documentos (generados con el modelo anterior) y el vector de la consulta (generado con el nuevo modelo) viven en espacios distintos y su similitud no tiene significado semántico. La abstracción del modelo de embeddings debe incluir: la interfaz de generación de embeddings (estandarizada sobre la misma interfaz de texto → vector), y el proceso de re-indexación controlada cuando el modelo cambia.

**Gestión de las diferencias entre modelos** es el desafío práctico de la abstracción. Los modelos no son intercambiables perfectamente: un prompt que produce excelentes resultados con Claude puede producir resultados distintos con GPT-4o, porque tienen diferentes capacidades de razonamiento, distintos comportamientos ante las instrucciones de formato, y diferentes límites de ventana de contexto. La abstracción de modelos no elimina estas diferencias: gestiona el impacto de las diferencias confinando los ajustes necesarios (en el prompt, en los parámetros, en el post-procesamiento del output) dentro de la capa de integración, sin que propaguen a la lógica de negocio de la aplicación.

**Estrategia de modelos múltiples simultáneos** es una extensión natural de la abstracción. En lugar de usar un único modelo para todas las tareas, la capa de abstracción puede enrutar dinámicamente cada solicitud al modelo más apropiado: el modelo más económico para tareas simples, el modelo más potente para tareas complejas, el modelo especializado en código para generación de código, y el modelo multimodal para solicitudes que incluyen imágenes. Este enrutamiento puede basarse en reglas estáticas (según el tipo de tarea detectado) o en enrutamiento dinámico (un clasificador ligero decide qué modelo usar para cada solicitud). La lógica de negocio de la aplicación permanece ajena a estas decisiones de enrutamiento.

La abstracción de modelos es la inversión arquitectónica con el mayor retorno a largo plazo en sistemas de IA. El ecosistema de modelos evolucionará en formas que nadie puede predecir con exactitud. El sistema que está abstraído de esa evolución puede adoptarla con el mínimo de fricción; el sistema que no lo está pagará el precio de esa dependencia en cada actualización.
