# Módulo 4 – Capítulo 10 – Sección 04

## Automatización de la Evolución

Un sistema que requiere intervención manual intensiva para actualizarse acumula deuda de evolución: los cambios se posponen porque son costosos y arriesgados, y mientras se posponen, el sistema envejece tecnológicamente. La automatización de la evolución resuelve este problema convirtiendo los cambios en procesos seguros, repetibles y de bajo riesgo mediante pipelines de CI/CD, pruebas automatizadas e infraestructura como código. En sistemas de IA, esta automatización tiene dimensiones específicas que van más allá de los pipelines de CI/CD de software tradicional.

**Pipeline de CI/CD para sistemas de IA** extiende el pipeline estándar con etapas específicas de validación de IA. Un pipeline completo para un sistema RAG o de agentes incluye:

1. **Validación de código y prompt:** análisis estático del código, verificación de que los cambios de prompt están versionados correctamente, y que los modelos referenciados están en la lista de modelos aprobados por la política de gobierno.
2. **Tests unitarios de componentes de IA:** pruebas de las funciones individuales del pipeline (extracción, chunking, embedding) con entradas sintéticas conocidas.
3. **Tests de integración del pipeline:** verificación de que el flujo completo — desde la consulta hasta la respuesta — produce outputs que superan un umbral mínimo de calidad sobre un conjunto de consultas de referencia pequeño.
4. **Evaluación de regresión:** ejecución del dataset completo de evaluación y comparación de las métricas (context recall, faithfulness, answer relevancy) con la línea base de la versión en producción. El pipeline bloquea el despliegue si las métricas degradan por encima del umbral configurado.
5. **Tests de safety:** ejecución de un conjunto de consultas diseñadas para verificar que los guardrails de seguridad funcionan correctamente: intentos de prompt injection, consultas de categorías restringidas, y solicitudes de información sensible.
6. **Despliegue canary:** si todos los tests anteriores pasan, el despliegue inicia en modo canary al 5-10% del tráfico, con monitoreo automático de las métricas de latencia y error rate durante un período definido.
7. **Promoción o rollback automático:** si las métricas del canary se mantienen dentro de los parámetros esperados, el despliegue se completa automáticamente. Si las métricas degradan, el sistema revierte al 0% de tráfico para la nueva versión sin intervención humana.

**Infraestructura como código (IaC) para plataformas de IA** gestiona la infraestructura del sistema de IA (base vectorial, servicio de inferencia, pipeline de ingesta, servicios de soporte) mediante código versionado en repositorios de control de versiones. Terraform, Pulumi, y AWS CDK son las herramientas más utilizadas. La infraestructura como código garantiza que el entorno de producción puede reproducirse exactamente en staging, que los cambios de infraestructura pasan por el mismo proceso de revisión que el código, y que es posible reconstruir el entorno completo a partir del código en caso de desastre.

Para sistemas de IA, la IaC debe gestionar elementos adicionales respecto a los sistemas convencionales: la configuración de la base vectorial (colecciones, índices, configuración de sharding), los secretos de las APIs de LLM (a través de servicios de gestión de secretos como HashiCorp Vault o AWS Secrets Manager, nunca hardcodeados), los parámetros de configuración del pipeline (modelos de embeddings, estrategia de chunking, configuración del retriever), y los recursos de cómputo para el pipeline de ingesta.

**Re-indexación automatizada** es el proceso de actualizar el índice vectorial cuando cambia el modelo de embeddings o cuando la estrategia de chunking es modificada. Este proceso — que requiere leer todos los documentos de la fuente, regenerar los chunks y los embeddings con la nueva configuración, y reconstruir el índice — puede ser muy costoso computacionalmente para bases de conocimiento grandes. La automatización de este proceso incluye: detección automática de cuándo es necesaria una re-indexación (cuando el modelo de embeddings cambia o cuando la configuración del pipeline cambia), ejecución del proceso de re-indexación en paralelo con el índice de producción (sin interrumpir el servicio), y migración del tráfico al nuevo índice solo cuando la re-indexación está completa y validada.

**Feature flags para sistemas de IA** permiten activar o desactivar funcionalidades del sistema de IA sin necesidad de desplegar nuevo código. El umbral de reranking, el número de chunks recuperados, el modelo utilizado para un tipo específico de consulta, o la activación de la caché semántica son parámetros que con frecuencia necesitan ajustarse en respuesta a observaciones de producción. Los feature flags permiten estos ajustes de forma controlada y reversible: la activación puede ser gradual (al 10% del tráfico, luego al 50%), por segmento de usuario (solo usuarios premium), o condicional (solo en horario de baja carga). LaunchDarkly, Unleash (open source), y AWS AppConfig son implementaciones comunes.

La automatización de la evolución convierte la actualización de sistemas de IA de un evento estresante en un proceso ordinario. El equipo que tiene un pipeline de CI/CD completo con evaluaciones automatizadas puede actualizar el modelo de lenguaje, cambiar la estrategia de chunking, o refinar el system prompt con la confianza de que cualquier regresión será detectada antes de llegar a producción. Esa confianza acelera la cadencia de mejora del sistema y reduce la deuda de evolución tecnológica.
