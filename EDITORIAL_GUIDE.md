# EDITORIAL_GUIDE.md

# Ingeniería de IA desde los Fundamentos

## Guía Editorial del Proyecto

**Versión:** 1.0\
**Estado:** Vigente

------------------------------------------------------------------------

# 1. Propósito

Este documento define las reglas editoriales del proyecto **Ingeniería
de IA desde los Fundamentos**.

Su objetivo es garantizar que todos los capítulos mantengan el mismo
nivel de calidad, profundidad, estilo y coherencia.

El libro debe poder leerse como una única obra, aunque haya sido
desarrollado en múltiples iteraciones.

------------------------------------------------------------------------

# 2. Visión

Este libro **no pretende enseñar herramientas**.

Pretende formar profesionales capaces de:

-   comprender la IA;
-   analizar problemas;
-   diseñar arquitecturas;
-   justificar decisiones técnicas;
-   evaluar riesgos;
-   comunicar soluciones.

La prioridad siempre será desarrollar criterio.

------------------------------------------------------------------------

# 3. Público objetivo

El lector ideal es:

-   desarrollador de software;
-   arquitecto de software;
-   profesional de infraestructura;
-   responsable de IT;
-   líder técnico;
-   consultor;
-   estudiante avanzado.

No se asumen conocimientos profundos sobre IA.

Sí se asume experiencia general en tecnología.

------------------------------------------------------------------------

# 4. Filosofía

Cada capítulo debe responder cuatro preguntas:

1.  ¿Qué problema intenta resolver este concepto?
2.  ¿Por qué apareció?
3.  ¿Cuándo conviene utilizarlo?
4.  ¿Cuándo NO conviene utilizarlo?

Nunca comenzar por la herramienta.

Siempre comenzar por el problema.

------------------------------------------------------------------------

# 5. Principios editoriales

-   Enseñar desde primeros principios.
-   Explicar el "por qué" antes del "cómo".
-   Evitar el marketing y las exageraciones.
-   Diferenciar hechos de opiniones.
-   Utilizar lenguaje claro y preciso.
-   Favorecer el razonamiento por sobre la memorización.

------------------------------------------------------------------------

# 6. Estructura obligatoria de cada capítulo

1.  Objetivos de aprendizaje.
2.  Motivación del problema.
3.  Desarrollo conceptual.
4.  Analogías.
5.  Diagramas.
6.  Ejemplos reales.
7.  Conversación con un arquitecto.
8.  Errores frecuentes.
9.  Buenas prácticas.
10. Laboratorio.
11. Preguntas de reflexión.
12. Resumen.
13. Checklist.
14. Bibliografía.
15. Próximo capítulo.

------------------------------------------------------------------------

# 7. Estilo de escritura

-   Profesional.
-   Conversacional.
-   Rigurosamente técnico.
-   Sin tecnicismos innecesarios.
-   Sin frases vacías.
-   Cada afirmación debe aportar valor.

------------------------------------------------------------------------

# 8. Diagramas

Siempre que un concepto sea complejo deberá incluir al menos uno de los
siguientes:

-   Mermaid
-   PlantUML
-   Diagrama de flujo
-   Arquitectura
-   Mapa conceptual

Los diagramas deben explicar, no decorar.

------------------------------------------------------------------------

# 9. Laboratorios

Cada laboratorio debe incluir:

-   Objetivo.
-   Requisitos.
-   Pasos.
-   Resultado esperado.
-   Preguntas para reflexionar.
-   Variantes opcionales.

Siempre que sea posible utilizar herramientas gratuitas.

------------------------------------------------------------------------

# 10. Casos de estudio

Priorizar escenarios reales.

Ejemplos:

-   Asistente corporativo.
-   RAG documental.
-   Data Warehouse.
-   Automatización.
-   Desarrollo de software.
-   Seguridad.
-   Salud.
-   Gobierno.

El foco debe estar en la toma de decisiones.

------------------------------------------------------------------------

# 11. Código

Todo ejemplo debe ser:

-   ejecutable;
-   comentado;
-   sencillo;
-   progresivo.

Cuando corresponda incluir:

-   Docker
-   Docker Compose
-   Python
-   .NET
-   SQL
-   JavaScript
-   APIs

------------------------------------------------------------------------

# 12. Revisión técnica

Antes de aprobar un capítulo verificar:

-   precisión conceptual;
-   consistencia con capítulos anteriores;
-   ejemplos correctos;
-   diagramas actualizados;
-   terminología uniforme;
-   referencias cruzadas.

------------------------------------------------------------------------

# 13. Control de versiones

Estados recomendados:

-   v0.1 → estructura inicial.
-   v0.3 → contenido ampliado.
-   v0.5 → revisión conceptual.
-   v0.8 → revisión técnica.
-   v0.9 → revisión editorial.
-   v1.0 → capítulo aprobado.

------------------------------------------------------------------------

# 14. Criterios de calidad

Un capítulo estará terminado cuando:

-   pueda estudiarse de forma independiente;
-   mantenga coherencia con el resto del libro;
-   responda las preguntas fundamentales;
-   incluya práctica y teoría;
-   sea útil para consulta futura.

------------------------------------------------------------------------

# 15. Frase editorial

Todos los capítulos finalizarán con la frase:

> "Un arquitecto no memoriza respuestas. Comprende problemas para poder
> diseñar soluciones."

------------------------------------------------------------------------

# 16. Criterio de aprobación

Antes de considerar terminado un capítulo, responder:

-   ¿Forma mejores profesionales?
-   ¿Desarrolla criterio?
-   ¿Podría seguir siendo útil dentro de cinco años?
-   ¿Explica el problema antes de la solución?
-   ¿Ayuda a tomar decisiones?

Si alguna respuesta es negativa, el capítulo vuelve a revisión.

------------------------------------------------------------------------

# 17. Objetivo final

Construir una obra de referencia en español sobre Ingeniería de IA,
centrada en el razonamiento, la arquitectura y la toma de decisiones,
más que en herramientas específicas.
