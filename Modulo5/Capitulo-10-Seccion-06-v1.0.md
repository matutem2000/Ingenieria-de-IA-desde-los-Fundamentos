# Cierre: diseñar aplicaciones de IA mantenibles y evolucionables

Las aplicaciones de IA mantenibles y evolucionables comparten los mismos atributos que el software bien diseñado en general —bajo acoplamiento, alta cohesión, interfaces claras, cobertura de tests—, con una dimensión adicional: la separación explícita entre el código determinista (lógica de negocio, validación, persistencia) y el componente no determinista (el LLM), con un boundary bien definido entre ambos que facilita testear el primero con mocks y evaluar el segundo con datasets. Los patrones de diseño presentados en este capítulo —Gateway, Circuit Breaker, validación de entrada, parsing robusto de salida, composición tipada— no son frameworks ni bibliotecas sino principios de ingeniería que se implementan con código Python puro, son comprensibles para cualquier ingeniero backend, y no requieren conocer el dominio de IA para entender su propósito. La evolucionabilidad de una aplicación de IA se mide por la facilidad con que puede cambiar el modelo subyacente sin modificar el código de la aplicación: si cambiar de `claude-3-5-sonnet-20241022` a `claude-3-5-haiku-20241022` requiere modificar 15 archivos del proyecto, el sistema tiene un problema de acoplamiento que crecerá con cada actualización de modelo; si requiere cambiar una sola variable de configuración, el sistema está bien diseñado.

## Principios de diseño para aplicaciones de IA mantenibles

- Separación explícita determinista/no-determinista: el código que llama al LLM es una capa delgada de traducción entre el dominio de la aplicación y la API del modelo; toda la lógica de negocio vive en código Python testeable con el LLM mockeado
- Configuración externalizada: `model_id`, `temperature`, `max_tokens`, `prompt_version`, `system_prompt_path` son variables de configuración inyectadas en runtime, no constantes en el código; cualquier cambio de estos valores se hace en config sin tocar el código
- Interfaces estables sobre implementaciones cambiantes: definir protocolos Python (`Protocol` de typing o ABC) para el LLM client, el retriever, y el parser; las implementaciones concretas son intercambiables sin que el código llamante cambie
- Evolución de prompts como disciplina de ingeniería: cada cambio de prompt es un PR con diff legible, tests que verifican el impacto en el dataset de evaluación, y aprobación del equipo antes de mergearse; los prompts no son texto informal sino código versionado con las mismas garantías de calidad
- Deuda técnica de IA como deuda técnica de software: prompts no testeados, parsers frágiles sin manejo de errores, caché de prompts no instrumentada, y modelos sin versionado explícito son formas de deuda técnica que se acumulan y hacen más costoso cada cambio futuro; pagarlas proactivamente en cada sprint es la práctica de un equipo de AI Engineering maduro

*"Good design is not just about making things look pretty; it's about making systems that are easy to change."* — Martin Fowler, "Refactoring: Improving the Design of Existing Code". En aplicaciones de IA, la facilidad de cambio es doblemente crítica porque el componente más importante del sistema —el modelo de lenguaje— es externo y evoluciona continuamente, y el sistema que no está diseñado para absorber ese cambio acumula deuda técnica con cada nueva versión de modelo que el proveedor lanza.
