# Módulo 5 – Capítulo 04 – Sección 01

## Patrones de integración: síncrono, asíncrono, event-driven y por lotes

Añadir capacidades de IA a una aplicación existente no es simplemente agregar llamadas al LLM en el código que ya existe: es una decisión arquitectónica sobre cómo el sistema de IA se integra en el flujo de datos, el modelo de concurrencia y el contrato de latencia que la aplicación ya tiene. El patrón de integración equivocado puede hacer que un sistema de IA correctamente implementado resulte inutilizable en producción: una tarea de análisis de documentos que toma 30 segundos no puede servirse con una conexión HTTP que el cliente espera síncrona, ni un chat conversacional puede implementarse con un job de procesamiento nocturno.

El patrón síncrono —request/response— es el más simple y el más adecuado para interacciones conversacionales con latencia tolerable de 2 a 10 segundos y volumen bajo a medio. El cliente hace un POST, el servidor llama al LLM, y la respuesta llega en la misma conexión HTTP antes de que el timeout del cliente expire. La variante más común en producción combina el patrón síncrono con streaming SSE: `StreamingResponse` en FastAPI transmite los tokens del LLM al cliente a medida que se generan, eliminando la espera en blanco inicial sin cambiar la naturaleza síncrona del request. Este patrón es suficiente para la mayoría de los chatbots, asistentes de redacción y herramientas de análisis de texto con latencia de usuario aceptable.

El patrón asíncrono desacopla la recepción de la solicitud de la entrega del resultado. El cliente envía el request y recibe inmediatamente un `job_id`; la tarea se ejecuta en background; el cliente consulta el estado via polling (`GET /jobs/{job_id}/status`) o recibe notificación cuando la tarea termina via webhook. Este patrón es correcto para tareas que toman entre 30 segundos y varios minutos —análisis de documentos largos, procesamiento de audios, generación de reportes— donde mantener la conexión HTTP abierta durante ese tiempo es costoso e inestable. Celery con broker Redis o RabbitMQ, o el servicio ARQ (Async Redis Queue) para Python asyncio, implementan este patrón con workers que consumen tareas de una cola y actualizan el estado en la base de datos.

El patrón event-driven con brokers de mensajes como Kafka, RabbitMQ o AWS SQS permite escalar horizontalmente el procesamiento de IA distribuyendo el trabajo entre múltiples workers consumidores, con control de backpressure y dead letter queues para manejo robusto de fallos. Este patrón es correcto cuando el pipeline de IA es un componente dentro de un sistema de eventos más amplio: un evento de "documento cargado" dispara el pipeline de análisis; el resultado del análisis genera un evento de "análisis completado" que otros sistemas consumen. La arquitectura event-driven desacopla completamente el productor del procesamiento, permitiendo escalar la capacidad de procesamiento de IA independientemente de la aplicación que genera los eventos.

El batch processing nocturno procesa grandes volúmenes de datos en ventanas de tiempo donde la latencia por item individual no importa. Scripts que leen N registros de una base de datos, los procesan con el LLM en paralelo usando `asyncio.gather()` con un semáforo que controla la concurrencia máxima, y escriben los resultados de vuelta son apropiados para enriquecimiento masivo de datos, clasificación de corpus, y generación de embeddings para indexación. La optimización de throughput en batch incluye usar el Batch API de Anthropic —que procesa requests con hasta 50% de descuento a cambio de un SLA de latencia de 24 horas— para tareas que no requieren resultados en tiempo real.

## Aspectos técnicos de los patrones de integración

- **Síncrono con streaming:** FastAPI `StreamingResponse` con `media_type="text/event-stream"` y un generador async que re-transmite los chunks del proveedor al cliente; configurar `timeout=httpx.Timeout(read=120)` para respuestas largas.
- **Asíncrono con Celery:** task `@app.task` que llama al LLM, actualiza el estado en Redis o PostgreSQL, y opcionalmente dispara un webhook al callback URL del cliente; polling con `GET /tasks/{task_id}` o eventos via WebSocket.
- **Event-driven con SQS + Lambda:** mensaje en SQS dispara Lambda que procesa con el LLM y escribe el resultado en DynamoDB o SNS; el dead letter queue captura los mensajes que fallan tras `maxReceiveCount` intentos.
- **Batch con control de concurrencia:** `asyncio.Semaphore(MAX_CONCURRENT=20)` limita las llamadas paralelas al LLM para respetar el rate limit del proveedor; `asyncio.gather(*tasks, return_exceptions=True)` procesa todos los items en paralelo respetando ese límite.
- **Elección del patrón:** latencia < 5s y UX conversacional → síncrono con streaming; análisis de documento individual → asíncrono con webhook; enriquecimiento de millones de registros → batch; pipeline de eventos en tiempo real → event-driven.

> **Nota del Arquitecto:** El error de diseño más frecuente en proyectos de IA nuevos es usar el patrón síncrono para tareas que son inherentemente asíncronas —análisis de documentos de 50 páginas, generación de reportes, transcripción de audio— porque "es más simple al inicio". El resultado es un timeout en producción que fuerza una reescritura bajo presión. El patrón de integración determina el diseño del sistema completo; cambiarlo después de estar en producción es una refactorización mayor. Vale la pena elegirlo correctamente desde el primer sprint.

El patrón de integración elegido determina no solo la arquitectura de la capa de IA sino la del sistema completo que la rodea: el modelo de autenticación, el manejo de errores, la estrategia de escalabilidad y la experiencia del usuario. La siguiente sección aborda cómo exponer las capacidades de IA hacia otras aplicaciones y servicios mediante APIs REST diseñadas para durar.

---

**Principio rector:** El patrón de integración es la decisión arquitectónica más importante al añadir IA a una aplicación; elegirlo correctamente desde el inicio —síncrono, asíncrono, event-driven o batch según la latencia, volumen y acoplamiento requeridos— determina la viabilidad del sistema en producción.
