# Módulo 5 – Capítulo 01 – Sección 02

## APIs de modelos fundacionales: OpenAI, Anthropic, Google — estructura y autenticación

¿Cuán diferentes son realmente las APIs de los tres proveedores dominantes del mercado? La respuesta importa porque determina cuánto esfuerzo cuesta construir una abstracción portable y qué capacidades diferenciadoras pierde el sistema si se abstrae demasiado. Las APIs de OpenAI, Anthropic y Google Vertex AI comparten el modelo HTTP REST con autenticación por token y serialización JSON, pero difieren en la estructura del mensaje, los mecanismos de autenticación, la forma de expresar el contexto del sistema y las capacidades multimodales. Comprender estas diferencias en detalle —no en abstracto— es la diferencia entre una integración que funciona correctamente la primera vez y una que falla de formas sorprendentes a las tres semanas de estar en producción.

La API de OpenAI es la más establecida y la más imitada: su endpoint `https://api.openai.com/v1/chat/completions` recibe un cuerpo JSON con el campo `model` (ej. `gpt-4o-2024-08-06`, siempre con la fecha para evitar actualizaciones silenciosas), un array `messages` con objetos `{role, content}` donde el rol `system` es el primer elemento del array, y parámetros de inferencia como `temperature`, `max_tokens`, `top_p` y `stream`. La autenticación se realiza con el header `Authorization: Bearer $OPENAI_API_KEY`. Los tiers de rate limit escalan desde Tier 1 con 500 RPM y 30.000 TPM hasta Tier 5 con 10.000 RPM y 30.000.000 TPM, determinados por el gasto histórico acumulado. Los errores 429 incluyen el header `Retry-After` que indica los segundos de espera antes del siguiente intento.

La API de Anthropic tiene una diferencia estructural importante: el campo `system` no es parte del array `messages` sino un campo de primer nivel en el cuerpo del request. Esta separación no es cosmética —tiene implicaciones en el prompt caching, porque el campo `system` puede marcarse con `cache_control: {"type": "ephemeral"}` independientemente de los mensajes del turno, lo que permite cachear instrucciones largas del sistema mientras los mensajes del usuario varían libremente. La autenticación requiere dos headers en cada request: `x-api-key: $ANTHROPIC_API_KEY` y `anthropic-version: 2023-06-01`, siendo el segundo obligatorio para garantizar la compatibilidad con la versión del protocolo que el código espera. El código de error 529 es exclusivo de Anthropic e indica sobrecarga temporal del servicio, distinto del 429 de rate limit: ambos son retryables pero con estrategias diferentes.

Google ofrece dos rutas de acceso a Gemini. Vertex AI es la ruta enterprise: autenticación con OAuth2 via service account JSON o Application Default Credentials (ADC), endpoint dinámico por región `{region}-aiplatform.googleapis.com`, soporte nativo multimodal con `inline_data` y `file_data` que permiten intercalar texto, imagen, audio y video en el mismo mensaje, y acceso a controles de seguridad VPC, CMEK y VPC Service Controls. AI Studio es la ruta de desarrollo rápido: autenticación simplificada con `x-goog-api-key`, misma capacidad de modelo sin los controles enterprise, sin SLA de producción. La elección entre Vertex AI y AI Studio es siempre la misma: Vertex AI en producción con datos sensibles, AI Studio en prototipado y desarrollo.

## Aspectos técnicos de las APIs principales

- **OpenAI API:** endpoint `/v1/chat/completions`, header `Authorization: Bearer`, campo `system` dentro del array `messages`, tiers de rate limit por gasto acumulado, soporte de `response_format: {"type": "json_schema"}` para structured outputs garantizados.
- **Anthropic API:** campo `system` de primer nivel (no en `messages`), headers `x-api-key` y `anthropic-version` obligatorios, error 529 para sobrecarga temporal, `cache_control` para prompt caching granular por bloque de contenido.
- **Google Vertex AI:** autenticación OAuth2 con service accounts, endpoint regional dinámico, soporte multimodal nativo con `contents[].parts[]`, controles enterprise de VPC y CMEK, `generationConfig.responseMimeType: "application/json"` para salida estructurada.
- **Google AI Studio:** `x-goog-api-key` para desarrollo, misma capacidad del modelo sin controles enterprise, adecuado para prototipado y evaluación de modelos.
- **Códigos de error críticos:** 400 (parámetros inválidos o contexto excedido), 401 (API key ausente o revocada), 422 (contenido que viola políticas de uso), 429 (rate limit con `Retry-After`), 529 (sobrecarga temporal de Anthropic, retryable con backoff).

> **Nota del Arquitecto:** El error más frecuente al integrar múltiples proveedores es asumir que el campo `system` funciona igual en todos ellos. En Anthropic, mover el contenido de contexto estático (reglas de negocio, ejemplos few-shot, documentos de referencia) al campo `system` separado habilita el prompt caching sin cambiar el resto de la llamada. En OpenAI, el mismo contenido va como primer mensaje del array con `role: "system"` y el caching es automático para prefijos de más de 1.024 tokens. Entender esta diferencia antes de diseñar el sistema de caching puede ahorrar semanas de refactorización posterior.

Las diferencias estructurales entre APIs son argumentos concretos a favor de encapsular el acceso al proveedor en un adaptador interno: cuando el código de la aplicación llama a `llm.complete(system_prompt, messages)` en lugar de llamar directamente al SDK de cada proveedor, cambiar el proveedor o aprovechar una nueva capacidad de autenticación requiere modificar solo el adaptador. La siguiente sección explora precisamente cómo los SDKs oficiales de cada proveedor encapsulan estas diferencias y simplifican las primeras llamadas al modelo.

**Para recordar:** Cada proveedor impone su propio contrato de autenticación, estructura de mensajes y semántica del campo `system`; abstraer estas diferencias en un adaptador interno es más robusto que depender de wrappers de terceros para aplicaciones de producción donde los detalles del protocolo importan.
