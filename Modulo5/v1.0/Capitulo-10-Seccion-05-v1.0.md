# Módulo 5 – Capítulo 10 – Sección 05

## Patrones de composición: encadenamiento secuencial, paralelo y condicional

Los sistemas de IA reales raramente consisten en una sola llamada al LLM. Un sistema de análisis de documentos puede necesitar: extraer las entidades relevantes del documento con una llamada, clasificar el tipo de documento con otra llamada simultánea, y generar un resumen ejecutivo con una tercera llamada que depende de los resultados de las dos anteriores. La composición de múltiples operaciones de LLM en un flujo coherente —con manejo explícito de dependencias, errores y estado parcial— es el dominio de los patrones de composición. La diferencia entre un sistema bien compuesto y uno mal compuesto es la diferencia entre un pipeline donde cada paso conoce exactamente qué recibe y qué produce, y un pipeline donde el estado viaja como dictionaries anidados de significado ambiguo que solo el autor original puede interpretar.

El encadenamiento secuencial es el patrón más común: la salida de cada paso es la entrada del siguiente. La implementación correcta tipifica explícitamente la salida de cada paso con Pydantic: el `Step1Output` se convierte en el `Step2Input` a través de un mapping explícito, no de `response["field"]` sobre un dict anónimo. Esta tipificación hace que el flujo sea comprensible para cualquier miembro del equipo sin necesidad de rastrear el dict a través de múltiples funciones. En LCEL, el operador `|` encadena `Runnable` components de forma que el output del primero alimenta el input del segundo, con type checking en tiempo de ejecución.

El encadenamiento paralelo —fan-out/fan-in— es el patrón para operaciones independientes que pueden ejecutarse concurrentemente. `asyncio.gather(*[step_a(input), step_b(input), step_c(input)])` ejecuta las tres operaciones en paralelo y espera a que todas terminen antes de continuar. La latencia total del paso paralelo es la latencia del paso más lento, no la suma de todas las latencias: si cada llamada tarda 2 segundos, el paso paralelo tarda 2 segundos en lugar de 6. En LCEL, `RunnableParallel(key_a=chain_a, key_b=chain_b)` implementa fan-out/fan-in con manejo de errores integrado. La semántica de `asyncio.gather` con `return_exceptions=True` permite que el paso paralelo continúe incluso si alguna rama falla, con el error capturado como valor en lugar de excepción propagada.

El encadenamiento condicional —routing— selecciona qué rama del pipeline ejecutar según el resultado de un paso anterior. El paso de clasificación produce una categoría, y el router selecciona el paso de procesamiento correcto para esa categoría: `{"legal": legal_chain, "financial": financial_chain, "general": general_chain}[document_type]`. El routing puede ser determinístico (basado en el resultado tipado del clasificador) o probabilístico (basado en la distribución de confianza del clasificador). La implementación correcta hace el routing explícito en el código en lugar de delegarlo al LLM vía instrucciones de "si el documento es X, haz Y", porque el routing explícito es testeable, loggeable y modificable sin cambiar el prompt.

Los checkpoints y la reanudación son el mecanismo que hace que los pipelines largos sean tolerantes a fallos. En un pipeline de diez pasos donde cada paso tarda 3 segundos, un fallo en el paso 8 descarta 21 segundos de trabajo completado. Guardar el output de cada paso en Redis —`redis.set(f"pipeline:{request_id}:step_{n}", json.dumps(step_output), ex=3600)`— permite reanudar el pipeline desde el último checkpoint en lugar de reiniciar desde el principio. LangGraph implementa checkpointing como característica nativa de su `StateGraph`, con backends de persistencia en memoria, SQLite, o PostgreSQL.

## Patrones de composición en la práctica

- **Tipos explícitos entre pasos:** `class Step1Output(BaseModel): entities: List[str]; class Step2Input(BaseModel): entities: List[str]`; transformar explícitamente entre tipos con `step2_input = Step2Input(entities=step1_output.entities)` en lugar de pasar dicts anónimos; el type checking estático detecta incompatibilidades antes de llegar a producción.
- **Fan-out/fan-in tipado:** `results = await asyncio.gather(step_a(input), step_b(input), return_exceptions=True)`; verificar si cada resultado es una excepción con `isinstance(r, Exception)` antes de usarlo; decidir si la falla de una rama es fatal o si el pipeline puede continuar con las ramas exitosas.
- **Router explícito en código:** `HANDLERS: Dict[str, Runnable] = {"legal": legal_chain, "financial": financial_chain}`; `handler = HANDLERS.get(classification, default_chain)`; loggear el valor de `classification` y el `handler` seleccionado para cada request como métrica operativa.
- **Checkpointing con Redis:** guardar el output de cada paso con `redis.set(f"pipeline:{request_id}:step_{step_num}", serialized_output, ex=ttl_seconds)` antes de continuar; en la reanudación, verificar qué pasos ya tienen checkpoint y empezar desde el primero que falta; el TTL debe ser mayor que el tiempo máximo total del pipeline.
- **LangGraph para pipelines con ciclos:** cuando el flujo requiere ciclos (reintento de un paso hasta que cumple una condición, evaluación de calidad que puede redirigir a un paso anterior), LangGraph es la herramienta correcta; un `StateGraph` con `add_conditional_edges` implementa el routing condicional con ciclos de forma explícita y testeable.

> **Nota del Arquitecto:** El antipatrón más común en composición de LLM es el "god prompt": un prompt único que intenta hacer todo lo que el pipeline haría en múltiples pasos. El god prompt es atractivo por su aparente simplicidad pero produce sistemas frágiles: un cambio en un aspecto del prompt puede romper otro aspecto no relacionado, el debugging es difícil porque no hay pasos intermedios observables, y el testing es prácticamente imposible porque el output es holístico y no verificable paso a paso. La descomposición en pasos explícitos con tipos entre ellos es siempre superior a largo plazo.

Un pipeline de composición bien diseñado es un sistema donde cada paso tiene una única responsabilidad, una interfaz tipada de entrada y salida, y un comportamiento de error definido explícitamente. Esta claridad de diseño es lo que permite al equipo evolucionar el pipeline —reemplazar un paso, agregar una rama, cambiar el modelo de un paso específico— sin entender el comportamiento completo del sistema cada vez que se hace un cambio.

---

**Principio de composición:** La composición de múltiples llamadas al LLM en pipelines es más mantenible cuando cada paso tiene una única responsabilidad, tipos explícitos de entrada y salida, y un comportamiento de error definido; la alternativa del "god prompt" que intenta hacer todo en una llamada produce sistemas que no pueden testearse, observarse ni evolucionarse de forma independiente en cada parte.
