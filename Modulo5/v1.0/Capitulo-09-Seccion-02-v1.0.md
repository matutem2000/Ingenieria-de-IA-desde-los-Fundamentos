## Estrategias de reducción: compresión de contexto, caché semántica y batching

Las estrategias de reducción de costo en sistemas de IA atacan el problema desde tres ángulos complementarios: reducir la cantidad de tokens enviados en cada llamada (compresión de contexto), reutilizar respuestas de llamadas anteriores cuando la pregunta es suficientemente similar (caché semántica), y consolidar múltiples peticiones en una sola llamada cuando el caso de uso lo permite (batching). La regla de oro que debe preceder a cualquier implementación es: medir el impacto de cada estrategia en la calidad del sistema con el dataset de evaluación antes de desplegarla en producción, porque cada una de estas optimizaciones implica un trade-off potencial con la calidad que solo el sistema de evaluación puede cuantificar.

La compresión de contexto en sistemas conversacionales es la optimización de mayor retorno para sistemas con sesiones largas porque los tokens del historial son el componente que más crece con el tiempo. La estrategia de sliding window —mantener los últimos K turnos completos— es la más simple: `messages = messages[-2*K:]` donde K es el número de pares usuario-asistente a conservar, configurable por el requisito de coherencia del dominio. La estrategia de summarization es más costosa —requiere una llamada adicional al LLM con `temperature=0` para generar el resumen— pero preserva información de largo plazo mejor que la sliding window pura: `summary = llm.summarize(messages[:-K]); messages = [{"role": "system", "content": f"Historial resumido: {summary}"}] + messages[-K:]`. El costo del resumen —una llamada de ~1.000 tokens de entrada y ~500 de salida, aproximadamente $0.012 en Claude 3.5 Sonnet— se amortiza en todos los turnos futuros que usan el historial comprimido en lugar del historial completo.

La caché semántica extiende el concepto de caching más allá de la igualdad exacta de texto: en lugar de cachear solo respuestas a preguntas literalmente idénticas, cachea respuestas a preguntas semánticamente equivalentes. El proceso tiene dos pasos: generar el embedding de la query del usuario con un modelo eficiente (`text-embedding-3-small` de OpenAI o `embed-multilingual-v3.0` de Cohere), buscar en Redis o en Qdrant por similitud coseno con las preguntas cacheadas, y devolver la respuesta cacheada si la similitud supera el umbral configurado (típicamente 0.95). El TTL del caché debe alinearse con la frecuencia de cambio de los datos del dominio: para una base de conocimiento de productos que se actualiza mensualmente, un TTL de 24 horas es apropiado; para preguntas sobre datos en tiempo real, la caché semántica no aplica. En dominios con muchas preguntas frecuentes repetitivas —FAQs, consultas sobre catálogos de productos, preguntas sobre políticas de empresa—, el hit rate puede superar el 40%, con ahorro proporcional.

El batching consolida múltiples consultas independientes en una sola llamada al LLM cuando la latencia por item individual no es el requisito principal. En lugar de N llamadas separadas para clasificar N documentos con el mismo prompt, una sola llamada con los N documentos separados por delimitadores XML (`<document id="1">...</document><document id="2">...</document>`) reduce el costo del system prompt repetido N veces a una única instancia. Para pipelines de procesamiento nocturno o de enriquecimiento de datos, el Batch API de Anthropic permite enviar hasta 10.000 requests en un lote con hasta un 50% de descuento sobre el precio normal, a cambio de un SLA de latencia de hasta 24 horas.

## Estrategias técnicas de reducción de costos

- **Compresión de historial con sliding window:** `messages = messages[-2*K:]`; valor de K configurable en `config/conversation.yaml`; 10 a 20 turnos son suficientes para la coherencia en la mayoría de los casos de uso; monitor del costo por turno antes y después para cuantificar el ahorro.
- **Caché semántica con embeddings y Redis:** embedding de la query con `text-embedding-3-small`, búsqueda por similitud coseno con `redis.FT.SEARCH` o en Qdrant; threshold de 0.95 para evitar servir respuestas de preguntas superficialmente similares pero semánticamente diferentes.
- **Batching de requests independientes:** un único prompt con N documentos separados por `<doc id="N">` reduce el overhead del system prompt de N copias a una; especialmente efectivo para clasificación y extracción de entidades en batch.
- **Truncación selectiva del contexto RAG:** de 5 chunks a 3 chunks de 500 tokens cuando el sistema de evaluación confirma que el tercer chunk raramente contribuye a la respuesta; ahorro de 1.000 tokens de entrada por request verificado con métricas de context recall.
- **Reutilización de prefix con prompt caching del proveedor:** en sistemas con system prompt largo (>1.000 tokens) y documentos de referencia fijos, marcar con `cache_control` para que las llamadas sucesivas en la misma sesión paguen solo el costo de cache read; especialmente impactante en sesiones multi-turno.

Medir el impacto de cada estrategia de reducción de costo con el sistema de observabilidad antes y después de implementarla es la única forma de confirmar que el ahorro no viene acompañado de degradación de calidad que supere el valor del ahorro económico.

---

**Buena práctica:** Medir el impacto en calidad de cada estrategia de reducción de costo con el dataset de evaluación antes de implementarla en producción; la compresión de contexto reduce costo pero puede degradar la coherencia del diálogo si el resumen pierde información crítica del historial; solo la medición confirma que el trade-off es aceptable para el caso de uso específico.
