# Módulo 5 – Capítulo 09 – Sección 04

## Elección de modelo por costo-beneficio: cuándo usar modelos más pequeños

La elección del modelo de LLM para cada tarea es la decisión de costo-calidad con mayor impacto en el presupuesto total de un sistema de IA: usar `gpt-4o` para clasificar intenciones de usuario con cinco categorías en lugar de `gpt-4o-mini` puede ser quince a veinte veces más caro por request sin ninguna mejora medible en la tarea específica. El principio de routing por complejidad —asignar el modelo más capaz y costoso solo a las tareas que genuinamente lo requieren— puede reducir el costo total del sistema en un 40 a 70% sin degradar la calidad percibida por el usuario.

La forma correcta de decidir si una tarea necesita el modelo grande es empírica: ejecutar la tarea sobre el dataset de evaluación del dominio con modelos de diferentes capacidades, medir las métricas de calidad relevantes para esa tarea, y calcular el diferencial de calidad vs el diferencial de costo. Si `claude-3-haiku` obtiene un accuracy del 94% en clasificación de intenciones mientras `claude-3-5-sonnet` obtiene el 96%, y el costo por request es 15 veces mayor con el modelo grande, el modelo pequeño es la elección correcta: la diferencia de 2 puntos de accuracy no justifica un incremento de costo del 1.400%. Si el modelo pequeño obtiene el 78% mientras el grande obtiene el 95%, la diferencia de 17 puntos puede justificar el costo adicional dependiendo del impacto de los errores de clasificación en el negocio.

Las categorías de tarea con características bien establecidas permiten una orientación general que debe validarse con datos del dominio específico. La clasificación con pocas categorías bien definidas —intención del usuario con cinco a diez categorías, sentimiento con tres valores— es una de las tareas donde los modelos pequeños superan consistentemente el 90% de la calidad del modelo grande con instrucciones y few-shot examples correctos. La extracción de entidades con formato JSON definido —nombre, fecha, importe, categoría— alcanza el 95% o más de accuracy con modelos pequeños en dominios con vocabulario estable. Los resúmenes de documentos largos y el razonamiento multi-paso con múltiples constraints simultáneos son donde el modelo grande típicamente justifica su costo: la diferencia de calidad es de diez a veinte puntos en estos dominios.

El patrón LLM router lleva el principio al extremo operacional: un modelo ligero y rápido —Claude 3 Haiku, gpt-4o-mini— clasifica la complejidad de cada query del usuario y la enruta al modelo adecuado. La clasificación de routing es rápida (50-100ms con un modelo pequeño), barata ($0.00003 por request a precios de Haiku), y la distribución de rutas se convierte en una métrica operativa que informa el diseño del sistema: si el 85% del tráfico se clasifica como "simple", el sistema tiene espacio para reducir el costo total usando el modelo pequeño para esa mayoría y reservando el modelo grande para el 15% restante de queries complejas.

## Criterios técnicos para la selección de modelo por tarea

- **Clasificación e intent detection:** modelos pequeños (Haiku, gpt-4o-mini) son suficientes con buenas instrucciones y 5-10 ejemplos few-shot; la diferencia de accuracy vs el modelo grande es típicamente de 1 a 5 puntos en dominios con categorías bien definidas.
- **Extracción de entidades simples:** nombre, fecha, importe, categoría de texto estructurado → modelos pequeños con output JSON alcanzan el 95%+ de accuracy vs el modelo grande a diez a veinte veces menor costo; la calidad del few-shot prompt impacta más que el modelo.
- **Resumen de documentos largos:** los modelos pequeños tienden a omitir detalles o a repetir información; el modelo grande justifica su costo en resúmenes de alta calidad donde la completitud y la coherencia son requisitos; validar con métricas de BERTScore o coherence en el dataset del dominio.
- **Razonamiento multi-paso y coding:** mantener múltiples constraints simultáneos, razonamiento causal complejo, generación de código correcto → el modelo grande ofrece mejoras de diez a veinte puntos de calidad que justifican el costo adicional en la mayoría de los casos.
- **LLM router pattern:** `small_model.classify(query)` devuelve `{"complexity": "simple|medium|complex", "task_type": "classification|generation|reasoning"}`; enruta a diferentes endpoints con diferentes modelos; loggear el modelo usado para análisis de distribución de rutas y optimización continua.

> **Nota del Arquitecto:** El error más frecuente en la selección de modelo es asumir que "más grande es mejor" sin medir en el dominio específico. En un proyecto de clasificación de tickets de soporte técnico en telecomunicaciones que implementé, Claude 3 Haiku con diez ejemplos few-shot específicos del dominio superó a Claude 3 Sonnet sin few-shot en todas las métricas relevantes, a un costo quince veces menor. El few-shot prompting específico del dominio importó más que la capacidad del modelo. Este resultado no es generalizable —cada dominio es diferente— pero sí es la razón por la que la medición empírica siempre supera a la intuición sobre capacidad del modelo.

El modelo correcto no es el más capaz disponible sino el menos capaz que cumple el requisito de calidad medido en el dataset de evaluación del dominio específico.

---

**Principio rector:** Sobre-aprovisionar modelo para una tarea es tan ineficiente como sub-aprovisionar infraestructura: el modelo correcto no es el más capaz disponible sino el menos capaz que cumple el requisito de calidad medido empíricamente en el dataset de evaluación del dominio específico de la tarea.
