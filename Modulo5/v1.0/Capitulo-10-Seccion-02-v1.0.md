# Módulo 5 – Capítulo 10 – Sección 02

## Patrones de salida: parseo estructurado, reintentos y fallbacks

El LLM produce texto; el sistema necesita datos. Esta brecha entre la salida natural del modelo y los tipos de datos que el resto de la aplicación consume es una de las fuentes de fragilidad más comunes en los sistemas de IA en producción: el código que parsea la respuesta del modelo asume un formato, el modelo produce un formato ligeramente diferente, y el sistema lanza una excepción que ningún test anticipó. El patrón de salida estructurada es el conjunto de técnicas que cierran esta brecha de forma sistemática: especificar el formato esperado en el prompt, usar las capacidades de structured output del proveedor cuando están disponibles, parsear y validar con Pydantic, y definir explícitamente qué hace el sistema cuando el parseo falla.

Las APIs modernas de LLM ofrecen tres mecanismos de structured output con garantías diferentes. El structured output nativo —disponible en OpenAI con `response_format={"type": "json_schema", "json_schema": {...}}` y en Google con `response_mime_type="application/json"` más `response_schema`— garantiza que el modelo produce JSON que conforma al schema especificado, usando constrained decoding en la capa de generación del modelo: el modelo elige solo tokens que son compatibles con el schema en cada paso. Esta garantía elimina la posibilidad de JSON malformado pero no garantiza que los valores del JSON sean semánticamente correctos. El JSON mode —`response_format={"type": "json_object"}` en OpenAI sin schema— garantiza JSON válido pero no el schema específico. El prompting explícito de JSON —instrucciones en el system prompt más ejemplos few-shot de JSON— no ofrece garantías formales pero funciona con cualquier proveedor.

Pydantic es la capa de validación semántica que complementa las garantías de formato. `model = ResponseModel.model_validate_json(response_text)` parsea el JSON y valida simultáneamente que todos los campos requeridos existen, que los tipos son correctos, que los valores de enum están en la lista permitida, y que las constraints de valor (`gt=0`, `max_length=500`) se cumplen. Cuando la validación falla con `ValidationError`, el sistema sabe exactamente qué campo tiene qué problema, con un mensaje de error estructurado que puede usarse para construir un prompt de corrección.

El retry con corrección es la pieza que convierte un error de parseo en una segunda oportunidad de éxito. El `OutputFixingParser` de LangChain implementa este patrón: cuando la respuesta falla la validación de Pydantic, construye un segundo prompt que incluye la respuesta original, el error de Pydantic, y la instrucción de corregir el error manteniendo el contenido. Esta segunda llamada tiene alta tasa de éxito para errores de formato (campo faltante, valor de tipo incorrecto) pero baja para errores semánticos (el modelo no tiene la información necesaria para responder con el schema requerido). Limitar el retry a dos intentos máximo previene el gasto de llamadas adicionales en casos donde el modelo estructuralmente no puede cumplir el schema.

La jerarquía de fallback define el comportamiento del sistema cuando todos los intentos fallan. La jerarquía correcta varía por dominio, pero un ejemplo común es: (1) respuesta parcial con los campos disponibles y `null` en los campos faltantes —si el sistema puede funcionar con información parcial—, (2) respuesta default del sistema como "No puedo responder a esta consulta en el formato requerido", o (3) escalamiento a revisión humana para respuestas que el sistema no puede procesar automáticamente.

## Componentes técnicos del parseo de salida estructurada

- **Structured output nativo de OpenAI:** `client.beta.chat.completions.parse(model=..., messages=..., response_format=ResponsePydanticModel)` devuelve el objeto Pydantic directamente; usar `response.choices[0].message.parsed` para acceder al objeto sin parseo manual; la guaranteed JSON conformance elimina errores de JSON malformado.
- **Validación con Pydantic:** definir el schema como `class Response(BaseModel): field: str = Field(description="...")` con validators explícitos; `model_validate_json(raw_text)` parsea y valida en un paso; capturar `ValidationError` para construir el error detallado que informa el retry prompt.
- **Retry con prompt de corrección:** dos intentos máximo; el segundo prompt incluye: la respuesta original entre `<original_response>` tags, el error de Pydantic en texto plano, y la instrucción `"Fix the above response to conform to the required JSON schema. Return ONLY valid JSON."`.
- **OutputFixingParser en LangChain:** `OutputFixingParser.from_llm(parser=PydanticOutputParser(pydantic_object=Model), llm=model)` encapsula el retry automáticamente; útil en cadenas LCEL para mantener el flujo limpio.
- **Jerarquía de fallback:** (1) parse completo exitoso → respuesta normal; (2) parse parcial con `ValidationError` → retry con corrección; (3) segundo intento fallido → respuesta parcial o default, log del error completo para revisión; (4) error de API en ambos intentos → error de sistema con dead letter queue.

> **Nota del Arquitecto:** Los errores de parseo de salida en producción raramente son aleatorios: ocurren sistemáticamente para ciertos tipos de queries o ciertos patrones de respuesta del modelo. El logging estructurado de todos los errores de parseo —incluyendo el texto de la respuesta que falló, el error de Pydantic, y el resultado del retry— permite identificar estos patrones sistemáticos y corregirlos en el prompt, en el schema, o en la lógica de validación. Un sistema que nunca loggea las respuestas que no puede parsear está perdiendo información crítica sobre sus propios puntos de fallo.

El parseo robusto de salida no es un detalle de implementación: es una propiedad de calidad del sistema que determina cuántos requests producen datos utilizables por el resto de la aplicación; un sistema que falla silenciosamente en el parseo —devolviendo un objeto vacío o un default sin loggear el error— produce bugs de datos difíciles de trazar cuya causa original fue una respuesta malformada del LLM que nadie detectó.

---

**Principio de diseño:** La robustez del parseo de salida es proporcional a la especificidad del schema, la calidad del prompt de structured output, y la integridad del sistema de fallback; los tres componentes deben diseñarse juntos desde el inicio porque un schema mal definido produce errores que el mejor retry no puede corregir.
