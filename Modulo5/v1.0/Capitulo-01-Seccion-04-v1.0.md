# Módulo 5 – Capítulo 01 – Sección 04

## Gestión de credenciales, variables de entorno y seguridad básica

Las API keys de modelos fundacionales no son credenciales ordinarias: conceden acceso irrestricto a la cuota de gasto del proyecto y, en muchos casos, a los datos que se envían como contexto al modelo. Una key de OpenAI filtrada en un repositorio público puede generar cargos de miles de dólares en horas antes de ser detectada y revocada —incidentes de este tipo están documentados en GitHub con frecuencia creciente desde 2023. Una key de Anthropic comprometida puede también exponer los prompts y documentos que el sistema envía como contexto, que pueden contener información confidencial de negocio o datos personales de usuarios. La gestión segura de credenciales no es un aspecto avanzado de la operación: es un requisito desde el primer commit del repositorio, antes de que la primera key sea generada.

La práctica universal para desarrollo local es almacenar las API keys en un archivo `.env` en la raíz del proyecto, cargado con `python-dotenv` mediante `from dotenv import load_dotenv; load_dotenv()` al inicio del proceso. Este archivo contiene las keys en texto plano —`OPENAI_API_KEY=sk-...`— y debe agregarse al `.gitignore` en el mismo commit en que se crea el repositorio, antes de que ninguna key exista. La secuencia correcta es: crear el repositorio, agregar `.env` y `.env.local` a `.gitignore`, crear el archivo `.env.example` con las variables de entorno esperadas pero sin valores reales (para que el equipo sepa qué keys configurar), y solo entonces generar las API keys y agregarlas al `.env` local. El orden importa: decenas de incidentes de seguridad documentados ocurrieron porque el desarrollador creó el `.gitignore` después de hacer el primer commit con el `.env` incluido.

En entornos de producción, las variables de entorno se inyectan desde un gestor de secretos externo en lugar de archivos locales. AWS Secrets Manager permite almacenar los secretos como pares clave-valor con rotación automática y acceso controlado por IAM roles; las aplicaciones en ECS o Lambda los leen via SDK de AWS sin que el valor aparezca en logs ni en el filesystem del contenedor. HashiCorp Vault ofrece rotación dinámica de secretos con leases temporales que expiran; es la opción dominante en infraestructuras multi-cloud. Google Secret Manager y Azure Key Vault son las equivalentes en sus respectivos clouds, con integración nativa con los servicios de cómputo del proveedor. Los pipelines de CI/CD —GitHub Actions, GitLab CI, CircleCI— tienen mecanismos propios de secretos que inyectan las variables en el entorno de ejecución sin exponerlas en los logs.

La detección preventiva es el segundo pilar de la gestión segura de credenciales. Herramientas como `detect-secrets`, `truffleHog` y `gitleaks` se instalan como hooks de pre-commit: antes de que cualquier commit llegue al repositorio, el hook escanea los archivos por patrones de API keys (el SDK de OpenAI usa el prefijo `sk-`, las keys de Anthropic usan `sk-ant-`) y rechaza el commit si detecta alguno. Configurar estos hooks en el repositorio como parte del archivo `.pre-commit-config.yaml` garantiza que todos los miembros del equipo los ejecuten sin necesidad de recordarles.

## Puntos críticos de seguridad en credenciales de IA

- **Regla de oro:** nunca hardcodear API keys en el código fuente; usar siempre `os.environ.get("API_KEY")` o `os.getenv("API_KEY")` como única forma de acceso dentro del código de la aplicación, con fallo explícito si la variable no existe.
- **Archivo `.env` local:** usar `python-dotenv` para cargar variables en desarrollo, con `.env`, `.env.local` y `.env.*.local` siempre presentes en `.gitignore` desde el primer commit del repositorio.
- **Gestores de secretos en producción:** AWS Secrets Manager, Azure Key Vault o Google Secret Manager proveen rotación automática, auditoría de accesos y acceso controlado por IAM roles sin hardcodear credenciales en el runtime de la aplicación.
- **Pre-commit hooks de detección:** configurar `detect-secrets` o `gitleaks` como hooks de pre-commit para detectar patrones de API keys antes de que lleguen al repositorio remoto.
- **Keys separadas por ambiente:** OpenAI y Anthropic permiten crear múltiples API keys con nombres descriptivos; usar keys diferentes para desarrollo, staging y producción con límites de gasto diferenciados por ambiente previene que experimentos en desarrollo consuman cuota de producción.

> **Nota del Arquitecto:** En organizaciones con múltiples equipos usando el mismo proveedor, crear proyectos separados por equipo o feature en la consola del proveedor (OpenAI Projects, Anthropic Workspaces) permite aislar el gasto y los límites de rate entre equipos sin gestionar una única key compartida. Una key compartida convierte cada incidente de rate limiting en un problema que afecta a todos los equipos simultáneamente; keys independientes por equipo aíslan el impacto y facilitan la atribución de costos en las revisiones presupuestarias.

La gestión segura de credenciales establece el primer perímetro de seguridad del sistema de IA. El segundo perímetro —validar la entrada del usuario para prevenir prompt injection y sanitizar la salida antes de exponerla— se aborda en el Capítulo 10. Lo que la sección siguiente explora es un problema diferente al de la seguridad: la elección de qué API, SDK y modelo usar según los requisitos técnicos y económicos del caso de uso, que es la decisión de diseño con mayor impacto en el costo y la calidad del sistema a largo plazo.

---

**Idea central:** Una credencial de API de modelo fundacional comprometida no solo expone gasto monetario sino potencialmente datos sensibles del contexto enviado al modelo; la gestión segura de secretos es un requisito de producción desde el primer día, no una consideración posterior de hardening.
