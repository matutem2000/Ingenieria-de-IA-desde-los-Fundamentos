# Módulo 5 – Capítulo 10 – Sección 03

## El patrón Gateway: punto de entrada único para llamadas al LLM

En un sistema de IA con múltiples features, múltiples modelos y múltiples proveedores, el código que llama directamente al SDK del proveedor desde cada punto del sistema crea un problema de mantenimiento que escala con la complejidad: si el equipo decide migrar de una librería a otra, cambiar el modelo por defecto, agregar logging centralizado, o implementar retry logic, debe hacer el cambio en decenas de puntos de llamada dispersos por el codebase. El patrón Gateway resuelve este problema estableciendo una clase o servicio único como mediador entre la aplicación y los proveedores de LLM: todo el código de la aplicación habla con el Gateway, y el Gateway habla con los proveedores. El resultado es que los cambios de proveedor, modelo, logging, rate limiting y circuit breaking se implementan una sola vez en el Gateway y se aplican automáticamente a todas las llamadas del sistema.

La `LLMGateway` class encapsula las responsabilidades que serían código duplicado si estuvieran dispersas: la selección del cliente correcto por proveedor (Anthropic, OpenAI, Google), el logging estructurado de cada llamada (tokens usados, costo calculado, latencia, feature que originó la llamada), el retry con backoff exponencial para errores transitorios, el circuit breaker para aislar proveedores con fallas, y el seguimiento del gasto acumulado contra el límite mensual configurado. Cada llamada al Gateway registra estos datos automáticamente, sin que el código de la aplicación deba implementarlos.

La sección de configuración del Gateway es crítica: la selección del modelo, el proveedor, y los límites de gasto son parámetros de configuración que deben poder cambiarse sin modificar el código de la aplicación. Una clase `LLMConfig` con los campos `provider`, `model`, `max_tokens`, `temperature`, y `monthly_budget_usd` —cargada desde un archivo YAML versionado en Git— permite cambiar el modelo por defecto de `claude-3-5-sonnet-20241022` a `claude-3-5-haiku-20241022` modificando una línea en el YAML, sin tocar el código del Gateway. Este nivel de configurabilidad es especialmente valioso durante la optimización de costos: permite comparar el comportamiento del sistema con diferentes modelos sin cambios de código.

LiteLLM Proxy lleva el patrón al extremo en arquitecturas de microservicios: en lugar de una clase gateway en la aplicación, es un servicio independiente que expone la API de OpenAI como interfaz unificada y traduce internamente a cualquier proveedor configurado. Cualquier cliente que entiende la API de OpenAI puede hablar con LiteLLM Proxy y obtener respuestas de Anthropic, Google, o cualquier modelo de código abierto via Ollama, sin ningún cambio en el código cliente. La ventaja para equipos grandes es que el Proxy puede desplegarse como un servicio central que el equipo de plataforma mantiene, mientras los equipos de producto consumen la API unificada sin gestionar credenciales ni lógica de retry.

## Componentes técnicos del patrón Gateway

- **LLMGateway class:** constructor que inicializa los clientes por proveedor y carga la configuración; método `complete(prompt, config, metadata)` como punto único de entrada; routing interno por `config.provider` al cliente correspondiente; el `metadata` dict (feature, request_id, user_id) se inyecta en cada log estructurado.
- **Logging automático en el Gateway:** cada llamada loggea `model`, `provider`, `input_tokens`, `output_tokens`, `cost_usd`, `latency_ms`, `cache_hit`, `feature`, `request_id` en JSON; el Gateway es el único lugar donde este log se emite, eliminando la duplicación.
- **Rate limiting en el Gateway:** `asyncio.Semaphore(MAX_CONCURRENT_CALLS)` limita la concurrencia por proveedor; `asyncio.sleep` con backoff exponencial cuando el proveedor devuelve 429; el Gateway absorbe la complejidad del rate limiting y expone una interfaz simple al código de la aplicación.
- **Límite de gasto mensual:** contador `self._monthly_spend` acumulado en cada llamada; `if self._monthly_spend + estimated_cost > self.config.monthly_budget_usd: raise BudgetExceededError()` antes de la llamada; reiniciar el contador al inicio de cada mes mediante un job scheduled; alertar cuando el gasto supera el 80% del límite.
- **LiteLLM Proxy como alternativa:** servicio independiente con UI web de configuración, soporte para más de cien modelos, logging centralizado, rate limiting por equipo o feature; ideal para organizaciones con múltiples equipos consumiendo LLMs y necesidad de control centralizado de costos y acceso.

> **Nota del Arquitecto:** El patrón Gateway resuelve el problema de la dispersión de código de infraestructura, pero introduce un punto único de acoplamiento que puede convertirse en un cuello de botella si no se diseña con las consideraciones de rendimiento correctas. El Gateway debe ser stateless (el estado de la sesión o el historial conversacional no pertenecen al Gateway), debe ser async-first para no bloquear el event loop, y debe tener tests de integración que verifican el comportamiento correcto cuando el proveedor devuelve errores, rate limits, y timeouts. Un Gateway sin tests de fallo es más peligroso que no tener Gateway: concentra el riesgo en un solo punto.

El Gateway es el lugar correcto para implementar cross-cutting concerns del sistema de LLM: logging, retry, rate limiting, cost tracking, y circuit breaking. Centralizar estas responsabilidades en el Gateway mantiene el código de la aplicación limpio y enfocado en la lógica de negocio, mientras el Gateway garantiza que la infraestructura de resiliencia y observabilidad se aplica consistentemente a todas las llamadas.

---

**Principio de arquitectura:** El patrón Gateway convierte los cross-cutting concerns del sistema LLM —logging, retry, rate limiting, cost tracking, circuit breaking— en responsabilidades centralizadas que se implementan una vez y se aplican a todas las llamadas; la alternativa de implementar estos concerns en cada punto de llamada al LLM es código duplicado que diverge con el tiempo.
