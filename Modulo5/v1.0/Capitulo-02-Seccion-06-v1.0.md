# Módulo 5 – Capítulo 02 – Sección 06

## Cierre: buenas prácticas para consumir APIs de LLM en producción

Llevar un sistema que consume APIs de LLM desde un prototipo funcional hasta un servicio de producción confiable requiere más que hacer que el "camino feliz" funcione correctamente. Las APIs de LLM son dependencias externas con tres características que las distinguen de cualquier otra dependencia de un sistema web: latencia variable que puede ir de 50 milisegundos a 30 segundos en la misma aplicación; costo por uso que puede dispararse ante errores de programación como loops sin límite o prompts sin control de longitud; y comportamiento probabilístico donde la misma entrada puede producir salidas diferentes. Cada una de estas características requiere disciplinas de ingeniería específicas que no se necesitan cuando la dependencia es una base de datos relacional con latencia de 5 milisegundos y comportamiento determinista.

La primera disciplina es la resiliencia. Todo el manejo de errores desarrollado en la sección anterior —retry con backoff exponencial, diferenciación entre errores retryables y permanentes, timeouts explícitos en conexión y lectura— debe estar encapsulado en una capa de integración única, no disperso en cada punto de llamada de la aplicación. La forma más simple de implementar esto es un wrapper de cliente: una función o clase `LLMClient` con un método `complete()` que internamente aplica el retry, el logging y el manejo de errores, y que todos los módulos de la aplicación usan en lugar del SDK directamente. Esta centralización tiene tres beneficios: los bugs de resiliencia se corrigen en un solo lugar, el logging es consistente en toda la aplicación, y el cambio de proveedor requiere modificar solo el wrapper.

La segunda disciplina es la gestión activa del costo. Además de las estrategias de la sección anterior, los límites de gasto configurables en la consola del proveedor son la red de seguridad contra escenarios catastróficos: OpenAI y Anthropic permiten configurar alertas por email y por webhook cuando el gasto mensual supera umbrales definidos (50%, 80%, 100% del presupuesto). Esta protección es especialmente importante en los primeros meses de un proyecto, cuando los bugs de contexto o los loops inadvertidos pueden generar cargos significativos antes de ser detectados. El uso de API keys separadas por ambiente —desarrollo, staging y producción con límites de gasto diferenciados— evita que los experimentos de desarrollo consuman la cuota de producción.

La tercera disciplina es la trazabilidad. Versionar los prompts como código —almacenados en archivos en el repositorio con identificadores de versión, revisados en PRs, con un changelog que documenta qué cambió y por qué— es tan importante como versionar el código de aplicación. El comportamiento de un sistema de IA está determinado en igual medida por el código Python que lo orquesta y por los prompts que guían al modelo; un cambio de prompt sin versionar es un cambio de comportamiento sin trazabilidad, el tipo de cambio que produce los incidentes más difíciles de diagnosticar en producción porque el sistema sigue respondiendo sin errores de runtime mientras la calidad se degrada silenciosamente.

La cuarta disciplina es el testing sin costo real. Las llamadas al LLM en tests unitarios deben reemplazarse por mocks del cliente que devuelven respuestas predefinidas: `mocker.patch.object(client, 'messages')` con un valor de retorno configurado al objeto Message que el test necesita. Esta práctica hace los tests rápidos, gratuitos, reproducibles y ejecutables en cualquier entorno sin credenciales de API. Las llamadas reales al LLM se reservan para los tests de integración y de evaluación de calidad, que se ejecutan bajo demanda y no en cada commit.

## Buenas prácticas consolidadas

- **Wrapper de cliente con observabilidad centralizada:** encapsular el SDK del proveedor en una función o clase que añade logging, métricas y manejo de errores; toda la aplicación usa este wrapper, no el SDK directamente.
- **Validación de salida estructurada:** si se espera JSON, validar con Pydantic o `json.loads()` dentro de un try/except e implementar al menos un reintento con instrucción de corrección antes de propagar el error al llamante.
- **Límites de gasto configurables:** configurar alertas en la consola del proveedor al 50%, 80% y 100% del presupuesto mensual, y usar API keys separadas con límites diferenciados por ambiente.
- **Separación de ambientes:** claves distintas para desarrollo, staging y producción, con límites de gasto que reflejan el volumen esperado de cada ambiente y evitan contaminación de cuota.
- **Testing sin costo real:** mocks del cliente LLM en tests unitarios para toda la lógica de Python; llamadas reales reservadas para tests de evaluación de calidad ejecutados bajo demanda en pipelines de CI con triggers condicionales.

La simplicidad en el código de integración —funciones pequeñas con responsabilidad única, validación explícita de entrada y salida, manejo deliberado de errores— no es una cuestión estética sino el predictor más confiable de que el sistema podrá diagnosticarse y mantenerse cuando sucedan los problemas que inevitablemente suceden en producción. El capítulo siguiente aborda la siguiente capa del stack: los frameworks de orquestación que emergen cuando los flujos de múltiples pasos justifican una abstracción adicional sobre el SDK puro.

*"Any fool can write code that a computer can understand. Good programmers write code that humans can understand."* — Martin Fowler. En AI Engineering, esto se traduce en que el código de integración con APIs de LLM debe ser tan legible y mantenible como cualquier otro código de producción, independientemente de la complejidad del modelo que orquesta.
