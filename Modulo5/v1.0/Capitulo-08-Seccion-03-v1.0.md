# Módulo 5 – Capítulo 08 – Sección 03

## Logging estructurado: prompts, respuestas, tokens y latencia

El logging en sistemas de IA trasciende el rol tradicional del logging en sistemas web —registrar eventos de ciclo de vida del servidor, errores de aplicación, accesos HTTP. En sistemas de IA, el log de cada llamada al LLM es simultáneamente un registro operacional para diagnóstico de incidentes, un registro de evaluación para detectar degradaciones de calidad, y potencialmente datos de entrenamiento para mejoras futuras del sistema. Esta triple función del log requiere que su diseño sea deliberado desde el inicio: la estructura, los campos, el nivel de detalle y la política de retención no son decisiones técnicas menores sino decisiones de producto que afectan múltiples aspectos del ciclo de vida del sistema.

La estructura mínima de un log de llamada al LLM debe incluir los campos que permiten responder las tres preguntas más frecuentes del diagnóstico: ¿qué llamada fue? (`request_id`, `trace_id`, `timestamp`), ¿qué pasó en términos de recursos? (`model`, `input_tokens`, `output_tokens`, `cached_tokens`, `latency_ms`, `cost_usd`, `finish_reason`), y ¿quién lo pidió en qué contexto? (`user_id`, `session_id`, `feature`, `prompt_version`). El campo `feature` —que identifica qué funcionalidad del producto generó la llamada— es especialmente valioso para el análisis de costos y calidad desagregado por feature, que es la granularidad necesaria para tomar decisiones de optimización: "el feature de resumen de emails cuesta $2.400/mes y tiene un score de faithfulness de 0.84" es una afirmación accionable; "el sistema de IA cuesta $15.000/mes" no lo es.

El nivel de detalle del log varía según el ambiente y las necesidades de diagnóstico. En desarrollo, es valioso loggear el prompt completo y la respuesta completa para facilitar la iteración rápida. En producción, loggear solo la metadata (tokens, latencia, costo, request_id) por defecto y el prompt completo solo para debugging específico activable via feature flag tiene sentido por tres razones: reduce el volumen de datos almacenados, limita la exposición de PII que puede estar en los prompts del usuario, y reduce el costo de almacenamiento que para sistemas de alto volumen puede ser significativo. La política de retención diferenciada —metadata de llamadas 90 días, prompts y respuestas 7 a 30 días, eventos de seguridad un año— es la práctica estándar que balancea utilidad analítica con costo de almacenamiento y compliance de privacidad.

Los logs de seguridad merecen un stream separado con retención extendida y acceso restringido por rol. Los intentos de prompt injection detectados, las respuestas que activaron filtros de contenido, las consultas de usuarios con patrones anómalos (volúmenes muy altos de requests, patrones de consulta que sugieren scraping del sistema, consultas que incluyen PII de terceros), y cualquier evento que requiera revisión de compliance son candidatos para este stream separado. La separación evita que los logs de seguridad se mezclen con los logs operacionales donde tienen menor visibilidad, y permite que el equipo de seguridad tenga acceso a su stream sin acceder al stream operacional completo.

## Aspectos técnicos del logging estructurado para IA

- **Logger JSON con structlog:** `import structlog; log = structlog.get_logger(); log.info("llm_call", model=model, input_tokens=usage.input_tokens, output_tokens=usage.output_tokens, latency_ms=elapsed, cost_usd=cost, feature=feature_name)` genera JSON parseable automáticamente.
- **Nivel de detalle configurable:** variable de entorno `LOG_FULL_PROMPTS=false` en producción por defecto; activable temporalmente para debugging con `LOG_FULL_PROMPTS=true` y filtro opcional por `user_id` o `session_id` específico para no exponer prompts de todos los usuarios.
- **Retención diferenciada:** metadata de llamadas (tokens, latencia, costo) → 90 días; prompts y respuestas → 7-30 días; eventos de seguridad → 1 año; implementada con lifecycle policies en S3, CloudWatch Logs o GCS.
- **Logs de seguridad separados:** stream dedicado para intentos de prompt injection, activaciones de filtros de contenido, patrones de consulta anómalos; retención extendida de 1 año; acceso controlado por IAM role independiente del acceso a los logs operacionales.
- **Campos de negocio en el log:** `feature`, `user_plan`, `locale`, `experiment_id` añadidos al log de cada llamada permiten queries de análisis de costo y calidad desagregado por dimensión de negocio desde el sistema de logging sin necesidad de un data warehouse adicional.

Los logs de producción de un sistema de IA son el activo de datos más rico que el equipo genera: cada log contiene información sobre el comportamiento del usuario, el rendimiento del modelo, el costo de la operación, y la calidad de la respuesta. Su estructura correcta desde el inicio es la diferencia entre tener datos que permiten tomar decisiones de mejora y tener texto sin estructura que solo sirve para leer en emergencias.

---

**Idea central:** Los logs de producción de un sistema de IA son simultáneamente datos de operación para el diagnóstico de incidentes, datos de evaluación para detectar degradaciones de calidad, y datos de entrenamiento potencial para mejoras futuras; su estructura y completitud impactan múltiples equipos durante todo el ciclo de vida del sistema.
