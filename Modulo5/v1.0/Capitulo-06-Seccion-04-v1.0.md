# Módulo 5 – Capítulo 06 – Sección 04

## Despliegue continuo: blue-green, canary y feature flags para modelos

El principio de despliegue progresivo —nunca pasar del 0% al 100% del tráfico en un solo paso— aplica con especial fuerza a sistemas de IA porque la evaluación offline sobre datasets curados no captura todo el espacio de queries reales del tráfico de producción. Un dataset de 200 casos representa una muestra representativa pero finita del comportamiento del sistema; el tráfico real puede incluir patrones de consulta que el dataset no tiene, y el comportamiento del nuevo modelo o prompt sobre esos patrones solo puede observarse cuando reciben tráfico real. El despliegue gradual es el mecanismo que permite observar el comportamiento real con impacto acotado —el 5% del tráfico en lugar del 100%— y revertir antes de que el problema escale.

El blue-green deployment para sistemas de IA mantiene dos entornos de producción con configuraciones diferentes: el entorno activo (blue) con la versión actual del modelo y prompt, y el entorno preparado (green) con la nueva versión. La transición ocurre cuando el entorno green ha sido validado con métricas de calidad satisfactorias en un período de observación suficiente: el balanceador de carga o el DNS redirige el 100% del tráfico de blue a green en un momento controlado. La ventaja es la reversión instantánea: si las métricas del entorno green se degradan después del flip, volver al entorno blue requiere cambiar la configuración del balanceador de carga, no un redeploy. La desventaja es el costo de mantener dos entornos completos, incluyendo sus dependencias de bases de datos, cachés y servicios auxiliares.

El canary deployment expone la nueva versión a un porcentaje creciente del tráfico real con monitorización continua de métricas de calidad. La secuencia típica es 5% → 25% → 50% → 100%, con períodos de observación de 30 minutos a 24 horas entre cada escalada según el riesgo del cambio. En Kubernetes, `HorizontalPodAutoscaler` con dos deployments (stable y canary) y configuración de peso en el Ingress —nginx o Istio— distribuye el tráfico porcentualmente entre los dos deployments. Argo Rollouts automatiza este proceso con la estrategia `canary`: define los pasos de escalado, configura el análisis de métricas en Prometheus, y ejecuta automáticamente el rollback si las métricas superan los umbrales de degradación definidos.

El shadow mode es una variante especialmente valiosa para evaluaciones de alto riesgo: ejecuta la nueva versión del pipeline en paralelo con la versión de producción, sin afectar la respuesta que llega al usuario, y compara las salidas de ambas versiones para evaluar la nueva antes de cualquier exposición de tráfico real. En shadow mode, el 100% de los requests se procesan por la versión de producción (cuya respuesta se envía al usuario) y simultáneamente por la versión candidata (cuya respuesta se descarta pero se evalúa y loggea). Esta técnica permite acumular evidencia de comportamiento del candidato sobre el tráfico real sin ningún riesgo de impacto al usuario.

## Aspectos técnicos del despliegue progresivo para modelos

- **Canary con Argo Rollouts:** estrategia `canary` con pasos definidos, `analysis.templates` que leen métricas de calidad desde Prometheus, y `progressDeadlineSeconds` que define cuánto tiempo esperar en cada step antes de escalar o revertir automáticamente.
- **A/B testing de modelos:** `user_id % 2 == 0` → modelo A; `user_id % 2 == 1` → modelo B; logging del modelo usado como campo en cada request para análisis diferencial de métricas de negocio (engagement, resolución en primer contacto, CSAT) y de calidad.
- **Shadow mode con asyncio:** `await asyncio.gather(production_call(messages), shadow_call(messages), return_exceptions=True)`; la respuesta de producción se devuelve al usuario; la respuesta shadow se loggea para análisis diferencial sin impacto en latencia percibida.
- **Rollback automático basado en métricas:** Argo Rollouts con `successCondition: result[0] >= 0.80` sobre una PromQL query de la métrica de calidad; si la condición no se cumple en la ventana de análisis, el rollback se ejecuta automáticamente sin intervención humana.
- **Registro de experimentos:** cada despliegue canary se registra con `experiment_id`, fechas de inicio y fin, porcentaje de tráfico, modelo y versión de prompt exactos, y métricas resultantes; este registro histórico es la base de conocimiento de qué cambios mejoran el sistema.

El despliegue gradual no es una práctica avanzada reservada para sistemas maduros: es la práctica mínima responsable para cualquier sistema de IA con usuarios reales, porque el comportamiento del modelo sobre el tráfico real nunca se puede predecir completamente con la evaluación offline.

---

**Para recordar:** El despliegue gradual no es opcional en sistemas de IA de producción: el comportamiento de un nuevo modelo o prompt sobre el tráfico real nunca se puede predecir completamente con datasets de evaluación offline, y la exposición gradual es el mecanismo que protege a todos los usuarios de una regresión masiva ante un cambio que pasó el pipeline de CI pero falla en producción.
