# Módulo 5 – Capítulo 06 – Sección 03

## Gestión de versiones de prompts, modelos y configuraciones

Los prompts son código. Esta afirmación, aunque simple, tiene consecuencias prácticas profundas: si un prompt determina el comportamiento del sistema tanto como cualquier función Python, debe versionarse con el mismo rigor, revisarse en PRs con el mismo proceso de aprobación, y trackearse en el historial de cambios con el mismo nivel de documentación. La diferencia entre un sistema de IA donde los prompts son texto informal editado en una consola web sin historial y uno donde los prompts son archivos versionados en Git con diff visible, revisión de pares y changelog documentado es la diferencia entre un sistema que no puede diagnosticarse cuando el comportamiento cambia y uno que puede.

La estrategia más simple y más efectiva es almacenar los prompts como archivos de texto en el repositorio Git: `prompts/system_prompt_v2.jinja2`, `prompts/extraction_prompt_v1.txt`. Un archivo de configuración mapea el nombre lógico a la versión activa: `config/prompt_versions.yaml: {system_prompt: "v2", extraction_prompt: "v1"}`. Cambiar de una versión de prompt a otra requiere editar el archivo de configuración, lo que crea un commit con diff visible, fecha exacta del cambio, autor, y mensaje que documenta el motivo. El `git diff` entre dos commits muestra exactamente qué texto cambió en el prompt, con las mismas herramientas de comparación que se usan para cualquier otro cambio de código. Esta visibilidad es invaluable cuando un comportamiento inesperado aparece en producción y hay que determinar qué cambio lo introdujo.

El versionado semántico aplicado a prompts sigue la lógica MAJOR.MINOR.PATCH adaptada. MAJOR se incrementa cuando el prompt cambia el comportamiento observable del sistema de forma significativa: nueva tarea, nuevo formato de salida obligatorio, cambio de idioma, eliminación de una capacidad previa. MINOR se incrementa cuando se añaden instrucciones que extienden el comportamiento sin cambiar el comportamiento existente: nuevos ejemplos few-shot, instrucciones adicionales para casos borde. PATCH se incrementa para correcciones sin impacto en el comportamiento: ortografía, claridad de redacción, reorganización de párrafos. Esta taxonomía hace que el número de versión comunique el riesgo del cambio antes de leer el diff.

Las configuraciones del modelo —`model_id`, `temperature`, `max_tokens`, `top_p`— deben vivir en archivos de configuración separados del código Python (`config/llm_config.yaml`) y ser inyectadas al servicio como variables de entorno en producción. Esta separación permite cambiar el modelo activo, ajustar la temperatura, o aumentar el límite de tokens sin modificar el código de la aplicación: una práctica especialmente valiosa cuando es necesario cambiar rápidamente de proveedor ante una degradación o para probar un nuevo modelo. Usar el identificador de modelo con fecha exacta —`claude-3-5-sonnet-20241022` en lugar de `claude-3-5-sonnet`— es la garantía de que el comportamiento del sistema no cambia sin que el equipo lo decida explícitamente, incluso si el proveedor actualiza el alias.

## Aspectos técnicos del versionado de prompts y modelos

- **Almacenamiento en Git como archivos:** prompts en `prompts/` como archivos `.jinja2` o `.txt`; el diff de un cambio de prompt es visible en el PR con el mismo `git diff` que cualquier cambio de código; el historial de Git registra la evolución de cada prompt con fecha y autor.
- **Registro en plataforma de prompts (alternativa):** LangSmith Prompt Hub o Langfuse Prompt Management permiten a no-programadores editar prompts sin acceso al repositorio, con versionado y rollback visual; adecuado cuando PMs o especialistas de dominio deben poder iterar sobre prompts sin un PR.
- **Modelo pinado por identificador completo:** `claude-3-5-sonnet-20241022` o `gpt-4o-2024-08-06` en lugar de aliases sin fecha; previene cambios silenciosos de comportamiento cuando el proveedor actualiza el modelo al que apunta el alias.
- **Config-as-code para parámetros de inferencia:** `config/llm_config.yaml` con todos los parámetros del LLM; cargado al inicio del servicio y validado con Pydantic Settings antes de aceptar tráfico; cambios en este archivo generan un PR con diff visible.
- **Changelog de prompts:** `prompts/CHANGELOG.md` con entradas por versión que documentan qué cambió, por qué se hizo el cambio, y cuál fue el impacto medido en la suite de evaluación; crea el historial institucional del sistema de prompts que es invaluable cuando hay rotación en el equipo.

El principio unificador es que cualquier elemento que determina el comportamiento del sistema —código Python, prompts, configuración del modelo, parámetros de inferencia— debe ser versionable, auditable y revertible. Un sistema donde el comportamiento puede cambiar sin trazabilidad en el historial de versiones es un sistema que no puede diagnosticarse ni mejorar de forma deliberada.

---

**Principio rector:** Un prompt sin versión en un sistema de producción es un riesgo de debugging: cuando el comportamiento cambia inesperadamente, la incapacidad de correlacionar el cambio con un commit específico convierte el diagnóstico en arqueología de código sin evidencia documental.
