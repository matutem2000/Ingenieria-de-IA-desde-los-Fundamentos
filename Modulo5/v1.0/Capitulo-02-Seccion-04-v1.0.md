# Módulo 5 – Capítulo 02 – Sección 04

## Gestión de errores: rate limiting, timeouts y reintentos con backoff exponencial

Las APIs de LLM son dependencias externas con disponibilidad imperfecta: el SLA típico del 99.5% de los proveedores principales equivale a hasta 44 horas de indisponibilidad acumulada por año, y las degradaciones parciales —donde el servicio responde pero con latencia elevada o tasa de error aumentada— ocurren con mayor frecuencia que las interrupciones completas. Un sistema de producción que no trata los errores transitorios como ciudadanos de primera clase convierte cada degradación del proveedor en una indisponibilidad del servicio propio, propagando hacia arriba un problema que podría haberse absorbido con una estrategia de reintento correctamente implementada.

Los errores que produce una API de LLM se dividen en dos categorías con estrategias de manejo radicalmente diferentes. Los errores retryables —429 (rate limit excedido), 500/502/503 (error interno del servidor), 529 (sobrecarga temporal, específico de Anthropic), y timeouts de conexión o lectura— son transitorios: el mismo request puede tener éxito si se reintenta después de un tiempo de espera. Los errores no retryables —400 (parámetros inválidos), 401 (API key ausente o revocada), 422 (contenido que viola políticas de uso)— son permanentes: reintentar el mismo request producirá el mismo error, por lo que el reintento automático solo desperdicia recursos y cuota. Confundir estas categorías —reintentar un 401 o no reintentar un 429— es un error de implementación frecuente con consecuencias operacionales.

La respuesta correcta a un error 429 no es reintentar inmediatamente sino esperar el tiempo indicado en el header `Retry-After` cuando está presente, o aplicar backoff exponencial con jitter cuando no lo está: `wait = min(cap, base * 2^n) + random.uniform(0, 1)`. El jitter aleatorio es esencial: sin él, múltiples workers que fallan simultáneamente ante el mismo rate limit reintentan al mismo tiempo y amplifican el problema en lugar de distribuirlo en el tiempo. La biblioteca `tenacity` en Python implementa este patrón con una API declarativa: `@retry(wait=wait_exponential(multiplier=1, min=4, max=60), stop=stop_after_attempt(5), retry=retry_if_exception_type((RateLimitError, APIStatusError)))`. Los SDKs oficiales de OpenAI y Anthropic ya incluyen retry automático con backoff por defecto (2 reintentos), pero para sistemas de alto volumen o con requisitos de resiliencia específicos, configurar la estrategia con `tenacity` da control total sobre el número de intentos, el tipo de backoff y el logging de cada intento fallido.

Los timeouts deben configurarse en dos niveles independientes: el timeout de conexión (tiempo para establecer la conexión TCP, típicamente 10-30 segundos) y el timeout de lectura (tiempo para recibir la respuesta completa o el primer byte en streaming, típicamente 60-300 segundos dependiendo de la longitud máxima esperada de las respuestas). Usar un timeout único sin diferenciación entre conexión y lectura puede resultar en que respuestas largas sean truncadas por un timeout de lectura demasiado corto, o que el sistema espere indefinidamente si la conexión nunca se establece. `httpx.Timeout(connect=10.0, read=120.0, write=10.0, pool=5.0)` da granularidad completa sobre cada fase de la conexión HTTP.

## Puntos críticos en gestión de errores de API

- **Backoff exponencial con jitter:** la fórmula `wait = min(cap, base * 2^n) + random(0, 1)` distribuye los reintentos en el tiempo; el parámetro `cap` previene esperas excesivas (ej. `cap=60` segundos); el jitter aleatorio evita el "thundering herd" cuando múltiples workers fallan simultáneamente.
- **Diferenciación por categoría de error:** errores 400, 401 y 422 se propagan inmediatamente como errores permanentes; errores 429, 500, 502, 503 y 529 se reintenten con backoff; timeouts se reintenten con backoff pero con menor número de intentos para no bloquear recursos por demasiado tiempo.
- **Circuit breaker para degradaciones prolongadas:** después de N fallos consecutivos en una ventana de tiempo, el circuit breaker abre y rechaza inmediatamente las llamadas durante un período de cooldown, devolviendo un error rápido o activando un fallback; el capítulo 10 desarrolla este patrón en detalle.
- **Dead letter queue en sistemas asíncronos:** mensajes que fallan tras el máximo de reintentos se enrutan a una DLQ (SQS, RabbitMQ) para inspección manual en lugar de perderse silenciosamente; es la red de seguridad para requests que ningún número de reintentos puede salvar.
- **Logging contextual de errores:** incluir en cada log de error el `request_id` del proveedor, el número de intento, el modelo usado, los tokens del prompt, y el tipo de error específico facilita el diagnóstico retrospectivo en sistemas de alta concurrencia.

La gestión de errores no es una funcionalidad que se añade después de que el sistema funciona: es una dimensión de diseño que se decide desde el primer sprint. El siguiente paso es comprender el costo de las llamadas al LLM y cómo gestionarlo activamente con conteo de tokens, caché de prompts y elección estratégica del modelo para cada tarea.

**Para recordar:** Un sistema que no maneja correctamente los errores transitorios de una API externa no es un sistema de producción; la resiliencia ante fallos del proveedor debe diseñarse desde el primer sprint, con distinción clara entre errores retryables y no retryables, backoff con jitter y timeouts explícitos en ambas fases de la conexión.
