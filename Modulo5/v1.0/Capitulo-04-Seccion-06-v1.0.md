# Módulo 5 – Capítulo 04 – Sección 06

## Cierre: integración de IA sin reescribir el sistema existente

La narrativa más peligrosa en la adopción de IA en organizaciones con sistemas existentes es la de "hay que reescribir todo para poder usar IA de forma correcta". Esta narrativa conduce a proyectos de reescritura de seis a doce meses que consumen presupuesto, congelan funcionalidades durante el desarrollo, y entregan el mismo valor que podría haberse entregado en seis semanas con integración incremental. La realidad operacional de cientos de proyectos de IA en producción es que las capacidades más valiosas se construyeron como capas sobre sistemas existentes, sin tocar el código heredado, usando los datos y la infraestructura que ya existían.

El principio guía es el strangler fig aplicado a IA: identificar las funciones de negocio que más se beneficiarían de capacidades de IA —redacción, clasificación, resumen, análisis, búsqueda semántica—, crear endpoints nuevos paralelos a los existentes que implementan esas funciones con LLMs, y migrar el tráfico gradualmente hacia los nuevos endpoints mientras los antiguos permanecen operativos como fallback. Un sistema CRM existente no necesita ser reescrito para añadir un asistente de redacción de emails de seguimiento: basta con un nuevo endpoint `POST /crm/emails/generate` que lee el historial del contacto de la base de datos existente, llama al LLM con ese contexto, y devuelve el borrador al frontend, que añade un botón "Generar con IA" que consume ese endpoint.

El adapter pattern para el LLM es la práctica de diseño más importante para la integrabilidad y la evolucionabilidad. Toda la interacción con el proveedor de LLM se encapsula en una única clase o módulo con una interfaz estable y semántica —`AIAssistant.generate_email_draft(contact, context)`, `DocumentAnalyzer.extract_key_points(document)`— que abstrae el proveedor, el modelo, el prompt y el framework de orquestación detrás de una interfaz de dominio. El código de negocio llama al servicio de IA a través de esta interfaz sin saber si detrás hay Claude o GPT-4, si el prompt cambió en la última iteración, o si el sistema ahora usa RAG en lugar de llamada directa. Cambiar el proveedor, actualizar el modelo o refactorizar el pipeline de IA requiere modificar solo el adaptador.

Los antipatrones que deben evitarse activamente en la integración son: integrar el SDK del LLM directamente en el ORM o en los modelos de dominio existentes, creando acoplamiento entre la lógica de negocio y los detalles del proveedor de IA; usar el objeto de sesión del framework web para almacenar el historial conversacional, que no escala más allá de un único proceso; y hardcodear el proveedor o el modelo en múltiples puntos del código, haciendo que cada migración requiera búsqueda y reemplazo en toda la base de código.

La validación del valor antes del compromiso de recursos es el argumento más poderoso para la integración incremental: un endpoint nuevo que añade IA a una función existente puede estar en producción para un subconjunto de usuarios en dos semanas, produciendo datos reales sobre si el caso de uso tiene el impacto esperado antes de invertir en integración profunda. El monitoreo diferencial —comparar métricas de negocio entre usuarios que usan las nuevas capacidades de IA y los que usan el flujo tradicional— provee la evidencia objetiva para decidir si escalar la inversión o pivotar hacia un caso de uso diferente.

## Buenas prácticas de integración incremental

- **Strangler fig para IA:** endpoints nuevos paralelos que implementan funciones de negocio con IA, sin modificar el código heredado; migración gradual del tráfico hacia los nuevos endpoints con feature flags; los endpoints antiguos permanecen como fallback hasta que la nueva versión alcanza el 100% de rollout.
- **Adapter pattern para el LLM:** una única clase o módulo que encapsula toda la interacción con el proveedor; la lógica de negocio llama al servicio de dominio, no al SDK del proveedor; cambiar el proveedor o el modelo requiere modificar solo el adaptador.
- **Separación de concerns:** la lógica de negocio no sabe que existe un LLM; llama a un servicio de "análisis" o "generación" que internamente usa el LLM, manteniendo la abstracción limpia, testeable con mocks, y reemplazable sin tocar el código de negocio.
- **Migraciones de schema sin bloqueo:** añadir columnas nullable para almacenar outputs del LLM en tablas existentes con `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` no bloquea la tabla en PostgreSQL; evitar `ALTER TABLE` que reescribe la tabla completa en sistemas con carga de producción.
- **Monitoreo diferencial:** comparar métricas de negocio entre el grupo de usuarios con IA habilitada y el grupo de control con el flujo tradicional; la evidencia diferencial es el argumento más sólido para continuar o pivotar la inversión.

La integración de IA en sistemas existentes no es un proyecto de reescritura sino una extensión incremental con validación continua de valor. El próximo capítulo aborda el testing de estos sistemas —cómo verificar que funcionan correctamente cuando la salida del LLM es no determinista y cuando los cambios del proveedor son imprevisibles.

---

*"Make it work, make it right, make it fast."* — Kent Beck. En AI Engineering aplicado a sistemas existentes, el orden es: hacer que la capacidad de IA funcione correctamente en un subconjunto del tráfico, luego integrarla limpiamente en la arquitectura con el adapter pattern y la separación de concerns, y finalmente optimizar para escala y costo cuando el valor está validado con datos reales.
