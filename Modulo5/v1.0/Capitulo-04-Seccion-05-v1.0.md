# Módulo 5 – Capítulo 04 – Sección 05

## Feature flags y despliegue gradual de capacidades de IA

Los feature flags —también llamados feature toggles— son la herramienta de control de riesgo más rápida disponible para sistemas de IA en producción: permiten activar o desactivar capacidades, cambiar parámetros de configuración o redirigir tráfico entre versiones de modelo en segundos, sin redeploy de código, sin ventana de mantenimiento, y con reversión instantánea ante cualquier señal de degradación. En el ciclo de vida de un sistema de IA, esta capacidad es especialmente valiosa porque los problemas de calidad son frecuentemente subtiles —el sistema continúa respondiendo sin errores de runtime mientras la calidad se degrada— y la velocidad de detección y rollback determina cuántos usuarios son expuestos al problema.

Los sistemas de feature flags modernos —LaunchDarkly, Unleash (open source), Flagsmith, AWS AppConfig— almacenan la configuración de los flags en un backend centralizado y la distribuyen a los servicios vía SDK con latencia de actualización de milisegundos a segundos, sin requerir redeploy. La evaluación de un flag es una llamada local al SDK que consulta el estado cacheado: `client.is_enabled("new-llm-model", context={"userId": user_id, "properties": {"plan": "enterprise"}})`. El contexto de evaluación permite targeting sofisticado: activar el flag solo para usuarios del plan enterprise, solo para un porcentaje determinístico de users (hasheado por user_id para que el mismo usuario reciba siempre el mismo tratamiento), o solo para una región geográfica específica.

En el contexto específico de IA, los feature flags tienen aplicaciones que no existen en sistemas de software tradicionales. El modelo de LLM activo puede ser un valor de configuración leído del sistema de flags en lugar de una constante en el código: `model_name = config_client.get_string("active_llm_model", "claude-3-5-sonnet-20241022")`. Cambiar el modelo para el 10% del tráfico para hacer A/B testing requiere actualizar el flag en la consola web, sin tocar código ni hacer un deploy. Desactivar un agente autónomo que está tomando decisiones erróneas —por ejemplo, un agente de booking que está creando reservas duplicadas— puede hacerse en menos de un minuto desde que se detecta el problema, reduciendo el número de usuarios afectados mientras se diagnostica y corrige la causa raíz.

El rollout gradual porcentual —exponer el nuevo sistema al 5% de usuarios, monitorear métricas de calidad durante 24 horas, escalar al 25%, luego al 50%, luego al 100%— es el patrón más seguro para lanzar cambios significativos en sistemas de IA. A diferencia del blue-green deployment que cambia del 0% al 100% en un momento, el rollout porcentual permite detectar problemas con un impacto acotado y revertir antes de escalar. La condición para que este patrón funcione es tener las métricas de calidad instrumentadas y visibles en tiempo real: si la tasa de feedback negativo del grupo de usuarios del 5% sube del 3% al 15%, el rollout se revierte antes de exponer al 95% restante.

## Aspectos técnicos del despliegue gradual con feature flags

- **Rollout porcentual determinístico:** hashear `user_id` y comparar con el umbral de porcentaje garantiza que el mismo usuario recibe siempre el mismo tratamiento (no cambia entre requests); esto es crítico para reproducibilidad de experimentos y coherencia de UX.
- **Flags de configuración de modelo:** `config.get_string("llm_model", default="claude-3-5-sonnet-20241022")` leído del sistema de flags en lugar de hardcodeado; permite cambiar el modelo sin deploy, con audit trail automático de quién hizo el cambio y cuándo.
- **Circuit breaker via feature flag:** integrar el sistema de flags con el sistema de alertas para desactivar automáticamente el flag cuando una métrica de calidad supera un umbral; la respuesta automatizada reduce el tiempo de exposición al problema de minutos a segundos.
- **Testing de ambas ramas:** implementar tests unitarios que ejerciten el código con el flag habilitado y con el flag deshabilitado; el código del flag deshabilitado tiende a deteriorarse silenciosamente si no se testea, comprometiendo la capacidad de rollback cuando se necesita.
- **Limpieza de flags obsoletos:** eliminar del código los flags que han alcanzado el 100% de rollout y han sido estables durante semanas; los flags obsoletos son deuda técnica que aumenta la complejidad del código sin aportar capacidad de control.

Los feature flags son la herramienta de resiliencia más rápida para sistemas de IA en producción: un rollback via flag tarda segundos mientras que un rollback via redeploy puede tardar minutos, y en una degradación activa cada segundo cuenta.
