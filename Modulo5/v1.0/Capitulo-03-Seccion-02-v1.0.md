# Módulo 5 – Capítulo 03 – Sección 02

## LangChain y LangGraph: cadenas, runnables, agentes con estado

LangChain es el framework de orquestación de IA más adoptado en la industria, con más de 90.000 estrellas en GitHub y un ecosistema de integraciones que cubre más de 200 vectorstores, herramientas y proveedores de LLM. Su arquitectura actual se organiza en cuatro paquetes con responsabilidades separadas: `langchain-core` contiene las interfaces base y el protocolo LCEL; `langchain` provee las cadenas y agentes de alto nivel; `langchain-community` concentra las integraciones de terceros mantenidas por la comunidad; y los paquetes específicos de proveedor —`langchain-openai`, `langchain-anthropic`, `langchain-google-genai`— encapsulan las integraciones con los SDKs nativos de cada uno. Esta modularidad permite instalar solo las dependencias que el proyecto necesita, en lugar del monolito que fue en sus versiones iniciales.

La columna vertebral del framework en su versión moderna es LCEL, LangChain Expression Language. LCEL implementa la interfaz `Runnable` con métodos `invoke(input)`, `stream(input)`, `batch(inputs)` y sus variantes async `ainvoke`, `astream`, `abatch`. El operador `|` conecta componentes que implementan `Runnable` en una secuencia: `chain = ChatPromptTemplate.from_messages([...]) | ChatAnthropic(model="claude-3-5-sonnet-20241022") | PydanticOutputParser(pydantic_object=MySchema)`. Cuando se llama `chain.invoke({"question": "..."})`, el framework gestiona internamente el formateo del template con las variables, la llamada al LLM con los parámetros configurados, el parseo de la respuesta según el schema Pydantic, y el retry con `OutputFixingParser` si el parseo falla. Cada paso recibe la salida tipada del paso anterior, lo que el framework verifica en tiempo de ejecución.

`RunnableParallel` y `RunnableBranch` extienden el modelo lineal hacia flujos más complejos. `RunnableParallel` ejecuta múltiples runnables en paralelo con asyncio y combina sus salidas en un diccionario: útil para llamar simultáneamente a múltiples recuperadores de datos o ejecutar el mismo query sobre diferentes modelos para comparación. `RunnableBranch` implementa routing condicional: evalúa una condición sobre la entrada y enruta hacia uno de varios runnables según el resultado, permitiendo flujos donde diferentes tipos de query reciben procesamiento diferenciado sin código imperativo explícito.

**LangGraph** es la extensión de LangChain para flujos cíclicos y agentes con estado persistente —el mecanismo de implementación para los agentes con memoria que el Módulo 4 describió arquitectónicamente. Donde LCEL modela flujos como cadenas lineales o DAGs acíclicos, LangGraph modela flujos como grafos dirigidos con nodos, aristas condicionales y estado compartido. Un grafo de LangGraph se define con `StateGraph(MyState)`, donde `MyState` es un TypedDict que representa el estado compartido entre nodos. Los nodos son funciones Python que reciben el estado completo y devuelven actualizaciones parciales: `def process_query(state: MyState) -> dict: ...`. Las aristas condicionales se añaden con `add_conditional_edges(node, routing_function, {"option_a": "node_a", "option_b": "node_b"})`, donde la función de routing decide hacia qué nodo avanzar según el estado actual. El `MemorySaver` persiste el estado entre ejecuciones del grafo en memoria o en una base de datos, haciendo posible los agentes con historial de sesión que retienen contexto entre sesiones separadas.

La observabilidad de LangGraph se integra de forma nativa con LangSmith cuando `LANGCHAIN_TRACING_V2=true` está configurado: cada nodo del grafo aparece como un span hijo en la traza jerárquica, mostrando el estado antes y después de cada nodo, los modelos llamados, y el routing condicional tomado en cada arista, lo que transforma el debugging de agentes complejos de una tarea artesanal en una tarea visual.

## Componentes principales de LangChain y LangGraph

- **`ChatPromptTemplate.from_messages()`:** define la estructura del prompt con slots para variables `{variable}` y para el historial conversacional `MessagesPlaceholder`; soporta formateo condicional de mensajes y reutilización entre cadenas.
- **Wrappers de LLM (`ChatOpenAI`, `ChatAnthropic`):** implementan la interfaz `Runnable` y encapsulan el SDK del proveedor; son intercambiables dentro de una cadena LCEL sin modificar los demás componentes.
- **`PydanticOutputParser` + `with_structured_output()`:** el método `with_structured_output(MySchema)` disponible en los wrappers modernos usa tool use o structured outputs del proveedor para garantizar JSON válido según el schema sin necesidad de parser manual.
- **`StateGraph` (LangGraph):** el grafo de estado donde cada nodo es una función Python con acceso al estado completo; `add_node()`, `add_edge()` y `add_conditional_edges()` construyen la topología del grafo de forma declarativa.
- **`MemorySaver` (LangGraph):** checkpointer que persiste el estado del grafo por `thread_id`, habilitando agentes con memoria de sesión; soportable con backends de base de datos para persistencia durable entre reinicios del servicio.

> **Nota del Arquitecto:** LangChain tiene historial de breaking changes significativos entre versiones mayores (v0.1 a v0.2, v0.2 a v0.3). La práctica de anclar la versión exacta en `requirements.txt` (`langchain==0.3.7`, `langchain-anthropic==0.3.2`) y revisar el changelog antes de actualizar no es paranoia sino experiencia acumulada de proyectos que sufrieron regresiones tras actualizaciones automáticas de dependencias. LangGraph, por ser una extensión más joven, tiene aún mayor velocidad de cambio de API.

La decisión de usar LangGraph en lugar de LCEL puro depende de un criterio concreto: si el flujo del agente necesita ciclos (llamar al LLM, evaluar el resultado, y volver a llamar al LLM con el resultado corregido) o ramificación condicional compleja que depende del estado acumulado entre pasos, LangGraph es la abstracción correcta. Si el flujo es una secuencia lineal de pasos sin ciclos, LCEL es suficiente y más simple de debuggear.

---

**Para recordar:** LangGraph implementa los agentes con estado que el Módulo 4 describió arquitectónicamente: el modelo de nodos-aristas-estado transforma las cadenas lineales de LCEL en grafos dirigidos con ciclos de reflexión, memoria persistente entre sesiones y routing condicional que habilita el comportamiento autónomo de los agentes.
