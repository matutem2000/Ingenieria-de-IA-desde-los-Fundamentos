# Módulo 5 – Capítulo 02 – Sección 01

## Anatomía de una llamada a la API: messages, system, role y contenido

Una llamada a la API de un LLM es, en esencia, un POST HTTP con un cuerpo JSON. Pero la semántica exacta de cada campo de ese JSON es el contrato sobre el que se construye toda la aplicación: si ese contrato se entiende superficialmente, los errores que emergen en producción son difíciles de diagnosticar porque ocurren en capas de abstracción muy alejadas del bug original. El campo que el desarrollador interpoló incorrectamente, el rol que está en el array equivocado, el límite de tokens que se ignora hasta que el modelo trunca una respuesta JSON a la mitad y rompe el parser: todos estos problemas tienen su raíz en una comprensión incompleta de la estructura del mensaje. Esta sección disecciona esa estructura con el nivel de detalle que la producción exige.

El campo `messages` es el núcleo de la llamada: un array ordenado de objetos donde el orden importa porque el modelo procesa los mensajes en secuencia y usa el historial para construir la respuesta. Cada objeto tiene al menos dos campos: `role` y `content`. El campo `role` define la perspectiva del mensaje dentro del diálogo —`system` para instrucciones globales de comportamiento, `user` para la entrada del usuario o del sistema externo que actúa como usuario, `assistant` para las respuestas previas del modelo que forman parte del historial conversacional. El campo `content` puede ser una cadena de texto simple para mensajes de texto puro, o un array de bloques de contenido para mensajes multimodales que mezclan texto, imágenes, audio y resultados de tool calls.

La semántica del rol `system` varía entre proveedores de forma que tiene consecuencias reales. En OpenAI, el mensaje de sistema es el primero del array `messages` con `role: "system"`; en Anthropic, el campo `system` vive fuera del array como campo independiente de primer nivel en el cuerpo del request, lo que habilita el prompt caching de ese contenido de forma independiente del historial conversacional. Esta diferencia estructural de Anthropic no es accidental: separar el system prompt del historial permite que las instrucciones estáticas del sistema —que raramente cambian entre turnos— se cacheen en el servidor y se reutilicen a costo reducido en llamadas sucesivas de la misma sesión. En Google Gemini, el campo equivalente es `systemInstruction` con la estructura `{parts: [{text: "..."}]}`.

El rol `assistant` en el array `messages` sirve para dos propósitos. El primero es mantener el historial de una conversación multi-turno: cada respuesta del modelo se agrega al array antes del siguiente mensaje del usuario, permitiendo que el modelo tenga contexto de los turnos previos. El segundo —específico de Anthropic— es el "pre-fill" o prefillado de respuesta: colocar un mensaje `assistant` con un prefijo parcial como `{` o ````json` al final del array instruye al modelo a continuar desde ese prefijo, garantizando que la respuesta comience con ese texto. El pre-fill es la técnica más confiable para forzar salida JSON sin depender de instrucciones en el prompt que el modelo puede ignorar.

## Conceptos clave de la estructura de mensajes

- **Campo `model`:** especifica el identificador exacto del modelo con versión (`claude-3-5-sonnet-20241022`, `gpt-4o-2024-08-06`), determinando capacidades, ventana de contexto y precio; nunca usar alias sin fecha que el proveedor puede actualizar silenciosamente.
- **Rol `system`:** establece el comportamiento, formato de salida, restricciones y persona del modelo; tiene mayor peso en el comportamiento que las instrucciones en mensajes `user`; en Anthropic vive fuera del array `messages` como campo de primer nivel.
- **Rol `assistant` para pre-fill:** en Anthropic, colocar `{"role": "assistant", "content": "{"}` como último elemento del array fuerza al modelo a comenzar la respuesta con `{`, garantizando salida JSON sin necesidad de parsear un JSON embebido en texto libre.
- **Bloques de contenido multimodal:** imagen en OpenAI como `{"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}`; en Anthropic como `{"type": "image", "source": {"type": "base64", "media_type": "image/jpeg", "data": "..."}}`.
- **Campo `stop_sequences`:** array de strings que detienen la generación cuando el modelo los produce; útil para delimitar secciones de salida estructurada (`</output>`, `###`) o prevenir que el modelo continúe generando después de un delimitador conocido.

> **Nota del Arquitecto:** El campo `max_tokens` es más crítico de lo que parece. Si el modelo está generando un JSON de respuesta y `max_tokens` se alcanza antes de que la respuesta esté completa, el JSON queda truncado e inválido —y el parser lanzará una excepción que puede enmascararse como un error del parser en lugar de un error de configuración. En sistemas donde la longitud de la respuesta es variable y difícil de predecir, establecer `max_tokens` con suficiente margen (típicamente 2-3x la longitud media esperada) y monitorear el campo `finish_reason` en cada respuesta detecta los truncados antes de que rompan el parseo silenciosamente.

La estructura del array `messages` es el contrato principal entre la aplicación y el modelo. Comprenderla en detalle —no asumir que todos los proveedores la implementan de la misma forma— es el primer paso hacia una integración robusta. La sección siguiente explora los parámetros de inferencia: los controles sobre el proceso de muestreo que determinan cuán deterministas o variadas son las respuestas del modelo y qué impacto tienen en el costo y la latencia.
