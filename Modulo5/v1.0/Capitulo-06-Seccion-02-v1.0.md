## Pipelines de evaluación automatizada en el ciclo de integración

Un pipeline de evaluación automatizada en CI es el componente que transforma la evaluación de calidad de una actividad manual y ocasional en un gate sistemático que ejecuta en cada cambio relevante, compara resultados con un baseline registrado, y produce una decisión binaria —aprobado o bloqueado— con evidencia objetiva. Sin este pipeline, la pregunta "¿este cambio de prompt mejora o degrada el sistema?" se responde con intuición y experiencia; con el pipeline, se responde con datos cuantificados sobre el mismo dataset que el sistema usa en producción.

La implementación con GitHub Actions es representativa del patrón: un workflow `.github/workflows/evaluate.yml` con trigger condicional sobre archivos relevantes, que instala las dependencias del proyecto, ejecuta el script de evaluación sobre el dataset curado, compara las métricas resultantes con los umbrales configurados en `eval_config.yaml`, y falla el job con código de salida 1 si alguna métrica cae por debajo del umbral, bloqueando el merge del PR. La integración con la API de GitHub permite que el pipeline publique automáticamente las métricas de evaluación como un comentario en el PR con una tabla de comparación baseline vs actual: el revisor ve directamente en el PR si el cambio mejoró la faithfulness en 0.03 puntos, degradó la answer relevancy en 0.01 puntos, y cómo se comporta el sistema en los 10 casos con mayor degradación.

El dataset de evaluación es el activo más crítico del pipeline, más que la herramienta de evaluación o el modelo evaluador. Un dataset pequeño pero representativo del dominio real —50 casos bien seleccionados que cubren los patrones de consulta más frecuentes y los casos borde conocidos— es más valioso que 500 casos genéricos que no reflejan el comportamiento real de los usuarios. La gestión del dataset requiere las mismas prácticas que el código: versionado en Git, revisión en PRs cuando se añaden casos, y crecimiento orgánico que incorpora los casos de fallo observados en producción. Cuando el dataset supera los 500 MB por la inclusión de embeddings pre-computados o documentos de contexto, DVC (Data Version Control) permite versionarlo en S3 o GCS con la misma semántica de Git, referenciando la versión exacta desde el pipeline de CI.

LangSmith Datasets y Langfuse Experiments proveen infraestructura cloud para el dataset y el pipeline de evaluación: el dataset se mantiene en la plataforma con versionado, y las evaluaciones se ejecutan contra él desde el pipeline de CI via el SDK de Python. La ventaja es que el historial de runs de evaluación queda registrado en la plataforma con visualización de tendencias de métricas a lo largo del tiempo, facilitando el análisis de cómo la calidad del sistema evoluciona con cada cambio. La desventaja es la dependencia de un servicio cloud externo y el costo asociado para datasets y volúmenes altos.

## Componentes principales del pipeline de evaluación

- **Script de evaluación centralizado:** `evaluate.py --dataset tests/eval/dataset.json --model claude-3-5-sonnet-20241022 --output results.json` ejecuta todos los casos, calcula métricas con RAGAS o DeepEval, y genera un reporte JSON estructurado con score por caso y métricas agregadas.
- **Comparación con baseline:** `baseline_metrics.json` en el repositorio con las métricas de la versión en producción; el script de comparación `compare.py --baseline baseline_metrics.json --current results.json --threshold 0.03` falla con código 1 si alguna métrica degrada más del umbral.
- **Comentario automático en PR:** el pipeline usa la API de GitHub para publicar una tabla Markdown con las métricas baseline vs actual en el PR, con las filas más degradadas destacadas; el revisor tiene toda la información sin salir de la interfaz de GitHub.
- **Dataset versionado con DVC:** para datasets con embeddings pre-computados, `dvc.yaml` y `dataset.dvc` referencian la versión exacta del dataset en S3; `dvc pull` en el pipeline de CI recupera la versión correcta del dataset antes de ejecutar la evaluación.
- **Paralelización de la evaluación:** dividir el dataset en N chunks con la estrategia `matrix` de GitHub Actions y ejecutar N jobs en paralelo reduce el tiempo total del pipeline de evaluación de minutos a segundos cuando el dataset tiene más de 100 casos y la paralelización de la API del proveedor lo permite.

> **Nota del Arquitecto:** El momento más valioso de un pipeline de evaluación en CI no es cuando bloquea un PR que degrada el sistema —que es su función principal y esperada— sino cuando aprueba con evidencia un cambio que el equipo tenía dudas sobre si era seguro desplegar. La confianza que da un pipeline que dice "este cambio de prompt mejoró faithfulness en 0.04 y no degradó ninguna métrica sobre el dataset de 150 casos" es cualitativamente diferente de la confianza que da la intuición del autor del PR.

El dataset de evaluación es el activo más valioso del pipeline de CI de IA; invertir en su crecimiento continuo —añadiendo casos de los fallos en producción— tiene mayor impacto en la confiabilidad del sistema que sofisticar las métricas de evaluación sobre un dataset estático.

---

**Buena práctica:** El dataset de evaluación es el activo más valioso del pipeline de CI de IA; invertir en su crecimiento continuo añadiendo casos de los fallos observados en producción tiene mayor retorno que sofisticar las métricas de evaluación sobre un dataset que no evoluciona con el comportamiento real del sistema.
