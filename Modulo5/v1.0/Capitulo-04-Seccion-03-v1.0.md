# Módulo 5 – Capítulo 04 – Sección 03

## Integración con bases de datos relacionales y documentales

Las aplicaciones de IA empresariales raramente operan sobre texto puro: necesitan datos del usuario almacenados en PostgreSQL, historial de transacciones en MySQL, documentos en MongoDB, o búsqueda full-text en Elasticsearch. La integración de estas fuentes de datos con el LLM es el puente entre el modelo y el contexto de negocio que hace que la respuesta sea relevante para ese usuario específico, en ese momento específico, con ese historial de interacciones. Un sistema de atención al cliente que no tiene acceso al historial de pedidos del usuario antes de construir el prompt no puede personalizar la respuesta; un asistente legal que no recupera los documentos relevantes del expediente solo puede ofrecer respuestas genéricas.

El patrón más común en aplicaciones conversacionales es la recuperación de datos del usuario antes de construir el prompt: una consulta SQL que obtiene el perfil, el historial de interacciones, el estado de la cuenta o los productos adquiridos, y lo serializa en texto o JSON estructurado que se inserta en el contexto del LLM. `SELECT u.name, u.plan, o.status, o.items FROM users u JOIN orders o ON u.id = o.user_id WHERE u.id = $1 ORDER BY o.created_at DESC LIMIT 5` seguido de un formateador que convierte los registros en texto enriquece el prompt con el contexto real del usuario en segundos. La clave es que esta consulta es parte de la preparación del prompt, no del manejo de la respuesta, y su latencia se suma a la latencia total del request de IA.

La integración con bases de datos vectoriales —pgvector, Qdrant, Chroma— implementa la capa de recuperación semántica del patrón RAG. pgvector merece atención especial: al ser una extensión de PostgreSQL, no requiere infraestructura adicional cuando el proyecto ya usa Postgres, y su integración con SQLAlchemy es directa. `CREATE EXTENSION IF NOT EXISTS vector; ALTER TABLE documents ADD COLUMN embedding vector(1536)` añade capacidad vectorial a una tabla existente. La búsqueda por similitud coseno usa el operador nativo: `ORDER BY embedding <=> $1::vector LIMIT 10`. Para proyectos que comienzan con RAG y no quieren gestionar un servicio de base de datos vectorial adicional, pgvector es el punto de entrada natural antes de migrar a Qdrant o Pinecone cuando el volumen o los requisitos de rendimiento lo justifiquen.

La escritura de resultados del LLM de vuelta en la base de datos debe tratarse con las mismas garantías de consistencia que cualquier escritura transaccional. Si el pipeline de IA clasifica un ticket de soporte y actualiza su categoría en la base de datos, esa actualización debe ocurrir en la misma transacción que cualquier otro cambio de estado del ticket: o se guarda el resultado completo del pipeline o no se guarda nada, evitando estados parciales difíciles de diagnosticar. El JSON que devuelve el LLM debe validarse con el schema Pydantic esperado antes de intentar insertarlo en la base de datos, rechazando y loggeando los casos donde el LLM devolvió un formato inesperado en lugar de insertar datos malformados silenciosamente.

La caché de resultados con Redis es la optimización más efectiva para queries frecuentes cuya respuesta del LLM es determinista para las mismas entidades: si la clasificación de la categoría de un producto no cambia entre requests del mismo producto, cachear el resultado con TTL alineado a la frecuencia de cambio del catálogo elimina llamadas redundantes al LLM. `redis.setex(f"classify:{product_id}", 3600, result)` con un TTL de una hora es apropiado para datos que cambian diariamente; `redis.setex(f"classify:{product_id}", 86400, result)` para datos que cambian semanalmente.

## Aspectos técnicos de la integración con bases de datos

- **pgvector con SQLAlchemy:** columna `Vector(1536)` en el modelo SQLAlchemy, operador `<=>` para distancia coseno en queries de búsqueda, índice `CREATE INDEX ON documents USING ivfflat (embedding vector_cosine_ops)` para búsqueda aproximada eficiente a escala.
- **SQLAlchemy async:** `AsyncSession` con `asyncpg` para no bloquear el event loop de asyncio durante consultas a la base de datos; `async with async_session() as session: result = await session.execute(select(User).where(User.id == user_id))` es el patrón estándar.
- **MongoDB para datos semiestructurados:** colección de logs de prompts y respuestas con schema `{request_id, model, input_tokens, output_tokens, latency_ms, prompt_text, response_text, created_at, user_id, feature}`; indexar `user_id` y `created_at` para queries frecuentes de historial.
- **Connection pooling:** `pool_size=10`, `max_overflow=20` en SQLAlchemy para no agotar las conexiones de la base de datos bajo carga concurrente; el pool debe configurarse antes del primer request de producción, no después de la primera crisis de conexiones agotadas.
- **Caché de resultados con Redis:** `redis.get(cache_key)` antes de la llamada al LLM; si existe el valor, devolverlo sin llamar al API; si no existe, llamar al LLM, almacenar el resultado con TTL apropiado y devolverlo; loggear cache hit/miss como métrica operativa.

Separar la capa de acceso a datos de la lógica de llamada al LLM con interfaces claras —repositorios o servicios de datos que exponen métodos semánticos como `get_user_context(user_id)` en lugar de queries SQL en el código del pipeline— permite testear cada capa independientemente con mocks y evita el acoplamiento entre el schema de la base de datos y los prompts.

---

**Buena práctica:** La separación entre la capa de recuperación de datos y la capa de llamada al LLM con interfaces semánticas es la práctica más impactante para la testeabilidad y el mantenimiento a largo plazo; los cambios en el schema de la base de datos o en la estructura del prompt no deben propagarse al código de la capa contraria.
