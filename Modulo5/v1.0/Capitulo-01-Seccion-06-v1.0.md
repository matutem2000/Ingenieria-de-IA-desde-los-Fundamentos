# Módulo 5 – Capítulo 01 – Sección 06

## Cierre: el stack mínimo viable para un AI Engineer

El síndrome del stack sobreingeniado es una patología recurrente en equipos que comienzan a construir con IA: ante la abundancia de herramientas disponibles, el equipo adopta LangChain para orquestación, LlamaIndex para recuperación, pgvector para almacenamiento vectorial, Langfuse para observabilidad, RAGAS para evaluación y Redis para caché semántica —todo antes de tener un solo usuario real. El problema no es que alguna de estas herramientas sea mala; es que cada una introduce dependencias, una curva de aprendizaje, versiones que actualizar y un punto potencial de fallo adicional. El stack sobreingeniado no falla por ser complejo sino por ser complejo demasiado pronto, antes de que la evidencia de producción justifique cada capa de abstracción.

El stack mínimo viable para construir y operar un sistema de IA en producción converge en un conjunto acotado de herramientas que resuelven los problemas fundamentales sin sobrecarga prematura. La base es el SDK oficial del proveedor: `openai`, `anthropic` o `google-generativeai`, con retry automático, tipado estricto y streaming incluidos. Sobre esta base se añade gestión segura de credenciales —`.env` más `python-dotenv` en desarrollo, un gestor de secretos en producción— y logging estructurado con Python `structlog` o el módulo estándar `logging` configurado en formato JSON, capturando como mínimo el modelo usado, los tokens de entrada y salida, la latencia, el costo estimado y el `request_id`. Este núcleo de tres elementos es suficiente para operar un sistema de IA en producción y diagnosticarlo cuando algo falla.

La primera extensión que se justifica casi siempre en el primer sprint, no como añadido tardío, es una herramienta de observabilidad: Langfuse (open source y self-hosteable con Docker Compose en menos de una hora) o LangSmith si el proyecto ya usa LangChain. Esta herramienta captura trazas de cada llamada al LLM con su prompt completo, la respuesta, los tokens, la latencia y el costo, creando el primer activo de observabilidad del sistema. Sin esta capa, el equipo opera ciegamente: no puede responder "¿cuánto costó el sistema ayer?", "¿qué porcentaje de llamadas están fallando?" ni "¿qué prompts están generando las respuestas de menor calidad?".

Las extensiones adicionales se añaden cuando la evidencia las justifica. Un framework de orquestación como LangChain o LlamaIndex se incorpora cuando el flujo supera los 3-4 pasos interdependientes y la implementación directa requiere más de 200 líneas de código para manejar correctamente todos los casos borde. Una base de datos vectorial se agrega cuando el volumen de documentos supera los 10.000 chunks o cuando la búsqueda semántica en memoria es demasiado lenta. Un sistema de evaluación automatizado con RAGAS o DeepEval se configura desde el primer sprint, pero sobre un dataset pequeño de 20-50 casos representativos, no como un sistema elaborado. La secuencia es siempre: operabilidad primero, luego escala, luego sofisticación.

## Componentes del stack mínimo viable

- **SDK del proveedor:** `openai`, `anthropic` o `google-generativeai` para las llamadas al modelo con tipado estricto, retry automático y soporte de streaming incorporado.
- **Gestión de secretos:** `.env` más `python-dotenv` en desarrollo local; Secret Manager o variables de entorno del CI/CD en producción; nunca hardcodear API keys en el código fuente.
- **Logging estructurado:** captura de modelo, tokens de entrada, tokens de salida, latencia, costo estimado, `request_id` y errores en formato JSON, almacenado en la plataforma de logging del cloud o en archivos locales.
- **Observabilidad básica:** Langfuse self-hosted o LangSmith para trazas de llamadas, costos acumulados, y comparación de versiones de prompts; se configura en el mismo sprint que el primer endpoint de IA.
- **Testing desde el primer día:** pytest con mocks del cliente LLM para unit tests de la lógica Python, y un dataset pequeño de casos representativos para regression testing; no un sistema elaborado, pero sí la infraestructura básica desde el inicio.

El conjunto de herramientas descrito en este capítulo —APIs, SDKs, gestión de credenciales, observabilidad básica y testing— es el sustrato sobre el que se construyen todos los sistemas del módulo. Los capítulos siguientes profundizan en cada aspecto: el Capítulo 2 disecciona el protocolo de comunicación con los modelos en detalle, el Capítulo 3 explora los frameworks de orquestación con sus criterios de adopción y sus limitaciones, y los capítulos posteriores abordan el testing, el CI/CD, la evaluación de calidad y la optimización de costos como disciplinas de ingeniería de producción. La progresión es deliberada: cada capa del stack se introduce cuando el lector tiene el contexto para entender por qué existe y qué problema específico resuelve.

---

*"Simplicity is a prerequisite for reliability."* — Edsger Dijkstra. En AI Engineering, cada herramienta adicional en el stack introduce un punto potencial de fallo, una versión que actualizar y un concepto que el equipo debe dominar; el stack mínimo viable no es una limitación de capacidades sino la base de un sistema comprensible, diagnosticable y confiable a lo largo del tiempo.
