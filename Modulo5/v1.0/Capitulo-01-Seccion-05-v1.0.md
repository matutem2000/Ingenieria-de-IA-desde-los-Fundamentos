# Módulo 5 – Capítulo 01 – Sección 05

## Elección de herramientas según el caso de uso: criterios técnicos y económicos

La elección de qué API, SDK, modelo y framework usar no debe tomarse por popularidad ni por la última tendencia en Hacker News sino por una evaluación rigurosa y empírica de los requisitos específicos del caso de uso. Este punto es más importante de lo que parece: la elección de modelo incorrecto puede multiplicar el costo por 20x sin mejora medible en calidad, o introducir latencia inaceptable en una interfaz conversacional que requiere respuesta en menos de un segundo. El proceso correcto siempre comienza con la medición: definir el conjunto de criterios relevantes para el caso de uso, medir el desempeño de los candidatos sobre un dataset representativo del dominio, y tomar la decisión con evidencia empírica, no con supuestos.

La latencia de Time-to-First-Token (TTFT) es el criterio dominante en interfaces conversacionales en tiempo real. Un chatbot de atención al cliente donde el usuario espera una respuesta en una interfaz de chat tiene un umbral de experiencia de usuario aceptable de 500ms a 1 segundo de TTFT; si el sistema supera esos valores regularmente, los usuarios perciben el sistema como lento aunque la respuesta sea excelente. Modelos como Claude 3.5 Haiku y gpt-4o-mini tienen TTFT típicos de 200-400ms; modelos más grandes como Claude 3.5 Sonnet y gpt-4o alcanzan 400-800ms bajo carga normal; modelos de razonamiento como o1 pueden tomar de 5 a 60 segundos antes del primer token porque ejecutan razonamiento interno extenso. La elección del modelo de razonamiento se justifica solo en tareas donde la calidad del razonamiento es crítica y la latencia no importa —análisis de código complejo, evaluación de decisiones estratégicas— nunca en interfaces de chat.

El costo por tarea es el segundo criterio. El cálculo correcto es `(input_tokens × precio_entrada + output_tokens × precio_salida) × volumen_diario × 30`, y los números resultan reveladores. Un sistema de clasificación de intención de usuario con 5 categorías que procesa 100.000 requests diarios con 500 tokens de entrada y 50 tokens de salida cuesta con Claude 3.5 Haiku (`$0.80/M entrada, $4/M salida`) aproximadamente `(500×0.80 + 50×4.0)/1M × 100.000 × 30 = $720/mes`; el mismo sistema con Claude 3.5 Sonnet (`$3/M entrada, $15/M salida`) costaría `$3.750/mes` —5x más caro— sin ninguna mejora en la tarea de clasificación que un modelo pequeño resuelve con 95%+ de accuracy. Ejecutar el benchmark antes de comprometer la arquitectura con un modelo es la inversión de tiempo con mayor retorno en proyectos de IA de volumen alto.

Los requisitos de privacidad y soberanía de datos son el tercer eje. Las APIs de los tres proveedores principales envían los datos del prompt a servidores externos; para datos regulados (HIPAA, GDPR con datos especialmente sensibles, datos de defensa o inteligencia) esto puede ser un bloqueador. Las alternativas son: Azure OpenAI Service con contrato de datos dentro del tenant del cliente, Vertex AI con VPC Service Controls que mantienen los datos dentro de la VPC del cliente, o modelos self-hosted con Ollama (para desarrollo y bajo volumen) o vLLM (para producción con GPU dedicada). Ollama permite ejecutar modelos como Llama 3.1 70B, Mistral 7B o Qwen 2.5 72B localmente con una API compatible con OpenAI vía `base_url="http://localhost:11434/v1"`, sin costo de inferencia pero con costo de hardware. vLLM es el servidor de inferencia de alto throughput para GPU, con soporte de batching continuo, tensor parallelism y compatibilidad con la API de OpenAI que permite usar el SDK de OpenAI sin modificación.

## Criterios técnicos y económicos de selección

- **Latencia vs capacidad:** Claude 3.5 Haiku con TTFT típico <500ms para interfaces conversacionales; gpt-4o para tareas que requieren razonamiento amplio con latencia moderada; o1 o Claude 3.5 Opus para razonamiento profundo donde la latencia no es crítica.
- **Costo por tarea medido:** calcular `(input_tokens × precio_entrada + output_tokens × precio_salida) × volumen`; para clasificación y extracción simple, los modelos pequeños ofrecen 90-97% de la calidad del modelo grande a 5-20x menor costo.
- **Ventana de contexto:** Gemini 1.5 Pro con 1 millón de tokens para análisis de codebase completa; Claude 3.5 Sonnet con 200K para documentos largos; gpt-4o con 128K para conversaciones largas; la elección depende del tamaño del corpus que debe caber en una sola llamada.
- **Privacidad y cumplimiento:** APIs de terceros para datos no regulados; Azure OpenAI o Vertex AI con VPC para datos regulados dentro del cloud del proveedor; vLLM o Ollama para datos que no pueden salir de la infraestructura propia.
- **Ecosistema y estabilidad operacional:** proveedores con SLA documentado, changelog público, foro activo de soporte y latencia de resolución de incidentes de <24h tienen ventaja en proyectos de producción donde los incidentes deben resolverse rápidamente.

> **Nota del Arquitecto:** El criterio que más frecuentemente se omite en las evaluaciones de modelo es la estabilidad del comportamiento ante cambios del proveedor. OpenAI actualiza los modelos bajo el mismo identificador sin aviso previo; Anthropic publica notas de deprecación con 6 meses de antelación. Para sistemas donde la consistencia de comportamiento es crítica (clasificadores con thresholds calibrados, sistemas donde los usuarios reportan inconsistencias), anclar el identificador de modelo con fecha (`claude-3-5-sonnet-20241022` en lugar de `claude-3-5-sonnet`) y monitorear el campo `model` devuelto en cada respuesta detecta actualizaciones silenciosas del proveedor antes de que afecten al sistema.

La elección de herramientas no es definitiva: se revisita cuando el volumen escala más allá del tier de rate limit actual, cuando aparece un nuevo modelo con mejor relación costo-calidad, o cuando los requisitos de privacidad del cliente cambian. La siguiente sección cierra el capítulo con una síntesis del stack mínimo viable: el conjunto acotado de herramientas con el que un AI Engineer puede construir y operar un sistema de IA en producción sin añadir complejidad innecesaria.

---

**Buena práctica:** Evaluar modelos con un benchmark representativo del caso de uso real —al menos 100-200 ejemplos del dominio específico con métricas de calidad y costo medidas simultáneamente— antes de comprometer la arquitectura con un proveedor o modelo específico.
