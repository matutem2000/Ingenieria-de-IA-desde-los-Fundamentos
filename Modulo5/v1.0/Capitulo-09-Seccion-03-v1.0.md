## Prompt caching: Anthropic, OpenAI y su impacto en costos repetitivos

El prompt caching es la funcionalidad de proveedor con el mayor ratio de impacto en costo versus complejidad de implementación disponible en el ecosistema de LLMs: el cambio necesario en el código es agregar un campo `cache_control` en el cuerpo del request de Anthropic, o simplemente estructurar el prompt con prefijos largos en OpenAI donde el caching es automático. El ahorro resultante puede llegar al 80-90% en el costo de los tokens de entrada repetitivos. Pocos cambios en un sistema de IA tienen un impacto de costo tan alto con tan poca complejidad de implementación.

La implementación en Anthropic es explícita: el desarrollador marca qué bloques del prompt deben cachearse con `cache_control: {"type": "ephemeral"}`. El bloque marcado —el system prompt, un documento de referencia, una lista de ejemplos few-shot— se cachea en los servidores de Anthropic durante cinco minutos desde el último uso, con renovación automática del TTL en cada llamada que reutiliza el mismo prefijo. La condición de éxito es que el contenido marcado para caché sea textualmente idéntico entre llamadas —cualquier diferencia en un solo carácter invalida el cache hit— y que supere el mínimo de 1.024 tokens para activarse. La estructura óptima de prompt para maximizar el cache hit rate es "static first, dynamic last": `[system prompt estático - 2.000 tokens][documentos de referencia fijos - 5.000 tokens]` marcados con `cache_control`, seguido de `[historial conversacional reciente][query variable del usuario]` sin marcar.

La implementación en OpenAI es automática para prefijos de 1.024 tokens o más: el proveedor cachea automáticamente los prefijos de los prompts sin requerir configuración explícita, aplicando un descuento del 50% sobre el precio de entrada para los tokens cacheados. El campo `usage.prompt_tokens_details.cached_tokens` en la respuesta indica cuántos tokens vinieron del caché para cada llamada. La activación automática tiene la ventaja de no requerir ningún cambio de código, pero la desventaja de no proveer control explícito sobre qué se cachea: el caching ocurre cuando la infraestructura de OpenAI lo determina, que puede no ser consistente en todos los requests.

Google Gemini Context Caching tiene una API separada con características diferentes: `genai.caching.CachedContent.create(contents=..., ttl=datetime.timedelta(hours=1))` crea un objeto de caché en la nube con un TTL configurable y un costo de almacenamiento por token por hora ($1 por millón de tokens por hora). Este modelo es diferente al de Anthropic: el caché tiene un costo de mantenimiento por tiempo en lugar de un costo de escritura único, y el beneficio se materializa cuando el volumen de llamadas que reutilizan el mismo contenido es suficientemente alto para justificar el costo de almacenamiento. El mínimo de 4.096 tokens para activar Context Caching en Gemini limita su aplicabilidad a contextos suficientemente grandes.

## Aspectos técnicos del prompt caching

- **Estructura óptima para caching en Anthropic:** `[system prompt estático][documentos fijos]` con `cache_control: {"type": "ephemeral"}` seguido de `[query variable]`; el prefijo estático debe ser textualmente idéntico entre llamadas para activar el cache hit; cualquier diferencia invalida el caché.
- **Monitoreo del cache hit rate:** campo `usage.cache_read_input_tokens` en la respuesta de Anthropic indica cuántos tokens vinieron del caché; monitorizar este campo como métrica operativa con alerta cuando cae por debajo del expected para detectar cambios en la estructura del prompt que reducen el hit rate.
- **Casos de uso de mayor ahorro:** system prompts largos con instrucciones de empresa (>1.000 tokens), documentos de referencia fijos por sesión (contratos, manuales de producto), y ejemplos few-shot estáticos que se repiten en cada llamada.
- **TTL y renovación en Anthropic:** el caché dura 5 minutos desde el último uso; para sesiones conversacionales activas, cada turno renueva el TTL automáticamente; para pipelines batch con intervalos de más de 5 minutos, estructurar el procesamiento para que cada batch comience renovando el caché con una llamada inicial.
- **Google Gemini Context Caching:** API `genai.caching.CachedContent.create()` con TTL configurable y costo de $1/M tokens/hora; breakeven depende del volumen de llamadas que reutilizan el mismo contenido y del precio diferencial de generación con caché vs sin caché.

El prompt caching es la optimización de costo de mayor impacto para sistemas con system prompts o contextos documentales largos y repetitivos; habilitarlo puede reducir el costo de las llamadas en un 40-80% sin ningún cambio en la calidad de las respuestas, lo que lo convierte en una de las primeras optimizaciones a implementar cuando el sistema alcanza un volumen de tráfico significativo.
