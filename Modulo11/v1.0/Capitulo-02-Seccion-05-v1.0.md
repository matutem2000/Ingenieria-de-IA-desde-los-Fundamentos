# Módulo 11 – Capítulo 02 – Sección 05

## Landing zones de IA: entornos aislados para desarrollo, staging y producción

Uno de los problemas más frecuentes en la adopción de IA enterprise es el tiempo que los equipos pierden configurando la infraestructura de base antes de poder escribir la primera línea de código del sistema de IA. Configurar una VPC, definir los roles IAM, crear los buckets de S3 con las políticas de cifrado correctas, configurar los logs de auditoría, y establecer las políticas de red para que los servicios puedan comunicarse sin exponerse a internet — cada uno de estos pasos, realizado por separado para cada nuevo equipo y cada nuevo entorno, consume semanas de trabajo y produce configuraciones inconsistentes entre proyectos que dificultan la auditoría de seguridad.

Una landing zone de IA es un entorno cloud pre-configurado y pre-aprobado que proporciona toda esta infraestructura de base mediante Infrastructure as Code, ejecutada una vez por el equipo de plataforma y disponible para todos los equipos consumidores en horas en lugar de semanas. El concepto, popularizado por AWS con su Landing Zone Accelerator, se adapta al dominio de IA añadiendo los componentes específicos que los sistemas de IA requieren: acceso configurado a las APIs de LLM mediante Private Link sin tráfico por internet, namespaces pre-aprovisionados en la base de datos vectorial, cuotas de GPU para instancias de experimentación, y políticas de retención de datos que cumplen con los requisitos de GDPR e ISO 27001.

La arquitectura de landing zones define al menos tres entornos con separación física — no solo lógica — entre ellos. El entorno de **desarrollo** es donde los AI Engineers experimentan con datos anonimizados o sintéticos, sin acceso a datos de producción, con cuotas de gasto limitadas y sin restricciones de proceso que ralenticen la experimentación. El entorno de **staging** es una réplica funcional del entorno de producción con datos de prueba reales bajo las mismas políticas de seguridad, donde se validan los cambios antes del despliegue final. La distinción crítica entre staging y un simple entorno de test es que staging refleja exactamente las restricciones de producción: si producción requiere aprobación del CAB para despliegues, staging también la requiere. Si producción tiene audit logging activo, staging también lo tiene. Esta equivalencia es lo que hace que las pruebas en staging sean predictivas del comportamiento en producción.

El entorno de **producción** opera con datos reales de negocio, acceso estrictamente restringido mediante políticas de Just-In-Time access que los ingenieros deben solicitar explícitamente con justificación técnica para cada intervención, y todos los cambios gestionados mediante el proceso de change management formal aprobado por el CAB. La separación física entre estos entornos — mediante cuentas de AWS distintas, subscripciones de Azure separadas, o proyectos de GCP independientes — con Service Control Policies que impiden cualquier acceso cross-cuenta no autorizado, es lo que garantiza que un bug en el código de desarrollo no puede, bajo ninguna circunstancia técnica, afectar los datos de producción.

> **Nota del Arquitecto:** La regla de oro de las landing zones es que usarlas debe ser más fácil que evitarlas. Si el proceso de aprovisionamiento de una landing zone requiere esperar una semana a que el equipo de seguridad la revise manualmente, los equipos encontrarán formas de trabajar fuera de ella — configurando sus propias cuentas de cloud con tarjeta de crédito personal, o trabajando directamente en producción sin staging. El compliance bypasseado por inconveniencia es el peor resultado posible. La landing zone bien diseñada es la que se convierte en el camino de menor resistencia.

## Componentes de una landing zone de IA

- **Aislamiento de red:** VPC dedicada por entorno con subnets privadas para los servicios de IA, NAT Gateway para salida controlada a internet, y Private Link para acceso a APIs de LLM sin tráfico público; las Network Policies de Kubernetes refuerzan el aislamiento a nivel de pod.
- **Gestión de identidad y acceso:** roles IAM por función (AI Engineer, Data Scientist, Operator) con principio de mínimo privilegio, MFA obligatorio, y acceso Just-In-Time para operaciones privilegiadas mediante AWS IAM Identity Center o Azure PIM.
- **Almacenamiento de datos:** buckets S3/GCS/ADLS con cifrado SSE-KMS, versionado activado, políticas de retención según clasificación de datos, y bloqueo de acceso cross-cuenta que impide que datos de producción sean accesibles desde entornos de desarrollo.
- **Registro y auditoría:** CloudTrail/Cloud Audit Logs habilitado en todos los servicios, logs retenidos mínimo 12 meses en almacenamiento inmutable (S3 con Object Lock), y alertas automáticas para acciones de alto riesgo como borrado masivo de datos o cambios de política IAM.
- **Guardrails automatizados:** AWS Config Rules, Azure Policy, o GCP Organization Policies que verifican continuamente el cumplimiento y generan alertas o bloqueos automáticos, sin necesidad de auditorías manuales periódicas.

---

**Buena práctica:** La landing zone de IA debe ser el camino de menor resistencia para los equipos: si configurarla por fuera es más fácil que usarla, los equipos la evitarán y con ello eludirán los controles de seguridad y cumplimiento que protegen al negocio.

La sección de cierre sintetiza el argumento del capítulo: por qué el tiempo invertido en definir la arquitectura de referencia antes de comenzar el desarrollo es sistemáticamente más barato que el tiempo que cuesta refactorizar sistemas ya en producción con integraciones activas.
