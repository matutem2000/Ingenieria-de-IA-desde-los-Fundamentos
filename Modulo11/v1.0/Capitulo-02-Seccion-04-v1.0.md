# Módulo 11 – Capítulo 02 – Sección 04

## API management para servicios de IA: versionado, contratos y retrocompatibilidad

Los servicios de IA enterprise no operan en aislamiento. Son consumidos por aplicaciones de producto, sistemas de integración, y otros servicios internos que dependen de ellos para funcionar. Cuando hay una docena de consumidores y el equipo productor decide cambiar el esquema de respuesta del endpoint de análisis de contratos — agregando un campo nuevo, eliminando un campo que parecía redundante, o cambiando el tipo de un campo de string a objeto — cada uno de esos consumidores puede romper silenciosamente si no existe un proceso formal de gestión de cambios de API. En enterprise, estos rompimientos silenciosos se descubren días después, en producción, cuando el equipo de soporte empieza a recibir reportes de errores de aplicaciones que nadie conectó inmediatamente con el cambio de API.

El versionado semántico aplicado a APIs de IA (v1, v2, v3 en el path, o versión en el header Accept) es el mecanismo que permite al equipo productor evolucionar la API sin romper a los consumidores existentes. Pero el versionado semántico solo es efectivo si se acompaña de dos compromisos: un período de deprecación explícito durante el cual ambas versiones coexisten y el equipo productor provee soporte activo para la migración, y una comunicación proactiva que notifica a los consumidores con suficiente antelación para que puedan planificar su migración. En el contexto enterprise, el mínimo razonable es 6 meses para APIs internas y 12 meses para APIs expuestas a clientes externos. Estos plazos no son arbitrarios: reflejan el tiempo real que necesitan los equipos enterprise para priorizar, planificar, y ejecutar una migración de integración dentro de sus ciclos de desarrollo.

El contrato de una API de IA incluye dimensiones que no existen en las APIs convencionales. Además del esquema de petición y respuesta, el contrato debe documentar explícitamente: el modelo subyacente que se utiliza y si puede cambiar sin previo aviso (un cambio de GPT-4 a GPT-4o puede producir respuestas cualitativamente distintas aunque el esquema JSON sea idéntico), los campos del esquema de respuesta que son estables versus los que son experimentales y pueden cambiar entre versiones menores, los SLOs de latencia (p50, p95, p99) y la garantía o ausencia de garantía de determinismo en las respuestas (dos llamadas idénticas al mismo endpoint pueden producir respuestas distintas, lo que tiene implicaciones para los sistemas que verifican la respuesta por comparación exacta).

Las herramientas de API management enterprise — Kong Gateway, AWS API Gateway, Azure APIM, o Apigee — son el componente operacional que hace ejecutable el contrato: aplican el rate limiting por cliente sin que cada servicio tenga que implementarlo, mantienen el registro centralizado de todas las peticiones para auditoría, y activan los circuit breakers que protegen los sistemas upstream cuando el servicio de LLM tiene una degradación de rendimiento. Sin esta capa de gestión, cada equipo implementa sus propios mecanismos de throttling y circuit breaking, con resultados inconsistentes y sin visibilidad centralizada del uso de la plataforma.

## Aspectos técnicos de API management para IA

- **Versionado de API:** URI versioning (/v1/completions, /v2/chat) combinado con deprecation headers HTTP estándar (Sunset: fecha de desactivación, Deprecation: fecha de anuncio de deprecación) para notificar a los consumidores de manera automática.
- **Contratos OpenAPI/AsyncAPI:** especificaciones Swagger 3.0 que documentan todos los campos, tipos, ejemplos, y restricciones de la API, publicadas en el portal de desarrolladores interno con historial de cambios entre versiones.
- **Rate limiting inteligente:** límites configurados a nivel de tenant, endpoint, y modelo, con headers de respuesta (X-RateLimit-Remaining, Retry-After) que permiten a los clientes adaptar su comportamiento antes de recibir un 429.
- **Circuit breaker y fallback:** patrón implementado con Resilience4j o Polly que devuelve respuestas de fallback predefinidas cuando el LLM upstream supera el timeout configurado; el fallback puede ser una respuesta en caché, un mensaje de degradación graceful, o la activación del modelo de respaldo.
- **API versioning governance:** proceso de RFC interno para proponer cambios breaking, con período de review, aprobación explícita de los principales consumidores, y release notes detalladas que documentan exactamente qué cambia y cómo migrar.

---

**Principio rector:** Un contrato de API es una promesa. En sistemas enterprise, romper esa promesa sin un proceso formal de deprecación genera desconfianza que tarda meses en reconstruirse — y en algunos casos lleva a los equipos consumidores a construir sus propias alternativas para no depender de un servicio que perciben como inestable.

Con el API management establecido como la interfaz de contrato entre el sistema de IA y sus consumidores, la sección siguiente aborda el componente de infraestructura que garantiza que los equipos puedan trabajar de manera aislada y segura desde el primer día: las landing zones de IA.
