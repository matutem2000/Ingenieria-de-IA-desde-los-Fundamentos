# Módulo 11 – Capítulo 07 – Sección 03

## Model routing enterprise: combinar modelos de bajo costo para tareas simples con modelos premium para tareas complejas

El anti-patrón más costoso en sistemas de IA enterprise es el modelo único de alta gama: enviar todas las peticiones — desde "¿cuáles son los horarios de la cafetería?" hasta "analiza este contrato de 50 páginas e identifica los riesgos legales" — al mismo modelo premium, porque es el modelo que mejor garantiza calidad. Esta uniformidad tiene un costo de simplicidad que se vuelve insostenible a escala: si el 75% de las peticiones de un sistema de soporte interno son preguntas de bajo nivel cognitivo que un modelo de gama media responde con calidad idéntica al modelo premium, el sistema está pagando el precio del modelo premium para el 75% del tráfico donde ese precio adicional no genera ningún valor de negocio adicional.

La diferencia de costo entre modelos premium y económicos en el mercado actual es sustancial (los precios exactos cambian frecuentemente; verificar en las páginas de precios de los proveedores). Lo que es estructuralmente estable es la relación: los modelos de gama media cuestan entre 10x y 20x menos que los modelos premium por token, y este diferencial justifica la inversión en un sistema de routing que dirija selectivamente el tráfico al modelo apropiado. Un sistema que enruta el 75% del tráfico al modelo económico y el 25% al modelo premium reduce el costo de inferencia en aproximadamente 8-10x respecto a enviar todo al modelo premium, con impacto mínimo en la calidad percibida si el routing es preciso.

El **clasificador de complejidad** — el componente que decide qué modelo usar para cada petición — puede implementarse con diferentes niveles de sofisticación y latencia. Las **reglas heurísticas** son las más simples: si la petición tiene más de 500 tokens → modelo premium; si la petición contiene keywords de dominio especializado (análisis legal, diagnóstico médico, modelado financiero) → modelo premium; si la petición es una pregunta de FAQ de respuesta corta → modelo económico. La ventaja es la latencia cero y la transparencia; la desventaja es que las reglas no capturan la complejidad semántica de la petición.

Un **clasificador lightweight de complejidad** — un modelo BERT fine-tuned o un XGBoost entrenado sobre 1.000-5.000 pares (petición, modelo_apropiado) etiquetados manualmente o por LLM-as-a-judge — añade latencia de 10-30ms pero produce un routing significativamente más preciso porque capta la complejidad semántica que las reglas heurísticas no pueden. El dataset de entrenamiento se construye sobre el tráfico histórico del sistema, etiquetando cada petición con el modelo mínimo que habría producido una respuesta de calidad suficiente — un proceso que puede hacerse parcialmente automático con un LLM-as-a-judge que compara las respuestas del modelo económico y del premium para cada petición.

El **cascading** — enviar la petición primero al modelo económico y escalar al modelo premium solo si la respuesta no es satisfactoria — elimina la necesidad del clasificador de complejidad a cambio de un aumento potencial de latencia en los casos que necesitan escalar. Un evaluador de confianza ligero (perplexity de la respuesta, puntuación de un evaluador embeddings-based) determina si la respuesta del modelo económico es suficiente o si debe re-enviarse al modelo premium. El riesgo es que en los casos que requieren escalada, la latencia total se duplica: el tiempo de la llamada al modelo económico más el tiempo de la llamada al modelo premium.

## Patrones de model routing enterprise

- **Reglas heurísticas de routing:** tabla de decisión basada en longitud del prompt (tokens), presencia de keywords de dominio especializado, y tipo de tarea inferida de la categoría del endpoint de API — latencia de routing < 1ms, mantenimiento manual requerido.
- **Clasificador de complejidad lightweight:** modelo BERT fine-tuned o XGBoost entrenado sobre peticiones etiquetadas, con inferencia de 10-30ms que no impacta perceptiblemente la latencia del usuario — la opción con mejor balance entre precisión y complejidad operacional.
- **Cascading con escalada automática:** enviar al modelo económico primero, evaluar la calidad de la respuesta con un evaluador ligero, y re-enviar al modelo premium si el score de calidad no supera el threshold — la opción de mayor precisión pero con riesgo de duplicar la latencia en los casos más complejos.
- **Routing por caso de uso y endpoint:** configuración explícita en el tenant configuration service que asigna un modelo específico a cada tipo de petición por endpoint de API, independientemente de la complejidad individual de cada petición.
- **A/B testing del router:** experimentar con diferentes estrategias de routing midiendo el impacto en costo y calidad para encontrar el punto óptimo del trade-off para cada caso de uso específico, con los mismos principios del A/B testing de prompts del Capítulo 05.

---

**Principio rector:** El model routing empresarial debe optimizarse para minimizar el costo total dado un umbral mínimo de calidad — no para maximizar la calidad ignorando el costo, ni para minimizar el costo ignorando la calidad. El umbral mínimo de calidad es la restricción; el costo es la variable a minimizar dentro de esa restricción.
