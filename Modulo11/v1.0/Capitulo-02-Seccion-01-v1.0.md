# Módulo 11 – Capítulo 02 – Sección 01

## Enterprise AI reference architecture: capas, componentes y flujos de datos

Cuando un equipo de AI Engineering enfrenta la pregunta de cómo organizar su sistema para producción enterprise, la respuesta más peligrosa es "empecemos y ya iremos añadiendo lo que necesitemos". Esta improvisación produce sistemas donde la lógica de orquestación está mezclada con el acceso a datos, donde la autenticación fue añadida como afterthought sobre un servicio que no fue diseñado para múltiples identidades, y donde cambiar el proveedor de LLM requiere modificar docenas de archivos distribuidos en tres repositorios distintos. La arquitectura de referencia enterprise existe para evitar exactamente este patrón: es un conjunto de decisiones de diseño documentadas que responden a restricciones reales antes de que el código exista.

Una arquitectura de referencia no es un diagrama aspiracional que muestra el sistema ideal en el estado futuro. Es un conjunto de decisiones tomadas sobre restricciones concretas: la latencia máxima aceptable por caso de uso (un asistente de chat interno puede tolerar 3 segundos; un sistema de aprobación de transacciones en tiempo real no puede tolerar más de 500ms), los requisitos de disponibilidad (un SLA del 99.9% implica menos de 9 horas de downtime al año, lo que requiere redundancia activa y planes de failover probados), el modelo de seguridad de red (qué servicios pueden hablar entre sí, cuáles requieren Private Link para evitar tráfico por internet público, qué políticas de Network Policy en Kubernetes gobiernan el tráfico intra-cluster), y la estrategia de cloud (si el enterprise opera en multi-cloud o cloud híbrido, la arquitectura debe contemplar dónde reside cada componente y cómo se conectan entre sí sin introducir dependencias de un único proveedor).

La arquitectura de referencia define cinco flujos de datos primarios que coexisten en el sistema. El **flujo de inferencia en tiempo real** sigue el camino petición de usuario → API Gateway → servicio de orquestación → LLM → respuesta, y es el flujo que determina la latencia percibida por el usuario. El **flujo de recuperación en RAG** añade los pasos de query → embedding service → vector database → reranker → contexto enriquecido antes de la llamada al LLM, con un impacto de latencia adicional de 100 a 500ms dependiendo del tamaño del índice y la calidad del reranker. El **flujo de ingesta de datos** opera en background, moviendo datos desde las fuentes enterprise al feature store y al data lake mediante pipelines ETL/ELT orquestados con Airflow o Prefect. El **flujo de evaluación** es el pipeline de calidad del sistema, que toma muestras del tráfico de producción y las somete a evaluadores automáticos cuyos resultados se registran en MLflow o LangSmith. El **flujo de retroalimentación** cierra el ciclo de mejora, capturando el feedback explícito e implícito de los usuarios para alimentar el proceso de mejora del sistema.

> **Nota del Arquitecto:** Los flujos de datos más olvidados en las arquitecturas de referencia iniciales son el flujo de evaluación y el flujo de retroalimentación. Se documenta con detalle el flujo de inferencia — el camino feliz — pero no el circuito de control de calidad que detecta cuando ese camino empieza a degradarse. En mi experiencia, los equipos que documentan los cinco flujos desde el inicio tienen incidentes de producción significativamente menos frecuentes y más cortos en tiempo de resolución.

## Componentes principales de la arquitectura

- **API Gateway y autenticación:** Kong, AWS API Gateway, o Azure APIM con OAuth 2.0/OIDC, rate limiting por cliente, y logging de todas las peticiones para auditoría; el punto único de entrada que permite aplicar políticas de seguridad y observabilidad de manera centralizada.
- **Capa de orquestación de IA:** servicio stateless que implementa la lógica de negocio, gestiona el contexto conversacional en Redis, y coordina las llamadas a LLMs, tools, y bases de datos vectoriales; diseñado para escalar horizontalmente sin estado compartido entre réplicas.
- **Servicio de embeddings compartido:** instancia de text-embedding-3-large (OpenAI) o multilingual-e5-large desplegada centralmente para evitar la duplicación de costos que ocurre cuando cada equipo llama independientemente a la API de embeddings para los mismos documentos.
- **Base de datos vectorial enterprise:** Pinecone, Weaviate con RBAC, o pgvector sobre PostgreSQL con índices HNSW para búsqueda aproximada de vecinos cercanos a escala; la elección depende del volumen de vectores, los requisitos de aislamiento multi-tenant, y la capacidad operacional del equipo.
- **Plataforma de observabilidad:** stack de OpenTelemetry para traces distribuidos, Prometheus para métricas de infraestructura, y LangSmith o Langfuse para trazas específicas de LLM; los tres niveles son necesarios porque cada uno cubre una dimensión que los otros no pueden ver.

---

**Idea central:** Una arquitectura de referencia enterprise reduce el tiempo de decisión de cada equipo al establecer las elecciones de componentes ya tomadas, liberando el foco de ingeniería para las decisiones genuinamente específicas de cada caso de uso. Su valor no está en ser perfecta sino en ser explícita.

La sección siguiente introduce el patrón organizacional que determina cómo múltiples equipos pueden usar la misma arquitectura de referencia sin convertir al equipo de plataforma en un cuello de botella de coordinación: el modelo Hub-and-Spoke.
