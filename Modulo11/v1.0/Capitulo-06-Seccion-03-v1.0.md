# Módulo 11 – Capítulo 06 – Sección 03

## RAG sobre datos estructurados y no estructurados en el enterprise

Los datos enterprise se distribuyen entre dos categorías con propiedades de retrieval fundamentalmente distintas, y la mayoría de las preguntas de negocio relevantes requieren acceso a ambas. Los **datos no estructurados** — documentos PDF, presentaciones PowerPoint, correos electrónicos, tickets de soporte, transcripciones de reuniones, contratos — se indexan como texto mediante chunking y embedding para búsqueda vectorial: la pregunta "¿cuáles son los términos de rescisión del contrato con el proveedor X?" requiere recuperar el fragmento específico del contrato que contiene esa cláusula. Los **datos estructurados** — tablas de bases de datos relacionales, data warehouses, APIs de sistemas ERP, hojas de cálculo — se consultan mejor mediante queries SQL precisas: la pregunta "¿cuánto hemos facturado al cliente X en el último trimestre?" requiere una agregación exacta sobre la tabla de transacciones, no un retrieval semántico sobre embeddings de los registros de facturación.

El problema del RAG exclusivamente vectorial sobre datos estructurados es evidente: generar embeddings de filas de base de datos para buscarlas por similitud semántica es técnicamente posible pero conceptualmente inadecuado para la mayoría de las consultas financieras o transaccionales, donde la exactitud matemática importa más que la similitud semántica. Si el usuario pregunta "¿cuál es la facturación del Q3?", una búsqueda vectorial recuperará filas que son semánticamente similares a la pregunta, no la suma exacta de las transacciones del tercer trimestre.

El patrón **Text-to-SQL** resuelve este problema para datos estructurados: el LLM convierte la pregunta en lenguaje natural en una query SQL ejecutable sobre la base de datos. La ventaja es que los datos están siempre actualizados (la query se ejecuta contra el estado actual de la base de datos, no contra un índice vectorial que puede estar desactualizado) y la precisión es matemática. El riesgo es que el LLM puede generar SQL incorrecto, SQL que accede a tablas no autorizadas, o SQL computacionalmente costoso que satura el servidor de base de datos. Estos riesgos se mitigan con guardrails específicos: validación de la query SQL con EXPLAIN antes de ejecutarla, whitelist de tablas y columnas accesibles para el LLM (schema masking: el LLM solo ve el schema relevante para su dominio), y timeout de 5 segundos que previene queries de larga duración.

El **RAG híbrido** que combina retrieval vectorial con Text-to-SQL es la arquitectura que cubre el espectro completo de necesidades de información enterprise. Un router — implementado como un clasificador de intención de la pregunta, que puede ser tan simple como un LLM con un prompt de routing — analiza la pregunta del usuario y determina la estrategia de retrieval apropiada: retrieval vectorial para preguntas sobre política interna, contratos, y documentación técnica; Text-to-SQL para preguntas sobre métricas, cifras, y datos transaccionales; o una combinación de ambos para preguntas que requieren contexto documental y datos cuantitativos simultáneamente (por ejemplo: "¿el nivel de servicio del proveedor X cumple con el SLA acordado en el contrato?" requiere recuperar el SLA del contrato mediante RAG vectorial y los datos de cumplimiento del servicio mediante Text-to-SQL).

> **Nota del Arquitecto:** El schema masking — proporcionar al LLM solo el subset del schema de base de datos relevante para su dominio — es tanto un control de seguridad como una optimización de calidad. Sin schema masking, el LLM puede generar queries sobre tablas que el usuario no tiene autorización de consultar; con un schema completo de decenas de tablas, el LLM produce queries menos precisas porque la información irrelevante en el prompt interfiere con la tarea. Mantener catálogos de schema por dominio de usuario que se sirven dinámicamente al LLM según el contexto es la implementación correcta.

## Componentes del RAG sobre datos heterogéneos

- **Chunking semántico para no estructurados:** estrategia de chunking con LangChain SemanticChunker o LlamaIndex SentenceWindowNodeParser que produce chunks de 512-1024 tokens con overlap del 20%, preservando el contexto entre chunks adyacentes y respetando los límites naturales del texto.
- **Text-to-SQL con schema masking:** el LLM recibe solo el schema relevante para el dominio del usuario, no el schema completo de la base de datos, reduciendo el riesgo de queries sobre tablas no autorizadas y mejorando la precisión de las queries generadas.
- **Validación de SQL generado:** ejecución en modo EXPLAIN antes de la ejecución real para verificar el plan de query, comprobación de que la query solo accede a tablas en el whitelist configurado, y timeout de 5 segundos para prevenir queries costosas.
- **Reranker cross-encoder:** modelo de reranking (ms-marco-MiniLM-L-12-v2, Cohere Rerank, Jina Rerank) que reordena los chunks recuperados por similitud vectorial usando un score de relevancia contextual más preciso antes de incluirlos en el contexto del LLM.
- **Router de estrategia de retrieval:** clasificador de intención que determina si la pregunta requiere RAG vectorial, Text-to-SQL, o una combinación de ambos, basándose en palabras clave, estructura de la pregunta, y el historial del contexto conversacional.

---

**Idea central:** El RAG híbrido que combina retrieval vectorial para datos no estructurados con Text-to-SQL para datos estructurados es la arquitectura que cubre el espectro completo de necesidades de información de un enterprise, donde la mayoría de las preguntas de negocio estratégicas requieren ambos tipos de contexto para ser respondidas con precisión.
