# Módulo 11 – Capítulo 03 – Sección 02

## Patrones de integración: Adapter, Facade y Anti-Corruption Layer para sistemas legacy

La integración con sistemas legacy sin patrones de diseño explícitos produce inevitablemente uno de dos problemas: el acoplamiento directo, donde el sistema de IA depende de los detalles de implementación del legacy (sus formatos de datos, sus convenciones de nomenclatura, sus reglas de negocio implícitas) y debe modificarse cada vez que el legacy cambia; o la duplicación, donde la lógica de transformación de datos legacy se replica en múltiples partes del sistema de IA sin un lugar centralizado donde mantenerla. Los patrones de integración del Domain-Driven Design y de los Enterprise Integration Patterns (EIP) ofrecen soluciones verificadas a ambos problemas, y su aplicación al contexto específico de sistemas de IA enterprise permite construir integraciones que son robustas ante los cambios en los sistemas subyacentes.

El **patrón Adapter** es la solución más directa: traduce la interfaz de un sistema legacy a una interfaz que el sistema de IA puede consumir sin acoplarse a los detalles del legacy. Un Adapter SOAP-to-REST, implementado con Apache Camel, MuleSoft, o un AWS API Gateway con mapping templates, convierte las llamadas SOAP/XML de un sistema SAP en endpoints RESTful con payloads JSON, absorbiendo la conversión de formato y el manejo de errores específicos del protocolo SOAP — los faults, los timeouts de la conexión SOAP, y los esquemas XML con namespaces anidados — sin que el sistema de IA tenga que saber que el sistema subyacente habla SOAP. Cuando SAP actualiza su API SOAP, solo el Adapter necesita actualizarse; el sistema de IA y todos los demás consumidores continúan hablando REST sin interrupción.

El **patrón Facade** es más ambicioso: agrega múltiples sistemas legacy detrás de una única interfaz unificada. En un sistema de RAG que necesita contexto sobre un cliente para responder preguntas, la Facade puede orquestar internamente consultas al ERP (para datos de facturación), al CRM (para datos de contacto y historial de interacciones), y al sistema de gestión documental (para contratos activos), devolviendo al sistema de IA un objeto de contexto unificado del cliente sin que el sistema de IA tenga que saber qué sistemas fueron consultados. La ventaja no es solo de simplicidad: cuando se agrega un cuarto sistema fuente (por ejemplo, el sistema de soporte técnico para el historial de tickets), la Facade absorbe la integración nueva sin que el sistema de IA necesite modificarse.

El **Anti-Corruption Layer (ACL)** es el patrón más crítico para sistemas de IA enterprise. Un legacy que lleva décadas en producción acumula inconsistencias en su modelo de datos que son normales dentro del sistema — una dirección de cliente puede estar en tres formatos distintos dependiendo de cuándo fue creado el registro — pero que, si se propagan al sistema de IA sin normalización, contaminan el conocimiento del LLM con inconsistencias que producen respuestas incoherentes. El ACL actúa como una capa de traducción bidireccional que normaliza los datos del legacy antes de que entren al pipeline de IA, aplicando las reglas de dominio que el sistema de IA espera. En Python, esto se implementa con Pydantic validators que rechazan activamente los datos que no cumplen el modelo de dominio del sistema de IA, forzando la detección de discrepancias en el momento de la integración en lugar de en el momento de la generación de la respuesta.

## Aspectos técnicos de los patrones de integración

- **Adapter SOAP-to-REST:** implementado con Apache Camel (Java), MuleSoft Anypoint, o AWS API Gateway con mapping templates que convierten WSDLs en OpenAPI specs; herramientas como soap2rest o Postman pueden generar el mapping inicial de manera semi-automática.
- **Facade de agregación:** microservicio que implementa el patrón Backend-for-Frontend (BFF) específico para IA, consolidando datos de múltiples fuentes legacy en un esquema de contexto optimizado para el formato de entrada del LLM, reduciendo el tamaño del contexto al eliminar campos innecesarios para el caso de uso.
- **Anti-Corruption Layer con Pydantic:** modelos de datos del dominio de IA con validaciones estrictas (tipos, rangos, formatos) que rechazan activamente los datos del legacy que no cumplen las invariantes del dominio, con logging de todos los rechazos para detectar tendencias de calidad de datos.
- **Change Data Capture (CDC) con Debezium:** en lugar de polling periódico a las tablas del legacy, Debezium monitorea el transaction log de MySQL, PostgreSQL, u Oracle, publicando cada cambio en Kafka en tiempo real y sin impacto de rendimiento en la base de datos fuente.
- **Circuit breaker para legacy:** Resilience4j o Polly con timeouts agresivos (2-3 segundos máximo para sistemas legacy con SLAs débiles) y fallbacks a datos cacheados o respuestas degradadas cuando el sistema legacy no responde dentro del tiempo esperado.

---

**Principio rector:** Aislar la complejidad del legado en capas de integración explícitas permite que el sistema de IA evolucione independientemente de los cambios — o la falta de cambios — en los sistemas legacy subyacentes. La disciplina de no permitir que las abstracciones del legacy crucen la frontera del ACL es lo que hace que este principio sea sostenible a largo plazo.

Los patrones de integración resuelven el problema de cómo extraer datos del legacy. La sección siguiente aborda el problema de cómo transformarlos: la decisión entre ETL y ELT, y sus implicaciones específicas para los pipelines que alimentan sistemas de RAG.
