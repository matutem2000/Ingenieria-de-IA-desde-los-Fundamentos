# Módulo 11 – Capítulo 05 – Sección 02

## Evaluación continua de LLM en producción: calidad, coherencia y alineación con el negocio

La evaluación de sistemas de LLM es el componente de LLMOps que más frecuentemente se subestima en las fases tempranas y que más se lamenta en los incidentes tardíos. Un equipo que despliega un sistema de IA sin evaluación automatizada opera a ciegas: sabe que el sistema respondía bien durante el piloto, pero no tiene forma de detectar cuándo una actualización del prompt, un cambio en el modelo, o una modificación en los datos de RAG produce una degradación de calidad. La primera señal de que algo está mal llega de un usuario insatisfecho, días después del cambio que introdujo el problema.

La evaluación continua debe operar en tres planos simultáneamente. El primero es la **calidad técnica**: coherencia gramatical, seguimiento de instrucciones del prompt, ausencia de alucinaciones verificables. El segundo es la **alineación con el negocio**: las respuestas representan correctamente la política de la empresa, usan el tono adecuado para el contexto, y contienen la información que el usuario necesita para tomar una decisión o resolver su problema. El tercero es la **seguridad y cumplimiento**: ausencia de contenido prohibido, no divulgación de información confidencial, respeto a las restricciones configuradas por el tenant. Estos tres planos tienen métricas distintas, evaluadores distintos, y thresholds de alerta distintos.

La implementación técnica combina tres tipos de evaluadores con diferente costo y precisión. Los **evaluadores basados en reglas** son los más rápidos y baratos: verificaciones deterministas como "la respuesta está en el idioma correcto", "la respuesta contiene una referencia de ticket cuando se solicita", o "la longitud de la respuesta está dentro del rango configurado". Se ejecutan en el path síncrono de cada petición con latencia adicional de menos de 10ms. Los **evaluadores basados en embeddings** miden la similitud semántica entre la respuesta generada y las respuestas de referencia del golden set: una similitud coseno por debajo del threshold (típicamente 0.85) indica que la respuesta se desvía semánticamente del comportamiento esperado. Los **evaluadores LLM-as-a-judge** son los más costosos y precisos: un LLM de alta calidad (GPT-4o o Claude Opus) recibe la pregunta del usuario, la respuesta del sistema, y un rubric de evaluación, y califica la respuesta en dimensiones como relevancia (1-5), precisión factual (1-5), y adherencia al estilo (1-5). Se ejecutan de manera asíncrona sobre el 5-10% del tráfico de producción para no impactar la latencia.

La integración en el pipeline de CI/CD como **gate de despliegue** es el elemento que convierte la evaluación de un proceso de calidad en un mecanismo de control de cambios. Cada pull request que modifica el sistema prompt, actualiza el modelo, o cambia la configuración del RAG debe pasar el gate de evaluación antes de poder fusionarse a la rama de producción: el pipeline ejecuta el golden dataset completo, calcula las métricas de evaluación, y rechaza el merge si cualquier métrica cae por debajo del threshold definido. Esta integración transforma la evaluación de un proceso periódico en una propiedad continua del sistema.

> **Nota del Arquitecto:** La calibración de los evaluadores LLM-as-a-judge es el trabajo más importante y menos glamuroso de LLMOps. Un evaluador LLM-as-a-judge que no está calibrado contra juicio humano puede producir scores que no correlacionan con la satisfacción real del usuario — y en ese caso, el gate de CI/CD está midiendo algo diferente a lo que el usuario experimenta. Dedicar 2-3 semanas a calibrar el evaluador contra 200-300 casos con evaluación humana como ground truth es la inversión que hace que el sistema de evaluación sea fiable.

## Componentes del sistema de evaluación continua

- **Golden dataset:** conjunto de 100-500 pares (input, output_esperado) representativos de los casos de uso críticos, mantenido en Git con proceso de revisión para agregar nuevos casos cuando se identifican brechas de cobertura.
- **Evaluadores LLM-as-a-judge:** prompts de evaluación calibrados con correlación verificada contra evaluación humana, que califican dimensiones como relevancia, precisión factual, y adherencia al estilo con scores de 1-5 reproducibles.
- **Métricas de evaluación de RAG con RAGAS:** faithfulness (la respuesta es fiel al contexto recuperado), answer relevancy (la respuesta es relevante a la pregunta), y context precision (el contexto recuperado es relevante para la pregunta), ejecutadas de manera asíncrona sobre el tráfico de producción.
- **CI/CD gate de calidad:** job en GitHub Actions o GitLab CI que ejecuta la suite de evaluación sobre el golden dataset, bloquea el merge si las métricas caen por debajo del threshold, y genera un reporte de evaluación detallado visible en el pull request.
- **Sampling de producción:** interceptor en el servicio de orquestación que con probabilidad configurable (1-5%) registra pares (input, output) en una cola asíncrona para evaluación posterior, construyendo el dataset de producción que alimenta la mejora continua del golden set.

---

**Buena práctica:** Las métricas de evaluación y sus thresholds deben definirse antes de desplegar el primer sistema de IA a producción, junto con el proceso de revisión cuando una métrica falla — ¿rollback automático o revisión humana? La respuesta a esa pregunta determina la arquitectura del sistema de evaluación.

Con el sistema de evaluación continua establecido como pilar del LLMOps, la sección siguiente aborda el artefacto que más frecuentemente se gestiona de manera informal y que más frecuentemente produce incidentes cuando no se gestiona correctamente: el prompt.
