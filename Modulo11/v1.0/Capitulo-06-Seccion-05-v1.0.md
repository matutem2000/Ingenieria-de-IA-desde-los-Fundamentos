# Módulo 11 – Capítulo 06 – Sección 05

## Casos de uso enterprise: soporte interno, asistentes de ventas, análisis de contratos y RAG sobre código

El RAG enterprise no es una solución única: cada caso de uso tiene requisitos técnicos específicos que determinan la arquitectura del pipeline de retrieval, la estrategia de chunking, las métricas de evaluación relevantes, y los controles de calidad necesarios. Entender estas diferencias antes de diseñar el sistema evita la trampa de construir un pipeline genérico que funciona razonablemente para ningún caso de uso en particular, en lugar de uno especializado que funciona excelentemente para el caso de uso que el negocio necesita.

El **asistente de soporte interno** (HR helpdesk, IT support, Legal FAQ) es el caso de uso de menor riesgo y mayor velocidad de despliegue por varias razones estructurales: el corpus es relativamente estable (las políticas de HR y los procedimientos de IT se actualizan con frecuencia mensual o trimestral, no diaria), los usuarios son empleados autenticados con permisos conocidos, el impacto de una respuesta incorrecta es bajo (el empleado puede verificar la política directamente), y las métricas de éxito son claramente cuantificables (reducción del 30-50% en tickets de soporte de primer nivel). La arquitectura técnica es la más simple: chunking semántico del corpus de documentos de política, embeddings con text-embedding-3-large, índice por departamento para respetar la segmentación, y evaluación con golden set de las 50 preguntas más frecuentes del helpdesk histórico.

El **asistente de ventas** (product information, pricing, competitive intelligence) introduce una complejidad crítica: la frescura de los datos. Los precios, la disponibilidad de productos, y las condiciones especiales cambian con alta frecuencia — diaria en algunos sectores como el comercio electrónico o el sector financiero — y la información desactualizada tiene un impacto directo y medible: un vendedor que cita un precio incorrecto pierde la negociación o genera un contrato con condiciones que la empresa no puede cumplir. La arquitectura debe integrar RAG vectorial sobre la documentación de producto (relativamente estable) con Text-to-SQL sobre el sistema PIM o ERP para precios y disponibilidad en tiempo real, con alertas cuando la información del índice tiene más de 24 horas de antigüedad para documentos de precio.

El **análisis de contratos** es el caso de uso con mayor impacto por documento procesado y mayor exigencia de precisión. Los errores de extracción pueden tener consecuencias legales: si el sistema extrae incorrectamente una cláusula de penalización, la empresa puede operar durante meses bajo el supuesto de condiciones contractuales incorrectas. Por esta razón, el sistema de análisis de contratos debe implementarse como **asistente de revisión** (herramienta que asiste al abogado en su análisis) no como tomador de decisiones autónomo, y debe presentar siempre la cita exacta del texto del contrato junto a cada extracción, permitiendo al revisor humano verificar la fuente original. El pipeline incluye procesamiento de PDF con extracción de texto estructurado (Unstructured.io, pdfplumber para PDFs con texto; Azure Document Intelligence para PDFs escaneados), clasificadores de tipo de cláusula, y modelos de extracción con Pydantic models que validan los campos extraídos.

El **RAG sobre codebase** (code assistant con contexto del repositorio corporativo) tiene requisitos de embeddings distintos a los documentos de texto: el código tiene una estructura semántica diferente del lenguaje natural, y los embeddings de texto general (text-embedding-3-large) producen retrieval de menor calidad para código que los embeddings especializados. Herramientas como Voyage Code-3 o CodeBERT están entrenadas específicamente en código fuente y producen mejores resultados de retrieval para preguntas sobre implementaciones, patrones de arquitectura, y uso de librerías internas. El chunking debe respetar los límites sintácticos del código — por función o por clase — no simplemente por número de tokens, para garantizar que cada chunk es una unidad semántica coherente que puede entenderse de manera independiente.

## Características técnicas por caso de uso

- **Soporte interno:** corpus de 1.000-10.000 documentos de política y procedimientos, chunking semántico con overlap del 20%, filtros de departamento para segmentación de acceso, latencia de respuesta < 3 segundos, y métrica principal de deflection rate de tickets (objetivo: reducción del 30-50%).
- **Asistente de ventas:** integración con PIM y ERP para datos de precios en tiempo real via Text-to-SQL, corpus de documentación de producto para RAG vectorial, alertas de freshness cuando la información tiene más de 24 horas de antigüedad, y validación de precios contra la fuente authoritative antes de presentarlos.
- **Análisis de contratos:** pipeline de PDF con extracción de texto estructurado, clasificadores de tipo de cláusula (penalización, terminación, renovación automática, SLA), extracción con Pydantic models validados, UI de revisión con citas exactas del texto original, y presentación siempre como herramienta de asistencia al revisor humano.
- **RAG sobre codebase:** indexación de repositorios Git con tree-sitter para parsing sintáctico, chunking por función o clase respetando límites semánticos, embeddings especializados en código (Voyage Code-3), y filtros por repositorio y rama según permisos de acceso al código del usuario.

---

**Para recordar:** Cada caso de uso de RAG enterprise tiene una métrica de negocio específica que debe definirse antes de la implementación y medirse continuamente en producción. Sin esa métrica, es imposible demostrar el valor del sistema una vez en producción, justificar la inversión adicional en mejoras, o detectar cuándo el sistema deja de generar valor.

La sección de cierre sintetiza el argumento central del capítulo sobre RAG enterprise: que la complejidad de estos sistemas no está en la sofisticación del retrieval sino en la robustez del control de acceso y la frescura del conocimiento indexado.
