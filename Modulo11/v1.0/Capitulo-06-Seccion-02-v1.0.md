# Módulo 11 – Capítulo 06 – Sección 02

## Document-level permissions: que el sistema RAG respete el control de acceso de los documentos fuente

La implementación técnica del control de acceso en sistemas RAG enterprise tiene una propiedad contraintuitiva que sorprende a los equipos que la encuentran por primera vez: filtrar los resultados en la capa de presentación, después de que el LLM ha generado su respuesta, no proporciona ninguna protección de seguridad real. Si el LLM recibió en su contexto un fragmento de un documento clasificado como "confidencial" antes de generar la respuesta, esa información ya fue procesada y puede estar presente en la respuesta generada, aunque el sistema filtre la respuesta antes de mostrarla al usuario. El control de acceso real en sistemas RAG debe implementarse en la **capa de retrieval**, antes de que ningún documento no autorizado entre en el contexto del LLM.

El mecanismo técnico del **pre-filtering** funciona así: antes de ejecutar la búsqueda por similitud vectorial, el sistema resuelve los grupos de permisos del usuario autenticado consultando al Identity Provider (Okta, Azure AD, o el LDAP corporativo) y construye un filtro de metadata que restricta la búsqueda vectorial a los documentos donde el usuario tiene permiso de lectura. En Pinecone, el filtro se especifica como un parámetro `filter` en la query vectorial con operadores `$in` (el campo `allowed_groups` del documento contiene al menos uno de los grupos del usuario) — la búsqueda vectorial opera solo sobre los vectores que pasan el filtro de metadata, no sobre el índice completo. En Weaviate, los `where` filters cumplen la misma función. En pgvector sobre PostgreSQL, las políticas de Row Level Security implementan el filtro de manera automática e incluso más robusta: el filtro se aplica a nivel del motor de base de datos, independientemente de cómo la aplicación construya la query SQL.

El desafío de rendimiento de este enfoque es real y no debe ignorarse. La lista de grupos de permisos del usuario puede ser larga — un ejecutivo senior puede pertenecer a 50-100 grupos de seguridad — y los filtros de metadata en bases de datos vectoriales tienen un overhead de rendimiento proporcional a la complejidad del filtro. La solución estándar es un **permissions-resolver service** que cachea en Redis el resultado de la consulta al IAM por user_id con un TTL de 5-10 minutos, reduciendo el número de consultas al IAM corporativo de una por petición a una cada 5-10 minutos por usuario activo. Esta caché introduce una latencia de revocación — en el peor caso, un usuario al que se le revocó el acceso puede seguir accediendo a documentos durante el TTL de la caché — que debe ser explícitamente documentada y aprobada por el CISO como parte del contrato de seguridad del sistema RAG.

La **herencia de permisos** añade una capa adicional de complejidad: cuando un directorio en SharePoint tiene permisos asignados, todos los documentos dentro de ese directorio heredan esos permisos a menos que tengan permisos explícitos propios. Esta lógica de herencia, que los sistemas DMS como SharePoint gestionan automáticamente, debe replicarse exactamente en el pipeline de indexación del RAG: cuando se indexa un documento, el sistema debe resolver los permisos efectivos del documento incluyendo los heredados del directorio, y almacenarlos como metadata junto al vector. Sin esta replicación, el índice vectorial puede tener permisos incorrectos que no reflejan el estado real del DMS.

## Aspectos técnicos de document-level permissions

- **Permission metadata en embeddings:** cada documento se vectoriza con metadata que incluye `document_acl` (lista de grupos con acceso de lectura), `classification_level`, y `owner_department`, almacenada como campos filtrables en el índice vectorial.
- **Pre-filtering vs post-filtering:** pre-filtering (filtro antes de la búsqueda vectorial) garantiza que ningún documento no autorizado entra en el contexto del LLM; post-filtering no proporciona protección real porque el LLM ya procesó la información.
- **Permissions resolver con caché:** servicio que consulta Azure AD Graph API o LDAP, cachea el resultado por user_id en Redis con TTL de 5-10 minutos, y expone el permission set como lista de group_ids para construir el filtro vectorial.
- **Herencia de permisos:** el pipeline de indexación debe resolver los permisos efectivos de cada documento incluyendo los heredados del directorio contenedor en el DMS, actualizando la metadata del vector cuando los permisos del directorio cambian.
- **Revocación y TTL de caché:** el contrato de seguridad del sistema RAG debe documentar explícitamente el tiempo máximo de revocación de acceso (equivalente al TTL del caché de permisos), con aprobación explícita del CISO como parte del proceso de diseño de seguridad.

---

**Buena práctica:** Documentar explícitamente en el security design document del sistema RAG el tiempo máximo de revocación de acceso — el tiempo que puede transcurrir entre que el IAM revoca un permiso y que el sistema RAG refleja ese cambio. Este parámetro (equivalente al TTL del caché de permisos) debe ser aprobado formalmente por el CISO, no decidido unilateralmente por el equipo de ingeniería.

Con el control de acceso a nivel de documento establecido, la sección siguiente amplía el scope del RAG enterprise más allá de los documentos no estructurados para incluir los datos estructurados que residen en bases de datos y data warehouses — el RAG híbrido que cubre el espectro completo de necesidades de información de un enterprise.
