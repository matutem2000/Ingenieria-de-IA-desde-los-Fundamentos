# Módulo 11 – Capítulo 10 – Sección 03

## Construcción de plataforma incremental: comenzar simple y añadir complejidad con evidencia

La tentación más común en la construcción de plataformas de IA enterprise es diseñar la plataforma completa antes de construir nada: la arquitectura de referencia con todos los componentes, el hub-and-spoke con el IDP, el sistema multi-tenant con aislamiento de datos completo, el pipeline de evaluación continua, el cost allocation por equipo. Esta estrategia produce diagramas de arquitectura impresionantes y proyectos que tardan 18 meses en entregar un primer resultado tangible, durante los cuales los requisitos del negocio cambian, los modelos de LLM evolucionan de manera que invalidan algunas decisiones de diseño, y la credibilidad del equipo se erosiona por la ausencia de resultados visibles. La alternativa es comenzar con la infraestructura mínima que permite entregar el primer caso de uso en producción, y añadir cada componente de plataforma cuando la evidencia de uso demuestre que es necesario.

El **principio de la complejidad justificada** define el proceso: no se añade un componente de plataforma hasta que existe evidencia operacional de que la ausencia de ese componente está produciendo un problema real en producción. El sistema de gestión de prompts no se construye porque "algún día vamos a necesitar versionado de prompts" — se construye cuando el equipo ha tenido que hacer rollback de un prompt en producción y el proceso manual fue tan costoso y riesgoso que justifica la inversión en el sistema formal. El pipeline de evaluación continua no se implementa porque "las mejores prácticas recomiendan evaluación automática" — se implementa cuando el equipo ha detectado una degradación de calidad en producción que habría sido detectada antes si hubiera existido el pipeline de evaluación.

La **secuencia de construcción incremental** que produce resultados verificables en cada etapa sigue una progresión lógica dictada por las dependencias entre los componentes. La primera etapa — que puede completarse en 2-4 semanas — establece la base mínima: un repositorio Git para todos los artefactos del sistema de IA (prompts, código del pipeline, configuración del entorno), un Dockerfile que garantiza la reproducibilidad del entorno de inferencia, y un entorno de staging separado del entorno de producción donde probar los cambios antes del despliegue. Sin esta base, ningún componente más avanzado puede construirse con confianza. La segunda etapa — semanas 4-10 — añade el pipeline de CI/CD básico, la evaluación manual con el golden dataset como gate de calidad antes de cada despliegue, y el logging básico de trazas de producción. La tercera etapa — semanas 10-20 — introduce la evaluación automática con LLM-as-a-judge, el prompt registry con API, y los dashboards de observabilidad con las métricas de calidad definidas en el Capítulo 09.

El **criterio de añadir multi-tenancy** es particularmente importante de calibrar bien: la arquitectura multi-tenant del Capítulo 04 es esencial para plataformas que sirven a múltiples equipos de negocio, pero añadirla prematuramente — cuando la plataforma sirve a un solo equipo con un solo caso de uso — introduce complejidad que frena la velocidad sin aportar valor. El indicador de que ha llegado el momento de añadir multi-tenancy es la presencia de al menos 3-4 equipos consumidores con casos de uso activos en producción: en ese punto, la ausencia de aislamiento de datos, de rate limiting por equipo, y de cost allocation produce problemas reales que requieren el componente formal.

> **Nota del Arquitecto:** "Comenzar simple" no significa "comenzar de cualquier manera." Hay componentes que siempre deben estar presentes desde el día uno: el control de versiones del código y los prompts, el entorno de staging separado de producción, y el logging de trazas para diagnóstico. Omitir estos tres componentes para "ir más rápido" en la primera etapa produce una deuda técnica que es extraordinariamente costosa de pagar más tarde — el refactoring de un sistema sin control de versiones ni separación de entornos tiene un costo mayor que haberlos construido desde el inicio.

## Secuencia de construcción incremental de la plataforma

- **Etapa 1 (semanas 1-4) — Base mínima viable:** repositorio Git con todo el código y los prompts del sistema, Dockerfile reproducible para el servicio de inferencia, entorno de staging separado de producción, pipeline básico de CI con tests unitarios. Sin estos cuatro elementos, la plataforma no puede evolucionar de manera controlada.
- **Etapa 2 (semanas 4-10) — Calidad básica:** golden dataset con 50-100 casos curados como gate de calidad, pipeline de CD que despliega automáticamente cuando el build y los tests pasan, logging de trazas con el par (input, output) de cada petición de producción, alertas básicas de errores HTTP y latencia p95.
- **Etapa 3 (semanas 10-20) — Evaluación y observabilidad:** LLM-as-a-judge ejecutándose sobre muestras del tráfico de producción, prompt registry con API de versionado y rollback, dashboards de observabilidad con las métricas de calidad del sistema, detección básica de drift sobre la distribución de inputs.
- **Etapa 4 (semanas 20-40) — Plataforma compartida:** multi-tenancy con aislamiento de datos cuando hay 3+ equipos consumidores, cost allocation por equipo, Internal Developer Portal con templates de casos de uso, detección automática de anomalías en las métricas de calidad.
- **Criterio de avance de etapa:** cada etapa se completa solo cuando el componente añadido está en producción con datos reales — no cuando el prototipo funciona en staging. El avance basado en prototipos produce plataformas que funcionan en condiciones ideales pero no en las condiciones reales de la organización.

---

**Idea central:** La complejidad de la plataforma debe crecer al mismo ritmo que la evidencia que la justifica — no más rápido, para evitar construir componentes que nadie usa, y no más lento, para evitar acumular deuda técnica que frena la velocidad operacional. El proceso de construcción incremental es el mecanismo que calibra ese ritmo.

La sección siguiente aborda el complemento necesario de la construcción incremental: cómo identificar, clasificar, y gestionar la deuda técnica que inevitablemente se acumula durante el proceso de construcción rápida de los primeros casos de uso y los primeros componentes de plataforma.
