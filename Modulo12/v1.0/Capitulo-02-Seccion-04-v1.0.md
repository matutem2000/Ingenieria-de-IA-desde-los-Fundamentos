# Módulo 12 – Capítulo 02 – Sección 04

## ADR-003: diseño de agentes — framework, herramientas, autonomía y estado persistente

La decisión sobre el framework agéntico y el nivel de autonomía del agente es simultáneamente una decisión de funcionalidad y una decisión de seguridad. Un agente que puede ejecutar código arbitrario, acceder a bases de datos de producción en escritura o encadenar herramientas sin límite de iteraciones ofrece más capacidades pero introduce una superficie de ataque que es técnicamente muy difícil de cerrar por completo. Un agente que solo puede hacer consultas de lectura sobre una base de conocimiento interna tiene menos superficie de ataque pero también menos autonomía. El ADR-003 documenta las decisiones sobre dónde se ubica este sistema en ese espectro, y por qué.

La comparación entre frameworks evaluó tres opciones: LangChain AgentExecutor, LangGraph y AutoGen. LangChain AgentExecutor fue la primera opción descartada: implementa el ciclo ReAct como una secuencia lineal de pasos sin soporte de grafos de estado con ciclos condicionales. En la práctica, esto significa que si el agente necesita reintentar una búsqueda con una query reformulada después de recibir un resultado insatisfactorio, AgentExecutor no tiene un mecanismo limpio para expresar ese ciclo — requiere hacks que hacen el código difícil de debuggear y mantener. AutoGen fue descartado porque su arquitectura de conversaciones multi-agente (con un agente usuario y un agente asistente que se comunican en lenguaje natural) añade complejidad de configuración innecesaria para un caso de uso de agente único, y su integración con el ecosistema LangChain que el pipeline RAG usa es menos directa. LangGraph fue elegido porque es el único que soporta grafos de estado con ciclos condicionales, checkpointing nativo para persistencia de sesión y control granular de las condiciones de parada del ciclo.

Las herramientas del agente se eligieron siguiendo el principio de mínima autonomía suficiente: el agente tiene acceso únicamente a las herramientas que necesita para cumplir su función de asistencia técnica, y todas son de solo lectura. `search_knowledge_base(query, filters, top_k)` encapsula el pipeline RAG completo y es la herramienta más frecuentemente llamada. `get_document_by_id(doc_id)` permite al agente recuperar el texto completo de un documento cuando necesita más contexto del que el chunk recuperado provee. `list_available_sources(document_type)` permite al agente verificar qué tipos de documentos están indexados antes de formular una búsqueda, evitando buscar runbooks si el tipo "runbook" no está disponible. Estas tres herramientas cubren el 95% de los casos de uso del asistente técnico sin exponer ninguna capacidad de escritura.

Un aspecto que el Capítulo 4 desarrolla en detalle pero que debe quedar establecido en el ADR es la gestión del estado persistente del agente entre sesiones. El campo `session_id` del schema de la API `QueryRequest` implica que el sistema mantiene estado por sesión — el agente recuerda el historial de la conversación del mismo usuario dentro de una sesión activa. Ese estado se implementa con LangGraph Persistence sobre PostgreSQL (RDS en producción): el grafo de estado del agente se serializa y almacena en PostgreSQL con clave `(session_id, checkpoint_id)` después de cada paso del ciclo ReAct. La política de retención almacena el historial completo de la sesión activa (últimas 10 iteraciones del ciclo) más un resumen comprimido de sesiones anteriores del mismo usuario (últimas 3 sesiones, comprimidas a 500 tokens por sesión mediante un LLM de summarización). Este diseño permite al agente recordar el contexto de la conversación actual sin almacenar indefinidamente toda la historia de interacciones.

El nivel de autonomía máximo del agente se fija explícitamente en el ADR: el agente puede tomar decisiones de búsqueda y reformulación de queries de forma autónoma hasta max_iterations=5. Para queries clasificadas como `high_risk` por el clasificador de intent (queries que piden información sobre sistemas de seguridad internos o credenciales de acceso), se activa un modo Human-in-the-Loop donde el agente presenta su plan de acción y espera aprobación antes de ejecutar las herramientas.

## Decisiones del diseño agéntico

- **Framework**: LangGraph seleccionado sobre LangChain AgentExecutor (no soporta grafos con ciclos) y AutoGen (complejidad multi-agente innecesaria para caso de uso de agente único).
- **Patrón de razonamiento**: ReAct (Reasoning + Acting) con ciclo `Thought → Action → Observation`, max_iterations=5 y fallback a respuesta parcial más informativa al alcanzar el límite.
- **Herramientas disponibles**: `search_knowledge_base`, `get_document_by_id`, `list_available_sources` — todas de solo lectura, sin acceso a sistemas externos en escritura.
- **Nivel de autonomía**: autónomo para queries clasificadas como `safe` o `suspicious`; Human-in-the-Loop para queries clasificadas como `high_risk` por el clasificador de intent.
- **Estado persistente**: checkpointing LangGraph en PostgreSQL (RDS) con clave `(session_id, checkpoint_id)`, retención de últimas 10 iteraciones activas + resumen comprimido de últimas 3 sesiones del usuario.

> **Nota del Arquitecto**: La decisión sobre el estado persistente del agente es más importante de lo que parece en el diseño inicial. Un agente sin memoria de sesión trata cada mensaje del usuario como una conversación nueva — el usuario tiene que repetir el contexto en cada turno. Un agente con memoria persistente entre sesiones introduce preguntas sobre privacidad (¿quién puede ver el historial de conversación de otro usuario?), sobre seguridad (¿el historial de sesión puede ser manipulado mediante injection?), y sobre costo (¿cuánto storage consume almacenar el historial de todos los usuarios?). Definir la política de retención en el ADR — no en el código — garantiza que esas preguntas tienen respuesta antes de la implementación.

El ADR-003 establece el marco dentro del cual el Capítulo 4 implementa el agente. El contrato de herramientas tipado con Pydantic, el sistema prompt con instrucciones de grounding y criterios de parada, y el testing de escenarios de fallo son consecuencias directas de las decisiones documentadas en este ADR. Los equipos que omiten esta documentación suelen descubrir semanas después que el agente puede entrar en bucles, que las herramientas no tienen manejo de errores consistente, o que el estado de sesión se filtra entre usuarios — problemas que el ADR habría señalado como riesgos a mitigar.

**Para recordar**: Documentar el nivel de autonomía máximo del agente en el ADR es una decisión de seguridad, no solo de diseño — define qué acciones el sistema puede tomar sin aprobación humana y cuáles requieren confirmación explícita.
