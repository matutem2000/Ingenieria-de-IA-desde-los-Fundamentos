# Módulo 12 – Capítulo 05 – Sección 03

## Autenticación y autorización: control de acceso al sistema y a las herramientas del agente

La autenticación verifica que el usuario es quien dice ser; la autorización determina qué puede hacer ese usuario verificado. En sistemas de IA agénticos, la autorización tiene una dimensión adicional que los sistemas convencionales no tienen: el agente puede recuperar información de múltiples fuentes y sintetizarla en una respuesta, de modo que los límites de acceso deben aplicarse no solo al nivel de qué endpoints puede llamar el usuario, sino a qué información puede el agente recuperar en nombre de ese usuario. Un sistema donde la autorización opera solo a nivel de endpoint pero no a nivel de retrieval puede ser explotado por un usuario que formula queries creativas que llevan al agente a recuperar documentos a los que ese usuario no tiene acceso directo.

La autenticación del sistema usa JWT (JSON Web Tokens) con algoritmo RS256. La elección de RS256 sobre HS256 es deliberada: HS256 usa una clave simétrica compartida entre el issuer del token y el verificador, lo que requiere que FastAPI tenga acceso a la clave secreta del identity provider. RS256 usa un par de claves asimétrico: el identity provider firma con la clave privada y FastAPI verifica con la clave pública, que puede distribuirse sin riesgo. Si la instancia de FastAPI es comprometida, el atacante obtiene solo la clave pública — insuficiente para crear tokens válidos. El middleware FastAPI de autenticación verifica la firma del JWT en cada petición, valida la expiración del token (`exp` claim) y extrae los claims de autorización (`roles` y `allowed_document_types`).

Los claims de autorización `allowed_document_types` son la clave del control de acceso a nivel de retrieval. Un ingeniero del equipo de infraestructura con acceso a documentación de infraestructura tiene en su JWT `allowed_document_types: ["runbook", "adr", "api-spec"]`. Un colaborador externo con acceso solo a documentación pública tiene `allowed_document_types: ["api-spec"]`. Cuando cualquiera de los dos usuarios formula una query, la herramienta `search_knowledge_base` extrae `allowed_document_types` del contexto de autenticación del request y lo añade como filtro mandatory en la query de Qdrant — no como un check post-retrieval sino como una restricción en la búsqueda misma. Qdrant aplica el filtro usando el payload index de `document_type`, garantizando que los chunks de tipos no autorizados ni siquiera aparecen en los candidatos de recuperación. El agente no puede eludir este control aunque sea manipulado mediante injection para intentar acceder a tipos de documentos no autorizados — el filtro está en la capa de infraestructura, fuera del control del LLM.

El lifecycle de tokens sigue el patrón de tokens de corta duración con refresh automático. Los access tokens tienen una vida de 15 minutos, lo que minimiza la ventana de explotación si un token es comprometido — un atacante que roba un access token tiene máximo 15 minutos antes de que expire. Los refresh tokens tienen una vida de 24 horas con rotación automática: cada vez que el cliente usa un refresh token para obtener un nuevo access token, el refresh token usado se invalida y se emite uno nuevo. Los refresh tokens se almacenan en httpOnly cookies, inaccesibles a JavaScript malicioso en el navegador del cliente, protegiendo contra ataques XSS que intenten robar credenciales de sesión.

El audit trail de autenticación registra cada petición autenticada en PostgreSQL: `user_id`, `timestamp`, `endpoint`, `method`, `result` (success/auth_failure/authz_failure), `ip_address_hash` (hash para privacidad) y `session_id`. Este registro permite reconstruir la actividad de un usuario específico en un intervalo de tiempo — esencial para investigación de incidentes de seguridad y para cumplimiento regulatorio. La retención del audit log es de 90 días en PostgreSQL caliente y de 1 año en S3 archivado.

## Controles de autenticación y autorización

- **JWT RS256**: tokens firmados con clave privada del identity provider (AWS Cognito o Auth0), verificados con clave pública en cada petición al middleware FastAPI — la clave privada nunca toca la instancia del servidor.
- **Claims de autorización**: `roles` (lista de roles del usuario) y `allowed_document_types` (tipos de documentos autorizados) incluidos en el JWT; validados y extraídos por el middleware de autenticación antes de llegar al agente.
- **Filtros automáticos a nivel de retrieval**: `search_knowledge_base` aplica `allowed_document_types` como filtro mandatory en Qdrant — garantía estructural independiente del comportamiento del agente o del LLM.
- **Token lifecycle**: access token 15 minutos, refresh token 24 horas con rotación automática; refresh tokens en httpOnly cookies; invalidación de refresh tokens previos en cada renovación.
- **Audit trail**: cada petición autenticada registrada en PostgreSQL con user_id, timestamp, endpoint, result e ip_hash; retención 90 días caliente + 1 año en S3 archivado; sin almacenamiento del contenido de las queries (solo metadata).

> **Nota del Arquitecto**: El filtro de `allowed_document_types` a nivel de Qdrant es la decisión de autorización más importante del sistema — y la más fácil de implementar incorrectamente. El error común es aplicar el filtro como un check post-retrieval en el código del agente: recuperar los chunks y luego verificar si el usuario tiene acceso a cada uno. Este enfoque tiene una vulnerabilidad sutil: en el momento entre el retrieval y el check, el chunk ya fue procesado por el LLM y puede haber influenciado el razonamiento del agente. El filtro en la query de Qdrant previene que ese chunk llegue al LLM en absoluto — es la única forma de garantizar que la autorización opera como control estructural, no como check de post-procesamiento que puede ser evadido por race conditions o bugs en el código del agente.

La autenticación y autorización del sistema cierra el vector de divulgación no autorizada de información — la amenaza de mayor probabilidad en un sistema donde el conocimiento indexado tiene diferentes niveles de sensibilidad. El Capítulo 5 continúa con la validación de inputs y el output filtering: los controles en los boundaries del sistema que complementan los controles dentro del agente.

**Para recordar**: La autorización a nivel de herramientas del agente es el control más efectivo contra divulgación no autorizada — si el retrieval filtra automáticamente por los permisos del usuario, el agente no puede devolver documentos a los que el usuario no tiene acceso, independientemente de cómo formule su query.
