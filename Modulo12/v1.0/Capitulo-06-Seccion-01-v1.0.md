# Módulo 12 – Capítulo 06 – Sección 01

## Containerización: Dockerfile del sistema, dependencias y configuración de producción

La containerización es el mecanismo que garantiza que el sistema que funciona en el entorno de desarrollo del ingeniero es exactamente el mismo sistema que se ejecuta en producción. "Funciona en mi máquina" es el síntoma de sistemas donde la containerización está incompleta o inconsistente — una dependencia que el desarrollador tiene instalada globalmente, una variable de entorno que existe en el shell del desarrollador pero no en el servidor, una versión de Python diferente entre local y producción. Un Dockerfile de producción correcto elimina esas fuentes de inconsistencia haciendo explícitas todas las dependencias del sistema.

El Dockerfile del proyecto usa un build multi-stage que separa el entorno de build del entorno de runtime. Esta separación tiene un beneficio de seguridad directo: el entorno de runtime no contiene las herramientas de compilación (gcc, build-essential, pip con todos sus archivos de caché) que son necesarias para instalar dependencias pero innecesarias para ejecutar la aplicación. Un contenedor más pequeño tiene menor superficie de ataque — menos binarios disponibles significa menos herramientas que un atacante puede usar si compromete el contenedor. El tamaño típico de la imagen final con multi-stage es de 200-300MB versus 800MB-1GB de un Dockerfile de stage único.

El **primer stage** (`builder`) usa `python:3.11-slim` como base, instala `build-essential` para compilar paquetes con extensiones nativas, y ejecuta `pip install --require-hashes -r requirements.txt`. La flag `--require-hashes` es crítica: requiere que cada paquete en `requirements.txt` tenga su hash SHA-256 especificado, verificado por pip durante la instalación. Si alguien modifica un paquete en el registry de PyPI después de la primera instalación — un ataque conocido como supply chain attack — la verificación de hash detectará la discrepancia y fallará la build. `requirements.txt` con hashes se genera con `pip-compile --generate-hashes` de `pip-tools`.

El **segundo stage** (`runtime`) usa `python:3.11-slim` limpio (sin build-essential), copia únicamente el directorio de site-packages del stage builder y el código de la aplicación. Configura un usuario no-root con `uid:gid 1000:1000` — un proceso que se ejecuta como root en un contenedor puede explotar vulnerabilidades de kernel para escapar al host; un proceso que se ejecuta como uid 1000 tiene capacidades limitadas incluso si logra explotar una vulnerabilidad del contenedor. El `ENTRYPOINT` configura uvicorn con 4 workers (adecuado para instancias c5.xlarge con 4 vCPU), sin `--access-log` (los logs de acceso se emiten via OpenTelemetry con mayor detalle y formato estructurado), y con `--timeout-keep-alive 30` para cerrar conexiones keep-alive inactivas que de otra forma consumen file descriptors.

Las variables de entorno sensibles nunca se incluyen en la imagen Docker — es uno de los errores de seguridad más frecuentes y con consecuencias más graves. Si `OPENAI_API_KEY` está en el Dockerfile, está en el layer history de la imagen, que es accesible para cualquiera que descargue la imagen. Las variables se inyectan en tiempo de ejecución mediante Kubernetes Secrets (sincronizados desde AWS Secrets Manager con External Secrets Operator en el Capítulo 6, Sección 5) o mediante Docker secrets en entornos de Docker Compose.

## Aspectos técnicos de la containerización

- **Multi-stage build**: stage `builder` con `build-essential` + `pip install --require-hashes`; stage `runtime` con artefactos compilados únicamente — imagen final 200-300MB vs 800MB+ sin multi-stage.
- **Usuario no-root**: grupo y usuario `appuser` con `uid:gid 1000:1000`, sin acceso a `/root` ni a binarios de sistema — reduce el impacto de vulnerabilidades de contenedor.
- **Hash verification**: `pip install --require-hashes -r requirements.txt` — detecta tampering de paquetes en PyPI; `requirements.txt` generado con `pip-compile --generate-hashes` para reproducibilidad.
- **Health check integrado**: `HEALTHCHECK --interval=30s --timeout=5s --retries=3 CMD curl -f http://localhost:8000/health || exit 1` — Kubernetes usa este health check para determinar cuándo el pod está listo para recibir tráfico.
- **Configuración de producción**: `uvicorn app.main:app --host 0.0.0.0 --port 8000 --workers 4 --timeout-keep-alive 30 --no-access-log` — workers configurados según vCPUs de la instancia, logs via OpenTelemetry.
- **Verificación pre-deploy**: el pipeline CI/CD ejecuta `docker inspect` para verificar que la imagen resultante tiene el usuario no-root configurado y que no hay secrets en las variables de entorno hardcodeadas.

> **Nota del Arquitecto**: La verificación de hashes en las dependencias es el control de seguridad que más frecuentemente se omite porque parece excesivo para un proyecto interno. La realidad es que los ataques de supply chain a paquetes de PyPI ocurren con regularidad — el typosquatting (paquetes con nombres similares a los populares, como `requets` en lugar de `requests`) y la inyección de código malicioso en paquetes legítimos comprometidos son vectores reales documentados. Para un sistema que procesa documentación técnica interna de una organización y tiene acceso a credenciales de servicios externos, la integridad de las dependencias no es una preocupación académica. `pip-compile --generate-hashes` añade 2 minutos al proceso de generación del requirements.txt y 30 segundos a cada build — es la inversión de tiempo más barata por unidad de reducción de riesgo en el pipeline de build.

Un Dockerfile de producción no es el Dockerfile de desarrollo con un CMD diferente. Requiere multi-stage build, usuario no-root, hash verification de dependencias y configuración explícita del runtime para ser seguro, reproducible y eficiente. El pipeline CI/CD del Capítulo 6, Sección 2 construye esta imagen en el stage de build y la publica en el registry privado — el fundamento sobre el que todos los despliegues posteriores se construyen.
