# Módulo 12 – Capítulo 09 – Sección 01

## README técnico: descripción del sistema, arquitectura y cómo ejecutarlo localmente

La observabilidad del Capítulo 8 permite detectar y diagnosticar incidentes — pero solo si el ingeniero que recibe la alerta sabe qué sistema está operando, cómo está estructurado y qué comandos ejecutar para intervenir. El Capítulo 9 es el complemento humano del stack de observabilidad: los artefactos de documentación que convierten el conocimiento tácito del equipo fundador en conocimiento explícito accesible a cualquier ingeniero del equipo. El runbook operativo que cada alerta del Capítulo 8 referencia mediante un URL vive en este capítulo; el README que permite ejecutar el sistema localmente en menos de 30 minutos transforma el onboarding de semanas a días.

El README técnico del proyecto es el primer documento que lee un nuevo ingeniero y el último que escribe el equipo — lo que significa que frecuentemente está desactualizado en el momento más crítico: cuando el nuevo ingeniero lo necesita. La solución no es "actualizar el README después" — es tratar el README como parte del criterio de aceptación de cada PR que modifica el proceso de setup. Si el PR añade una nueva variable de entorno requerida, el PR no puede fusionarse sin actualizar `.env.example` y el paso correspondiente en el README.

El README incluye cinco secciones obligatorias que responden las cinco preguntas que cualquier nuevo ingeniero tiene en su primer día. La **descripción del sistema** (qué hace, para quién, en qué estado está) establece el contexto sin asumir que el lector conoce el proyecto. Dos párrafos concisos son suficientes: el primero describe el caso de uso y el usuario objetivo, el segundo describe el estado actual del sistema (versión, nivel de madurez, restricciones conocidas). La **arquitectura de alto nivel** usa un diagrama Mermaid renderizable en GitHub que muestra los componentes principales, los flujos de datos entre ellos y las dependencias externas (OpenAI, Cohere, Qdrant Cloud). El diagrama Mermaid es preferible a una imagen PNG porque se versiona en texto y puede actualizarse en el mismo commit que el código que cambia la arquitectura.

Los **prerrequisitos** listan las versiones exactas de cada herramienta necesaria para el setup local: Python 3.11.x (no "Python 3+"), Docker 24.x, Docker Compose 2.x, acceso a credenciales de OpenAI y Cohere (con instrucciones sobre cómo obtenerlos en el entorno de desarrollo), y acceso a Qdrant (instrucciones para el despliegue local con Docker o para usar Qdrant Cloud tier gratuito). La especificidad de versiones no es excesiva — es lo que previene que un ingeniero pase horas debuggeando un error causado por usar Python 3.9 en lugar de 3.11.

Las **instrucciones de setup local** son la sección más crítica del README y deben ser verificadas con un checkout fresco en una máquina limpia antes de cada release. El proceso en 7 pasos: `git clone`, `cd technical-assistant`, `cp .env.example .env` (y editar las credenciales reales), `docker compose up -d` (levanta Qdrant, Redis y PostgreSQL localmente), `pip install -e ".[dev]"` (instala la aplicación y las dependencias de desarrollo), `python scripts/create_test_collection.py` (crea la colección de Qdrant con datos de prueba), y `curl http://localhost:8000/health` para verificar que el sistema responde. Si este proceso funciona en menos de 30 minutos en una máquina limpia, el README cumple su función.

## Secciones del README técnico

- **Descripción**: caso de uso (asistente técnico para ingenieros de software), usuario objetivo (equipos de ingeniería con documentación interna), estado del sistema (versión actual, restricciones de alcance documentadas, limitaciones conocidas).
- **Diagrama de arquitectura**: Mermaid graph LR con componentes (FastAPI, LangGraph, Qdrant, Redis, PostgreSQL) y flujos de datos; versionado en texto en el repositorio, actualizable en el mismo commit que el código.
- **Prerrequisitos**: Python 3.11.x, Docker 24.x, Docker Compose 2.x, API keys de OpenAI y Cohere (con instrucciones para obtenerlos), acceso a Qdrant (Docker local o Qdrant Cloud free tier).
- **Setup en 7 pasos**: verificado en máquina limpia antes de cada release; tiempo objetivo < 30 minutos; incluye comandos completos para copy-paste, no solo descripciones de alto nivel.
- **Troubleshooting**: los 3 errores más frecuentes en el setup local (basados en issues reportados por nuevos integrantes): `OPENAI_API_KEY not set`, puerto 8000 en uso (conflicto con otra aplicación) y error de conexión a Qdrant (Docker no corriendo).
- **Quick start**: un comando de verificación que confirma que el sistema está funcionando correctamente — `curl -X POST http://localhost:8000/query -H "..." -d '{"query": "¿qué es el pipeline RAG?"}'` con la respuesta esperada como referencia.

> **Nota del Arquitecto**: La sección de Troubleshooting del README es la que más impacto tiene en el onboarding pero la que requiere más disciplina para mantener. Los errores más frecuentes en el setup local cambian con cada versión del sistema; si el Troubleshooting no se actualiza cuando cambian los errores comunes, los nuevos ingenieros siguen procedimientos que ya no aplican. La práctica que funciona es mantener un archivo `SETUP_ISSUES.md` donde cualquier ingeniero puede añadir un error que encontró y su solución, y revisar ese archivo antes de cada release para actualizar el Troubleshooting del README con los casos más recientes. Este proceso de curaduría distribuida produce un Troubleshooting mucho más completo que el que cualquier ingeniero individual podría mantener.

El README técnico no documenta el código — para eso existen los docstrings y los comentarios inline. Documenta el sistema: cómo desplegarlo, cómo verificar que funciona y cómo orientarse en el código para contribuir al componente correcto. El Capítulo 9 continúa con la documentación de API, que formaliza el contrato entre el sistema y sus consumidores.

**Para recordar**: Un README técnico que no permite a un nuevo ingeniero ejecutar el sistema localmente en menos de 30 minutos sin ayuda no está cumpliendo su función — debe actualizarse cada vez que cambia el proceso de setup.
