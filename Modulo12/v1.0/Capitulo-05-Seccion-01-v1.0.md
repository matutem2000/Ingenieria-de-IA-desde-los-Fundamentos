# Módulo 12 – Capítulo 05 – Sección 01

## Threat model del sistema integrador: de la decisión a la implementación

Este capítulo implementa los controles definidos en el ADR-004 del Capítulo 2. No repite el análisis de amenazas STRIDE — ese análisis ya existe en el ADR-004 y mantenerlo en dos lugares produciría inconsistencias inevitables. En cambio, este capítulo toma cada amenaza documentada en el ADR-004 y describe cómo el control seleccionado se traduce en código concreto, en configuración verificable y en tests de regresión. La progresión es: ADR-004 define qué proteger y con qué controles; Capítulo 5 demuestra que esos controles están implementados y que funcionan bajo ataque.

El marco STRIDE aplicado al sistema integrador produce un conjunto de amenazas específicas de sistemas RAG agénticos que difieren cualitativamente de las amenazas de APIs convencionales. En una API REST convencional, la amenaza de **Tampering** significa que alguien modifica los datos en tránsito; en un sistema RAG, Tampering incluye el caso de un agente interno o externo que inserta documentos maliciosos en el pipeline de ingesta con instrucciones embebidas para el LLM. En una API convencional, **Elevation of Privilege** significa escalar de un rol de usuario a administrador; en un sistema agéntico, significa manipular al agente para que encadene herramientas de formas no previstas y acceda a información o ejecute acciones fuera de su mandato.

Para el sistema de asistente técnico, las cinco amenazas de mayor prioridad son: prompt injection directa (usuario inyecta instrucciones maliciosas en la query), prompt injection indirecta (documentos en la base de conocimiento contienen instrucciones que el agente ejecuta al recuperarlos), divulgación no autorizada de información (el agente recupera y devuelve documentos a los que el usuario no debería tener acceso por su rol), denial of service mediante token flooding (queries diseñadas para maximizar el consumo de tokens del LLM), y repudiation (ausencia de audit log que vincule cada respuesta al usuario y query que la generaron). Cada amenaza tiene un nivel de probabilidad y de impacto documentado en el ADR-004; este capítulo implementa los controles correspondientes en orden de prioridad de riesgo.

La distinción crítica entre la seguridad de sistemas RAG y la seguridad de sistemas convencionales es la superficie de ataque dinámica: el contenido de los documentos en la base de conocimiento es input implícito al LLM en cada query. Un sistema de archivos con ACLs correctas es seguro respecto a los archivos — pero si esos archivos pueden contener instrucciones para el LLM que los procesa, la superficie de ataque se extiende al contenido de cada documento ingestado. Esta es la razón por la que los controles de seguridad en este sistema aparecen en múltiples capas: en el pipeline de ingesta (Capítulo 3), en el diseño del agente (Capítulo 4) y en los controles específicos de este capítulo. La seguridad no se añade al final — se enhebra a través de cada componente del sistema.

## Amenazas identificadas y controles correspondientes

- **Prompt injection directa** (Alta probabilidad, Alto impacto): controles — input validator con lista negra de 200 patrones, clasificador de intent multilingüe, delimitadores XML en el system prompt del agente.
- **Prompt injection indirecta** (Media probabilidad, Alto impacto): controles — sanitización de documentos en el pipeline de ingesta, delimitadores XML para chunks recuperados `<retrieved_document>`, instrucción de grounding en el system prompt.
- **Divulgación no autorizada** (Alta probabilidad, Alto impacto): control — autorización a nivel de herramienta: `search_knowledge_base` aplica `allowed_document_types` del JWT como filtro mandatory en Qdrant, garantía estructural independiente del comportamiento del agente.
- **Denial of Service por token flooding** (Media probabilidad, Medio impacto): controles — longitud máxima de query 2000 caracteres en la validación Pydantic, rate limiting 10 req/min por usuario, timeout del agente a nivel de petición.
- **Repudiation** (Alta probabilidad con sistema sin audit log): control — audit logging de cada petición con `user_id`, `timestamp`, `query_hash`, `tool_calls_executed` y `result_metadata` en PostgreSQL, con retención de 90 días.
- **Tool chaining no autorizado** (Baja probabilidad, Alto impacto): controles — max_iterations=5 como límite estructural, clasificador de intent que detecta queries con patrones de exfiltración, herramientas de solo lectura como limitación de diseño.

> **Nota del Arquitecto**: La seguridad de un sistema de IA no es un problema que se resuelve una vez — es una práctica que se mantiene. Los patrones de ataque evolucionan: los primeros ataques de prompt injection usaban variantes de "ignora las instrucciones anteriores" en inglés, fácilmente detectables con listas negras básicas. Los ataques sofisticados actuales usan instrucciones embebidas en estructuras de datos (JSON, XML) que los modelos de clasificación de texto no reconocen como texto instruccional, instrucciones en idiomas de baja representación en los datos de entrenamiento del clasificador, y codificaciones alternativas (Base64, ROT13) que evaden el match textual. El red teaming periódico — trimestral como mínimo — es el mecanismo que mantiene los controles actualizados frente a la evolución de los vectores de ataque.

Este capítulo implementa los controles en el orden de prioridad que el threat model establece: primero los controles contra prompt injection (las amenazas de mayor impacto y mayor probabilidad), luego los controles de autenticación y autorización, luego la validación de inputs y output filtering, y finalmente el red teaming que valida la efectividad del conjunto de controles. Las secciones siguientes desarrollan cada uno con el detalle de implementación necesario para verificar que el control funciona.

**Para recordar**: El threat model de un sistema de IA no es una formalidad de seguridad — es el documento que determina cuáles controles son no negociables y cuáles son mejoras opcionales, permitiendo priorizar el trabajo de hardening con evidencia de riesgo.
