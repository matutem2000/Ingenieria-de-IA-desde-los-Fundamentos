# Módulo 12 – Capítulo 10 – Sección 04

## Extensiones posibles: cómo seguir evolucionando el sistema más allá del alcance del proyecto

El sistema integrador del proyecto final es una plataforma con capacidades de producción demostradas, no un prototipo. Tiene la arquitectura, la instrumentación y los controles que permiten evolucionar hacia capacidades más avanzadas sin reescritura estructural: el pipeline de ingesta es extensible mediante la interfaz `BaseDocumentParser`, el agente acepta nuevas herramientas mediante el decorador `@tool`, la base vectorial puede reconvertirse con un proceso blue-green documentado, y el pipeline CI/CD propaga automáticamente cualquier cambio con el gate de evaluación RAGAS activo como guardia de regresión. Las extensiones que se describen a continuación no son aspiraciones teóricas — son los siguientes pasos naturales del sistema, priorizados por impacto esperado sobre el caso de uso actual.

La extensión de mayor impacto a corto plazo es el **fine-tuning del modelo de embedding sobre el corpus técnico del dominio**. El modelo `text-embedding-3-small` de OpenAI es un modelo de embeddings de propósito general entrenado sobre un corpus masivo y diverso — lo que significa que su representación semántica del espacio latente no está optimizada para la terminología específica del corpus de documentación técnica de ingeniería de software del sistema. Términos como "HNSW", "scalar quantization", "payload index" o "ReAct" pueden ser representados de forma subóptima porque tienen baja frecuencia en el corpus de preentrenamiento relativa a su frecuencia en el corpus de producción del sistema. El fine-tuning con contrastive learning sobre pares (query, documento relevante) del golden dataset puede mejorar el recall@5 entre 0.05 y 0.12 puntos para consultas que usen terminología específica del dominio. La inversión es significativa (días de ingeniería para el pipeline de fine-tuning + costo de compute) y debe justificarse con el análisis de las categorías de queries donde el retrieval actual tiene bajo recall, antes de comenzar.

La segunda extensión es el **soporte multimodal para documentos con contenido visual**. La documentación técnica de ingeniería de software frecuentemente contiene diagramas de arquitectura, capturas de dashboards, tablas de métricas y pseudocódigo en imágenes. El sistema actual no puede indexar este contenido porque `text-embedding-3-small` no procesa imágenes. La extensión requiere un pipeline de preprocesamiento: detectar imágenes en los documentos durante la ingesta, enviarlas a GPT-4o Vision o Claude 3.5 Sonnet Anthropic con un prompt que solicita una descripción textual densa del contenido visual (no una descripción general — una descripción que capture los valores numéricos, las relaciones entre componentes, y el significado técnico del diagrama), y añadir esa descripción como un chunk de texto adicional asociado al documento fuente. Este enfoque no requiere cambios en el schema de Qdrant ni en el modelo de embedding.

La tercera extensión — **sistema de feedback activo con captura de ratings** — cierra el ciclo entre el comportamiento del sistema en producción y la mejora del modelo. Actualmente, el sistema produce respuestas pero no tiene un mecanismo para saber qué respuestas fueron útiles para el usuario. Añadir un endpoint `POST /feedback` que acepte `{session_id, message_id, rating: 1|-1, comment: Optional[str]}` permite acumular un dataset de preferencias: pares (pregunta, respuesta, rating) que representan la señal directa del usuario sobre la calidad del sistema. Estos datos pueden usarse para: identificar las categorías de queries donde el sistema tiene peor desempeño (análisis de ratings negativos agrupados por cluster de queries), mejorar el golden dataset con los pares de alta calidad positiva (las respuestas con rating +1 son candidatos a golden pairs), y eventualmente para DPO (Direct Preference Optimization) si se acumulan suficientes pares contrastivos (misma query, respuesta positiva vs respuesta negativa).

## Extensiones priorizadas por impacto

- **Fine-tuning de embedding (impacto: alto, plazo: 4-6 semanas)**: contrastive learning sobre pares del golden dataset para mejorar recall@5 en terminología específica del dominio; prerequisito: análisis de recall por categoría para confirmar que hay un gap de terminología significativo.
- **Soporte multimodal (impacto: medio-alto, plazo: 2-3 semanas)**: pipeline OCR + descripción GPT-4o Vision para indexar diagramas, tablas y capturas de dashboards como chunks de texto adicionales; sin cambios en el schema de Qdrant.
- **Feedback activo con ratings (impacto: medio, plazo: 1-2 semanas)**: endpoint `POST /feedback`, dashboard de ratings por categoría, pipeline de curación de golden pairs desde feedback positivo; base para DPO a largo plazo.
- **Multi-tenancy (impacto: alto si hay expansión de usuarios, plazo: 4-8 semanas)**: aislamiento por tenant en Qdrant (colecciones separadas para nivel de aislamiento alto, o particionamiento por payload para nivel de aislamiento medio), RBAC por organización, billing por tenant con atribución de costo.
- **Agent memory de largo plazo (impacto: medio, plazo: 3-4 semanas)**: base de datos de hechos aprendidos de conversaciones anteriores (PostgreSQL con pgvector para búsqueda semántica sobre el historial de conversaciones del usuario), inyección selectiva de contexto relevante histórico en cada nueva conversación.

> **Nota del Arquitecto**: La extensión de multi-tenancy merece una advertencia sobre su complejidad subestimada. La primera implementación de multi-tenancy que los equipos proponen es "añadir un campo `tenant_id` a los documentos en Qdrant y filtrar por él". Esa implementación funciona para uso interno con un conjunto pequeño de tenants de confianza mutua — pero no es multi-tenancy real porque no garantiza el aislamiento de datos entre tenants. Un bug en el filtro de tenant_id (un campo nulo, una condición de race condition en una transacción) puede exponer documentos de un tenant a otro. El multi-tenancy correcto con aislamiento garantizado requiere colecciones separadas en Qdrant por tenant — lo que añade complejidad operativa (más colecciones que monitorear, más índices que mantener) pero garantiza que ningún bug de aplicación puede violar el aislamiento. La decisión entre ambos enfoques es un ADR que debe documentarse antes de comenzar la implementación.

Las extensiones posibles del sistema deben priorizarse con el mismo rigor que el proyecto inicial — no como ideas interesantes sino como inversiones con impacto esperado cuantificado, costo de implementación estimado, y riesgo de aumento de complejidad del sistema. La práctica de escribir un ADR antes de comenzar cada extensión significativa no es overhead burocrático — es la diferencia entre extensiones que el sistema puede absorber y extensiones que lo hacen más difícil de operar que antes de añadirlas.

**Para recordar**: Las extensiones posibles del sistema deben priorizarse con el mismo rigor que el proyecto inicial: impacto esperado cuantificado, costo de implementación estimado, y documentación en un nuevo ADR antes de comenzar. Una extensión sin ADR es una decisión sin registro.
