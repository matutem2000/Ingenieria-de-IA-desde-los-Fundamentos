# Módulo 12 – Capítulo 08 – Sección 01

## Stack de observabilidad del proyecto: trazas, métricas, logs y alertas

La observabilidad de un sistema de IA en producción no es una capa que se añade después del despliegue — es la infraestructura que hace posible operar con confianza en lugar de con esperanza. Un sistema que no se puede observar no se puede mejorar, no se puede diagnosticar cuando falla y no se puede demostrar que funciona correctamente ante stakeholders que necesitan evidencia. La observabilidad convierte el sistema de una caja negra que "parece funcionar" en un sistema transparente cuyo comportamiento puede describirse con precisión en cualquier momento.

El stack de observabilidad del proyecto implementa los tres pilares de la observabilidad moderna más una capa de alertas, siguiendo el estándar OpenTelemetry para garantizar que la instrumentación es vendor-neutral y puede exportarse a cualquier backend sin cambiar el código de la aplicación. Esta independencia del vendor no es una consideración abstracta: si el equipo decide migrar de Grafana Tempo a Jaeger para las trazas, o de Grafana Loki a Elasticsearch para los logs, el código de instrumentación OpenTelemetry no cambia — solo cambia la configuración del OTEL Collector.

**Las trazas distribuidas** capturan el ciclo de vida completo de cada petición al sistema, desde que el cliente HTTP envía la request hasta que recibe la respuesta. El SDK de OpenTelemetry para Python instrumenta automáticamente FastAPI (spans HTTP por endpoint), httpx (spans para cada llamada a API externa — OpenAI, Cohere), SQLAlchemy (spans para cada query a PostgreSQL) y el cliente de Qdrant (spans para cada búsqueda en la base vectorial). Además de la instrumentación automática, el código del agente añade spans custom para cada paso del ciclo ReAct — `agent.thought_{n}`, `agent.tool_call.{tool_name}`, `agent.final_answer` — que no son instrumentables automáticamente porque son específicos de la lógica del agente. Las trazas se exportan a Grafana Tempo a través del OTEL Collector.

**Las métricas** se exponen via Prometheus scraping del endpoint `/metrics` de FastAPI mediante el middleware `prometheus_fastapi_instrumentator`. Las métricas automáticas incluyen histogramas de latencia HTTP por endpoint y método, contadores de requests por status code, y gauge de requests en proceso. Las métricas custom incluyen: `llm_tokens_total` (contador de tokens consumidos por modelo y por tipo — prompt/completion), `ragas_faithfulness` (gauge de la métrica de faithfulness calculada sobre el sample de evaluación online), `agent_iterations_total` (histograma del número de iteraciones por ejecución del agente) y `tool_call_duration_seconds` (histograma de duración por herramienta). Estas métricas custom son las que el Capítulo 7 usa para el framework de evaluación continua.

**Los logs estructurados** se emiten en formato JSON mediante el módulo `logging` de Python configurado con `python-json-logger`. Cada log incluye campos estándar (`level`, `timestamp`, `logger_name`) más campos específicos del dominio (`trace_id`, `span_id`, `user_id`, `tool_name`, `tokens_used`, `error_code`). La presencia de `trace_id` y `span_id` en los logs es crítica: permite que Grafana Loki correlacione un log específico con la traza que lo generó, haciendo posible el flujo de debugging "alerta → traza → log" sin saltar manualmente entre herramientas. Los logs se exportan a Grafana Loki a través del OTEL Collector con el exporter de logs de OpenTelemetry.

## Componentes del stack de observabilidad

- **OpenTelemetry SDK**: instrumentación automática de FastAPI, httpx, SQLAlchemy y cliente Qdrant; instrumentación custom del ciclo ReAct del agente con spans `agent.thought`, `agent.tool_call`, `agent.final_answer`; propagación automática de trace context entre servicios via headers W3C TraceContext.
- **OTEL Collector**: recibe trazas, métricas y logs; aplica transformaciones (filtrado, sampling, enriquecimiento con metadatos del entorno); exporta a Grafana Tempo (trazas), Prometheus (métricas) y Grafana Loki (logs).
- **Grafana Tempo**: almacenamiento y visualización de trazas distribuidas; correlación con métricas de Prometheus (click en un span → ver métrica correspondiente) y con logs de Loki (click en un span → ver logs de esa ejecución).
- **Prometheus + Grafana**: colección de métricas de FastAPI (automáticas) y del dominio (custom); dashboards con correlación entre métricas de calidad RAG, rendimiento del agente y métricas de infraestructura.
- **Grafana Loki**: almacenamiento de logs estructurados JSON; LogQL para queries complejas ("todos los logs de error del agente en las últimas 2 horas donde tool_name=search_knowledge_base"); correlación con trazas via trace_id.

> **Nota del Arquitecto**: El parámetro de sampling de trazas merece atención especial. En producción con 5000 queries/día, almacenar el 100% de las trazas en Grafana Tempo genera aproximadamente 15GB de datos diarios — caro y difícil de analizar. La estrategia de sampling correcta es: 100% de las trazas de requests que retornan error (para debugging de incidentes), 10% de las trazas de requests normales (muestra estadísticamente significativa para análisis de rendimiento), y 100% de las trazas de requests marcados como `suspicious` por el clasificador de intent (para análisis de seguridad). Este sampling adaptativo reduce el volumen de almacenamiento en un 85% sin perder la cobertura de debugging necesaria.

La instrumentación con OpenTelemetry debe comenzar desde el primer commit del proyecto, no añadirse después. Instrumentar retroactivamente un sistema existente es una tarea que puede tomar días y que frecuentemente produce cobertura incompleta — los spans custom del agente requieren conocer la estructura interna del grafo LangGraph, que es más difícil de entender después de que el código está escrito. El Capítulo 8 continúa con el tracing distribuido en detalle — la anatomía de una traza completa desde el cliente hasta el modelo y de vuelta.

**Para recordar**: Un stack de observabilidad solo es útil si los tres pilares están correlacionados — la capacidad de ir de una alerta de latencia alta a la traza específica que causó el problema, y de ahí a los logs de esa ejecución, es lo que permite diagnosticar incidentes en minutos en lugar de horas.
