# Módulo 12 – Capítulo 10 – Sección 01

## Rúbrica del proyecto final: criterios técnicos de evaluación por componente

El Capítulo 1 de este módulo presentó los criterios de éxito del sistema integrador como los destinos que guiarían cada decisión técnica: RAGAS faithfulness ≥ 0.85 en producción, task completion rate ≥ 75%, latencia P95 < 3s bajo carga, y tasa de bypass de controles de seguridad < 5%. A lo largo de los nueve capítulos siguientes, esos criterios funcionaron como la brújula que orientó las decisiones de diseño — por qué se eligió 512 tokens como tamaño de chunk, por qué el reranker Cohere permanece en el pipeline a pesar de sus 280ms de latencia adicional, por qué el intent classifier se configura para fallar de forma segura ante la incertidumbre. El Capítulo 10 cierra el ciclo: la rúbrica del proyecto final formaliza esos criterios como los instrumentos de medición con los que el sistema construido se evalúa objetivamente.

La rúbrica no es una lista de características a verificar — es un instrumento de medición con criterios cuantitativos que pueden verificarse con scripts automatizados, no con juicio subjetivo. La diferencia es importante: "la seguridad está implementada" es una afirmación que no puede verificarse de forma consistente; "la tasa de bypass en el red teaming de 50 ataques es < 5%" sí puede. Esta cuantificación tiene una consecuencia directa en la evaluación: dos sistemas con el mismo umbral de faithfulness son comparables; dos sistemas donde uno "tiene seguridad" y el otro "tiene una postura de seguridad razonablemente madura" no lo son. La rúbrica cuantitativa es la que produce evaluaciones reproducibles.

Las seis dimensiones de evaluación cubren el sistema completo. La dimensión de **pipeline RAG** evalúa la calidad técnica del retrieval: RAGAS faithfulness ≥ 0.82 sobre el golden dataset completo (el umbral de CI, no el de producción — el evaluador del proyecto usa el golden dataset que el equipo construyó, no el tráfico de producción), búsqueda híbrida implementada con RRF (verificable en el código del retrieval pipeline), reranking activo con umbral configurable, y pipeline de ingesta con deduplicación verificada con el test de ingesta de documentos duplicados. Un faithfulness de 0.81 pasa el umbral de producción pero no el de CI — en la rúbrica del proyecto, se usa el umbral de CI porque es el que el golden dataset del evaluador puede verificar de forma reproducible.

La dimensión **agéntica** evalúa la implementación del agente ReAct con LangGraph: estado persistente con `MemorySaver` o `SqliteSaver`, mínimo tres herramientas con schemas Pydantic tipados, `max_iterations` configurado como guardia de bucle infinito, y task completion rate ≥ 75% medido sobre el golden dataset de escenarios agénticos (los 20 escenarios de prueba incluyendo los de fallo: retrieval vacío, timeout, ambigüedad de consulta).

La dimensión de **seguridad** evalúa la implementación de ADR-004: threat model STRIDE documentado con las ocho amenazas del sistema, mínimo tres controles implementados con referencia al código (el intent classifier de prompt injection, el RBAC a nivel de Qdrant y la validación de outputs con filtro de PII son los tres mínimos), y red teaming documentado con mínimo 20 ataques de al menos tres categorías diferentes, con resultados: número de ataques intentados, número mitigados, tasa de bypass final.

## Criterios de evaluación por dimensión

- **Pipeline RAG**: RAGAS faithfulness ≥ 0.82 en golden dataset, búsqueda híbrida BM25+densas con RRF, reranking Cohere activo, ingesta con deduplicación verificada; verificable con script de evaluación autónomo.
- **Sistema agéntico**: ReAct con LangGraph, estado persistente implementado, ≥ 3 herramientas con schemas Pydantic, `max_iterations` configurado, task completion rate ≥ 75% en golden dataset de 20 escenarios incluyendo casos de fallo.
- **Seguridad**: ADR-004 con STRIDE documentado, ≥ 3 controles implementados con referencia al código, red teaming ≥ 20 ataques en ≥ 3 categorías con tasa de bypass < 5%; bypass > 5% es criterio de no aprobación de la dimensión.
- **MLOps**: Dockerfile multi-stage (usuario no-root, health check, hash de dependencias), pipeline CI/CD con ≥ 4 etapas incluyendo gate de evaluación RAGAS, despliegue reproducible con configuración de producción, secrets no presentes en el código.
- **Observabilidad**: OpenTelemetry instrumentado en ≥ 5 etapas del pipeline, dashboard con ≥ 5 paneles incluyendo métricas RAGAS y costo, ≥ 3 alertas configuradas con runbook_url referenciado, drift monitoring implementado.
- **Documentación**: README con setup funcional verificado por un revisor externo al equipo, API documentada con OpenAPI incluyendo ejemplos de borde, runbook con ≥ 3 incidentes, guía de contribución con ≥ 1 extensión documentada.

> **Nota del Arquitecto**: La rúbrica tiene deliberadamente un criterio de no aprobación automática en la dimensión de seguridad: tasa de bypass > 5% en el red teaming. Las otras dimensiones permiten evaluación Parcial con deficiencias documentadas — un sistema con faithfulness 0.79 que documenta el gap y su causa puede obtener evaluación Parcial. Pero un sistema con tasa de bypass del 10% en los controles de seguridad no puede considerarse "parcialmente seguro" de la misma manera: si el 10% de los ataques de prompt injection pasan, el sistema no puede desplegarse en un entorno donde esos ataques son reales. Este criterio absoluto en seguridad refleja la diferencia entre una métrica de calidad (donde el degraded gracefully tiene valor) y una condición de correctitud (donde el sistema falla en una dimensión no negociable).

La rúbrica del proyecto final no es el criterio que el equipo espera que el evaluador aplique — es el criterio que el equipo debe aplicar sobre su propio sistema antes de presentarlo. Un equipo que llega a la evaluación sin haber ejecutado el script de evaluación RAGAS, sin haber completado el red teaming de 20 ataques, o sin haber verificado que el README funciona en una máquina limpia, no está enviando un sistema para evaluación — está enviando un borrador. La rúbrica como práctica de auto-evaluación es parte de la competencia que el módulo desarrolla.

**Para recordar**: Una rúbrica con criterios cuantitativos verificables convierte la evaluación del sistema en un proceso reproducible, no en una opinión. Los mismos criterios que el evaluador aplica son los que el equipo debe aplicar en el checklist de producción del Capítulo 10-02.
