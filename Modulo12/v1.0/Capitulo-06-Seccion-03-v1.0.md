# Módulo 12 – Capítulo 06 – Sección 03

## Infraestructura como código: Terraform para provisionar el entorno de producción

La infraestructura como código es el principio de que el entorno de producción — los servidores, redes, bases de datos y configuraciones que ejecutan el sistema — se define en archivos de configuración versionados que pueden auditarse, reproducirse y revertirse con el mismo rigor que el código de la aplicación. Un entorno de producción provisionado manualmente mediante clicks en la consola de AWS es un entorno que nadie puede reproducir exactamente — las configuraciones exactas de los security groups, los tamaños de instancia, los parámetros de RDS viven en la memoria de quien lo configuró y en la interfaz de AWS, no en el repositorio. Cuando ese entorno falla o cuando el equipo necesita provisionar un entorno de staging idéntico, la única opción es "intentar recordar cómo se configuró".

La infraestructura del sistema integrador se provisiona con Terraform usando el provider de AWS. El estado de Terraform se almacena en un S3 bucket con versionado habilitado (`versioning { enabled = true }`) y DynamoDB para locking distribuido. El versionado del S3 bucket permite recuperar el estado anterior si un `terraform apply` falla a mitad — sin versionado, un apply fallido puede dejar el estado corrupto sin forma de restaurarlo. El locking con DynamoDB previene que dos ingenieros ejecuten `terraform apply` simultáneamente sobre el mismo entorno — una condición de race que puede producir configuraciones inconsistentes.

Los recursos se organizan en tres módulos Terraform con responsabilidades claramente separadas. El **módulo networking** provisiona la VPC con subnets públicas (para el load balancer que recibe tráfico externo) y privadas (para los workers de Kubernetes y las bases de datos que no deben ser accesibles desde internet) en tres Availability Zones para alta disponibilidad. Los security groups definen el tráfico permitido entre capas: el load balancer acepta tráfico en el puerto 443 desde internet, los pods de EKS aceptan tráfico desde el load balancer, y RDS solo acepta tráfico desde los security groups de los pods.

El **módulo compute** provisiona el cluster EKS v1.30 con managed node groups de instancias `c5.xlarge` (4 vCPU, 8GB RAM), el cluster autoscaler configurado para escalar entre 2 y 10 nodos según la carga, y IRSA (IAM Roles for Service Accounts) para que los pods de Kubernetes puedan asumir roles IAM de AWS sin credenciales estáticas — el pod de la aplicación necesita acceso a AWS Secrets Manager para leer las API keys, y IRSA le otorga ese acceso mediante tokens temporales de IAM sin hardcodear credenciales.

El **módulo services** provisiona RDS PostgreSQL 16 Multi-AZ para el almacenamiento del estado del agente (LangGraph Persistence), los audit logs y la tabla de documentos procesados. La configuración Multi-AZ garantiza failover automático en menos de 60 segundos si la instancia primaria falla — sin Multi-AZ, un fallo de la instancia RDS haría que el agente perdiera su estado de sesión y que el sistema no pudiera registrar peticiones en el audit log. ElastiCache Redis se provisiona para las colas Celery del pipeline de ingesta. Qdrant Cloud se usa como servicio administrado para la base vectorial en producción — la responsabilidad de backups, actualizaciones y alta disponibilidad es de Qdrant Cloud, no del equipo.

La parametrización por entorno usa workspaces de Terraform: `terraform workspace select dev`, `staging` o `prod`, con archivos `.tfvars` por workspace que definen `instance_type`, `min_nodes`, `max_nodes`, `db_instance_class` y `multi_az`. En dev, los nodos son `t3.medium` (más baratos), sin Multi-AZ en RDS y sin cluster autoscaler; en staging son `c5.large` con los mismos parámetros de seguridad que producción pero sin Multi-AZ; en prod son `c5.xlarge` con Multi-AZ y autoscaler habilitados. Esta parametrización permite que dev sea barato para experimentación, staging sea fiel a producción para pruebas de integración, y prod esté configurado para alta disponibilidad real.

## Componentes de infraestructura como código

- **State backend**: S3 bucket con versionado habilitado + DynamoDB table para state locking — prevención de race conditions en applies concurrentes y capacidad de restaurar estado anterior.
- **Módulo networking**: VPC con subnets públicas (load balancer) y privadas (EKS, RDS) en 3 AZs; NAT Gateway para acceso saliente de las subnets privadas; security groups con principio de mínimo privilegio por capa.
- **Módulo compute**: EKS v1.30 con managed node groups `c5.xlarge`, cluster autoscaler (min 2, max 10 nodos), IRSA para permisos IAM por pod sin credenciales estáticas.
- **Módulo services**: RDS PostgreSQL 16 Multi-AZ para estado del agente y audit logs; ElastiCache Redis para colas Celery; Qdrant Cloud como servicio administrado para la base vectorial.
- **Parametrización por entorno**: workspaces Terraform con `.tfvars` por entorno — dev barato (`t3.medium`, sin Multi-AZ), staging fiel a producción, prod con alta disponibilidad completa.

> **Nota del Arquitecto**: La elección de Qdrant Cloud como servicio administrado para producción (en lugar de auto-hospedar Qdrant en EKS) merece justificación explícita porque tiene un costo directo. Qdrant Cloud cuesta aproximadamente 120 USD/mes para el tier necesario para este caso de uso; auto-hospedar Qdrant en EKS con EBS persistence costaría aproximadamente 60 USD/mes en recursos de compute y storage. La diferencia de 60 USD/mes compra: backups automáticos con punto de restauración, actualizaciones automáticas de versión, monitoreo de disponibilidad gestionado, y eliminación de la responsabilidad operativa de mantener un stateful set de Qdrant en Kubernetes — una de las operaciones más delicadas en infraestructura de Kubernetes porque involucra gestión de volúmenes persistentes. Para un equipo pequeño, ese trade-off es casi siempre favorable a favor del servicio administrado.

La infraestructura como código no es solo documentación ejecutable — es el control de versiones de la infraestructura. El `git log` del directorio `infra/terraform/` muestra exactamente qué cambió en el entorno de producción, cuándo y quién lo cambió, con la posibilidad de revertir cualquier cambio a través de `terraform apply` del commit anterior. El Capítulo 6 continúa con la estrategia de despliegue canary que minimiza el riesgo de cada cambio al sistema.

**Para recordar**: La infraestructura como código no es solo documentación ejecutable — es el control de versiones de la infraestructura, que permite auditar qué cambió, cuándo y por quién, y revertir a un estado anterior si un cambio causa un incidente.
