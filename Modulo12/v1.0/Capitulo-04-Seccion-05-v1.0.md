# Módulo 12 – Capítulo 04 – Sección 05

## Observabilidad agéntica: trazas de razonamiento y métricas de completitud de tareas

Las métricas estándar de observabilidad de infraestructura — latencia, error rate, throughput — son necesarias pero insuficientes para un sistema agéntico. Un agente puede tener latencia dentro del SLA, error rate en cero y throughput adecuado, y aun así estar fallando en un 40% de las tareas porque el ciclo ReAct está usando la herramienta equivocada, porque el agente está iterando más de lo necesario antes de converger a una respuesta, o porque la tasa de citación de fuentes cayó silenciosamente después de un cambio en el system prompt. Ninguno de esos problemas se detecta con métricas de infraestructura. Se detectan con métricas de comportamiento del agente — las trazas de razonamiento y las métricas de completitud que revelan qué hace el agente dentro de cada iteración del ciclo ReAct.

Las trazas de razonamiento del agente se implementan con el SDK de OpenTelemetry para Python. Cada ejecución del agente genera un span raíz `agent.run` con atributos `session_id`, `iterations_count` y `task_completed` (boolean). Dentro de `agent.run`, hay spans hijo por cada paso del ciclo ReAct: `agent.thought_{n}` captura el razonamiento del LLM en cada iteración (qué herramienta decide usar y con qué argumento); `agent.tool_call.{tool_name}` captura la ejecución de cada herramienta con atributos `duration_ms`, `result_count` y `status`; y `agent.final_answer` captura la generación de la respuesta final con atributos `prompt_tokens`, `completion_tokens` y `finish_reason`. LangSmith complementa las trazas de OpenTelemetry almacenando las trazas completas de razonamiento — incluyendo el contenido completo de cada Thought y Observation — para debugging visual de ejecuciones fallidas. La distinción es importante: OpenTelemetry expone métricas agregadas para el dashboard de Grafana, mientras que LangSmith almacena el contenido completo de cada ejecución para debugging individual.

Las métricas de completitud de tareas se calculan de dos formas complementarias. La **task completion rate** mide el porcentaje de queries donde el agente entregó una respuesta con al menos un documento citado (vs queries donde el agente declinó responder o respondió con un error). Un decline es un outcome válido cuando la información genuinamente no está en la base de conocimiento; un decline es un fallo cuando la información existe pero el agente no la encontró (por reformulación de query inadecuada o por retrieval insuficiente). Distinguir entre los dos tipos de decline requiere correlacionar la task completion rate con el context recall del pipeline RAG: si context recall es alto pero task completion es bajo, el problema está en el razonamiento del agente, no en el retrieval. La **task accuracy rate** mide el porcentaje de respuestas evaluadas como correctas por LLM-as-judge — se calcula sobre una muestra del 5% del tráfico real de producción, donde las respuestas del agente se evalúan contra los criterios del golden dataset.

La distribución de `iterations_per_task` — cuántas iteraciones del ciclo ReAct necesita el agente para responder — es una señal valiosa de la complejidad de las queries en producción y de la eficiencia del razonamiento. Una distribución con moda en 1 (la mayoría de las preguntas se resuelven en una sola búsqueda) indica que el dominio tiene preguntas directas y bien cubiertas. Una distribución con moda en 5 (el límite de iteraciones) indica que el agente frecuentemente alcanza el límite antes de converger — lo que puede significar que max_iterations es demasiado bajo para la complejidad real de las preguntas, o que el agente está en bucles de búsqueda no productivos. La `tool_usage_rate` por herramienta detecta infrauso de capacidades: si `list_available_sources` nunca es llamada, puede indicar que el system prompt no describe bien cuándo es útil esa herramienta.

## Métricas de observabilidad agéntica

- **Trazas de razonamiento**: spans OpenTelemetry `agent.run` con spans hijo `agent.thought_{n}`, `agent.tool_call.{tool_name}` y `agent.final_answer`; atributos de duración, tokens consumidos y status por span.
- **Task completion rate**: porcentaje de queries con respuesta completa (vs declines y errores) — alertar si cae por debajo del 70% en ventana de 1 hora.
- **Task accuracy rate**: evaluación LLM-as-judge sobre muestra del 5% del tráfico real — pipeline automatizado de evaluación continua en producción.
- **Iterations distribution**: histograma de iteraciones por task en el dashboard de Grafana — pico en max_iterations (5) indica posible problema de razonamiento o de cobertura de la base de conocimiento.
- **Tool usage rate**: distribución de llamadas por herramienta en ventana de 24h — infrauso de una herramienta puede indicar problema en el system prompt que no la describe correctamente.
- **LangSmith tracing**: almacenamiento del contenido completo de cada ejecución (Thoughts + Observations) para debugging visual de ejecuciones individuales fallidas o con comportamiento inesperado.

> **Nota del Arquitecto**: Hay una tensión entre loggear suficiente información para hacer debugging efectivo y no loggear información sensible de las queries del usuario. La solución que usa este proyecto es logging en dos niveles: el nivel de producción loggea metadatos (duración, tokens, tool names, iteration count) sin el contenido de queries ni respuestas; el nivel de debugging loggea el contenido completo pero solo para ejecuciones marcadas como "fallidas" o seleccionadas explícitamente para revisión por un ingeniero autorizado. LangSmith permite configurar este nivel de granularidad por proyecto, incluyendo retención diferenciada de datos sensibles.

Las trazas de razonamiento agéntico no son solo herramientas de debugging — son la fuente de datos más valiosa para mejorar el sistema. Cuando el analysis de las trazas muestra que el agente sistematicamente reformula la query del usuario de una forma que produce peor retrieval que la query original, ese insight lleva a mejorar el system prompt para instruir al agente sobre cuándo y cómo reformular. Cuando el analysis muestra que `search_knowledge_base` es llamada con queries duplicadas en el 20% de las ejecuciones de más de 3 iteraciones, eso lleva a añadir gestión de deduplicación de queries en el estado del grafo. La observabilidad agéntica cierra el loop entre el sistema en producción y las decisiones de mejora del equipo de desarrollo.

**Para recordar**: Sin trazas de razonamiento, el comportamiento del agente es una caja negra — cuando el agente falla o produce una respuesta incorrecta, los spans de cada paso del ciclo ReAct son el único mecanismo para entender el porqué.
