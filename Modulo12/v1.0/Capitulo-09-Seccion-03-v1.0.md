# Módulo 12 – Capítulo 09 – Sección 03

## Runbook operativo: procedimientos para los incidentes más frecuentes

El runbook operativo es el documento que transforma las alertas del Capítulo 8 de señales de diagnóstico en acciones de resolución. Cada alerta CRITICAL y WARNING del sistema tiene un campo `runbook_url` que apunta a la sección correspondiente del runbook — cuando el ingeniero de guardia recibe la alerta a las 3am, el primer paso no es pensar qué hacer: es abrir el runbook y seguir el procedimiento. Un runbook efectivo no asume conocimiento previo del sistema: cualquier ingeniero del equipo con acceso al cluster de Kubernetes y familiaridad general con los componentes debe poder seguirlo hasta resolución o hasta el punto de escalation.

La estructura de cada entrada del runbook no es opcional — la consistencia estructural es lo que permite al ingeniero de guardia orientarse bajo presión. Cada entrada incluye: **Alerta que lo activa** (nombre exacto de la alerta en Grafana y threshold), **Síntomas observables** (qué experimenta el usuario cuando ocurre el incidente, qué muestran los paneles del dashboard), **Diagnóstico** (comandos en orden de ejecución para confirmar la causa raíz), **Mitigación inmediata** (pasos con comandos completos, no descripciones de alto nivel — un ingeniero bajo presión no debe tener que inferir qué comando ejecutar), **Escalation** (cuándo y a quién escalar si la mitigación no produce el resultado esperado en 15 minutos), y **Cierre del incidente** (verificación cuantitativa de que el sistema volvió al estado normal y nota sobre si el incidente requiere post-mortem).

El primer incidente documentado — **Alta latencia P95 > 5000ms** — es el más frecuente en los primeros semanas post-despliegue. Los síntomas son latencia percibida por el usuario > 5s y el stat panel de P95 en rojo en el dashboard. El diagnóstico comienza con Grafana Tempo: abrir una traza reciente y verificar qué span consume la mayor proporción del tiempo total — el span `llm.generate` (indicativo de latencia del proveedor) o el span `rerank.cohere` (indicativo de latencia del reranker). Si el span `llm.generate` supera los 4000ms en la traza, el diagnóstico es latencia de OpenAI API: verificar con `curl https://api.openai.com/v1/models -H "Authorization: Bearer $OPENAI_API_KEY"` y revisar el status de OpenAI en https://status.openai.com. Si la latencia de OpenAI es el problema, la mitigación es activar el modo degradado temporalmente: `kubectl set env deployment/assistant FALLBACK_MODE=true` — el sistema retorna respuestas de menor calidad usando únicamente el retrieval sin el agente, pero mantiene el SLA de latencia.

El segundo incidente — **Error rate > 5%** — requiere verificación inmediata de las dependencias críticas. El diagnóstico con Loki: `{app="assistant"} |= "ERROR" | json | line_format "{{.error}}"` para los últimos 5 minutos revela si el error es de tipo `openai.APIConnectionError`, `qdrant.ConnectionError` o `cohere.TooManyRequestsError`. Cada tipo de error tiene una mitigación diferente: para OpenAI connection errors, verificar el status de OpenAI y activar FALLBACK_MODE; para Qdrant connection errors, `kubectl exec -it qdrant-pod -- wget -q -O- http://localhost:6333/readyz` para verificar si el pod responde; para Cohere rate limit, reducir el sample de reranking temporalmente.

## Incidentes documentados en el runbook

- **Alta latencia P95 > 5000ms**: diagnóstico con spans de Grafana Tempo (span más lento), comandos kubectl top pods para recursos, escalado horizontal con `kubectl scale deployment/assistant --replicas=5` si el cuello de botella es CPU; activación de FALLBACK_MODE si el problema es latencia del proveedor.
- **Error rate > 5%**: query Loki para tipo de error en los últimos 5 minutos, verificación de health de OpenAI/Qdrant/Cohere con comandos curl y kubectl exec, activación de circuit breaker y modo degradado si la dependencia está indisponible.
- **Degradación de faithfulness (Alerta WARNING)**: comparación del faithfulness actual con el baseline en PostgreSQL (`SELECT * FROM evaluation_baselines ORDER BY created_at DESC LIMIT 5`), diagnóstico diferencial entre drift de datos (scores de reranking cayendo), drift de modelo (faithfulness cae en todas las categorías del golden dataset), y degradación de chunking (queries de alta complejidad tienen faithfulness bajo pero las simples no).
- **Pod OOM (OOMKilled)**: `kubectl describe pod <pod-name>` para confirmar el evento OOMKilled, `kubectl logs <pod-name> --previous` para ver el stack trace del proceso antes del kill, ajuste de resource limits en el Helm chart como mitigación inmediata y análisis de memory profile con `py-spy` en staging para diagnóstico de raíz.
- **Rate limiting agresivo**: query Loki por `user_id` en los últimos 15 minutos para identificar el origen del volumen anómalo, bloqueo temporal del user_id en Redis con TTL de 1 hora si es abuso confirmado, investigación del bug del cliente si el volumen anómalo es de un usuario legítimo con comportamiento inesperado.

> **Nota del Arquitecto**: El runbook debe ser revisado por un ingeniero que no lo escribió antes de ser declarado listo para producción. La razón es simple: el ingeniero que escribe el runbook tiene conocimiento implícito del sistema que no se da cuenta de que está omitiendo. Cuando un ingeniero que no conoce el sistema lo lee y sigue los procedimientos, descubre invariablemente pasos que están incompletos o asumen contexto que no se explica. Esta revisión por un segundo ingeniero es la equivalente al "test de nuevo empleado" para la documentación de setup — si no puede seguirse sin ayuda adicional, necesita más detalle. El objetivo no es el runbook más completo posible — es el runbook que permite a un ingeniero con conocimiento general del sistema resolver el incidente más frecuente en menos de 15 minutos.

Un runbook nunca está terminado — evoluciona con el sistema y con los incidentes reales. Cada incidente de producción que genere un post-mortem produce un aprendizaje: o el procedimiento de diagnóstico era incorrecto (hay que corregirlo), o faltaba una categoría de incidente (hay que añadirla), o el criterio de escalation era demasiado temprano o tardío (hay que ajustarlo). El runbook vivo es el que acumula ese aprendizaje.

**Para recordar**: Un runbook es efectivo cuando permite a un ingeniero con conocimiento general del sistema resolver el incidente sin ayuda del ingeniero que lo diseñó. Si el procedimiento asume conocimiento implícito, necesita más detalle — no menos.
