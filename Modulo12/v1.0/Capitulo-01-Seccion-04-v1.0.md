# Módulo 12 – Capítulo 01 – Sección 04

## Stack tecnológico: selección justificada de modelos, bases de datos, frameworks y herramientas

Elegir un stack tecnológico para un sistema de IA en producción es una de las decisiones con mayor costo de reversibilidad del proyecto. Cambiar el modelo de embedding después de indexar 50.000 documentos requiere re-indexar toda la colección. Cambiar el framework agéntico después de implementar el grafo de estado implica reescribir la lógica de razonamiento. Por eso la selección del stack no puede basarse en popularidad, familiaridad o "lo que todos usan" — debe basarse en criterios técnicos medibles que correspondan a las restricciones del sistema: latencia P95, costo por petición, operabilidad en Kubernetes y soporte de las capacidades necesarias para cada componente.

El modelo de lenguaje principal es GPT-4o (gpt-4o-2024-08-06), elegido mediante un benchmark interno de 100 preguntas del dominio técnico objetivo. Los tres candidatos evaluados fueron GPT-4o, Claude 3.5 Sonnet (Anthropic) y Gemini 1.5 Pro (Google). Los criterios de eliminación temprana descartaron a Gemini 1.5 Pro por inconsistencias en el soporte de function calling estructurado en el momento de la evaluación. El benchmark entre GPT-4o y Claude 3.5 Sonnet midió accuracy semántica evaluada por LLM-as-judge (0.88 vs 0.86 respectivamente), latencia TTFT (time to first token) y costo por 1000 tokens de output. GPT-4o fue elegido por combinar el mejor score de accuracy con soporte nativo para parallel tool calling, que el agente ReAct necesita para ejecutar múltiples herramientas en un solo turno del ciclo de razonamiento. La decisión se documenta en el ADR-001 del Capítulo 2 con los datos completos del benchmark.

Para embeddings, text-embedding-3-small (1536 dimensiones, 0.00002 USD por 1000 tokens) fue seleccionado sobre text-embedding-3-large (3072 dimensiones, 0.00013 USD por 1000 tokens) y sobre el modelo text-embedding-ada-002 que era la opción por defecto anterior. La comparación midió recall@5 en un conjunto de 500 pares query-documento del dominio: text-embedding-3-small alcanzó 0.82, text-embedding-3-large alcanzó 0.86, y ada-002 alcanzó 0.76. La diferencia de 0.04 puntos en recall@5 entre small y large no justifica un costo 6.5 veces mayor por token de embedding, especialmente considerando que el reranking posterior recupera parte del recall perdido en la recuperación inicial. La elección de ada-002 fue descartada por su inferior rendimiento en el benchmark del dominio.

Qdrant v1.9 fue seleccionado como base vectorial sobre ChromaDB y Pinecone. ChromaDB fue descartado por la ausencia de soporte de búsqueda híbrida nativa y sus limitaciones de escalabilidad en colecciones grandes. Pinecone fue evaluado y descartado por tres razones: su modelo serverless no permite despliegue local para desarrollo (lo que complica el setup local sin credenciales de producción), sus filtros por payload tienen un costo adicional por operación en el plan básico, y su API no soporta la configuración granular de índices HNSW que el sistema requiere. Qdrant soporta búsqueda híbrida nativa (sparse + dense) con fusión RRF sin configuración adicional, permite despliegue Docker para desarrollo y Qdrant Cloud para producción con la misma API, y ofrece cuantización escalar que reduce el uso de memoria un 75% con penalización de recall inferior al 2%.

LangGraph fue elegido sobre LangChain AgentExecutor y AutoGen para implementar el agente. LangChain AgentExecutor no soporta grafos de estado con ciclos condicionales, lo que limita la implementación del patrón ReAct a flujos lineales sin retroalimentación. AutoGen fue evaluado pero descartado por la complejidad de configuración de sus conversaciones multi-agente para un caso de uso de agente único y por la menor integración con el ecosistema LangChain que el resto del pipeline RAG usa. LangGraph es el único que soporta grafos de estado con ciclos, checkpointing nativo para reanudación de conversaciones y control granular del flujo de ejecución — exactamente lo que el ciclo ReAct requiere.

## Selección justificada del stack por componente

- **LLM principal**: GPT-4o (gpt-4o-2024-08-06) — context window de 128k tokens, JSON mode nativo, parallel tool calling; accuracy 0.88 en benchmark de dominio; latencia P95 < 2s medida bajo carga de 10 peticiones simultáneas.
- **Embeddings**: text-embedding-3-small (OpenAI) — recall@5 de 0.82 en benchmark de dominio, costo 6.5x menor que text-embedding-3-large, 62% de mejora sobre ada-002 en MTEB; 1536 dimensiones compatibles con cuantización escalar de Qdrant.
- **Base vectorial**: Qdrant v1.9 — búsqueda híbrida nativa (sparse + dense), filtros por payload con índices explícitos, cuantización escalar, despliegue Docker para dev y Qdrant Cloud para producción con la misma API REST.
- **Framework agéntico**: LangGraph — grafos de estado con ciclos condicionales, checkpointing en PostgreSQL para persistencia de sesión, control granular de condiciones de parada y fallback ante max_iterations.
- **Framework de API**: FastAPI + Uvicorn — generación automática de OpenAPI 3.1 desde schemas Pydantic, middleware de autenticación JWT, prometheus_fastapi_instrumentator para métricas, 4 workers en producción.
- **Infraestructura**: Docker Compose para desarrollo local, Kubernetes (EKS) para producción, Terraform para IaC, Argo Rollouts para canary deployment, Grafana + Tempo + Prometheus + Loki para observabilidad.

> **Nota del Arquitecto**: Documentar la alternativa evaluada y descartada para cada componente del stack es tan importante como documentar la elección final. Sin ese registro, el equipo repetirá la evaluación en cada revisión de arquitectura porque no habrá memoria de por qué se descartó ChromaDB o por qué se eligió LangGraph sobre AutoGen. Los ADRs del Capítulo 2 son el lugar donde este razonamiento se preserva formalmente — este capítulo de diseño es la base de datos mental sobre la que se construyen.

La selección del stack tecnológico es una decisión que debe tomarse una vez con evidencia y revisarse periódicamente con los mismos criterios. Los modelos fundacionales evolucionan: GPT-4o-2024-08-06 puede ser superado por una versión posterior en accuracy o en costo, y esa revisión debe hacerse con el mismo benchmark del dominio que produjo la elección original. El ADR-001 del Capítulo 2 establece el proceso de revisión: cuándo revisar (cuando el proveedor lanza una versión nueva o cuando las métricas de calidad en producción caen por debajo del umbral), cómo revisarlo (mismo benchmark de 100 preguntas del dominio) y quién toma la decisión final.

**Para recordar**: Documentar la alternativa evaluada y descartada para cada componente del stack es parte de la decisión técnica — sin ese registro, el equipo repetirá la evaluación en cada revisión de arquitectura.
