# Módulo 12 – Capítulo 05 – Sección 04

## Input validation y output filtering: sanitización en los boundaries del sistema

Todo sistema de producción tiene dos boundaries críticos donde la información entra y sale: el boundary de entrada, donde el input del usuario se transforma en una petición al sistema, y el boundary de salida, donde el resultado del sistema se transforma en una respuesta al usuario. En sistemas de IA, estos boundaries son especialmente críticos porque el input puede intentar manipular el comportamiento del modelo y el output puede contener información sensible extraída de los documentos o fabricada por el LLM. Los controles en estos dos boundaries son los más fáciles de verificar (se pueden testear de forma independiente del modelo) y los que más frecuentemente se omiten por considerarse "detalles de implementación".

La validación de inputs opera como un pipeline de tres capas que se ejecuta en secuencia antes de que la query llegue al agente. La primera capa valida el schema con Pydantic: el modelo `QueryRequest` define que `query` es un `str` de máximo 2000 caracteres con encoding UTF-8, que `filters` es un `Optional[QueryFilters]` con campos de tipo específico, y que `session_id` es un `Optional[str]` con formato UUID. Cualquier petición que no cumpla el schema es rechazada con HTTP 422 (Unprocessable Entity) con un mensaje de error que describe qué campo falló — sin exponer detalles internos del sistema que podrían ayudar a un atacante a reformular el ataque. La segunda capa aplica la lista negra de 200 patrones de injection; la tercera ejecuta el clasificador de intent que produce el label `safe/suspicious/malicious`. Solo las queries clasificadas como `safe` o `suspicious` llegan al agente; las `malicious` son rechazadas con HTTP 400 y registradas en el audit log.

La longitud máxima de 2000 caracteres no es arbitraria: es el resultado de analizar la distribución de longitudes de queries en el golden dataset y en las queries de red teaming. Las queries legítimas de ingenieros técnicos raramente superan los 500 caracteres; las queries de injection optimizadas para maximizar el contexto del LLM suelen superar los 1000 caracteres. El límite de 2000 permite consultas técnicas complejas legítimas (preguntas con contexto de error detallado que el usuario incluye en la query) mientras bloquea la mayoría de los ataques de context flooding. Los caracteres de control (ASCII < 32, excepto tab y newline) se eliminan automáticamente del input antes del processing — son frecuentemente usados en ataques de injection que intentan manipular el parsing del prompt.

El output filtering opera sobre la respuesta generada por el agente antes de devolverla al usuario. La primera verificación busca PII con expresiones regulares: emails (patrón RFC 5322 simplificado), números de teléfono en formatos internacionales, números de tarjeta de crédito (patrón Luhn), y números de seguridad social. La segunda verificación usa un modelo NER (spaCy con el modelo `en_core_web_lg`) para detectar nombres propios de personas en contextos que indiquen información personal — esto captura casos donde la PII no tiene formato estructurado (como "el ingeniero Juan García tiene acceso al sistema X"). La tercera verificación busca patterns de credenciales: AWS access keys (formato AKIA + 16 caracteres alfanuméricos), GitHub tokens (formato `ghp_` + 36 caracteres), OpenAI API keys (formato `sk-` + 48 caracteres), y strings con alta entropía que coinciden con el patrón general de claves de API. Cualquier match en alguna de estas verificaciones produce un redact del contenido sensible con `[REDACTED]` antes de devolver la respuesta.

Un caso importante que el output filtering debe manejar correctamente es el de la documentación de seguridad legítima que el sistema indexa. Un ADR de seguridad puede mencionar "la clave de API de Qdrant se almacena en AWS Secrets Manager con el nombre `qdrant-api-key`" — esta frase contiene el nombre del secret (no la clave real) y es información legítima que el agente debe poder reproducir. El output filter no debe censurar nombres de secrets, solo valores de secrets. La distinción se implementa verificando que el match del pattern tiene la longitud y estructura de una clave real (no solo el nombre de un secret), y usando una lista de allowlist de nombres de secrets conocidos que son seguros de reproducir en respuestas.

## Controles de validación y filtrado

- **Input schema validation**: Pydantic `QueryRequest` con `max_length=2000` para `query`, `str` con pattern exclusion para caracteres de control (ASCII < 32), validación de tipos y formatos para todos los campos.
- **Lista negra de injection**: 200 patrones en múltiples idiomas aplicados al texto normalizado (lowercase, sin diacríticos) de la query; matching de tiempo constante para prevenir timing attacks.
- **Clasificador de intent**: modelo de clasificación `safe/suspicious/malicious`; threshold de 0.85 para `malicious`; queries `suspicious` pasan al agente con flag de alto logging y análisis de output más riguroso.
- **Output PII scanning**: regex para emails, teléfonos, tarjetas; NER (spaCy `en_core_web_lg`) para nombres de personas en contextos sensibles; redact automático de matches con `[REDACTED]`.
- **Credential detection**: patrones regex para AWS keys, GitHub tokens, OpenAI API keys y strings de alta entropía; allowlist de nombres de secrets conocidos que son seguros de reproducir.
- **Respuesta de error sin información de sistema**: los rechazos por validación devuelven mensajes genéricos que no revelan qué patrón específico fue detectado o qué parte del input falló — para no ayudar al atacante a reformular el ataque.

> **Nota del Arquitecto**: El output filtering tiene un efecto secundario que los equipos frecuentemente no anticipan: la latencia. Un scan de NER sobre una respuesta de 500 tokens con spaCy `en_core_web_lg` añade entre 50 y 150ms de latencia al final del pipeline. Para respuestas muy largas (> 2000 tokens), esta latencia puede ser significativa respecto al SLA de 3 segundos. La solución es ejecutar el output filtering de forma asíncrona en paralelo con el envío de la respuesta usando streaming — el cliente comienza a recibir la respuesta mientras el filtro termina su análisis, y si detecta PII o credenciales, envía un mensaje de corrección al final del stream. Este patrón de streaming con post-procesamiento es compatible con la arquitectura de FastAPI con Server-Sent Events.

Los controles de validación de inputs y output filtering son los más fácilmente testeables del sistema: los tests unitarios en `tests/unit/test_security.py` no requieren el LLM ni ningún servicio externo. Se puede verificar que el sistema rechaza queries con patrones específicos, que el output filtering detecta emails y claves de API reales, y que los mensajes de error no revelan información del sistema. El Capítulo 5 continúa con el red teaming — la validación empírica de que todos los controles implementados funcionan bajo ataque real.

**Para recordar**: La validación de inputs y el filtrado de outputs son controles complementarios, no alternativos — un sistema que filtra el output pero no valida el input puede ser explotado para extraer información sensible mediante técnicas de jailbreak.
