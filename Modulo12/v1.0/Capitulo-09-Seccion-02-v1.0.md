# Módulo 12 – Capítulo 09 – Sección 02

## Documentación de API: endpoints, contratos y ejemplos de uso

La documentación de API es el contrato formal entre el sistema y sus consumidores. A diferencia del README —que documenta cómo ejecutar el sistema— la documentación de API documenta el comportamiento observable del sistema desde el exterior: qué endpoints existen, qué datos aceptan, qué datos retornan, y qué errores pueden producirse bajo qué condiciones. Para un sistema de IA con comportamiento no determinista como este asistente técnico, la documentación de API cumple una función adicional: establece qué aspectos del sistema son deterministas (la estructura del JSON de respuesta, los códigos de error, las validaciones de schema) y cuáles son variables (el texto de la respuesta, las fuentes citadas, el número de iteraciones del agente).

La elección de FastAPI como framework HTTP no fue arbitraria desde la perspectiva de la documentación. FastAPI genera automáticamente la especificación OpenAPI 3.1 a partir de los schemas Pydantic de los endpoints — lo que significa que la documentación de API es, por definición, consistente con el código que implementa la API. Cuando se añade un campo al schema `QueryRequest`, ese campo aparece automáticamente en la documentación de API en el próximo despliegue. Esto elimina la categoría de error más frecuente en la documentación de API de sistemas de software: la documentación que describe una versión anterior del sistema.

El endpoint principal `/query` es el corazón del contrato. Su schema de request `QueryRequest` acepta tres campos: `query` (string, obligatorio, longitud máxima 2000 caracteres), `session_id` (string opcional para habilitar la memoria de conversación del agente — si se omite, la interacción es stateless), y `filters` (objeto `QueryFilters` opcional con campos `document_types: list[str]`, `date_range: DateRange` y `team_attribution: str` para el filtrado RBAC a nivel de Qdrant). El schema de response `QueryResponse` retorna `answer` (string con la respuesta generada), `sources` (lista de objetos `Source` con `document_id`, `title`, `chunk_text` y `relevance_score`), y `metadata` (objeto `ResponseMetadata` con `agent_iterations`, `total_latency_ms`, `estimated_cost_usd` y `ragas_faithfulness` si la petición fue evaluada online). Los tipos de datos de `estimated_cost_usd` y `ragas_faithfulness` son `Optional[float]` porque no están presentes en el 95% de las respuestas — solo en el 5% que cae en el sample de evaluación online.

Los códigos de error documentados no son los genéricos del framework — son los códigos que el sistema efectivamente retorna, con el mensaje de error correspondiente que permite al cliente diagnosticar el problema. El 400 incluye el JSON de ValidationError de Pydantic con el campo que falló la validación y el mensaje de error. El 401 incluye el motivo del rechazo del JWT (expirado, firma inválida, audience incorrecto). El 403 incluye el tipo de autorización fallida (RBAC — el usuario no tiene acceso al tipo de documento solicitado). El 429 incluye los headers `Retry-After` y `X-RateLimit-Remaining` para que el cliente pueda implementar backoff correcto. El 503 incluye el nombre de la dependencia que está indisponible (OpenAI API, Qdrant, Cohere) para facilitar el diagnóstico.

## Elementos de la documentación de API

- **OpenAPI 3.1 spec autogenerada**: FastAPI genera la spec desde los schemas Pydantic; la documentación es garantizadamente consistente con el código en producción — no puede divergir.
- **Endpoint `/query`**: `QueryRequest` (query, session_id, filters) → `QueryResponse` (answer, sources, metadata con cost e iteraciones); tres ejemplos de request/response: pregunta simple, pregunta con filtros RBAC y pregunta fuera del dominio.
- **Endpoint `/ingest`**: `IngestRequest` (document_id, title, content, metadata con campos obligatorios: document_type, team, last_modified) y `BatchIngestRequest` (lista de hasta 100 documentos); response con `ingested_count`, `failed_ids` y `deduplication_stats`.
- **Códigos de error documentados**: 400 (ValidationError con campo y mensaje), 401 (JWT motivo de rechazo), 403 (RBAC tipo de acceso denegado), 429 (Retry-After, X-RateLimit-Remaining), 503 (dependencia indisponible con nombre).
- **Autenticación**: flujo JWT RS256 documentado con ejemplo de header `Authorization: Bearer <token>`, instrucciones para obtener el token del identity provider en entorno de desarrollo, y advertencia sobre la expiración de tokens (3600s por defecto, 900s en producción).
- **Entornos**: `/docs` (Swagger UI) y `/redoc` disponibles en desarrollo y staging; deshabilitados en producción con respuesta 404 para evitar exponer la spec a actores externos.

> **Nota del Arquitecto**: La decisión de deshabilitar `/docs` y `/redoc` en producción es una medida de seguridad por defensa en profundidad, no un sustituto de la autenticación. Un atacante con acceso al código fuente puede reconstruir la spec de OpenAPI del código Pydantic — deshabilitar `/docs` solo previene que la spec esté disponible sin esfuerzo para quien ya tiene acceso al endpoint. El beneficio real es que un crawler genérico de APIs no puede descubrir la estructura del sistema; el impacto en ingenieros internos es nulo porque tienen acceso a la spec generada en el proceso de CI/CD y disponible en la documentación interna del equipo. La spec OpenAPI completa se publica en el repositorio interno de documentación como artefacto del pipeline CI/CD después de cada despliegue a producción.

La documentación de API no es el último paso del desarrollo de un endpoint — es parte de la definición de Done del endpoint. El criterio de aceptación de cada PR que añade o modifica un endpoint incluye verificar que los ejemplos de la documentación retornan las respuestas documentadas (test contract en el pipeline CI/CD) y que los códigos de error documentados son los que efectivamente retorna el endpoint en los casos de borde correspondientes.

**Para recordar**: La documentación de API no es un comentario — es un contrato entre el sistema y sus consumidores. Cuando la documentación está desincronizada con la implementación, no es el código el que está mal — es la documentación. El test contract en CI previene esta desincronización.
