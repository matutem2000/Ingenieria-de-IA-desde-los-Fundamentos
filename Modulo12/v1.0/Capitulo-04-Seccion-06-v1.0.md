# Módulo 12 – Capítulo 04 – Sección 06

## Cierre: el agente como sistema de razonamiento sobre conocimiento verificable

El Capítulo 4 construyó el componente que transforma el pipeline RAG de un motor de búsqueda en un asistente técnico capaz de razonar. La diferencia entre los dos es la capacidad de iteración: el pipeline RAG responde una vez con lo que encuentra; el agente evalúa si lo que encontró es suficiente, reformula si no lo es, correlaciona información de múltiples búsquedas, y entrega una respuesta que sintetiza el conocimiento disponible con citación verificable. Esa diferencia tiene un costo — en latencia (las iteraciones del ciclo ReAct acumulan latencia), en costo (más llamadas al LLM y a las herramientas) y en complejidad de debugging — que el diseño de este capítulo justifica con evidencia: task completion rate, faithfulness y trazas de razonamiento que permiten entender y mejorar el comportamiento del agente.

Las lecciones más importantes del capítulo no son técnicas sino de diseño de sistema. El patrón de encapsular el RAG detrás de una herramienta tipada hace posible testear el agente con mocks deterministas. La gestión explícita del estado persistente en PostgreSQL con LangGraph Persistence cierra la brecha entre el diseño del agente y la realidad de que los usuarios tienen conversaciones multi-turno. El sistema prompt diseñado con los principios del Módulo 3 — instrucciones precisas de grounding, criterios de parada en lenguaje natural, delimitadores XML para separar instrucciones de datos — determina el comportamiento del agente con mayor impacto que cualquier ajuste de parámetro. Los tests en tres niveles — unitarios, de integración y de comportamiento — garantizan que el sistema se puede mejorar con confianza.

Lo que el Capítulo 4 también establece, como hilo de seguridad que recorre el módulo, es que cada capacidad del agente introduce una superficie de seguridad que debe evaluarse. El multi-step retrieval es una capacidad poderosa; también es el vector de tool chaining no autorizado. El estado persistente entre sesiones mejora la experiencia del usuario; también introduce preguntas sobre quién puede acceder al historial de conversación de quién. El sistema prompt con instrucciones de grounding mitiga la hallucination; también debe resistir el intento de los usuarios de modificarlo mediante injection. El Capítulo 5 implementa los controles de seguridad que cierran esas superficies de ataque — no como una capa añadida sobre el agente existente, sino como controles diseñados con conocimiento de las capacidades específicas del sistema.

## Lo que el Capítulo 4 implementó

- **Grafo de estado LangGraph**: nodos ReAct (reason/act/observe/respond) con condiciones de parada explícitas, max_iterations=5, fallback a respuesta parcial con nota de limitación.
- **System prompt de ingeniería**: instrucciones de grounding, descripción de herramientas con ejemplos de uso y no-uso, formato de citación `[doc_id]`, criterios de parada en lenguaje natural, delimitadores XML para separación de instrucciones y datos.
- **Estado persistente**: checkpointing LangGraph en PostgreSQL RDS — retención de 10 iteraciones activas + resumen comprimido de hasta 3 sesiones anteriores; expiración de sesión a 24h de inactividad.
- **Herramientas con contratos Pydantic**: validación de inputs, manejo de errores informativos, timeout por herramienta, filtro de autorización automático, logging estructurado con trace_id.
- **Testing en tres niveles**: unit tests (mocks, milisegundos), integration tests (Qdrant test, 3-8s), behavior tests (golden dataset 200 pares, LLM-as-judge) + adversarial tests como suite de regresión.
- **Observabilidad agéntica**: spans OpenTelemetry por paso ReAct, LangSmith para debugging visual, métricas de task completion rate, iterations distribution y tool usage rate en Grafana.

> **Nota del Arquitecto**: La integración del agente con el sistema completo revela algo que el testing aislado no puede capturar: el agente en producción recibe queries que ningún ingeniero habría anticipado en el diseño. Usuarios que preguntan en idiomas distintos al inglés o español, queries con errores tipográficos severos, queries que mezclan términos técnicos con contexto organizacional específico del equipo. Las trazas de razonamiento de las primeras dos semanas en producción son el dataset de mejora más valioso disponible — revelan el 20% de los patrones de uso que no estaban en el golden dataset y que el agente maneja mal. Esa retroalimentación de producción, procesada como mejoras al golden dataset y al sistema prompt, es el ciclo de mejora que convierte el sistema del primer despliegue en el sistema del tercer mes.

Un agente sin observabilidad y sin criterios de aceptación cuantitativos no es un sistema — es un experimento en producción. El Capítulo 5 convierte el sistema funcional en un sistema seguro, implementando los controles que el threat model del ADR-004 definió y que los capítulos de implementación señalaron como necesarios.
