# Módulo 12 – Capítulo 04 – Sección 04

## Testing del agente: casos de prueba, escenarios de fallo y criterios de aceptación

El testing de un agente de IA plantea un reto que el testing de software convencional no tiene: el comportamiento del agente no es completamente determinista. El mismo input puede producir outputs ligeramente diferentes en distintas ejecuciones porque el LLM tiene temperatura > 0 y porque el proceso de razonamiento ReAct puede tomar caminos distintos según las variaciones en el sampling. Esto significa que los tests del agente no pueden verificar "la respuesta exacta" sino "las propiedades de la respuesta": que cite al menos un documento, que la respuesta contenga la información clave del golden dataset, que el agente no haya fabricado afirmaciones sin soporte en el contexto. Este cambio de paradigma de testing — de verificación de output exacto a verificación de propiedades — es uno de los más importantes para los ingenieros que vienen del desarrollo de software convencional.

La estrategia de testing del agente opera en tres niveles complementarios. El primer nivel son los **tests unitarios de herramientas**: cada herramienta se testa de forma aislada usando `unittest.mock` para reemplazar las dependencias externas. El test de `search_knowledge_base` con Qdrant no disponible verifica que la herramienta devuelve `ToolError(error_code="QDRANT_UNAVAILABLE", retry_suggested=True)` y no lanza una excepción no capturada. El test con timeout verifica que `asyncio.wait_for` interrumpe la llamada después de 5 segundos y devuelve `ToolTimeoutError`. El test con resultados vacíos verifica que el agente recibe `ToolError(error_code="NO_RELEVANT_RESULTS", retry_suggested=False)` cuando ningún chunk supera el threshold de relevancia. Estos tests son rápidos (milisegundos), deterministas y no requieren credenciales de servicios externos.

El segundo nivel son los **tests de integración**: flujos end-to-end sobre una instancia de Qdrant de test con una colección de 50 documentos representativos del dominio. Los flujos cubiertos son: pregunta simple que requiere una sola llamada a herramienta, pregunta compuesta que requiere 2-3 llamadas con queries distintas, pregunta fuera del dominio donde el agente debe declinar correctamente (la información no está en los 50 documentos de test), y pregunta con prompt injection embebida en la query (el agente debe ignorar las instrucciones maliciosas). Estos tests validan que el grafo LangGraph fluye correctamente entre nodos, que los checkpoints se persisten en PostgreSQL y que el estado de sesión se carga correctamente en la siguiente llamada.

El tercer nivel son los **behavior tests** sobre el golden dataset completo: 200 queries evaluadas por LLM-as-judge con dos criterios binarios. El primero es task completion: ¿la respuesta del agente aborda la pregunta formulada con al menos una cita de documento fuente? Un respuesta de "no encontré información relevante" cuenta como task completion si la información efectivamente no está en el golden dataset de 50 documentos de test. El segundo es faithfulness: ¿las afirmaciones de la respuesta tienen soporte en los documentos citados? Este criterio se evalúa con el mismo pipeline RAGAS del Capítulo 3. Los criterios de aceptación son: task completion rate >= 80% en el golden dataset y faithfulness >= 0.82 sobre las respuestas evaluadas.

Los **adversarial tests** cubren los 50 casos de prompt injection del red teaming del Capítulo 5, ejecutados como suite de regresión antes de cada deploy. Cada ataque que fue exitoso en el red teaming inicial y luego fue mitigado se convierte en un test de regresión permanente — si un futuro cambio en el system prompt del agente o en el InputValidator rompe la mitigación, el test de regresión lo detectará en el CI antes de que llegue a producción.

## Tipos de pruebas del agente

- **Unit tests de herramientas**: pytest con `unittest.mock` — aislamiento de cada herramienta de Qdrant/Cohere/OpenAI; cobertura de errores (timeout, resultado vacío, input inválido) y del happy path; velocidad < 5ms por test.
- **Integration tests**: flujos end-to-end con Qdrant de test (colección de 50 documentos), PostgreSQL de test y API real de GPT-4o; duración 3-8 segundos por test; ejecutados en el stage de staging del CI/CD.
- **Behavior tests**: evaluación de task completion y faithfulness sobre el golden dataset de 200 queries con LLM-as-judge; criterios de aceptación: task completion >= 80%, faithfulness >= 0.82; ejecutados en cada deploy de release candidate.
- **Failure scenarios**: pruebas específicas de Qdrant unavailable, Cohere timeout, LLM rate limit, loop detection (max_iterations alcanzado), sesión expirada y checkpoint corrupto.
- **Adversarial tests**: suite de regresión con los 50 casos de prompt injection del red teaming — ejecutada en cada PR que modifica el system prompt del agente, el InputValidator o los controles de seguridad.

> **Nota del Arquitecto**: El test de "pregunta fuera del dominio" es uno de los más importantes y frecuentemente omitidos. Un agente que responde con información fabricada cuando la respuesta correcta sería "no tengo esa información" es más peligroso que un agente que declina silenciosamente. El test verifica específicamente que cuando ningún documento del golden dataset de 50 es relevante para la query (score de reranking < 0.3 para todos los candidatos), el agente responde con una negativa clara y sin afirmaciones sobre el tema — no con una respuesta parcialmente correcta construida sobre el conocimiento de preentrenamiento del LLM. Ese comportamiento de grounding estricto es el que el system prompt instruye explícitamente.

El conjunto de tests del agente en `tests/` — unitarios, de integración y de comportamiento — es el mecanismo que garantiza que cada cambio al sistema (nuevo system prompt, nueva herramienta, actualización del modelo LLM) no regresa a ninguno de los flujos cubiertos. El CI/CD ejecuta los tests unitarios en cada push, los tests de integración en cada PR a main, y los tests de comportamiento completos en cada build de release candidate. El Capítulo 4 cierra con la observabilidad agéntica — las métricas que permiten entender el comportamiento del agente en producción más allá de lo que los tests pueden anticipar.

**Para recordar**: Los escenarios de fallo del agente deben testearse tan sistemáticamente como los flujos felices — el comportamiento del agente ante errores (timeout, retrieval vacío, injection) define la experiencia del usuario en producción.
