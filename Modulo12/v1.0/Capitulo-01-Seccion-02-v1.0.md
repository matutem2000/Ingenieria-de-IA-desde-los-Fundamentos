# Módulo 12 – Capítulo 01 – Sección 02

## El problema a resolver: definición del caso de uso, alcance y restricciones técnicas

¿Cuánto tiempo pierde un ingeniero de software buscando en Confluence la configuración correcta de un servicio, el ADR que documenta por qué se eligió una base de datos, o el runbook del incidente que ocurrió hace tres meses con síntomas similares? En organizaciones de tamaño mediano con varios años de documentación acumulada, la respuesta es entre 30 minutos y 2 horas por semana por ingeniero. El asistente técnico que construye este proyecto final ataca ese problema directamente: un sistema capaz de responder preguntas sobre la base de conocimiento interna de la organización usando documentación técnica, ADRs, runbooks y tickets históricos como fuentes primarias, con respuestas que citan la fuente y pueden trazarse al documento original.

El caso de uso tiene una definición precisa porque la precisión es la que hace posible comprometerse con métricas. El sistema responde preguntas sobre documentación técnica interna — no genera código arbitrario, no ejecuta comandos en sistemas externos y no accede a bases de datos de producción. Esta delimitación no es una limitación de ambición; es una decisión de seguridad y de alcance que hace posible operar el agente con nivel de autonomía controlado. Un agente que puede ejecutar comandos en sistemas externos requiere un modelo de amenazas completamente diferente, controles mucho más rigurosos y un proceso de aprobación human-in-the-loop para cada acción de escritura. Al limitar el agente a consultas de lectura sobre una base de conocimiento interna, el sistema puede operar de forma autónoma con un nivel de riesgo aceptable para el equipo.

Las fuentes de datos incluyen documentación técnica en Markdown (archivos `.md` en repositorios Git), especificaciones de API en OpenAPI YAML, runbooks en Confluence exportados como HTML, y ADRs en formato Markdown. El alcance incluye también tickets históricos de incidentes con resolución documentada, que son especialmente valiosos para diagnóstico de problemas recurrentes. Las fuentes excluidas explícitamente son: código fuente de repositorios (riesgo de filtración de lógica de negocio sensible), emails y canales de Slack (contenido no estructurado sin proceso de validación editorial), y documentos marcados como confidenciales por el equipo de seguridad.

Las restricciones técnicas del sistema son cuantitativas y verificables, no aspiracionales. La latencia de respuesta inferior a 3 segundos para el percentil P95 es la restricción más exigente: incluye el tiempo de embedding de la query, búsqueda en Qdrant, reranking con Cohere, razonamiento del agente y generación de respuesta con GPT-4o. El costo máximo de 0.02 USD por petición es una restricción económica que impone disciplina en la elección del modelo y en el tamaño del contexto inyectado al LLM. La capacidad de manejar hasta 50 consultas concurrentes sin degradación visible impone requisitos de configuración de Uvicorn y de gestión de conexiones a los servicios externos. Estas tres restricciones interactúan entre sí: reducir la latencia suele requerir más paralelismo, que incrementa el costo; aumentar la calidad del retrieval suele requerir más chunks en el contexto, que incrementa la latencia y el costo.

## Restricciones técnicas definidas

- **Latencia P95 < 3 segundos**: para el pipeline completo — retrieval + reranking + generación LLM — medido bajo carga de 50 usuarios concurrentes con ramp-up de 10 segundos.
- **Costo por petición < 0.02 USD**: contabilizando tokens de prompt y completion con GPT-4o, costo de embedding con text-embedding-3-small, costo de reranking con Cohere y costo de infraestructura prorrateado.
- **Concurrencia mínima de 50 peticiones simultáneas**: con throughput sostenido sin memory leaks detectables en un test de 30 minutos de duración.
- **Superficie de ataque limitada**: el agente no ejecuta código arbitrario ni accede a sistemas externos en escritura; todas las herramientas son de solo lectura sobre la base de conocimiento interna.
- **SLA de disponibilidad del 99.5%**: con health checks activos cada 30 segundos y restart automático mediante Kubernetes liveness probes ante fallos de proceso.

> **Nota del Arquitecto**: Las restricciones que se definen en esta sección son las que el equipo tendrá que defender ante stakeholders cuando el sistema esté en producción. Si no puedes medir una restricción con un test automatizado, no puedes garantizarla en un SLA. "Rápido" no es una restricción — "latencia P95 < 3 segundos bajo carga de 50 usuarios" sí lo es. El nivel de especificidad importa porque determina si el sistema puede ser aprobado para producción con evidencia o solo con confianza.

Definir explícitamente qué queda fuera del alcance técnico es tan importante como definir qué está dentro. Las exclusiones del sistema — generación de código arbitrario, ejecución de comandos en sistemas externos, acceso a documentos confidenciales — son las que hacen posible comprometerse con las métricas de seguridad del red teaming. Sin exclusiones claras, el alcance crece durante el desarrollo y los criterios de seguridad pierden precisión. El Capítulo 2 documenta estas decisiones de alcance en el ADR-003, que registra el nivel de autonomía máximo del agente como una decisión arquitectónica explícita con justificación de seguridad.

**Para recordar**: Definir explícitamente qué queda fuera del alcance técnico es tan importante como definir qué está dentro — las restricciones son las que hacen posible comprometerse con métricas medibles y verificables.
