# Módulo 12 – Capítulo 06 – Sección 05

## Gestión de configuraciones: variables de entorno, secrets management y configuración por entorno

La gestión de configuraciones es el área donde los sistemas de producción fallan de formas que el desarrollo nunca anticipa. Las tres fuentes más comunes de incidentes de configuración en producción son: un secret hardcodeado en el código que se expone en el repositorio, una variable de entorno que varía entre dev y prod sin documentación explícita de las diferencias, y un cambio de configuración en producción que no tiene audit trail — alguien cambió el `OPENAI_API_KEY` en la consola de AWS y nadie recuerda cuándo ni por qué. El sistema integrador previene las tres con prácticas específicas.

El principio base es el de los Twelve-Factor App: toda la configuración que varía entre entornos se almacena en variables de entorno, nunca en el código ni en archivos commiteados al repositorio. Para el sistema integrador, la configuración tiene dos categorías: **secrets** (información sensible que nunca debe aparecer en texto plano en ningún artefacto versionado) y **parámetros no sensibles** (valores que configuran el comportamiento del sistema pero no son credenciales). La distinción determina el mecanismo de gestión.

Los secrets (`OPENAI_API_KEY`, `QDRANT_API_KEY`, `DATABASE_URL` con usuario y contraseña, `JWT_PRIVATE_KEY`) se almacenan en AWS Secrets Manager. El acceso desde los pods de Kubernetes se implementa con External Secrets Operator (ESO): un CustomResourceDefinition `ExternalSecret` define el mapping entre el nombre del secret en AWS SM y el Kubernetes Secret resultante. ESO sincroniza automáticamente el Kubernetes Secret cuando el secret en AWS SM cambia, sin necesidad de reiniciar los pods — el pod lee la variable de entorno del Secret montado como volume, y cuando el Secret se actualiza, Kubernetes propaga la actualización a los pods en ejecución. Este mecanismo de rotación sin downtime es crítico para la operación continua: rotar la API key de OpenAI cada 90 días no debe requerir un deployment del sistema.

La rotación automática de secrets se configura en AWS Secrets Manager con una Lambda function que genera nuevas API keys y actualiza el secret en AWS SM. El proceso para `OPENAI_API_KEY`: la Lambda crea una nueva API key en la API de OpenAI, la almacena en AWS SM, y AWS SM notifica automáticamente al ESO que el secret cambió; ESO actualiza el Kubernetes Secret; los pods leen la nueva key en el siguiente ciclo de sync (máximo 1 minuto). La API key antigua se mantiene válida durante 5 minutos adicionales para asegurar que ningún pod en ejecución la usa antes de invalidarla. Este proceso es completamente automatizado y genera un evento en CloudTrail con el timestamp y el ARN del secret rotado.

Los parámetros no sensibles (`CHUNK_SIZE=512`, `CHUNK_OVERLAP=64`, `TOP_K=5`, `MAX_ITERATIONS=5`, `RATE_LIMIT_PER_MINUTE=10`, `FAITHFULNESS_THRESHOLD=0.85`) se gestionan con ConfigMaps de Kubernetes, con un ConfigMap por servicio y por entorno. Los valores en los ConfigMaps de prod se diferencian de los de dev donde es apropiado: `RATE_LIMIT_PER_MINUTE` es 10 en prod y 100 en dev (para facilitar el desarrollo sin el rate limiting siendo un obstáculo). Los ConfigMaps se versionan en el repositorio como parte de los manifests de Kubernetes en `infra/k8s/`, por lo que cada cambio de parámetro tiene un commit asociado con autor, fecha y mensaje que explica el cambio.

La validación de configuración al inicio de la aplicación usa Pydantic Settings: la clase `Settings` define todos los parámetros esperados con tipos, valores por defecto y validadores. Si la aplicación arranca sin `OPENAI_API_KEY` (por un error en la configuración del Secret), `Settings` lanza una `ValidationError` inmediatamente — el pod falla el startup check y Kubernetes lo reinicia, y el problema queda registrado en los logs del pod. Este patrón de "falla rápido ante configuración incompleta" es más seguro que arrancar con configuración parcial y fallar más tarde cuando se intenta la primera llamada a la API.

## Gestión de configuraciones por capa

- **Secrets en AWS Secrets Manager**: `OPENAI_API_KEY`, `QDRANT_API_KEY`, `DATABASE_URL`, `JWT_PRIVATE_KEY` — sincronizados a Kubernetes Secrets via External Secrets Operator con sincronización continua.
- **Rotación automática**: AWS SM Secret Rotation con Lambda function para APIs de OpenAI y Cohere; rotación cada 90 días; proceso sin downtime con ventana de validez dual de 5 minutos.
- **ConfigMaps de Kubernetes**: parámetros no sensibles versionados en el repositorio en `infra/k8s/configmaps/`; diferenciados por entorno; cambios con commit message descriptivo para audit trail.
- **Pydantic Settings**: validación de configuración completa al startup — falla fast con `ValidationError` si cualquier variable requerida está ausente o tiene formato incorrecto.
- **`.env.example`**: archivo con todas las variables necesarias documentadas con descripciones, valores de ejemplo seguros para desarrollo, y notas sobre cómo obtener las credenciales reales.
- **CloudTrail**: cada cambio en AWS Secrets Manager emite un evento a CloudTrail con timestamp, ARN del secret y identidad del principal que realizó el cambio — audit trail completo de cambios de configuración.
- **detect-secrets**: hook de pre-commit que escanea cada commit en busca de patrones de secrets en el código — previene que API keys o passwords se commiteen accidentalmente.

> **Nota del Arquitecto**: El `.env.example` es el artefacto de incorporación más valioso para nuevos integrantes del equipo. Cuando está bien mantenido — con todas las variables necesarias, una descripción de para qué sirve cada una, y notas sobre cómo obtener las credenciales de desarrollo — un nuevo ingeniero puede hacer `cp .env.example .env` y tener el sistema corriendo localmente en 30 minutos. Cuando está desactualizado — le falta una variable que se añadió recientemente, o tiene una variable que ya no se usa — el nuevo ingeniero pierde horas debuggeando un error críptico de "variable de entorno no definida". Mantener `.env.example` actualizado con cada cambio de configuración debería ser un criterio de aceptación de cualquier PR que modifique la configuración del sistema.

La gestión de configuraciones correcta es el control de seguridad con mayor ROI del sistema: previene el tipo de incidente más frecuente (secret en el código) con un esfuerzo de implementación relativamente bajo. El Capítulo 6 cierra con la síntesis de las prácticas MLOps que convierten el sistema en un producto operacional.

**Para recordar**: La gestión de secrets es el control de seguridad más frecuentemente comprometido en sistemas de producción — un secret en el código o en un archivo .env commiteado es una vulnerabilidad crítica que puede explotarse durante años después del commit.
