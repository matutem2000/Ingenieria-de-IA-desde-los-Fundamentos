# Módulo 12 – Capítulo 02 – Sección 01

## ADR (Architecture Decision Record): estructura y propósito de documentar decisiones técnicas

Toda decisión técnica importante tiene un ciclo de vida que casi nunca se documenta: alguien propone una opción, el equipo debate, se elige una alternativa, y seis meses después nadie recuerda por qué se descartaron las otras. En sistemas de software convencionales, este olvido institucional es costoso. En sistemas de IA, donde los modelos fundacionales se actualizan trimestralmente, los precios cambian, los benchmarks se revisan y las decisiones de chunking o embedding tienen consecuencias en costo y calidad que son difíciles de revertir, el olvido es directamente peligroso. El equipo que no recuerda por qué eligió text-embedding-3-small sobre text-embedding-3-large repetirá el análisis completo cuando necesite justificar el gasto de embedding — o peor, cambiará al modelo más grande "porque parece mejor" sin datos que respalden el cambio.

Un Architecture Decision Record (ADR) es el mecanismo que previene ese olvido. Es un documento breve y estructurado que captura una decisión arquitectónica significativa junto con el problema que la motiva, las opciones evaluadas, la opción elegida y las consecuencias esperadas. El formato fue popularizado por Michael Nygard en 2011 y adoptado por Thoughtworks como práctica estándar de ingeniería. Los ADRs se versionan junto al código fuente del proyecto — en el directorio `docs/adr/` del repositorio — para que cada commit de código pueda asociarse con las decisiones arquitectónicas vigentes en ese momento. Cuando un ingeniero revisa el git log y encuentra "feat: switch embedding model to text-embedding-3-large", el ADR actualizado en ese commit explica por qué ese cambio fue necesario y qué trade-offs introduce.

La estructura de un ADR efectivo tiene cinco campos. El **Título** identifica la decisión con un número secuencial (ADR-001, ADR-002) y una frase que la nombra sin ambigüedad — "Selección del modelo fundacional para el sistema de asistencia técnica", no "Sobre el LLM". El **Estado** refleja el estado actual del documento: Proposed (para revisión), Accepted (vigente), Deprecated (reemplazado por una decisión posterior) o Superseded (con referencia al ADR que lo reemplaza). El **Contexto** describe el problema técnico que motiva la decisión, las restricciones activas (latencia, costo, seguridad) y las fuerzas en tensión — "necesitamos function calling paralelo para el agente ReAct, pero el modelo más barato no lo soporta". La **Decisión** enuncia la opción elegida con precisión y sin lenguaje evasivo: "Se usará GPT-4o (gpt-4o-2024-08-06)", no "se podría considerar usar GPT-4o". Las **Consecuencias** articulan efectos positivos esperados, trade-offs aceptados y riesgos residuales identificados — "mejora el accuracy en 0.02 puntos, incrementa el costo por petición en 0.003 USD, introduce dependencia en la API de OpenAI con SLA de 99.9%".

En sistemas de IA, los ADRs tienen una dimensión adicional que no existe en sistemas puramente de software: las decisiones sobre el modelo fundacional, el modelo de embedding y la estrategia de retrieval tienen consecuencias en la calidad, el costo y el riesgo que solo se revelan a través de evaluación empírica. Un ADR de software puede documentar "usaremos PostgreSQL porque soporta JSONB", una afirmación que se verifica en segundos. Un ADR de IA documenta "usaremos text-embedding-3-small con recall@5 de 0.82 en el benchmark del dominio" — una afirmación que requirió ejecutar un benchmark de 500 pares query-documento para ser formulada con precisión. Esta especificidad empírica es lo que distingue un ADR de IA útil de uno que solo parece formal.

## Estructura de un ADR efectivo

- **Título**: identificador numérico secuencial (ADR-001) más una frase que nombre la decisión sin ambigüedad y sin lenguaje vago.
- **Estado**: Proposed / Accepted / Deprecated / Superseded — con referencia al ADR que lo reemplaza cuando el estado es Superseded.
- **Contexto**: problema técnico que motiva la decisión, restricciones activas (latencia, costo, seguridad) y fuerzas en tensión que hacen que ninguna opción sea perfecta.
- **Decisión**: la opción elegida expresada con precisión técnica — incluye parámetros concretos, versiones de modelo y métricas de evaluación que respaldaron la elección.
- **Consecuencias**: efectos positivos esperados (qué mejora), trade-offs aceptados (qué empeora o qué se complica) y riesgos residuales identificados (qué podría salir mal y cómo se detectaría).

> **Nota del Arquitecto**: En proyectos de IA donde el equipo trabaja bajo presión de tiempo, la tentación es omitir los ADRs y "documentar después". Ese "después" rara vez llega. La práctica que funciona es escribir el ADR antes de tomar la decisión, no después — el proceso de formular el contexto y las consecuencias fuerza la claridad que la decisión necesita. Un ADR de media página escrito antes de elegir el framework agéntico previene semanas de debate posterior sobre si el framework elegido fue el correcto.

Los cuatro ADRs del proyecto final — modelo fundacional (ADR-001), estrategia RAG (ADR-002), diseño agéntico (ADR-003) y seguridad (ADR-004) — cubren las decisiones de mayor impacto y menor reversibilidad del sistema. Las secciones 02 a 05 de este capítulo desarrollan cada uno con el nivel de detalle técnico que justifica la elección y documenta las alternativas descartadas.

**Para recordar**: Un ADR documenta el razonamiento detrás de una decisión, no solo la decisión — sin el contexto de por qué se eligió una opción, el equipo no puede evaluar cuándo es válido cambiarla.
