# Módulo 12 – Capítulo 06 – Sección 02

## CI/CD pipeline: build, test, evaluación y despliegue automatizado

El pipeline CI/CD es el mecanismo que convierte el código de un PR en un sistema desplegado en producción de forma controlada, verificada y auditable. Para sistemas de software convencionales, ese pipeline típicamente incluye build, test y deploy. Para sistemas de IA, el pipeline incluye un stage adicional que no existe en ningún sistema convencional: la evaluación automática de la calidad del modelo. Sin ese stage, el CI/CD puede desplegar una versión que introduce una regresión de faithfulness o de task completion que ningún test de software convencional detectaría — el sistema funciona correctamente desde el punto de vista del código pero produce respuestas de menor calidad.

El pipeline del proyecto usa GitHub Actions con cuatro stages secuenciales que deben pasar todos para que el deploy proceda. La secuencia es no arbitraria: falla rápido en las validaciones más baratas (linting tarda segundos) antes de las más costosas (evaluación RAGAS con 20 muestras tarda varios minutos).

El **stage de build** construye la imagen Docker con `docker buildx build --cache-from type=registry,ref={registry}/{image}:cache --cache-to type=registry,ref={registry}/{image}:cache` para aprovechar el caché de layers entre builds, reduciendo el tiempo de build de 4-5 minutos a 1-2 minutos en casos donde solo el código de la aplicación cambió. Después del build, Trivy ejecuta un scan de vulnerabilidades sobre la imagen: `trivy image --severity CRITICAL --exit-code 1` falla el pipeline si hay algún CVE de severidad crítica en los paquetes de la imagen. Un CVE crítico en una dependencia de Python puede ser explotable para comprometer el contenedor — el scan automático en cada build garantiza que las vulnerabilidades conocidas se detectan antes de llegar a producción. La imagen se publica en el registry privado con dos tags: el SHA del commit (inmutable, para reproducibilidad) y la rama (mutable, para referencias de deployment).

El **stage de test** ejecuta en secuencia: linting con `ruff check --select E,F,W,I` (errores, flakes, warnings y ordenación de imports), type checking con `mypy --strict` (garantiza que los contratos de tipos Pydantic en las herramientas del agente son correctos), unit tests con pytest y cobertura mínima del 80% (`--cov-fail-under=80`), integration tests sobre el stack de test completo (Qdrant, Redis y PostgreSQL levantados con Docker Compose en el runner del CI), y un smoke test de la API que levanta el servidor con la imagen construida y verifica que `/health` responde con HTTP 200 en menos de 500ms.

El **stage de evaluate** es el diferenciador para sistemas de IA. Ejecuta el script de evaluación RAGAS sobre 20 muestras aleatorias del golden dataset usando la imagen del stage de build. El script llama al endpoint `/query` del sistema con cada una de las 20 queries, recoge las respuestas y calcula faithfulness y answer relevance con el framework RAGAS. Si faithfulness cae por debajo de 0.80 o answer relevance cae por debajo de 0.75, el stage falla y el deploy se bloquea. Los umbrales de 0.80 y 0.75 (ligeramente inferiores a los umbrales de producción de 0.85 y 0.80) se justifican estadísticamente por la varianza de muestreo en solo 20 pares — ver la explicación detallada en el Capítulo 3, Sección 5. Las métricas de evaluación se publican como artefactos del workflow de GitHub Actions y se envían a Slack mediante webhook: "Deploy {commit_sha}: faithfulness=0.87, answer_relevance=0.83 — PASSED".

El **stage de deploy** aplica los manifests de Kubernetes con `kubectl apply --server-side` (que usa Server-Side Apply para resolver conflictos de forma determinista) y espera la confirmación de que el rollout completó con `kubectl rollout status deployment/{name} --timeout=10m`. Si el rollout no completa en 10 minutos — porque los pods no pasan los health checks o porque hay un error en la imagen — el pipeline falla y el rollout se revierte automáticamente al estado anterior por el comportamiento default de Kubernetes deployments.

## Etapas del pipeline CI/CD

- **Build**: `docker buildx build` con cache de layers, Trivy scan `--severity CRITICAL --exit-code 1`, push a registry con tags SHA y rama; duración aproximada 2-3 minutos con cache hit.
- **Test**: ruff + mypy --strict + pytest --cov-fail-under=80 + integration tests (stack completo en Docker Compose) + smoke test API; duración aproximada 5-8 minutos.
- **Evaluate**: RAGAS evaluation sobre 20 muestras aleatorias del golden dataset con el sistema en producción; gate: faithfulness < 0.80 o answer_relevance < 0.75 bloquea el deploy; publicación de métricas como artefacto y notificación Slack.
- **Deploy**: `kubectl apply --server-side`, `kubectl rollout status --timeout=10m`; rollback automático si el rollout no completa; notificación Slack con resultado y enlace a Grafana.
- **Notificaciones**: Slack webhook en cada stage con resultado, duración y enlace a los logs del workflow — el equipo puede ver el estado del deploy sin abrir la interfaz de GitHub.

> **Nota del Arquitecto**: El stage de evaluate es el que más fricción introduce y el que más valor aporta. Los primeros deploy donde el gate bloquea un deploy porque faithfulness cayó de 0.87 a 0.79 van a generar frustración — "¿por qué el CI rechaza un cambio que no toca el pipeline RAG?". La respuesta es que un cambio en el system prompt del agente, una actualización de una dependencia, o un cambio en la configuración de la búsqueda híbrida puede afectar la calidad de las respuestas de formas que los tests de software no detectan. El gate de evaluación es exactamente el mecanismo que detecta esas degradaciones antes de que lleguen a los usuarios. Una vez que el equipo experimenta el primer bloqueo que previno una degradación real, la fricción inicial se convierte en confianza.

El pipeline CI/CD con gate de evaluación es el artefacto de MLOps que distingue un proyecto de IA maduro de uno que despliega por fe. El Capítulo 6 continúa con la infraestructura como código que provisiona el entorno donde este pipeline despliega — el cluster EKS, la base de datos PostgreSQL y la instancia de Qdrant Cloud que forman el entorno de producción.

**Para recordar**: El stage de evaluación automática en el pipeline CI/CD es lo que distingue el MLOps del DevOps para sistemas de IA — sin una puerta de calidad cuantitativa, los despliegues pueden degradar silenciosamente el comportamiento del modelo en producción.
