# Security testing pipeline: fuzzing, red teaming y SAST/DAST adaptados a IA

El security testing pipeline para sistemas de IA debe combinar técnicas del security testing de software tradicional (SAST, DAST, fuzzing) con técnicas específicas de IA (red teaming de prompts, adversarial testing, evaluación de clasificadores de seguridad) para proporcionar cobertura completa de la superficie de ataque del sistema. SAST (Static Application Security Testing) con herramientas como Semgrep, Bandit (Python) y CodeQL detecta vulnerabilidades en el código de la aplicación que rodea al modelo (hardcoded secrets, SQL injection en queries de preprocessing, unsafe deserialization de artefactos de modelo); DAST (Dynamic Application Security Testing) con OWASP ZAP o Burp Suite prueba el endpoint de la API de IA contra ataques de capa HTTP (authentication bypass, CORS misconfiguration, injection en parámetros de URL); el fuzzing de prompts genera inputs maliciosos automáticamente mediante mutación de prompts conocidos; y el red teaming (manual + automatizado) cubre las vulnerabilidades semánticas específicas de LLMs. La integración de todos estos componentes en el pipeline de CI/CD garantiza que la seguridad se verifica en cada commit, no solo antes de los releases.

## Aspectos técnicos

- SAST adaptado a proyectos de IA: reglas personalizadas de Semgrep para detectar patrones anti-seguros comunes en código de IA: concatenación directa de user input en prompts sin sanitización (`f"User said: {user_input}"`), uso de `pickle.load` para deserializar artefactos de modelo (vulnerable a deserialization attacks), hardcoded API keys en código o en archivos de configuración, y logging de inputs completos del usuario sin cifrado
- DAST para endpoints de IA: extender las pruebas estándar de OWASP ZAP con tests específicos de IA: autenticación requerida para todos los endpoints de inferencia, rate limiting activo (verificar HTTP 429 ante requests rápidas), headers de seguridad correctos (Content-Security-Policy, X-Content-Type-Options), y ausencia de información sensible del modelo en los headers de respuesta o en mensajes de error
- Fuzzing de prompts: generar variaciones de prompts adversariales mediante mutación (inserción de caracteres especiales, sustitución de palabras por homoglifos, traducción parcial a otros idiomas, fragmentación en múltiples messages) y ejecutar automáticamente contra el sistema bajo prueba; medir la tasa de activación de safety filters y la tasa de comportamientos anómalos
- Evaluación de clasificadores de seguridad: los clasificadores usados como controles de seguridad (LlamaGuard, Azure Content Safety) deben ser evaluados periódicamente con datasets de test que incluyan tanto true positives (content dañino que debe ser bloqueado) como false positives (content benigno que no debe ser bloqueado); la degradación del F1 score del clasificador en el tiempo puede indicar model drift o nuevas técnicas de evasión
- Pipeline de CI/CD para security testing de IA: SAST en cada PR (pull request) con fallo si se detectan hallazgos críticos, DAST en el ambiente de staging antes de cada deploy a producción, evaluación del clasificador de seguridad semanalmente con un dataset de golden tests, y red teaming automatizado (Garak + subconjunto de PyRIT) como gate del pipeline de deployment

## Para recordar

El security testing pipeline para sistemas de IA debe ser completamente automatizado para los controles que pueden automatizarse (SAST, DAST, fuzzing, evaluación de clasificadores) y complementado con red teaming manual periódico para las vulnerabilidades que requieren creatividad adversarial: la automatización proporciona cobertura consistente y escalable; el red teaming humano proporciona la profundidad que la automatización no puede alcanzar.
