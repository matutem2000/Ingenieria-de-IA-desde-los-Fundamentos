# Incident response para sistemas de IA: detección, contención y análisis forense

El incident response (IR) para sistemas de IA requiere adaptaciones específicas respecto al IR tradicional porque los "incidentes" en sistemas de IA tienen características únicas: pueden ser difíciles de detectar (un modelo comprometido por data poisoning se comporta normalmente el 99.9% del tiempo), pueden tener impacto difuso (un documento malicioso en el vectorstore afecta a todos los usuarios que hacen queries relacionadas), y la "contención" puede requerir decisiones de negocio complejas (¿desactivar el sistema de IA en producción mientras se investiga?). El IR lifecycle para sistemas de IA sigue el mismo framework NIST SP 800-61 (Preparación → Detección y Análisis → Contención, Erradicación y Recuperación → Post-incident) pero con procedimientos específicos para cada fase. La preparación pre-incidente incluye mantener runbooks específicos para los tipos de incidentes más probables (jailbreak en producción, data leakage, model extraction detectado, RAG poisoning), y los KPIs de IR para sistemas de IA deben incluir métricas como tiempo hasta detección de un jailbreak activo en producción y tiempo de contención de un documento malicioso en el vectorstore.

## Aspectos técnicos

- Playbooks específicos para incidentes de IA: (1) Jailbreak activo en producción: triggear revisión manual del log de las últimas 24h, identificar qué usuarios recibieron outputs problemáticos, revocar temporalmente el acceso del modelo si el impacto es amplio, notificar a usuarios afectados si aplica GDPR/CCPA; (2) RAG poisoning detectado: identificar el documento malicioso via el audit trail de document_ids, removerlo del vectorstore, ejecutar re-index, y auditar qué requests utilizaron ese documento
- Indicadores de compromiso (IoC) específicos de IA: spike en safety filter trigger rate, aumento en requests con características de model extraction (alta diversidad, coverage sistemática de topics), outputs que contienen el texto del system prompt (prompt leaking exitoso), tool calls a endpoints externos no en la allowlist, y queries con patrones de membership inference (textos muy similares a training data del modelo)
- Contención de un sistema de IA comprometido: opciones de contención en escala de impacto: (1) activar modo restrictivo del output filter (umbral más alto de bloqueo); (2) deshabilitar herramientas específicas del agente; (3) rollback al model checkpoint anterior; (4) failover a un sistema fallback más simple; (5) desactivación completa con mensaje de mantenimiento
- Análisis forense post-incidente: reconstruir la secuencia completa del ataque usando el audit trail; identificar el vector de entrada, la técnica utilizada, qué controles fallaron y por qué, qué datos fueron accedidos o expuestos; este análisis debe producir mejoras concretas en los controles del sistema y alimentar el threat model actualizado
- Post-incident activities: disclosure a reguladores si aplica (GDPR Art. 33 exige notificación a DPA en 72h si hay data breach de usuarios europeos), notificación a usuarios afectados (Art. 34 si hay riesgo alto para sus derechos), y actualización de los playbooks de IR con las lecciones aprendidas

## Para recordar

El incident response para sistemas de IA debe prepararse antes de que ocurra el incidente, no durante: los runbooks, los umbrales de alerta en el SIEM, los procedimientos de contención y los contactos de escalation deben estar documentados, probados (mediante simulacros) y actualizados antes de que el sistema entre en producción.
