# Módulo 9 – Capítulo 05 – Sección 04

## Sandboxing de herramientas de agentes: contención de ejecución de código y acceso a sistemas

El sandboxing en sistemas agénticos parte de un supuesto de diseño pesimista pero realista: el LLM puede ser comprometido. Dado ese supuesto, el sandbox garantiza que incluso un agente completamente bajo control del atacante no puede acceder a credenciales del sistema, modificar sistemas fuera de su scope autorizado, o comunicarse con hosts no autorizados. Esta es la aplicación del principio de defense in depth al nivel del agente: si el plano de control que valida las acciones falla, el sandbox es la siguiente línea de defensa que limita el daño. Sin sandbox, el fallo del plano de control convierte cualquier compromiso del agente en acceso completo a todo lo que el proceso del agente puede alcanzar.

El caso de uso más crítico de sandboxing en sistemas agénticos es la ejecución de código. Cuando el LLM puede ejecutar código —Code Interpreter de OpenAI, herramientas de bash en Claude Computer Use, el executor de código de LangChain— el código que genera el modelo debe ejecutarse en un entorno completamente aislado del sistema host. Las características mínimas de este aislamiento son: filesystem de solo lectura excepto en directorios temporales designados (para prevenir que el código malicioso modifique archivos del sistema), sin acceso a la red exterior por defecto (para prevenir conexiones a hosts del atacante o SSRF hacia servicios internos), con límites de CPU y memoria mediante cgroups (para prevenir DoS por consumo de recursos), y con un tiempo máximo de ejecución (para prevenir loops infinitos). OpenAI implementa el Code Interpreter de ChatGPT en containers Docker con estas restricciones; AWS Lambda proporciona entornos de ejecución con tiempo de vida corto; tecnologías como gVisor (Google) y Firecracker (AWS) añaden capas adicionales de aislamiento del kernel con menor overhead de performance que Docker completo.

El control de acceso a herramientas en el nivel de runtime es la segunda dimensión del sandboxing. Cada llamada a una herramienta debe pasar por un proxy de autorización —el plano de control— que verifica que la operación específica está dentro del scope autorizado para el agente en el contexto de la request actual. Esta verificación debe ser granular: no "el agente puede usar la base de datos" sino "el agente puede ejecutar SELECT en la tabla de pedidos para el customer_id asociado a la sesión actual del usuario, y no puede ejecutar UPDATE, DELETE, ni acceder a otras tablas". Cuando la verificación es binaria ("el agente tiene o no tiene acceso a la herramienta"), el compromiso del agente equivale a acceso completo a esa herramienta con todos sus permisos.

La gestión de secrets en sistemas agénticos merece atención especial porque la solución intuitiva —incluir las credenciales en el system prompt para que el agente pueda usarlas— crea la vulnerabilidad más directa posible: si el system prompt es extraído, las credenciales quedan completamente expuestas. La arquitectura correcta mantiene las credenciales completamente fuera del contexto del modelo: el plano de control inyecta las credenciales necesarias directamente en la llamada a la herramienta en el momento de la ejecución, sin que el LLM tenga acceso a ellas. HashiCorp Vault con Dynamic Secrets puede generar credenciales de duración limitada (con TTL de minutos u horas) específicas para la herramienta y la sesión actual, que se revocan automáticamente al finalizar la tarea.

## Aspectos técnicos

- **Sandboxing de ejecución de código:** containers Docker (o gVisor, Firecracker) con filesystem de solo lectura, sin acceso a red exterior, con límites de CPU/memoria por cgroups, y tiempo máximo de ejecución; el código generado por el modelo nunca se ejecuta directamente en el proceso del agente.
- **Network sandboxing:** los agentes con acceso web operan a través de un proxy HTTP de egress que aplica una allowlist de dominios permitidos y rechaza conexiones a rangos de IPs privadas (169.254.x.x, 10.x.x.x, 172.16-31.x.x, 192.168.x.x) para prevenir SSRF via herramientas del agente.
- **Control de acceso granular a herramientas en runtime:** el plano de control verifica que la operación específica (SELECT vs. UPDATE, directorio específico, API endpoint específico) está dentro del scope autorizado; la verificación binaria (el agente tiene o no tiene la herramienta) es insuficiente.
- **Secrets management:** las credenciales que el agente usa para llamar APIs externas se inyectan en las llamadas a herramientas por el plano de control, nunca se incluyen en el system prompt ni en el contexto del LLM; HashiCorp Vault con Dynamic Secrets para credenciales de duración limitada por sesión.
- **Ephemeral environments:** para tareas de alta sensibilidad, el entorno del agente se destruye completamente al finalizar la tarea, incluyendo todos los artefactos temporales, variables de entorno y estado de ejecución; sin persistencia que el atacante pueda explotar en sessions posteriores.

> **Nota del Arquitecto:** El error de sandboxing más frecuente que he visto es el "sandbox de papel": el proceso del agente está en un container Docker, pero ese container tiene montado el directorio home del usuario, el socket de Docker, o variables de entorno con credenciales de AWS. Un container con esos accesos no es un sandbox; es una ilusión de seguridad más peligrosa que no tener sandbox, porque da al equipo falsa confianza. El sandbox efectivo requiere auditar explícitamente qué volúmenes están montados, qué variables de entorno están disponibles en el container, y qué capabilities de Linux tiene el proceso.

El sandboxing de herramientas agénticas debe diseñarse asumiendo que el LLM puede ser comprometido, y el objetivo del sandbox es garantizar que ese compromiso no se propague a sistemas externos con consecuencias reales.
