# Módulo 9 – Capítulo 01 – Sección 04

## Modelado de amenazas para aplicaciones de IA: STRIDE y AI-specific frameworks

El modelado de amenazas es la actividad que convierte la intuición sobre riesgos en un inventario estructurado y priorizado de amenazas concretas. Sin este proceso, un equipo de AI Engineering aplica controles de seguridad en los lugares donde más los teme —frecuentemente los más visibles, como el endpoint de inferencia— mientras deja sin cubrir superficies de ataque igualmente críticas como el pipeline de MLflow o los permisos de escritura en el índice vectorial. El threat modeling transforma la seguridad de una colección de decisiones ad hoc en un programa sistemático donde cada control puede trazarse hasta una amenaza específica en el modelo, y cada brecha de control puede identificarse antes de que un adversario la explote.

STRIDE —Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege— es el framework desarrollado por Microsoft que organiza el espacio de amenazas en seis categorías cubren la mayoría de las situaciones que un equipo de ingeniería enfrenta en producción. Aplicado a sistemas de IA, cada categoría adquiere manifestaciones específicas que no existían en las versiones originales del framework: el Spoofing en un LLM puede ser un atacante que hace pasar instrucciones maliciosas como si vinieran del operador del sistema mediante prompt injection; el Tampering puede ser la modificación del comportamiento del modelo a través de data poisoning durante el fine-tuning; la Repudiation se manifiesta en la falta de logs inmutables que impiden atribuir con certeza qué output produjo el modelo ante qué input; la Information Disclosure cubre tanto el prompt leaking clásico como la memorización de datos sensibles del corpus de entrenamiento; el DoS incluye context-flooding con prompts de 128k tokens; y la Elevation of Privilege ocurre cuando un jailbreak exitoso permite al usuario hacer que el agente ejecute acciones que sus privilegios no deberían permitir.

MITRE ATLAS (Adversarial Threat Landscape for Artificial-Intelligence Systems) complementa STRIDE con una perspectiva orientada al adversario: en lugar de categorizar amenazas por tipo, organiza los ataques por las tácticas que los atacantes usan —ML Attack Staging, Model Evasion, Model Theft, Data Poisoning, entre otras— con técnicas documentadas y ejemplos reales de ataques observados en producción. ATLAS es análogo a MITRE ATT&CK para sistemas de IA: proporciona el vocabulario que los equipos de seguridad usan para comunicar amenazas de forma inequívoca y para mapear observaciones de producción a técnicas de ataque conocidas. La combinación de STRIDE (para el razonamiento sistemático por categoría de amenaza) y ATLAS (para el razonamiento orientado al adversario) es más completa que cualquiera de los dos frameworks por separado.

El elemento técnico más importante del proceso de threat modeling es el Data Flow Diagram (DFD) con trust boundaries explícitas. Un DFD de sistema RAG típico muestra cinco componentes: el usuario (fuera de confianza), el gateway de la aplicación, el LLM, el vectorstore, y las herramientas externas. Cada flecha entre componentes que cruza una trust boundary es un punto donde STRIDE debe aplicarse sistemáticamente: la flecha del usuario al gateway cruza la boundary "público → sistema confiado" y es vulnerable a Spoofing e Information Disclosure; la flecha del vectorstore al LLM cruza la boundary "datos externos → modelo" y es vulnerable a Tampering (documentos maliciosos) e Information Disclosure (datos de otros tenants). Aplicar STRIDE en cada cruce de boundary genera una lista completa de amenazas que puede priorizarse con frameworks como DREAD (Damage, Reproducibility, Exploitability, Affected users, Discoverability).

## Componentes del modelado de amenazas para IA

- **STRIDE aplicado a LLMs:** Spoofing del identity del sistema via prompt injection que hace pasar instrucciones del atacante como instrucciones del operador; Tampering de outputs via manipulación del contexto RAG; Repudiation por ausencia de logs inmutables de inferencia; Information Disclosure via prompt leaking o memorización; DoS via context-flooding; Elevation of Privilege via jailbreak que desbloquea capacidades restringidas.
- **MITRE ATLAS TTPs:** las 14 tácticas incluyen ML Attack Staging (preparar el ataque mediante reconnaissance del sistema), Model Evasion (eludir clasificadores de contenido), Model Theft (extraer el modelo propietario via queries sistemáticas), y Data Poisoning (contaminar el corpus de entrenamiento); cada táctica tiene técnicas documentadas con casos reales.
- **Data Flow Diagrams para IA:** el DFD debe incluir el modelo como componente con trust boundaries explícitas entre usuario, gateway, LLM, vectorstore y herramientas externas; los documentos del corpus RAG y los resultados de herramientas son entidades de datos en el DFD con su propio nivel de confianza.
- **AI-specific trust boundaries:** el prompt del usuario (untrusted), los documentos recuperados por RAG (semi-trusted según el origen), los resultados de herramientas (trusted solo si el tool está bajo control del sistema), y el historial de conversación (mixed-trust porque incluye tanto mensajes del sistema como del usuario).
- **Threat enumeration y priorización:** aplicar STRIDE a cada cruce de trust boundary genera la lista completa de amenazas; priorizarlas con DREAD o CVSS adaptado permite enfocar los controles en las amenazas de mayor impacto y probabilidad.

> **Nota del Arquitecto:** El DFD más incompleto que veo en revisiones de arquitectura es el que no incluye el pipeline de fine-tuning como superficie de ataque. Los equipos dibujan el sistema de inferencia con detalle, pero el proceso de entrenamiento —el S3 bucket con los datos de entrenamiento, el script de fine-tuning, el endpoint de MLflow donde se registra el modelo— queda fuera del diagrama y por tanto fuera del threat model. Un atacante con acceso de escritura al bucket de training data puede comprometer el modelo resultante sin tocar nunca el sistema de inferencia.

El threat model de un sistema de IA debe actualizarse cada vez que se agrega una nueva herramienta al agente, se cambia el modelo base, o se expande el corpus del vectorstore. Cada cambio de capacidad es un cambio en la superficie de ataque que invalida parcialmente el modelo de amenazas anterior. Esta necesidad de actualización continua es el puente hacia la siguiente sección, que trata la responsabilidad compartida: quién debe actualizar qué parte del threat model cuando el proveedor del modelo base lanza una nueva versión.
