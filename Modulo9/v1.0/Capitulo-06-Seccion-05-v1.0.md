# Módulo 9 – Capítulo 06 – Sección 05

## Auditoría de acceso a datos: logs de qué datos fueron procesados por el modelo

La auditoría de acceso a datos en sistemas de IA responde a preguntas que son críticas tanto para la seguridad operacional como para el compliance regulatorio: ¿qué datos personales de qué usuarios fueron procesados por qué versión del modelo en qué momento?, ¿qué documentos del corpus RAG fueron recuperados y usados como contexto para generar una respuesta específica?, ¿qué herramientas invocó el agente con qué argumentos durante la sesión de un usuario determinado? Estas preguntas son triviales de responder en sistemas CRUD con logs de queries de base de datos, pero en sistemas de IA requieren un diseño deliberado del sistema de logging porque el "procesamiento" de un dato por un LLM no genera automáticamente trazas auditables equivalentes.

El diseño del audit log para sistemas de IA requiere identificar qué información debe registrarse para responder a los tres casos de uso principales: el análisis forense de incidentes de seguridad (¿qué ocurrió exactamente y qué datos fueron expuestos?), el compliance regulatorio proactivo (¿podemos responder a una DSAR de GDPR dentro de 30 días?, ¿podemos demostrar que los controles de HIPAA estuvieron activos?), y el análisis de riesgo operacional (¿qué usuarios intentan ataques de jailbreak?, ¿qué documentos RAG se recuperan más frecuentemente ante queries relacionadas con temas sensibles?). El schema del audit log debe ser suficientemente rico para soportar todos estos casos de uso, pero también suficientemente disciplinado en la retención de texto completo para no crear él mismo un riesgo de privacidad.

La granularidad del tracking de documentos RAG es el elemento más específico de los sistemas de IA. Cada inferencia que usa RAG debe registrar los IDs únicos de los documentos recuperados del vectorstore, los scores de similitud con la query, y si el documento fue efectivamente incluido en el contexto enviado al modelo (top-k puede recuperar más documentos de los que caben en el contexto). Este nivel de granularidad permite responder preguntas como "¿los documentos de este usuario fueron recuperados como contexto para respuestas a otros usuarios?" —pregunta crítica para detectar cross-user contamination en RAG compartido y para responder DSARs de GDPR que pregunten qué uso se hizo de los datos del sujeto.

Los sistemas que procesan PHI bajo HIPAA tienen un requisito adicional: los audit logs de acceso a PHI deben mantenerse por mínimo seis años, y deben registrar no solo qué datos fueron accedidos sino también el "propósito" del acceso —qué tarea estaba realizando el usuario que generó el acceso a esos datos. Para sistemas de IA donde el "propósito" no es siempre explícito (el usuario hizo una pregunta y el RAG recuperó documentos que contenían PHI sin que el usuario lo solicitara específicamente), el log debe registrar suficiente contexto para que un auditor pueda entender el flujo: la query del usuario, los documentos recuperados, y si el modelo utilizó información de esos documentos en su respuesta.

## Aspectos técnicos

- **Schema del security event para sistemas de IA:** `{event_id, timestamp, user_id, session_id, request_id, model_id, model_version, system_prompt_hash, input_token_count, input_hash, retrieved_document_ids[], retrieved_document_scores[], tool_calls[{name, args_hash, result_hash}], output_hash, input_safety_score, output_safety_score, latency_ms}` con texto completo de input/output cifrado por usuario en campo separado.
- **Inmutabilidad del audit log:** S3 Object Lock en COMPLIANCE mode (AWS), Azure Immutable Blob Storage, o WORM storage equivalente; los logs de auditoría deben ser write-once para ser válidos como evidencia regulatoria y forense.
- **DSAR compliance automation (GDPR):** el audit log debe ser consultable por user_id para exportar todos los eventos que involucran datos de un usuario específico dentro de los 30 días que el GDPR permite; la estructura del log debe diseñarse con esta query en mente desde el inicio.
- **Borrado selectivo para el derecho al olvido:** implementar borrado mediante cifrado por usuario: cada usuario tiene una clave de cifrado única para el texto de sus inputs/outputs; el "borrado" consiste en descartar la clave, haciendo ilegible el contenido aunque el registro del evento permanezca.
- **Tracking de documentos RAG:** registrar retrieved_document_ids[] con scores de similitud permite responder si los documentos de un usuario fueron usados como contexto para respuestas a otros usuarios — crítico para detectar cross-user contamination y para DSARs de GDPR.

El audit log de un sistema de IA es el instrumento de análisis forense más crítico ante un incidente: sin los IDs de documentos RAG recuperados, los argumentos de tool calls, y los scores de clasificadores de seguridad, es imposible reconstruir si el sistema fue comprometido y cómo.
