# Módulo 9 – Capítulo 08 – Sección 03

## Trazabilidad de decisiones: explicabilidad y atribución en sistemas de IA

La trazabilidad de decisiones en sistemas de IA responde a una pregunta que es simultáneamente un requisito de compliance regulatorio y una necesidad operacional de seguridad: ¿por qué el sistema produjo este output específico dado este input específico? Para los reguladores del EU AI Act (que exige explicabilidad de decisiones automatizadas que afectan a personas en sistemas de alto riesgo), para los usuarios que quieren entender el fundamento de una recomendación, y para los equipos de seguridad que necesitan reconstruir cómo se produjo un incidente, la respuesta a esta pregunta es crítica. La complicación es que la explicabilidad matemática completa de un LLM —por qué exactamente estos pesos con estas atenciones producen exactamente este output dado exactamente este input— es computacionalmente intractable para modelos de producción de millones de parámetros. La trazabilidad práctica, sin embargo, es suficiente para la mayoría de los casos de uso.

La distinción entre explicabilidad y trazabilidad es más que semántica. La explicabilidad intenta responder "por qué el modelo tomó esta decisión" —una pregunta que requiere análisis de las representaciones internas del modelo, análisis de atención, o técnicas de interpretabilidad como SHAP o LIME, que son costosas computacionalmente y no siempre concluyentes para modelos grandes. La trazabilidad registra "qué inputs, herramientas, documentos y contexto estaban presentes cuando el sistema produjo este output" —una pregunta que puede responderse completamente con los logs correctamente diseñados, sin análisis de internals del modelo. Para la mayoría de los requisitos regulatorios y forenses, la trazabilidad es suficiente: el auditor o el investigador de seguridad puede ver exactamente qué información tenía el modelo disponible cuando generó el output en cuestión.

El chain of thought logging es la mejor aproximación disponible a la explicabilidad del proceso de decisión en sistemas que usan razonamiento explícito. En modelos que soportan extended thinking —Claude 3.7 Sonnet, GPT-o1, o modelos con chain-of-thought prompting explícito— el razonamiento intermedio del modelo antes de su respuesta final debe registrarse como parte del log del request. Este razonamiento no es la explicación matemática de la decisión, pero proporciona el proceso de inferencia del modelo: qué consideró, qué descartó, qué incertidumbre tenía. En análisis forense, la diferencia entre un output que fue el resultado de razonamiento coherente y uno que fue el resultado de un jailbreak que interrumpió el razonamiento normal puede ser visible en el chain of thought.

La atribución de documentos RAG —registrar qué documentos del corpus fueron recuperados y qué fragmentos específicos el modelo usó en su respuesta— es un mecanismo de explicabilidad aplicado específicamente a sistemas RAG. LlamaIndex, LangChain, y otros frameworks soportan citation generation: la respuesta del modelo incluye referencias explícitas a los chunks de documentos que fundamentaron cada afirmación. Este mecanismo es simultáneamente explicabilidad para el usuario (sabe de dónde viene la información), trazabilidad para el auditor (puede verificar que la información en la respuesta corresponde a los documentos del corpus), y control de seguridad (puede detectar si el modelo "alucinó" información sin fuente verificable).

## Aspectos técnicos

- **Chain of thought logging:** registrar el razonamiento intermedio del modelo (extended thinking, CoT explícito) como parte del log del request; crítico para análisis forense (¿el modelo razonó correctamente o fue manipulado?) y para compliance de explicabilidad en sistemas de alto riesgo del EU AI Act.
- **Citation generation para atribución de documentos RAG:** cada afirmación factual atribuida a un chunk de documento específico con su ID y score de similitud; LlamaIndex y LangChain soportan esto nativamente; simultáneamente explicabilidad para el usuario y trazabilidad para el auditor.
- **Versioning del system prompt:** registrar con qué versión exacta del system prompt se procesó cada request; un cambio en el system prompt puede cambiar significativamente el comportamiento del modelo, y sin versioning es imposible distinguir un ataque de un cambio no autorizado del prompt.
- **Model card y version tracking por request:** model_id + versión registrados en cada request; en sistemas con múltiples modelos (clasificador de input + LLM generativo + clasificador de output), cada componente versionado y su versión registrada en el log del request completo.
- **Decision audit trail para sistemas de alto impacto:** en sistemas donde la IA toma o influye en decisiones que afectan a personas (préstamos, diagnósticos, contratación), el audit trail debe incluir output del modelo, documentos de contexto, confidence scores, cualquier override humano, y el outcome final — suficiente para revisión regulatoria post-hoc del EU AI Act.

La trazabilidad de decisiones no es sinónimo de explicabilidad matemática del modelo sino el registro completo de las condiciones bajo las que se produjo cada output: versión del modelo, versión del system prompt, documentos recuperados, herramientas invocadas, y scores de clasificadores — suficiente para análisis forense de incidentes y para compliance regulatorio de sistemas de alto riesgo.
