# Módulo 9 – Capítulo 01 – Sección 01

## La superficie de ataque de los sistemas de IA: qué es nuevo respecto a sistemas tradicionales

En el Módulo 8 aprendimos a desplegar infraestructura de inferencia real: levantamos servidores vLLM y Text Generation Inference (TGI) para servir modelos en producción, configuramos pipelines de MLflow para rastrear artefactos de modelo, indexamos documentos en Pinecone o Weaviate para alimentar sistemas RAG, y conectamos pipelines de fine-tuning al almacenamiento en S3 o GCS. Esa infraestructura que construimos con tanto cuidado —el servidor vLLM escuchando en el puerto 8000, el índice vectorial actualizado periódicamente, el repositorio de modelos en MLflow— es exactamente la superficie de ataque que este módulo analiza. Pasar del Módulo 8 al Módulo 9 no es un salto temático: es girar la perspectiva ciento ochenta grados, del diseñador al adversario.

Los sistemas de IA introducen vectores de ataque que no existen en el software tradicional, y la diferencia es estructural, no incidental. En una API REST convencional, el servidor ejecuta lógica determinista: la misma entrada produce siempre la misma salida, y las vulnerabilidades son bugs en el código que pueden ser encontrados y corregidos con análisis estático. Un LLM como GPT-4o o Claude 3.5 Sonnet, en cambio, genera outputs probabilísticos basados en instrucciones en lenguaje natural. Este diseño hace que el modelo en sí mismo sea una superficie de ataque activa: puede ser inducido a cambiar su comportamiento mediante texto cuidadosamente construido, sin necesidad de explotar ninguna vulnerabilidad en el código. Un firewall de red no puede bloquear un prompt injection porque el payload malicioso llega en el mismo canal que las instrucciones legítimas; un WAF tradicional no entiende la semántica de un jailbreak porque el ataque no tiene firma a nivel de protocolo HTTP.

A esta superficie de ataque del modelo se suman las superficies de los componentes que lo rodean. El embedding space de los modelos de representación no tiene equivalente en sistemas CRUD: los vectores almacenados en Pinecone, Weaviate, Chroma o pgvector no son solo datos inertes sino representaciones semánticas que determinan qué información recibe el modelo como contexto. Un documento malicioso en el índice vectorial no rompe el sistema en el sentido técnico clásico, pero puede modificar el comportamiento del modelo de maneras que una query de SQL injection nunca podría. De manera similar, el pipeline de fine-tuning —que en el Módulo 8 configuramos con tanta atención a la calidad de los datos— es una superficie de ataque si los datos de entrenamiento pueden ser contaminados por un adversario.

Comprender esta expansión de la superficie de ataque es el prerequisito para cualquier decisión de seguridad que se tome en los capítulos siguientes. No se trata de aplicar las mismas soluciones de seguridad web a un contexto diferente; se trata de reconocer que los sistemas de IA requieren un modelo de amenazas propio.

## Componentes de la nueva superficie de ataque

- **Model input surface:** el prompt —en texto, imágenes, audio o documentos— es un vector de entrada que no puede sanitizarse mediante reglas tradicionales de WAF porque la "malicia" está en el significado semántico del texto, no en su estructura sintáctica o protocolar.
- **Model weights y fine-tuning pipeline:** los pesos del modelo pueden ser adulterados durante el fine-tuning si el dataset de entrenamiento está contaminado con ejemplos maliciosos, modificando el comportamiento del modelo en producción de maneras latentes y difíciles de detectar.
- **Retrieval layer (RAG):** los índices vectoriales y los documentos recuperados son superficies de inyección de instrucciones maliciosas que el modelo ejecutará como parte de su contexto, especialmente cuando el corpus incluye documentos de fuentes externas no verificadas.
- **Tool-calling interface:** en sistemas agénticos construidos con LangChain, LangGraph o CrewAI, las herramientas expuestas al modelo —ejecutar código, llamar APIs, leer archivos, enviar emails— amplifican exponencialmente el impacto de cualquier ataque exitoso.
- **Output processing pipeline:** las respuestas del modelo pueden contener código malicioso, instrucciones de rendering o rutas de exfiltración de datos si se renderizan en el frontend sin sanitización apropiada.
- **Serving layer:** el servidor vLLM, TGI, o Triton Inference Server que desplegamos en el Módulo 8 tiene sus propias vulnerabilidades de infraestructura —escapes de container, exploits de la API de administración, escalada de privilegios— que deben gestionarse con los mismos controles que cualquier servidor de aplicaciones crítico.

> **Nota del Arquitecto:** En producción, las vulnerabilidades más frecuentes no están en el modelo sino en la capa de aplicación que lo rodea: concatenar el input del usuario directamente en el prompt sin separación estructural, almacenar API keys en el system prompt, o indexar en el vectorstore documentos de usuarios sin validación de contenido. Estos errores de diseño ocurren porque los equipos tratan al LLM como una API más, sin reconocer que su input es también su "código ejecutable".

La superficie de ataque de un sistema de IA incluye cada capa del pipeline —desde el input del usuario hasta los pesos del modelo, pasando por el serving layer, el vectorstore y las herramientas del agente— y cada capa debe tener controles de seguridad independientes porque ninguna capa puede ser considerada confiable por sí sola. Esta es la premisa sobre la que se construye todo el módulo.
