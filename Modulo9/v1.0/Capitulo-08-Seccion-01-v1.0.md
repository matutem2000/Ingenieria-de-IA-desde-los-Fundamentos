# Módulo 9 – Capítulo 08 – Sección 01

## Logs de seguridad: qué registrar — inputs, outputs, herramientas invocadas y decisiones

El diseño del sistema de logging de seguridad es una decisión arquitectónica que debe tomarse antes de ir a producción, no como reacción a un incidente. Esta afirmación tiene una razón técnica concreta: añadir logging completo a un sistema en producción que no fue diseñado para ello requiere frecuentemente cambios en el esquema de la base de datos, en el formato de los eventos, y en los controles de acceso a los datos de logging —cambios que son costosos de implementar, riesgosos de desplegar en un sistema que ya está sirviendo tráfico, y que pueden crear brechas temporales de cobertura durante la transición. El sistema de logging diseñado desde el inicio puede ser parte del hot path de cada request sin sorpresas arquitectónicas posteriores.

La tensión fundamental en el diseño del logging es entre la cobertura forense y la privacidad. Registrar inputs y outputs completos de todas las requests proporciona máxima cobertura para análisis forense pero crea riesgos de privacidad —esos logs contienen todo lo que el usuario escribió, potencialmente incluyendo datos sensibles—, costos de almacenamiento significativos en sistemas de alto volumen, y obligaciones adicionales bajo GDPR y HIPAA para la gestión de retención y borrado de esos datos. La solución no es uno u otro extremo sino un diseño cuidadoso que maximiza el valor forense mientras minimiza el riesgo de privacidad: almacenar el texto completo de input y output cifrado por usuario con TTL definido, mientras los metadatos de seguridad (hashes, scores de clasificadores, IDs de documentos recuperados) se almacenan en un log estructurado de mayor durabilidad y acceso más amplio.

El schema del security event para sistemas de IA es sustancialmente más rico que el de un log HTTP convencional, porque la información relevante para análisis de seguridad incluye componentes específicos de IA que no tienen equivalente en logs de servidor web. Un log de acceso HTTP registra IP, método, path, status code, y latencia. El security event de un sistema de IA debe registrar adicionalmente: el model_id y la versión exacta del modelo que procesó la request (porque el mismo endpoint puede servir múltiples versiones del modelo), el hash del system prompt activo durante la request (no el texto completo, para proteger su confidencialidad pero permitir detectar cambios), los IDs de los documentos recuperados del vectorstore con sus scores de similitud, los nombres y hashes de argumentos de cada herramienta invocada por el agente, y los scores de los clasificadores de seguridad aplicados tanto al input como al output.

El logging de tool calls en sistemas agénticos merece atención especial porque es el registro más crítico para el análisis forense de incidentes en agentes. Cada invocación de herramienta debe registrarse con el nombre de la herramienta, un hash de los argumentos completos (los argumentos completos en un campo separado con cifrado), el resultado (hash del resultado + texto cifrado si es sensible), si la invocación fue autorizada o denegada por el plano de control, y la latencia de la ejecución. Sin este registro, es imposible reconstruir si una secuencia de tool calls fue el resultado de un ataque via tool injection, de un comportamiento inesperado del modelo, o de un uso legítimo del agente.

## Aspectos técnicos

- **Schema del security event de IA:** `{event_id, timestamp, user_id, session_id, request_id, model_id, model_version, system_prompt_hash, input_token_count, input_hash, retrieved_document_ids[], retrieved_document_scores[], tool_calls[{name, args_hash, authorized, result_hash, latency_ms}], output_hash, input_safety_score, output_safety_score, latency_ms, error_code}` con texto completo de input/output cifrado por usuario en almacenamiento separado con TTL.
- **Logging de tool calls en agentes:** cada herramienta invocada registrada con nombre, hash de argumentos, estado de autorización (aprobada/denegada), hash del resultado, y latencia; sin este registro es imposible reconstruir un ataque via tool injection.
- **Log levels para seguridad vs. telemetría:** eventos de seguridad (input clasificado como malicioso, rate limit excedido, auth failure, tool call denegada) a nivel ERROR con alerting inmediato; telemetría (request normal, latencias, token counts) a nivel INFO en batch; no mezclar levels para no saturar canales de alerta.
- **Correlación de eventos:** session_id y user_id permiten correlacionar múltiples requests de una sesión o usuario; request_id propagado con W3C Trace Context headers a todos los servicios del pipeline para trazabilidad end-to-end.
- **Logging en streaming:** acumular el output completo antes de registrar el evento final (no un evento por chunk); si se detecta una violación durante el streaming, registrar el evento de violación inmediatamente y truncar el streaming al usuario.

Los logs de seguridad de un sistema de IA son el instrumento de análisis forense más crítico ante un incidente: un log que registra solo "request procesada" sin los IDs de documentos RAG recuperados, los argumentos de tool calls, y los scores de clasificadores de seguridad hace imposible reconstruir si el sistema fue comprometido y cómo.
