# Módulo 9 – Capítulo 08 – Sección 02

## Inmutabilidad de logs: protección contra alteración de registros de auditoría

Los logs de seguridad solo tienen valor como evidencia regulatoria y forense si son inmutables: un log que puede ser modificado o borrado —por el sistema que lo generó, por un administrador con acceso, o por un atacante que comprometió el sistema— no puede usarse para determinar con certeza qué ocurrió durante un incidente, ni para demostrar compliance ante reguladores que preguntan qué controles estaban activos en un momento específico. Esta no es una distinción filosófica: los tribunales y los organismos regulatorios han rechazado logs como evidencia cuando el demandado no podía demostrar que los logs no habían sido alterados después del hecho que se investigaba.

La inmutabilidad de logs es un requisito explícito en múltiples frameworks regulatorios. PCI DSS en su Requirement 10.5 especifica "Secure audit trails so they cannot be altered". HIPAA en su Audit Controls Standard requiere procedimientos de hardware, software y procesos para registrar y examinar accesos a sistemas que contienen PHI, con la implicación de que esos registros deben ser preservados de modificación. El EU AI Act, en sus requisitos de trazabilidad para sistemas de alto riesgo, implica que los registros de decisiones deben poder auditarse con certeza de que no fueron alterados. El GDPR, aunque no especifica técnicamente el mecanismo, exige que los registros de procesamiento de datos personales sean confiables para responder a auditorías regulatorias y a litigios.

La inmutabilidad técnica puede implementarse con diferentes niveles de garantía y diferentes trade-offs de costo y complejidad. El nivel más básico es el almacenamiento write-once: Amazon S3 Object Lock en COMPLIANCE mode previene cualquier modificación o borrado de objetos durante el retention period configurado, incluyendo por usuarios root de la cuenta de AWS —el modo COMPLIANCE es más restrictivo que GOVERNANCE, que permite a administradores con permisos especiales desbloquear objetos. Azure Immutable Blob Storage ofrece capacidades equivalentes con certificación WORM. Para entornos self-hosted o on-premises sin acceso a estos servicios cloud, MinIO (el servidor de object storage open-source compatible con S3) implementa Object Locking que puede configurarse en modo COMPLIANCE para proporcionar las mismas garantías.

El nivel más robusto añade verificación criptográfica de integridad. Cada entrada de log firmada con HMAC-SHA256 usando una clave de signing almacenada en un KMS separado, donde cada firma incluye el hash de la entrada anterior (creando una cadena de hashes), hace que cualquier modificación —inserción, borrado, o cambio de una entrada— sea detectable porque invalida las firmas de todas las entradas posteriores. Este mecanismo de tamper evidence a nivel de secuencia es más robusto que el write-once storage solo, porque el write-once depende de las garantías del proveedor de storage mientras que la cadena de firmas puede ser verificada matemáticamente por cualquier auditor que tenga acceso a la clave pública de verificación.

## Aspectos técnicos

- **Amazon S3 Object Lock en COMPLIANCE mode:** previene modificación o borrado de objetos durante el retention period por cualquier usuario, incluyendo root de AWS; adecuado para logs de auditoría de sistemas de IA bajo GDPR, HIPAA, o PCI DSS; el modo COMPLIANCE es más restrictivo que GOVERNANCE.
- **Azure Immutable Blob Storage:** política time-based retention con lock habilitado que no puede ser reducida una vez aplicada; certificación WORM compatible; adecuado para organizaciones en ecosistema Azure.
- **MinIO Object Locking (self-hosted):** alternativa open-source compatible con S3 API para entornos on-premises o de nube privada; soporta COMPLIANCE mode equivalente al de AWS S3; adecuado para organizaciones sin acceso a cloud público.
- **Firma criptográfica de logs:** cada entrada firmada con HMAC-SHA256 donde la firma incluye el hash de la entrada anterior; cadena de firmas verificable matemáticamente; cualquier modificación invalida las firmas de todas las entradas posteriores.
- **SIEM como copia inmutable secundaria:** transmitir logs a un SIEM (Splunk, Elastic SIEM, Microsoft Sentinel, Wazuh/Graylog para self-hosted) en cuenta o infraestructura independiente como segunda copia inmutable; correlación cross-system y alertas en tiempo casi real.

> **Nota del Arquitecto:** La inmutabilidad de logs debe ser verificada periódicamente, no solo configurada. He auditado sistemas donde S3 Object Lock estaba configurado en modo GOVERNANCE en lugar de COMPLIANCE (modificable por administradores), o donde la retención estaba configurada en 7 días cuando el requisito regulatorio era 6 años. La verificación automática diaria de que la cadena de firmas es válida, y que el retention period es correcto, convierte la inmutabilidad de un estado declarado en una propiedad verificable del sistema.

La inmutabilidad de logs debe ser una propiedad verificable del sistema —demostrable matemáticamente o mediante auditoría del proveedor de storage— no una propiedad declarada que se asume correcta hasta que alguien pregunta por evidencia.
