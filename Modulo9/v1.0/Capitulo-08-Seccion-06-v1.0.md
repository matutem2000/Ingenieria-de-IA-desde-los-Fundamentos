# Módulo 9 – Capítulo 08 – Sección 06

## Cierre: sin trazabilidad no hay auditoría posible ni aprendizaje de incidentes

La trazabilidad y la auditoría en sistemas de IA no son capacidades que se añaden por compliance regulatorio externo sino herramientas de ingeniería que mejoran activamente la capacidad del equipo para entender, operar, y mejorar el sistema. Un sistema de IA sin trazabilidad se opera con los ojos cerrados: no se sabe si está siendo atacado ahora mismo, no se puede saber con certeza qué ocurrió cuando algo sale mal, y no se puede aprender de los incidentes para mejorar los controles porque no hay evidencia del incidente. La inversión en un sistema de logging e auditoría robusto —schema bien diseñado, almacenamiento inmutable, integración con SIEM, playbooks de IR— no es un gasto de compliance; es una inversión en capacidad operacional que tiene ROI medible en tiempo de detección de incidentes reducido, tiempo de respuesta reducido, y menor severidad de incidentes futuros porque las lecciones de incidentes pasados se incorporaron al sistema.

El ciclo de mejora continua que habilita la trazabilidad funciona de manera específica: el log de seguridad registra un intento de jailbreak detectado por el input filter; el análisis del log revela que la técnica era una variante de Crescendo attack que el filter identificó con un score bajo (casi falso negativo); el equipo calibra el umbral del classificador basado en esta observación; el red teaming periódico verifica que la calibración fue correcta; y el threat model se actualiza para incluir esta variante de Crescendo attack como amenaza documentada. Sin el log detallado con el safety score y la técnica detectada, esta cadena de mejora no puede iniciarse. La trazabilidad es el prerrequisito de la mejora continua del posture de seguridad.

Los sistemas de IA sin trazabilidad adecuada también presentan un problema específico ante auditorías regulatorias: no pueden demostrar que los controles estuvieron activos en el momento relevante. Un auditor de GDPR que pregunta "¿qué datos del usuario X fueron procesados por su sistema de IA entre las fechas A y B?" necesita una respuesta auditable con evidencia. Sin logs con los campos correctos, la única respuesta posible es "no tenemos registros" —que puede ser interpretada como incumplimiento en lugar de como ausencia de incidente.

## Conceptos clave del capítulo

- **Schema de security events:** user_id + session_id + model_id + model_version + system_prompt_hash + retrieved_document_ids[] + tool_calls[] + input_safety_score + output_safety_score — mínimo vital para análisis forense y compliance GDPR/HIPAA; texto completo cifrado por usuario con TTL.
- **Inmutabilidad de logs:** S3 Object Lock COMPLIANCE mode (AWS), Azure Immutable Blob Storage, MinIO Object Locking para self-hosted; firma criptográfica HMAC-SHA256 con cadena de hashes para tamper evidence verificable matemáticamente.
- **Trazabilidad de decisiones:** CoT logging para razonamiento intermedio del modelo, citation generation para atribución de fuentes RAG, versioning del system prompt y model card tracking por request.
- **SIEM integration:** formato CEF/OCSF, reglas de correlación cross-system (rate limit + IP nueva = extracción; safety triggers repetidos = jailbreak sistemático), dashboards específicos para IA; Wazuh/Graylog para entornos self-hosted.
- **Incident response:** runbooks específicos por tipo de incidente (jailbreak, RAG poisoning, data leakage), IoCs de IA como umbrales de alerta en el SIEM, opciones de contención escalonadas por impacto, análisis forense con mejoras documentadas.

*"Logging is not just for debugging — it is the historical record of your system's behavior, and without it you are flying blind into the past."* — Kelsey Hightower, Staff Developer Advocate en Google Cloud y uno de los ingenieros más influyentes en cloud-native architecture, sobre el rol fundamental del logging en sistemas de producción: no es un accesorio para cuando algo falla, sino el registro continuo que permite saber qué está pasando y qué pasó.
