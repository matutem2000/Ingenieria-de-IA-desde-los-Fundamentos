# Módulo 9 – Capítulo 10 – Sección 03

## Defense in depth: capas de control a nivel de prompt, API, red y datos

Si hubiera un solo control de seguridad que funcionara con perfecta efectividad contra todos los ataques conocidos y futuros a sistemas de IA, el diseño de seguridad sería simple: implementar ese control y el trabajo estaría hecho. La realidad es la contraria: cada control tiene sus límites de efectividad. LlamaGuard clasifica con alta precisión pero tiene falsos negativos ante perturbaciones adversariales bien diseñadas. Las instrucciones de refuerzo en el system prompt elevan el costo del jailbreak pero no eliminan su posibilidad. El rate limiting contiene los ataques de extracción masiva pero no los distribuidos con timing cuidadoso. Ante esta realidad, la arquitectura correcta no busca el control perfecto sino la combinación de múltiples controles independientes donde el fallo de cualquiera de ellos no compromete el sistema completo. Este es el principio de defense in depth: cada capa reduce de forma independiente la probabilidad de un ataque exitoso de extremo a extremo.

Defense in depth en sistemas de IA se implementa en cuatro capas que operan en niveles de abstracción diferentes y tienen superficies de ataque distintas. Esta independencia es la condición que hace que la arquitectura sea robusta: si el clasificador de output y el sistema de logging usaran la misma API key, un atacante que compromete esa key deshabilita dos controles simultáneamente; si comparten dependencias de red, un ataque de disponibilidad a esa red deshabilita ambas capas a la vez. Las cuatro capas deben diseñarse para tener diferentes superficies de ataque, diferentes dependencias, y diferentes mecanismos de fallo para que sean genuinamente independientes.

La primera capa opera a nivel del prompt: el system prompt con instrucciones de seguridad explícitas, los separadores estructurales que distinguen el contexto del sistema, los documentos recuperados por RAG y el input del usuario, y las instrucciones de refuerzo que instruyen al modelo a no seguir instrucciones encontradas en documentos externos. Esta capa es la más cercana al comportamiento del modelo y actúa directamente sobre su interpretación del contexto. Es también la más vulnerable a un adversario sofisticado, razón por la cual nunca debe ser la única capa.

La segunda capa opera a nivel de la API: input validation con LlamaGuard y Prompt Guard antes de que el input llegue al modelo, output validation con LlamaGuard y Presidio después del output del modelo y antes de que llegue al usuario, rate limiting multidimensional, autenticación con tokens JWT granulares, y logging de cada request con safety scores. Esta capa actúa como el sistema de verificación activa del comportamiento del sistema: independientemente de lo que el modelo decida hacer, la API valida que lo que entra y sale cumple las políticas del sistema.

La tercera capa opera a nivel de red: WAF tanto en la capa HTTP convencional (AWS WAF, Cloudflare) como en la capa semántica especializada para IA (Lakera Guard, Prompt Security), TLS 1.3 con verificación de certificados en todos los saltos del pipeline, segmentación de red que aísla el serving layer del LLM de otros componentes del sistema (el servidor vLLM no debe tener conectividad directa a la base de datos de usuarios), y network egress filtering para agentes con acceso web que previene conexiones a IPs privadas y dominios no autorizados.

La cuarta capa opera a nivel de datos: cifrado AES-256 del vectorstore y logs de inferencia con claves KMS rotadas, controles de acceso RBAC a los índices vectoriales donde un usuario solo puede recuperar documentos de su tenant, inmutabilidad de logs con S3 Object Lock o firma criptográfica HMAC-SHA256, y auditoría de acceso a datos sensibles. Esta capa garantiza que incluso si un atacante logra eludir las tres capas anteriores, los datos que accede están protegidos por controles independientes.

## Aspectos técnicos

- **Capa 1 - Prompt:** system prompt con instrucciones explícitas de seguridad y tags estructurales (`<system>`, `<retrieved_context>`, `<user_message>`), instrucciones de no revelar el system prompt, instrucciones de no seguir instrucciones en documentos recuperados; primera barrera de comportamiento del modelo.
- **Capa 2 - API:** LlamaGuard/Prompt Guard en input, LlamaGuard/Presidio en output, rate limiting multidimensional en Redis, autenticación JWT con claims granulares, logging de safety scores por request; verificación activa independiente del comportamiento del modelo.
- **Capa 3 - Red:** AWS WAF + Lakera Guard en paralelo, TLS 1.3 con certificate pinning, segmentación de red entre serving layer y otros componentes, network egress filtering con allowlist de dominios para agentes; protección perimetral y semántica complementarias.
- **Capa 4 - Datos:** AES-256 para vectorstore y logs con claves KMS, RBAC en índices vectoriales por tenant, S3 Object Lock COMPLIANCE para logs inmutables, auditoría de acceso a PHI y PII; protección que opera incluso si las capas anteriores son eludidas.
- **Testing de independencia:** en el red teaming, incluir escenarios donde una capa está deshabilitada y verificar que las capas restantes contienen el daño; la interdependencia entre capas (una asumiendo que la anterior ya validó) es una fuente de vulnerabilidades sistémicas.

> **Nota del Arquitecto:** Un error frecuente en la implementación de defense in depth es crear capas que son conceptualmente independientes pero técnicamente dependientes: el clasificador de input y el clasificador de output usan el mismo modelo, por lo que un adversario que aprende a evadir uno ha aprendido a evadir el otro. La independencia real requiere diversidad técnica: clasificadores con arquitecturas diferentes, frameworks de validación distintos, mecanismos de detección complementarios. La diversidad tiene un costo de mantenimiento, pero produce la independencia de fallo que el principio requiere.

Un atacante que logra eludir la capa de prompt de un sistema con defense in depth correctamente implementada aún debe eludir el clasificador de output (segunda capa), el WAF semántico (tercera capa), y el control de acceso a datos (cuarta capa) para lograr un impacto significativo. Cada capa reduce independientemente la probabilidad de un ataque de extremo a extremo, y la probabilidad combinada de eludir todas las capas es el producto de las probabilidades individuales — un número significativamente más pequeño que cualquiera por separado.
