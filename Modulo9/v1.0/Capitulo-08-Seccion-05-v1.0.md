# Módulo 9 – Capítulo 08 – Sección 05

## Incident response para sistemas de IA: detección, contención y análisis forense

El incident response (IR) para sistemas de IA comparte el framework general del NIST SP 800-61 —Preparación → Detección y Análisis → Contención, Erradicación y Recuperación → Post-incident— pero sus procedimientos específicos son sustancialmente diferentes de los del IR de aplicaciones web o sistemas de red. Un "incidente" en un sistema de IA tiene características únicas que lo hacen más difícil de detectar y de contener: puede ser difícil de distinguir de comportamiento normal (un modelo comprometido por data poisoning se comporta normalmente el 99.9% del tiempo), puede tener impacto difuso sobre múltiples usuarios sin que ningún usuario individual lo reporte (un documento malicioso en el vectorstore afecta a todos los usuarios que hacen queries relacionadas), y la "contención" puede requerir decisiones de negocio complejas que involucran la disponibilidad del servicio (¿desactivar el sistema de IA en producción mientras se investiga?).

La fase de preparación pre-incidente es la más crítica y la más frecuentemente subestimada. Cuando un incidente ocurre, el equipo debe poder actuar en minutos, no en horas que se pierden buscando documentación o pidiendo accesos. Los runbooks específicos para los incidentes más probables deben estar documentados, revisados, y probados (mediante simulacros anuales) antes de que el sistema entre en producción. Los runbooks mínimos necesarios para un sistema de IA son: jailbreak activo en producción (usuarios están recibiendo outputs problemáticos del modelo), RAG poisoning detectado (hay evidencia de un documento malicioso en el vectorstore), data leakage (el modelo está revelando datos que no debería), prompt leaking activo (el system prompt está siendo extraído en las respuestas), y model extraction sospechada (patrones de queries sugieren que alguien está replicando el comportamiento del modelo sistemáticamente).

Los indicadores de compromiso (IoC) específicos de sistemas de IA son el mecanismo que permite la detección proactiva antes de que el impacto sea visible para los usuarios. Un spike en la tasa de safety filter triggers que supera el doble de la línea de base histórica debe triggear alerta. Un aumento en requests con características de model extraction —alta diversidad semántica, cobertura sistemática de categorías de temas— debe triggear alerta. Outputs que contienen el texto del system prompt deben triggear alerta inmediata. Tool calls a endpoints externos no en la allowlist deben triggear alerta y bloqueo. Queries con patrones de membership inference (textos muy similares a secuencias conocidas del training data del modelo) deben triggear revisión manual. Estos umbrales deben estar configurados en el SIEM con reglas de correlación activas, no en un documento de seguridad que nadie consulta.

La contención de un sistema de IA comprometido tiene opciones de escalada que permiten calibrar la respuesta al nivel de confianza en el diagnóstico y al impacto del servicio. El nivel más conservador es activar el modo restrictivo del output filter —subir el umbral de bloqueo del clasificador para que más outputs sean bloqueados. El siguiente nivel es deshabilitar herramientas específicas del agente que se cree que fueron el vector de ataque. El siguiente es ejecutar rollback al checkpoint del modelo anterior si hay evidencia de data poisoning. El siguiente es failover a un sistema fallback más simple (un sistema de respuestas predefinidas o un modelo más pequeño y conservador). El nivel más extremo es la desactivación completa con mensaje de mantenimiento mientras se investiga. Cada opción tiene un trade-off explícito entre seguridad y disponibilidad que debe decidirse en el contexto del incidente, no improvisarse en el momento.

## Aspectos técnicos

- **Runbooks específicos para incidentes de IA:** jailbreak activo, RAG poisoning detectado, data leakage, prompt leaking, model extraction sospechada; cada runbook con pasos de detección, contención, erradicación, recuperación, y notificación a reguladores si aplica.
- **IoCs de sistemas de IA:** spike en safety filter trigger rate (>2x baseline), patterns de model extraction (alta diversidad semántica), outputs que contienen el system prompt, tool calls a endpoints no autorizados, queries con patterns de membership inference.
- **Opciones de contención escaladas:** modo restrictivo del output filter → deshabilitar herramientas específicas → rollback al modelo anterior → failover a sistema fallback simple → desactivación completa; cada nivel con su trade-off explícito de seguridad vs. disponibilidad.
- **Análisis forense post-incidente:** reconstrucción completa de la secuencia del ataque usando el audit trail (model_id, user_id, retrieved_document_ids, tool_calls, safety_scores); identificación del vector de entrada, técnica utilizada, controles que fallaron; mejoras concretas documentadas para el sistema.
- **Post-incident activities:** notificación a DPA bajo GDPR Art. 33 (72h si hay data breach de usuarios europeos), notificación a usuarios afectados si aplica Art. 34, actualización de runbooks con lecciones aprendidas, y actualización del threat model con las nuevas técnicas de ataque observadas.

El incident response para sistemas de IA debe prepararse antes de que ocurra el incidente: los runbooks, los umbrales de alerta en el SIEM, los procedimientos de contención escalonados, y los contactos de escalation deben estar documentados, probados, y actualizados antes de que el sistema entre en producción.
