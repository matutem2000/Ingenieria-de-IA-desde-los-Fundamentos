# Módulo 9 – Capítulo 08 – Sección 04

## SIEM integration: incorporar eventos de IA a los sistemas de monitoreo de seguridad

Los logs de seguridad de un sistema de IA, analizados en aislamiento, revelan patrones de seguridad que son visibles solo en el contexto de ese sistema: un usuario que hace múltiples requests con características de jailbreak, un patrón de queries con alta diversidad semántica que sugiere model extraction, o una secuencia de tool calls que podría indicar un agent injection exitoso. Pero muchos ataques a sistemas de IA no son ataques aislados: son parte de campañas más amplias que incluyen actividad maliciosa en otros sistemas de la organización. Un intento de model extraction puede correlacionarse con un acceso sospechoso a la cuenta de AWS desde una IP nueva. Un jailbreak exitoso puede correlacionarse con un acceso desde una IP de una red Tor. La integración con el SIEM corporativo —Splunk, Microsoft Sentinel, Elastic SIEM, IBM QRadar, o Wazuh/Graylog para entornos self-hosted— es el mecanismo que permite estas correlaciones cross-system.

La integración típica usa formatos estándar de intercambio de eventos de seguridad. CEF (Common Event Format) es el formato más adoptado en SIEMs maduros y proporciona una estructura de campos predefinida con extensiones para campos personalizados. OCSF (Open Cybersecurity Schema Framework), adoptado por AWS, Splunk, IBM, y otros en 2022, es el estándar emergente con mayor capacidad de extensión para casos de uso específicos como IA. Para sistemas de IA, los campos más críticos del evento SIEM son: el tipo de evento (PromptInjectionAttempt, JailbreakAttempt, RateLimitExceeded, SafetyFilterTriggered, ModelExtractionSuspected, ToolCallDenied), la severidad (0-10), el user_id, la IP del cliente, el model_id, y los campos de extensión específicos de IA (input_safety_score, retrieved_document_ids, tool_calls).

Las reglas de correlación en el SIEM son donde el valor operacional de la integración se materializa. La correlación requiere pensar en términos de escenarios de ataque completos, no en términos de eventos individuales: un rate limit excedido más una IP nunca vista previamente es una señal de possible model extraction; múltiples safety filter triggers del mismo user_id en 24 horas es una señal de jailbreak sistemático; una prompt injection detectada más una tool call a un endpoint externo no en la allowlist es una señal de posible exfiltración via agente. Cada una de estas correlaciones debe convertirse en una regla en el SIEM con su umbral de activación y su acción (alerta, bloqueo temporal, escalation a revisión manual).

Los entornos self-hosted o on-premises tienen alternativas completas a los SIEMs cloud: Wazuh (basado en OSSEC) es una plataforma de SIEM/XDR open-source con reglas de correlación configurables y capacidad de ingestion de logs en formato CEF; Graylog es una alternativa open-source orientada a log management con capacidades de alerting. Ambas pueden instalarse on-premises y configurarse para recibir los eventos de seguridad del sistema de IA, aplicar reglas de correlación, y enviar alertas al equipo de seguridad. La diferencia con SIEMs cloud es la responsabilidad operacional: el equipo gestiona la infraestructura del SIEM, las actualizaciones, y el escalado.

## Aspectos técnicos

- **Formato de eventos para SIEM:** CEF (Common Event Format) para compatibilidad con SIEMs maduros (Splunk, QRadar), OCSF (Open Cybersecurity Schema Framework) como estándar emergente adoptado por AWS, Splunk, y otros; campos de extensión específicos de IA (input_safety_score, retrieved_document_ids, tool_calls).
- **Reglas de correlación para sistemas de IA:** rate limit excedido + IP nueva = posible model extraction; safety filter triggers repetidos del mismo user_id = jailbreak sistemático; prompt injection detectada + tool call a endpoint externo no autorizado = posible exfiltración via agente.
- **Pipeline de integración:** logs del sistema de IA (JSON en CloudWatch/Azure Monitor/stdout) → transformación con Fluentd/Logstash a formato CEF/OCSF → ingestion al SIEM con latencia <60 segundos para alertas en tiempo casi real.
- **Alternativas on-premises:** Wazuh (OSSEC-based, open-source) con capacidades SIEM/XDR + reglas de correlación configurables; Graylog para log management + alerting; ambos reciben eventos en CEF y soportan correlación cross-source.
- **Dashboards de seguridad específicos para IA:** volumen de requests por tiempo y tenant, distribución de safety filter triggers por categoría, top usuarios por intentos de jailbreak, latencia P99 de clasificadores de seguridad, y rate limits excedidos por IP y tenant.

> **Nota del Arquitecto:** El valor principal de la integración SIEM no es el alerting de eventos individuales —eso puede hacerse con CloudWatch Alarms o Azure Monitor Rules sin un SIEM completo— sino la correlación cross-system. El mismo atacante que intenta model extraction en el sistema de IA probablemente también probó acceder a otros sistemas de la organización. Sin integración SIEM, esos eventos son puntos de datos aislados en sistemas diferentes que nadie correlaciona. Con integración SIEM, son parte de un patrón de ataque identificable.

La integración con SIEM convierte los eventos de seguridad del sistema de IA en parte del programa de seguridad corporativo, permitiendo que las amenazas específicas de IA sean detectadas y respondidas con las mismas herramientas y procesos que otras amenazas, eliminando el punto ciego que un sistema de IA sin integración SIEM crea en el landscape de seguridad de la organización.
