# Módulo 9 – Capítulo 07 – Sección 04

## Output filtering: detección y redacción de contenido sensible en las respuestas

El output filtering es la capa de defensa que verifica las respuestas del modelo antes de entregarlas al usuario final. Su existencia como capa independiente del input filtering no es redundante: es la consecuencia lógica de aceptar que ningún control de input es perfecto y que el modelo puede generar outputs problemáticos incluso cuando el input parecía inofensivo. Los jailbreaks que el input filter no detectó, las alucinaciones que generan información médica incorrecta pero coherente, la PII memorada del corpus de pretraining que aparece en la respuesta sin que el usuario la haya mencionado, el texto del system prompt revelado mediante un ataque de prompt leaking exitoso —todos estos casos producen outputs problemáticos que llegan al usuario si no hay una segunda línea de defensa en el output.

La arquitectura de output filtering tiene múltiples capas que abordan diferentes tipos de problemas. LlamaGuard-3 ejecutado sobre el output del modelo clasifica la respuesta contra las mismas 13 categorías de contenido dañino que el input filter, proporcionando una segunda oportunidad de detección para jailbreaks que el modelo ejecutó a pesar del input filter. La detección de PII en el output —ejecutando Presidio sobre la respuesta antes de entregarla— detecta datos personales que el modelo pudo haber incluido provenientes de memorización del pretraining, del contexto del usuario incluido de maneras no esperadas, o de documentos RAG que contenían PII no redactada. La detección del texto del system prompt en la respuesta —mediante búsqueda de n-gramas del system prompt en el output— detecta intentos de prompt leaking exitosos donde el modelo incluyó el contenido del system prompt en su respuesta.

La validación de policies específicas de la aplicación es la dimensión del output filtering más subestimada. Las políticas de contenido del proveedor del modelo —OpenAI Content Policy, Anthropic Usage Policy— son el mínimo regulatorio del proveedor, no el máximo de la aplicación. Una aplicación de atención al cliente de un banco tiene restricciones adicionales que el LLM base no puede conocer: no generar consejo de inversión específico, no mencionar productos de la competencia, no revelar información que no está en los documentos autorizados del banco, no hacer promesas sobre plazos o condiciones que el banco no puede garantizar. Estas políticas específicas de la aplicación deben verificarse en el output antes de entregarlo al usuario, independientemente de si el proveedor del modelo las implementa o no.

El streaming es una consideración adicional en el diseño del output filter. Cuando el sistema usa streaming —el output llega token a token, mejorando la experiencia percibida del usuario— el output filtering debe operar en modo buffered (acumular el output completo antes de entregarlo) para poder clasificarlo como un todo, o en modo chunk-based (evaluar chunks de tokens acumulados), con un trade-off explícito entre latencia percibida y cobertura de detección. En modo buffered, el usuario espera hasta que el output completo ha sido validado antes de ver la primera palabra; en modo chunk-based, el usuario ve chunks validados con latencia más baja pero con menor cobertura ante ataques distribuidos en el output.

## Aspectos técnicos

- **LlamaGuard sobre el output:** ejecutar LlamaGuard-3 sobre la respuesta del modelo antes de entregarla al usuario; si el output clasifica como violación de alguna de las 13 categorías, retornar un mensaje de error estándar sin revelar qué categoría fue violada.
- **Detección de PII en outputs con Presidio:** escanear el output del modelo con Microsoft Presidio para detectar y redactar PII que el modelo pudo incluir de memorización del pretraining, del contexto del usuario, o de documentos RAG no correctamente anonimizados.
- **Detección del system prompt en el output:** búsqueda de n-gramas del system prompt en el output para detectar prompt leaking exitoso; alternativamente, comparar fragmentos del output contra el hash del system prompt para detectar similitudes significativas.
- **Content policy enforcement específico de la aplicación:** verificación de restricciones de contenido que van más allá de las policies del proveedor del modelo: no consejo de inversión, no promesas de plazos, no mención de competidores, no información no autorizada por la política editorial del sistema.
- **Streaming y output filtering:** modo buffered (menor latencia para el output filter, mayor latencia percibida para el usuario) vs. modo chunk-based (menor latencia percibida, menor cobertura de detección); la elección debe documentarse explícitamente con su justificación.

> **Nota del Arquitecto:** El output filtering añade latencia — típicamente 50-200ms para LlamaGuard, más para Presidio sobre responses largas. He visto equipos eliminarlo en producción porque "ralentiza la experiencia del usuario". La decisión correcta no es eliminarlo sino optimizarlo: LlamaGuard puede ejecutarse en paralelo con el streaming del output para que el output se presente al usuario solo si la evaluación en paralelo no detecta violaciones; Presidio puede ejecutarse solo sobre outputs que superen un threshold de longitud. El output filter no puede ser opcional porque es la última línea de defensa.

El output filtering es la última línea de defensa antes de que el contenido del modelo llegue al usuario: siempre debe implementarse, independientemente de cuán robusto sea el input filtering, porque no existe sistema de input filtering con cero falsos negativos.
