# Módulo 9 – Capítulo 06 – Sección 02

## Datos en tránsito y en reposo: cifrado de prompts, respuestas e índices vectoriales

El cifrado de datos en tránsito y en reposo en sistemas de IA sigue los mismos principios que en cualquier sistema de procesamiento de datos sensibles, pero su aplicación tiene consideraciones específicas para los componentes que son únicos de la arquitectura de IA. Los prompts que viajan entre la aplicación y la API del LLM, los vectores de embedding almacenados en el vectorstore, los artefactos de modelo fine-tuned que contienen representaciones de datos de entrenamiento, y los logs de inferencia que registran inputs y outputs completos son todos componentes con características particulares que determinan qué nivel y qué tipo de cifrado se requiere.

Para datos en tránsito, TLS 1.3 es el estándar mandatorio para todas las conexiones a APIs de LLMs —OpenAI, Anthropic, Azure OpenAI, Vertex AI— y para cualquier componente interno del pipeline que transmita datos de usuarios. En arquitecturas multi-tier donde el gateway de la aplicación reenvía requests al proveedor del modelo, cada salto de red debe usar TLS con certificados válidos; la terminación de TLS en el gateway no debe resultar en re-transmisión en plaintext en la red interna entre el gateway y el servicio de inferencia. Para endpoints self-hosted de modelos (vLLM, TGI), TLS debe configurarse explícitamente porque no está habilitado por defecto en la mayoría de las implementaciones.

Los índices vectoriales merecen mención especial porque frecuentemente no se tratan con el nivel de protección que merecen. Los vectores de embedding no son datos "anonimizados" de ninguna manera: las representaciones vectoriales de texto preservan suficiente información semántica sobre el texto original para que técnicas de inversión de embeddings puedan recuperar aproximaciones del texto fuente, especialmente cuando el atacante conoce el modelo de embedding utilizado. Pinecone cifra datos en reposo con AES-256 por defecto; Weaviate y pgvector requieren configuración explícita del cifrado a nivel de storage y no lo habilitan automáticamente. En implementaciones self-hosted de vectorstores, el cifrado debe configurarse a nivel del sistema de archivos si el vectorstore no lo implementa nativamente.

Los logs de inferencia son el elemento más frecuentemente subestimado en términos de sensibilidad de datos. Un log de inferencia que registra el input completo del usuario y el output del modelo durante su historial completo de uso del sistema es un activo de datos extremadamente sensible: contiene todo lo que el usuario escribió en la aplicación, incluyendo datos personales, consultas de carácter privado, y potencialmente información confidencial de negocio que el usuario compartió para obtener asistencia. El tratamiento correcto de los logs de inferencia es el mismo que el de una base de datos de conversaciones privadas de usuarios: cifrado AES-256 en reposo con claves KMS, retención limitada por TTL definido, acceso auditado y necesidad justificada, y mecanismos de borrado selectivo por usuario para compliance con GDPR.

## Aspectos técnicos

- **TLS 1.3 mandatorio en tránsito:** para todas las APIs de LLMs y para cada salto interno del pipeline; en endpoints self-hosted (vLLM, TGI) configurar TLS explícitamente ya que no está habilitado por defecto; sin transmisión en plaintext en la red interna entre gateway y servicio de inferencia.
- **Cifrado del vectorstore en reposo:** Pinecone AES-256 por defecto; Weaviate y pgvector requieren configuración explícita; los vectores de embedding contienen información semánticamente reversible sobre el texto original y deben protegerse equivalentemente a los datos fuente.
- **Cifrado de modelos fine-tuned en reposo:** artefactos de modelo en S3/GCS/Azure Blob con SSE-KMS usando claves gestionadas por el cliente (no las del proveedor de storage), que permiten revocar el acceso al modelo sin depender del proveedor.
- **Logs de inferencia como datos sensibles de primera clase:** cifrado AES-256 en reposo con claves KMS, retención con TTL definido basado en necesidad justificada, acceso auditado, y mecanismo de borrado selectivo por user_id para compliance con GDPR Art. 17.
- **Gestión de claves y rotación:** claves de cifrado en KMS (AWS KMS, Azure Key Vault, GCP Cloud KMS o HashiCorp Vault para self-hosted), nunca en variables de entorno ni código; rotación automática anual con proceso de re-cifrado de datos existentes.

La visión correcta de seguridad de datos en sistemas de IA trata al sistema completo —modelo, vectorstore, logs de inferencia, pipeline de inferencia— como un sistema de procesamiento de datos sensibles equivalente a cualquier base de datos de producción con datos personales, aplicando el mismo rigor de cifrado, acceso y retención a cada componente.
