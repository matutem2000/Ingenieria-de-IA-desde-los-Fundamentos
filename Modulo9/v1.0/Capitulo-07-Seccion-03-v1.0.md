# Módulo 9 – Capítulo 07 – Sección 03

## Input validation: sanitización y límites de longitud antes de llegar al modelo

Con la identidad verificada y los límites de uso aplicados, la request autenticada llega al tercer control: la validación del contenido que va a enviarse al modelo. La validación de inputs en sistemas de IA tiene dos objetivos distintos que frecuentemente se confunden. El objetivo de seguridad busca detectar intentos de prompt injection, jailbreaking, o contenido diseñado para comprometer el sistema; el objetivo de calidad de servicio busca asegurar que los inputs están en el formato esperado, dentro de los límites operacionales, y son procesables por el modelo de manera eficiente. Confundir ambos objetivos lleva a implementaciones que mezclan controles con diferentes mecanismos y diferentes trade-offs de sensibilidad y performance.

La validación semántica del input —detectar intent malicioso en texto— no puede hacerse efectivamente mediante pattern matching basado en listas de palabras prohibidas o expresiones regulares. Esta estrategia, intuitiva pero fundamentalmente inadecuada, es eludible trivialmente: cualquier palabra prohibida puede reformularse mediante sinónimos, codificarse en Base64, traducirse a otro idioma, o fragmentarse en múltiples turns de conversación. Los clasificadores especializados son la herramienta correcta para la validación semántica. LlamaGuard-3, desarrollado por Meta y disponible en Hugging Face (llama-guard-3 en modelos de 8B parámetros), es un modelo fine-tuned específicamente para clasificar inputs y outputs contra 13 categorías de contenido dañino, incluyendo violencia, contenido sexual, actividades ilegales, y ciberseguridad ofensiva. Prompt Guard, también de Meta (2024), es un clasificador BERT-based diseñado específicamente para detectar intentos de prompt injection directa e indirecta, con latencia inferior a 10 milisegundos que lo hace viable en el hot path de cada request. Azure Content Safety API proporciona una alternativa gestionada para equipos que prefieren no operar infraestructura de clasificación propia.

La validación estructural complementa la semántica con controles sobre el formato del input. El límite de longitud en tokens —no en caracteres ni en bytes— es crítico porque el costo computacional del modelo escala con los tokens, y un input que es pequeño en caracteres puede ser extremadamente largo en tokens para ciertos contenidos. El conteo de tokens debe hacerse con el tokenizador específico del modelo target: tiktoken para modelos OpenAI, el tokenizador de sentencepiece de Anthropic para Claude, el tokenizador de LLaMA para modelos Llama-3. El límite de longitud debe ser menor al context window del modelo para dejar espacio al system prompt, los documentos RAG, y la respuesta esperada; un input que consume todo el context window deja sin espacio para el system prompt y puede causar comportamientos inesperados.

La validación de schema es relevante cuando la aplicación acepta inputs estructurados: un formulario con campos específicos, un JSON con campos definidos, o una query en un formato controlado. En estos casos, la validación del schema del input antes de incluirlo en el prompt previene que el usuario añada campos no esperados que podrían alterar la estructura del prompt o inyectar instrucciones adicionales en el formato esperado.

## Aspectos técnicos

- **Límites de longitud en tokens:** tokenizar el input con el tokenizador específico del modelo target antes de enviarlo; rechazar inputs que superen el límite definido (conservativamente menor al context window para dejar espacio a system prompt y respuesta); tiktoken para OpenAI, sentencepiece para Anthropic, llama-tokenizer para modelos Llama.
- **LlamaGuard-3 (Meta, open-source):** clasificador de 8B parámetros fine-tuned para 13 categorías de contenido dañino; latencia de 50-200ms dependiendo del hardware; disponible en Hugging Face como modelo open-source o via Fireworks AI como API gestionada.
- **Prompt Guard (Meta, 2024):** clasificador BERT-based para detección específica de prompt injection directa e indirecta; latencia <10ms apto para el hot path de cada request; distingue entre prompt injection directa (del usuario) e indirecta (en datos recuperados).
- **Validación de schema:** para inputs estructurados (JSON, formularios), validar el schema antes de incluir en el prompt; previene inyección de campos adicionales o modificación de la estructura esperada que podría alterar la interpretación del modelo.
- **Sanitización de documentos para ingestión RAG:** los documentos que ingresan al pipeline RAG deben pasar por las mismas validaciones que el input del usuario —un documento malicioso en el corpus es tan peligroso como un prompt malicioso en el input.

La validación de input no puede basarse únicamente en reglas de filtering de texto —son trivialmente eludibles— sino que debe combinar clasificadores semánticos especializados (LlamaGuard, Prompt Guard) con controles estructurales (límites de tokens, validación de schema) que juntos forman la primera línea de defensa del contenido que llega al modelo.
