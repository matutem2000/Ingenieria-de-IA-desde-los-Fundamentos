# Módulo 9 – Capítulo 07 – Sección 02

## Rate limiting y throttling: protección contra abuso y ataques de extracción masiva

Una vez que la identidad del cliente está verificada y sus permisos establecidos, el siguiente control en el ciclo de vida de la request es el rate limiting: cuánto puede acceder este cliente autenticado. En el contexto de sistemas de IA, el rate limiting tiene objetivos de seguridad que van más allá del rate limiting de APIs convencionales. Además de proteger contra ataques de DDoS y abuso de recursos computacionales, debe proteger contra model extraction —queries sistemáticas diseñadas para replicar el comportamiento del modelo—, contra ataques de amplificación donde el costo computacional de generar la respuesta supera significativamente el costo de la request (un prompt de 100 tokens puede generar una respuesta de 4,000 tokens con un uso de GPU desproporcionado), y contra ataques de context flooding que consumen toda la ventana de contexto disponible con inputs diseñados para agotar los recursos del sistema.

La granularidad del rate limiting es lo que determina su efectividad como control de seguridad. Un rate limit global por API key —por ejemplo, 1,000 requests por minuto— es insuficiente si diferentes endpoints tienen diferentes costos de seguridad y de recursos. El endpoint de completions tiene un perfil de riesgo diferente al endpoint de embeddings, que tiene un perfil diferente al de fine-tuning, que tiene un perfil diferente al de los endpoints de administración de modelos. El rate limiting correcto aplica límites independientes a cada categoría de endpoint, con valores calibrados al costo real de seguridad: el endpoint de fine-tuning, que puede iniciar un proceso de entrenamiento con costos de horas de GPU y acceso a todos los datos de entrenamiento del tenant, debe tener límites mucho más restrictivos que el endpoint de completions que procesa una sola request.

Las dimensiones del rate limiting para sistemas de IA deben cubrir al menos tres variables: requests por minuto (RPM), que protege contra ataques de alta frecuencia y DoS; tokens por minuto (TPM), que protege contra amplificación computacional y model extraction mediante queries largas; y ventanas temporales más largas (tokens por hora, tokens por día) para detectar ataques distribuidos de extracción que evaden los límites de corto plazo utilizando patrones de baja frecuencia sostenida en el tiempo. La detección de model extraction requiere además análisis de la distribución de topics de los requests: un cliente que hace requests con alta diversidad semántica —cubriendo sistemáticamente el espacio de comportamientos del modelo en lugar de un caso de uso específico— exhibe el patrón característico de extracción, que debe triggear alertas incluso si cada request individual está dentro de los límites de RPM y TPM.

Para implementación técnica, Redis con Sliding Window Counter es el estándar de producción: una sorted set (ZSET) de Redis donde cada elemento es el timestamp de una request, permite contar requests en cualquier ventana temporal con una query ZRANGEBYSCORE sin la imprecisión del Fixed Window Counter que puede ser explotada ubicando requests en los bordes de las ventanas. Para TPM, la misma estructura acumula el count de tokens de cada request en lugar de contar requests unitariamente. La latencia de Redis para estas operaciones es <1ms en redes de datacenter, lo que la hace adecuada para el hot path de cada request.

## Aspectos técnicos

- **Rate limiting multidimensional:** RPM (requests por minuto), TPM (tokens por minuto), y ventanas largas (tokens por hora/día) para detectar ataques distribuidos de baja frecuencia sostenida que evaden límites de corto plazo.
- **Límites específicos por endpoint:** endpoints de completions, embeddings, fine-tuning y administración de modelos con límites independientes calibrados al costo real de seguridad y recursos de cada operación; el endpoint de fine-tuning requiere límites mucho más restrictivos.
- **Algoritmos de implementación:** Sliding Window Counter con Redis ZSET para precisión sin vulnerabilidad a bordes de ventana fija; Token Bucket para casos de uso donde se permiten bursts hasta el tamaño del bucket; Leaky Bucket para traffic shaping uniforme.
- **Detección de model extraction en el rate limiter:** análisis de distribución de topics de los últimos N requests de cada API key usando embeddings; alta diversidad semántica que cubre sistemáticamente el espacio de comportamientos del modelo es señal de extracción.
- **Respuesta a rate limit excedido:** HTTP 429 con headers Retry-After y X-RateLimit-Remaining-Tokens como estándar; para patrones de extracción detectados, escalation a revisión manual y suspensión preventiva de la key.

> **Nota del Arquitecto:** La trampa del rate limiting en IA es copiarlo directamente de los parámetros del proveedor: "OpenAI permite X requests por minuto en mi tier, así que configuro lo mismo". Los límites del proveedor protegen al proveedor de sus costos; los tuyos deben proteger tu sistema de sus riesgos específicos. Si un cliente de un rol "basic" puede hacer 1,000 requests por minuto al endpoint de fine-tuning, puede iniciar un proceso de entrenamiento masivo que consume tu presupuesto de GPU y potencialmente contamina el modelo con data poisoning en escala.

El rate limiting debe diseñarse como control de seguridad específico para los ataques de IA —model extraction, amplificación computacional, context flooding— no simplemente como protección de recursos computacionales, que es el único objetivo del rate limiting en APIs convencionales.
