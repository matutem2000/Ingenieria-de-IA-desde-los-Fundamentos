# Módulo 9 – Capítulo 03 – Sección 05

## Supply chain security para ML: verificar lo que se descarga y se instala

Cuando en el Módulo 8 aprendimos a descargar modelos de Hugging Face Hub, instalar dependencias con `pip install transformers torch accelerate`, y construir pipelines de fine-tuning sobre modelos base públicos, estábamos construyendo la funcionalidad del sistema. Lo que no discutimos en ese contexto —y que este capítulo aborda ahora— es que cada uno de esos pasos implica confiar en el contenido de sistemas externos: el repositorio de modelos de Hugging Face, el índice de paquetes de PyPI, los datasets públicos de Hugging Face Datasets. Esta cadena de dependencias es la supply chain del sistema de IA, y es una superficie de ataque crítica que la mayoría de los equipos no gestiona con el mismo rigor que el código que ellos mismos escriben.

El riesgo de supply chain en ML tiene componentes distintos al supply chain security del software tradicional, aunque comparte su lógica fundamental. El más documentado es la explotación del formato `pickle` —el mecanismo de serialización estándar de Python— para distribuir modelos con código malicioso embebido. Un archivo `.bin` o `.pt` de PyTorch descargado de Hugging Face Hub es un archivo pickle que se deserializa con `torch.load()`, y la deserialización de pickle es equivalente a ejecutar código Python arbitrario: si el archivo fue modificado por un actor malicioso, el simple acto de cargar el modelo ejecuta el payload. Este vector fue demostrado múltiples veces en modelos reales alojados en Hugging Face, que periódicamente detecta y elimina modelos maliciosos pero no puede garantizar que todos los modelos en su plataforma son seguros. La solución técnica existe: el formato `safetensors` de Hugging Face almacena solo los tensores de los pesos sin capacidad de ejecutar código arbitrario durante la carga, y debe preferirse sobre `.bin` o `.pt` para todos los modelos descargados de fuentes externas.

El escaneo de integridad de modelos es otra capa de defensa esencial. La herramienta `modelscan` (desarrollada por Protect AI, open-source) analiza archivos de modelos en busca de código malicioso embebido antes de cargarlos. El proceso debería ser: descargar el modelo en un entorno aislado, ejecutar `modelscan` contra el archivo, verificar el hash SHA256 del archivo contra el publicado en la Model Card si está disponible, y solo entonces mover el modelo a un entorno de producción. Esta secuencia de verificación, que añade unos minutos al proceso de descarga, es la diferencia entre un pipeline de ML que confía ciegamente en el contenido descargado y uno que lo verifica antes de ejecutarlo.

Las dependencias de Python para ML —`torch`, `transformers`, `accelerate`, `datasets`, `peft`, `bitsandbytes`— también son parte de la supply chain y deben gestionarse con herramientas de análisis de vulnerabilidades. `pip-audit` analiza el entorno de Python instalado buscando vulnerabilidades conocidas en los paquetes y sus dependencias transitivas. Trivy puede escanear imágenes Docker que contengan el entorno de ML para detectar vulnerabilidades en los paquetes instalados. El uso de un archivo `requirements.txt` o `pyproject.toml` con versiones exactas y hashes verificables (usando `pip download --require-hashes`) proporciona reproducibilidad y garantiza que las versiones instaladas en producción son exactamente las aprobadas por el equipo, no las últimas versiones disponibles que podrían incluir una vulnerabilidad reciente.

Los datasets utilizados para pretraining o fine-tuning son la tercera componente de la supply chain. Un dataset descargado de Hugging Face Datasets, Common Crawl, o un repositorio académico puede contener datos envenenados, sesgos amplificados, o incluso PII de personas que no consintieron que sus datos se usaran para entrenar modelos. El proceso de revisión de datasets antes de usarlos en producción debe incluir: verificación de la fuente y licencia, análisis estadístico de la distribución de datos, detección de PII con Microsoft Presidio o Amazon Comprehend, y revisión de la Model Card del dataset para entender cómo fue recopilado y qué filtros se aplicaron.

## Aspectos técnicos

- **Riesgo pickle en modelos de Hugging Face:** archivos `.bin` y `.pt` se deserializan con `torch.load()`, que ejecuta código arbitrario; un modelo malicioso puede comprometer el host al cargarse. Solución: usar `safetensors` que almacena solo tensores sin capacidad de ejecutar código.
- **modelscan (Protect AI, open-source):** herramienta de escaneo de archivos de modelo que detecta código malicioso embebido en formatos pickle antes de cargar el modelo; debe integrarse en el pipeline de descarga como gate de seguridad obligatorio.
- **Verificación de integridad via hash SHA256:** comparar el hash del archivo descargado con el publicado en la Model Card del repositorio; detecta modificaciones post-publicación aunque el repositorio no haya sido comprometido de manera obvia.
- **pip-audit y Trivy:** `pip-audit` detecta vulnerabilidades conocidas en dependencias de Python del entorno de ML; Trivy escanea imágenes Docker completas incluyendo el sistema operativo y todos los paquetes instalados.
- **SBOM (Software Bill of Materials) para ML:** documentación explícita de todos los componentes del sistema: modelo base con su versión y hash, datasets de entrenamiento con su fuente y versión, dependencias de Python con versiones exactas; permite auditoría y respuesta rápida ante vulnerabilidades descubiertas en cualquier componente.

> **Nota del Arquitecto:** La supply chain de ML tiene un nivel de confianza implícita que sorprende a equipos acostumbrados a entornos más controlados. Descargamos modelos de 10GB de repositorios que cualquiera puede publicar, instalamos decenas de dependencias con `pip install`, y ejecutamos código de notebooks de Jupyter descargados de la web — todo esto en entornos que frecuentemente tienen acceso a credenciales de cloud, conexiones a bases de datos de producción, y sistemas de almacenamiento con datos de usuarios. El modelo correcto es tratarlo con la misma desconfianza que trataríamos código externo en cualquier otro contexto: verificar antes de ejecutar, aislar la ejecución, y auditar periódicamente las dependencias.

La supply chain security para ML es una laguna que muchos equipos no reconocen como riesgo hasta que ocurre un incidente. Los controles descritos en esta sección —safetensors, modelscan, pip-audit, verificación de hashes— son específicos de ML pero operacionalmente simples de implementar como parte del pipeline de descarga y actualización de modelos.
