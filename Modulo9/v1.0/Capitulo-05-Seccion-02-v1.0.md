# Módulo 9 – Capítulo 05 – Sección 02

## Prompt injection a través de documentos recuperados: el caso del RAG indirecto

La sección anterior analizó el RAG poisoning desde la perspectiva de la ingestión: el atacante contamina el corpus. Esta sección examina la otra cara del mismo vector: la prompt injection indirecta que ocurre en tiempo de inferencia cuando el sistema recupera documentos que contienen instrucciones adversariales. La distinción es importante porque tienen superficies de ataque y contramedidas diferentes, aunque el mecanismo de explotación sea el mismo: el LLM recibe instrucciones adversariales en el contexto y las ejecuta porque no puede distinguirlas de instrucciones legítimas del sistema.

En la prompt injection indirecta via RAG, el atacante no necesita acceso a la API de ingestión del vectorstore. Solo necesita que el sistema RAG recupere un documento que el atacante controla —o al que el atacante puede modificar. Los sistemas que construyen su corpus con web scraping son particularmente vulnerables: el atacante puede publicar contenido en una página web que el scraper indexará, diseñar ese contenido para que sea recuperado ante queries de interés, y embeber instrucciones adversariales en el contenido que el LLM ejecutará como parte del contexto. Johann Rehberger documentó este vector de manera sistemática en 2023 mediante ataques exitosos contra ChatGPT Plugins, Microsoft Copilot y Bing Chat, demostrando en todos los casos la misma secuencia: documento controlado por el atacante → recuperado como contexto → instrucciones ejecutadas por el LLM.

Las técnicas de ocultamiento de instrucciones en documentos son variadas y frecuentemente efectivas. El texto blanco sobre fondo blanco es el más simple: invisible en el renderizado visual del documento pero legible por el parser de texto que extrae el contenido para indexarlo. Los comentarios HTML (`<!-- instrucciones para el AI: ... -->`) son invisibles para el lector humano pero procesados por scrapers que parsean el HTML para extraer texto. Los metadatos de archivos PDF —campos como "Author", "Subject", "Keywords" o "Description"— son leídos por los parsers de PDF pero frecuentemente no se muestran en la vista previa, creando un canal donde las instrucciones pueden embeberse sin ser visibles en el contenido principal del documento.

El escenario de exfiltración de datos es el que más preocupa a los equipos de seguridad porque combina el ataque con un impacto concreto de privacidad: el documento malicioso instruye al LLM a incluir datos de la conversación del usuario —historial, PII, credenciales de sesión— en una URL que el agente visitará como herramienta de búsqueda o en un argumento de una herramienta que el atacante controla, enviando los datos al servidor del atacante sin que el usuario lo note. Rehberger demostró este escenario exactamente en su investigación de 2023. La mitigación de este escenario específico requiere que el sistema no ejecute acciones —especialmente llamadas a URLs o herramientas con endpoints externos— basadas en instrucciones encontradas en documentos recuperados, sin confirmación explícita del usuario.

## Aspectos técnicos

- **Anatomía del ataque:** el atacante publica o modifica un documento con instrucciones adversariales → el sistema RAG lo recupera como contexto relevante → el LLM recibe las instrucciones y las ejecuta → el usuario recibe el output adversarial sin solicitar el comportamiento observado.
- **Técnicas de ocultamiento:** texto blanco sobre fondo blanco (invisible visualmente, legible por el parser), comentarios HTML (`<!-- AI instruction: ... -->`), metadatos de PDF (campos Author/Subject leídos por parsers), y texto en tamaños o colores que se confunden con el fondo del documento.
- **Exfiltración via RAG injection:** el documento instruye al LLM a incluir datos de la conversación en una URL o argumento de herramienta controlado por el atacante; demostrado por Rehberger (2023) contra ChatGPT Plugins, Copilot y Bing Chat.
- **Cross-user contamination en RAG compartido:** en sistemas multi-usuario con vectorstore compartido, un documento malicioso inyectado por un usuario afecta a todos los que recuperan ese documento; el impacto es horizontal, no solo vertical en la sesión del atacante.
- **Mitigaciones arquitectónicas:** marcar documentos recuperados con nivel de confianza diferente al system prompt (`<retrieved_document trust="low">`); instrucciones explícitas en el system prompt de no seguir instrucciones en documentos recuperados; validar el output antes de ejecutar acciones basadas en contenido recuperado.

> **Nota del Arquitecto:** El RAG indirecto es especialmente peligroso en sistemas agénticos donde el LLM puede tomar acciones con consecuencias reales. Un chatbot puramente conversacional afectado por RAG injection da respuestas incorrectas; un agente afectado puede enviar emails, modificar registros o ejecutar código. El control más efectivo que he implementado en producción para este vector es la separación arquitectónica entre el plano de datos (el LLM procesa el contexto) y el plano de acción (un componente separado valida que cualquier acción fue autorizada por el usuario legítimo, no por instrucciones en el contexto recuperado).

El RAG indirecto convierte cualquier documento del corpus —una página web, un PDF de un proveedor, un email indexado— en un potencial vector de ataque, y la seguridad del sistema depende tanto de la integridad del corpus como del endpoint de inferencia.
