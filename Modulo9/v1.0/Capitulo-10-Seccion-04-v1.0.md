# Módulo 9 – Capítulo 10 – Sección 04

## Threat modeling continuo: actualizar el modelo de amenazas con cada nueva capacidad

El threat model de un sistema de IA no es un documento que se escribe una vez durante el diseño inicial, se revisa en la primera reunión de seguridad, y luego vive archivado en Confluence hasta que alguien lo menciona en una retrospectiva. Es un artefacto vivo que debe evolucionar en paralelo con las capacidades del sistema, porque las capacidades de un sistema de IA determinan directamente su superficie de ataque: cada nueva capacidad abre nuevas posibilidades de uso y, con ellas, nuevos vectores de ataque que no existían antes. Tratar el threat model como un documento estático es equivalente a desarrollar una aplicación web, hacer el análisis de seguridad inicial, y nunca revisarlo cuando se añaden nuevas rutas, se cambia la base de datos, o se integran APIs externas.

La razón por la que los sistemas de IA hacen especialmente crítica esta actualización continua es la velocidad con la que sus capacidades cambian. En sistemas de software tradicional, añadir una nueva funcionalidad generalmente expande la superficie de ataque de forma acotada y predecible: una nueva ruta de API tiene sus propias validaciones de input y control de acceso. En un sistema de IA, cambiar el modelo base de Claude 3.5 Sonnet a Claude 3.7 puede introducir capacidades de razonamiento extendido (extended thinking) que crean nuevos comportamientos ante ataques multi-turn; añadir visión multimodal introduce el vector de prompt injection a través de imágenes (instrucciones adversariales en imágenes que el modelo lee pero el humano no detecta); añadir memoria persistente entre sesiones crea el riesgo de que datos de una sesión contaminen decisiones en sesiones futuras. Cada uno de estos cambios invalida parte del threat model anterior e introduce nuevas amenazas que deben ser analizadas explícitamente.

El proceso de actualización del threat model se articula en seis pasos que deben ejecutarse cada vez que ocurre un trigger de cambio significativo. Primero, documentar la nueva capacidad con precisión técnica: no "añadimos búsqueda web" sino "el agente ahora puede usar la herramienta `web_search(query)` que hace requests a un proxy egress y devuelve el texto de las páginas, incluyendo metadatos y comentarios HTML". Esta precisión determina qué amenazas son relevantes. Segundo, actualizar el Data Flow Diagram para incluir los nuevos flujos de datos y componentes. Tercero, aplicar STRIDE a cada nuevo flujo y componente. Cuarto, consultar MITRE ATLAS para las TTPs (Tactics, Techniques, and Procedures) relevantes a la nueva capacidad. Quinto, estimar el riesgo de cada nueva amenaza con la combinación de likelihood e impact. Sexto, definir los controles de mitigación para los riesgos que superen el umbral de aceptación, con owner y fecha de implementación.

Mantener el threat model en el repositorio del proyecto como código —en YAML o JSON usando notaciones como PASTA o STRIDE-in-YAML, con herramientas como Threatspec u OWASP Threat Dragon— tiene varias ventajas operacionales sobre el documento de texto tradicional. La historia de cambios en git muestra exactamente cuándo se añadió cada amenaza y con qué motivación; el diff entre versiones permite verificar que cada cambio de capacidad fue acompañado de la actualización correspondiente del threat model; las discrepancias entre la historia de git del código y la historia del threat model revelan cambios de capacidad que no fueron analizados desde la perspectiva de seguridad.

## Aspectos técnicos

- **Triggers de actualización obligatoria:** cambio de modelo base (de Claude 3.5 a una nueva versión), adición o modificación de herramientas en el agente, expansión del corpus RAG con fuentes externas no controladas, habilitación de multimodalidad (vision, audio, code execution), adición de memoria persistente entre sesiones, cambio en el perfil de usuarios (de internos a públicos).
- **Proceso de actualización:** documentar la nueva capacidad con precisión técnica → actualizar el DFD → aplicar STRIDE a los nuevos flujos → consultar MITRE ATLAS para TTPs relevantes → estimar likelihood × impact de cada amenaza → definir controles de mitigación con owner y fecha → registrar en changelog del threat model.
- **Threat model como código:** formato YAML/JSON en el repositorio del proyecto con historia de cambios en git; herramientas como Threatspec, OWASP Threat Dragon, o IriusRisk para gestión y generación de informes; el diff entre versiones es la evidencia de que el threat model se actualizó ante cada cambio de capacidad.
- **Threat intelligence para IA:** suscribirse a fuentes específicas de amenazas para sistemas de IA: MITRE ATLAS updates, OWASP LLM Top 10 actualizaciones, publicaciones de Anthropic/OpenAI/Google sobre vulnerabilidades descubiertas, Hugging Face Security Advisories; incorporar nuevas técnicas de ataque al threat model antes de que sean explotadas en producción.
- **Validación mediante red teaming:** cada actualización del threat model debe triggear un ejercicio de red teaming enfocado en las nuevas amenazas identificadas; el threat model sin red teaming de validación es teoría sin verificación empírica, y la teoría sin verificación puede crear una falsa sensación de seguridad.

> **Nota del Arquitecto:** El threat model tiene un valor secundario que frecuentemente se subestima: como herramienta de comunicación. Cuando el equipo de producto propone añadir una nueva funcionalidad al agente —por ejemplo, capacidad de enviar emails en nombre del usuario— el threat model actualizado es el mecanismo que convierte esa discusión de "sí/no" a "sí, con estos controles específicos". El threat model da al equipo de ingeniería el vocabulario y el artefacto para participar en decisiones de producto con argumentos de seguridad concretos y cuantificables, no solo con intuiciones.

El threat model debe revisarse obligatoriamente antes de cualquier release significativo del sistema de IA y periódicamente en producción para incorporar nuevas técnicas de ataque documentadas en la comunidad de seguridad. El landscape de amenazas para sistemas de IA evoluciona significativamente más rápido que el de sistemas de software tradicional: lo que no era un vector de ataque conocido hace seis meses puede ser una técnica documentada y ampliamente replicada hoy.
