# Módulo 9 – Capítulo 05 – Sección 06

## Cierre: RAG y agentes son multiplicadores de capacidad — y de riesgo

Los sistemas RAG y agénticos representan el salto cualitativo más significativo en la utilidad práctica de los LLMs para aplicaciones empresariales reales. RAG permite que el modelo acceda a conocimiento actualizado y específico del dominio, superando el knowledge cutoff y la incapacidad del modelo para razonar sobre datos propietarios. Los agentes permiten que el modelo ejecute acciones en el mundo real, transformando el LLM de un generador de texto a un asistente que puede completar tareas, gestionar flujos de trabajo, y operar en sistemas existentes. La proliferación de estos patrones —RAG en prácticamente toda aplicación empresarial seria, agentes con herramientas en los sistemas más sofisticados— refleja un valor real que los usuarios y organizaciones están experimentando.

Pero este salto en capacidad es también un salto proporcional en la superficie de ataque y en el impacto potencial de los ataques exitosos. Los principios establecidos en este capítulo —tratar todos los datos externos como untrusted, aplicar sandboxing a la ejecución de código, implementar autorización granular por operación, validar el output de sub-agentes antes de procesarlo, y exigir confirmación humana para acciones irreversibles— no son restricciones opcionales que se pueden diferir para "la versión 2.0". Son los controles que distinguen un sistema agéntico seguro de uno que espera ser comprometido, y la decisión de no implementarlos es equivalente a tomar la decisión consciente de no poner control de acceso en una base de datos de producción porque "es más cómodo para el desarrollo".

La secuencia correcta de diseño de un sistema agéntico desde la perspectiva de seguridad es la inversa de la secuencia natural de desarrollo. El camino natural es: construir las herramientas primero, darle al agente acceso a todas ellas, y "añadir seguridad después". El camino correcto es: definir el threat model del sistema antes de escribir código, especificar los permisos mínimos de cada herramienta, implementar el plano de control que valida acciones, y luego implementar las herramientas dentro de esos límites. La seguridad añadida después a un sistema agéntico en producción siempre tiene brechas porque la arquitectura no fue diseñada para acomodarla.

## Conceptos clave del capítulo

- **RAG poisoning:** inyección de documentos maliciosos en el vectorstore recuperados como contexto confiable; el vectorstore requiere controles de acceso en ingestión, validación de contenido, auditoría periódica del corpus, y monitoreo de outputs.
- **Prompt injection via RAG indirecto:** instrucciones adversariales en documentos recuperados ejecutadas por el modelo como si vinieran del sistema; mitigada marcando documentos recuperados como untrusted y validando output antes de ejecutar acciones.
- **Seguridad agéntica:** herramientas amplifican el impacto de cualquier ataque; el blast radius debe limitarse por diseño mediante mínimo privilegio; acciones irreversibles requieren confirmación explícita del usuario.
- **Sandboxing:** ejecución de código en containers aislados (Docker/gVisor/Firecracker) con restricciones de red, filesystem y CPU; network proxy egress con allowlist de dominios; secrets inyectados por el plano de control, nunca en el contexto del LLM.
- **Seguridad multi-agente:** el output de sub-agentes es input externo no confiable; cascading compromise propaga el impacto de un sub-agente comprometido al orquestador; cada agente es un límite de confianza que requiere validación de inputs.

*"With great power comes great attack surface."* — Parafraseando a Simon Willison, creador de Datasette e investigador prolífico en seguridad de sistemas de IA generativa, sobre el trade-off fundamental entre capacidad y riesgo en sistemas agénticos: cada herramienta que el agente puede usar es también una herramienta que un atacante puede usar si compromete al agente.
