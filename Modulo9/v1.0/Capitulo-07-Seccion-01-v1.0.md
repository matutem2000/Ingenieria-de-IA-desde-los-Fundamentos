# Módulo 9 – Capítulo 07 – Sección 01

## Autenticación y autorización: OAuth2, API keys y control de acceso a modelos

Antes de que cualquier request llegue al modelo, debe responder dos preguntas independientes: ¿quién eres? (autenticación) y ¿qué puedes hacer? (autorización). En sistemas de IA, estas preguntas tienen dimensiones adicionales respecto a las APIs convencionales: la autorización debe ser granular no solo a nivel de endpoint sino a nivel de capacidad del modelo —qué modelos puede usar este cliente, con qué parámetros, en qué volumen—, y las credenciales de acceso no deben nunca aparecer en el contexto del LLM porque ese contexto puede ser extraído mediante prompt leaking. Comenzar el diseño de seguridad del endpoint por la autenticación no es un detalle de orden: sin autenticación, el rate limiting es irrelevante porque el atacante sin autenticar ya está en el punto incorrecto del sistema.

El stack de autenticación estándar para APIs de IA sigue los mismos protocolos que el software moderno: OAuth 2.0 con PKCE para aplicaciones que actúan en nombre de usuarios finales (donde el usuario debe autenticarse con su proveedor de identidad antes de que la aplicación pueda acceder al LLM en su nombre), API keys con rotación automática para comunicación server-to-server entre servicios internos, y JWT (JSON Web Tokens) con claims específicos de IA para autorización stateless en arquitecturas de microservicios. La diferencia con implementaciones convencionales es la granularidad de los claims en el JWT: además de los claims estándar (sub, iss, aud, exp), los claims específicos de IA deben incluir qué modelos están autorizados para esta identidad, qué límites de tokens aplican, y a qué tenants o recursos tiene acceso.

La jerarquía de API keys es el mecanismo de gestión de credenciales más utilizado en APIs de LLMs, y debe implementarse con tres niveles para minimizar el impacto de un compromiso: la clave maestra de organización —que no se usa directamente en ningún código de aplicación sino solo para generar claves de proyecto—, las project keys con scope limitado (qué modelos, qué endpoints, qué límites de tokens) que se usan en aplicaciones específicas, y los session tokens de corta duración que pueden generarse para requests específicas de alta sensibilidad. Cada nivel tiene diferente capacidad de daño si se compromete y diferente frecuencia de rotación: la clave maestra rota anualmente con proceso controlado; las project keys rotan automáticamente cada 90 días; los session tokens expiran en horas o días.

El modelo de RBAC (Role-Based Access Control) para sistemas de IA traduce los permisos en términos de capacidades del modelo, no solo de endpoints. Un rol "basic" puede tener acceso a GPT-3.5-turbo con temperatura máxima de 0.7 y límite de 4k tokens por request; un rol "advanced" tiene acceso a GPT-4o con parámetros completos; un rol "fine-tuning-operator" tiene acceso a los endpoints de fine-tuning y a los modelos fine-tuned del tenant. Un rol "model-admin" puede ver y modificar los modelos fine-tuned de la organización. Esta granularidad no es un ejercicio académico: un atacante que compromete credenciales de un rol "basic" no puede acceder a los modelos fine-tuned ni a los endpoints de administración, limitando significativamente el daño potencial.

## Aspectos técnicos

- **Jerarquía de API keys:** clave maestra (nunca en código, solo para generar project keys) → project keys con scope por modelo y endpoint (rotación automática 90 días) → session tokens de duración limitada (horas/días) para requests específicas; HashiCorp Vault con Dynamic Secrets para project keys y session tokens de duración limitada.
- **OAuth 2.0 con PKCE para usuarios finales:** el usuario se autentica con su IdP (Okta, Auth0, Azure AD) y la aplicación recibe tokens de acceso de alcance limitado al LLM; el modelo no recibe las credenciales del IdP, solo el token validado.
- **JWT con claims específicos de IA:** además de claims estándar, incluir allowed_models[], max_tokens_per_request, tenant_id, user_tier; el middleware de autorización verifica estos claims antes de reenviar la request al proveedor del modelo.
- **RBAC por modelo y capacidad:** diferentes roles tienen acceso a diferentes modelos, endpoints, y parámetros; la autorización verifica que el model_id en la request está autorizado para el role del token de autenticación.
- **Detección de uso anómalo de API keys:** patrones de uso inusuales (nueva geolocalización, volumen anormal, endpoints no utilizados previamente) deben triggear alertas y opcionalmente suspensión temporal de la key para verificación; las credenciales comprometidas frecuentemente se usan primero con actividad anómala detectable.

> **Nota del Arquitecto:** El error más común en autenticación de APIs de IA no es la ausencia de autenticación —casi todos los equipos la implementan— sino la ausencia de autorización granular. La misma API key que da acceso a las completions también da acceso a los endpoints de fine-tuning, de listado de modelos, y de administración de la cuenta. Si esa key se filtra en un log de errores o en un repositorio público (que ocurre más frecuentemente de lo que los equipos reconocen), el atacante tiene acceso completo al sistema. La jerarquía de keys con scope limitado y rotación automática es la solución, y HashiCorp Vault la hace operacionalmente manejable.

La autenticación y autorización son el primer control que cualquier request debe atravesar, y su diseño granular es el prerrequisito para que todos los controles siguientes —rate limiting, input validation, output filtering— operen en el contexto correcto de quién está haciendo la request y qué está autorizado a hacer.
