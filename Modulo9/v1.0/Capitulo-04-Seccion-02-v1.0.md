# Módulo 9 – Capítulo 04 – Sección 02

## Metodología: scoping, threat modeling, ejecución y reporte

El red teaming sin metodología estructurada produce resultados inconsistentes, difíciles de comparar entre iteraciones, y con cobertura de amenazas que refleja los sesgos del equipo en lugar del threat model del sistema. El equipo que hace red teaming sin scoping previo tiende a atacar lo que le resulta interesante en lugar de lo que es más arriesgado para el sistema específico; el que no tiene criterios de éxito definidos termina con hallazgos que no pueden priorizarse ni compararse entre ejercicios; el que no produce reportes reproducibles genera conocimiento que muere con el ejercicio y no puede verificarse después de una mitigación. La metodología no es burocracia —es el mecanismo que convierte el red teaming en un proceso de ingeniería con resultados acumulables y verificables.

La fase de scoping es la más frecuentemente subestimada y la que más determina la calidad del ejercicio. En esta fase se define el threat model del ejercicio: quién es el adversario (un usuario frustrado sin capacidades técnicas, un competidor con acceso a modelos open-source, un investigador de seguridad, un actor estatal), cuáles son sus motivaciones (causar daño a usuarios, extraer el sistema propietario, comprometer la infraestructura), y qué capacidades tiene (acceso solo a la interfaz pública, conocimiento del sistema prompt, acceso a modelos open-source como surrogates). También se definen los harm criteria: qué outputs específicos constituyen una vulnerabilidad reportable y cuál es su severidad mínima para ser incluida en el reporte. Un harm criterion bien definido podría ser "cualquier respuesta que proporcione instrucciones actionables para actividades ilegales que puedan causar daño físico" o "cualquier respuesta que incluya el texto del system prompt".

La fase de threat modeling prioriza las categorías de ataque más relevantes para el sistema específico usando los frameworks establecidos. OWASP LLM Top 10 proporciona una lista priorizada de vulnerabilidades específicas de LLMs que debe revisarse completa para identificar cuáles aplican al sistema bajo prueba. MITRE ATLAS extiende esta lista con tácticas, técnicas y procedimientos documentados en incidentes reales. Para sistemas agénticos, las categorías de tool call injection, confused deputy problem, y amplificación de impacto mediante herramientas deben estar explícitamente en el scope. Para sistemas RAG, RAG poisoning e indirect injection a través de documentos recuperados deben ser prioridades.

La ejecución estructurada convierte el threat model en un programa de trabajo ejecutable. Los roles del equipo se asignan según el expertise: expertos en jailbreaking manejan las categorías de manipulación del comportamiento del modelo; especialistas en ataques de privacidad se enfocan en extracción de training data y prompt leaking; ingenieros de sistemas atacan la infraestructura y las herramientas del agente. Cada attempt se registra en un sistema de tracking con el prompt exacto enviado, la respuesta recibida, la clasificación de éxito o fallo, y la severidad tentativa. Esta granularidad de registro es lo que permite reproducir el hallazgo después de implementar una mitigación y verificar que la mitigación fue efectiva.

## Aspectos técnicos de cada fase

- **Scoping:** threat model del adversario (motivación, capacidades, acceso al sistema), harm criteria específicos con ejemplos de qué califica y qué no, y perímetro del ejercicio (qué sistemas, qué capacidades, qué no está en scope).
- **Threat modeling para red teaming:** priorización de OWASP LLM Top 10 + MITRE ATLAS relevantes para el sistema específico; harm taxonomy en cuatro dimensiones: seguridad (bypasses, exfiltración), safety (contenido dañino), privacidad (PII, datos de entrenamiento), y alineación (el sistema hace cosas que el operador no pretendía).
- **Criterios de severidad:** adaptar CVSS para IA evaluando probabilidad de explotación real, impacto del comportamiento adversarial obtenido, facilidad de reproducción sin capacidades especializadas, y alcance del daño (un usuario afectado vs. todos los usuarios del sistema).
- **Ejecución:** roles especializados, log detallado de cada attempt (prompt, respuesta, clasificación), tracking en Jira o GitHub Issues para asegurar reproducibilidad y seguimiento de mitigaciones.
- **Reporte de hallazgos:** cada hallazgo incluye el prompt o técnica exacta que reproduce la vulnerabilidad, el output observado, la clasificación de severidad, el harm scenario concreto (quién se daña y cómo), y recomendaciones específicas de mitigación.

> **Nota del Arquitecto:** El reporte del red teaming es un documento de seguridad de alta sensibilidad: contiene los prompts exactos que comprometen el sistema. Debe distribuirse solo a las personas que necesitan implementar las mitigaciones, almacenarse con cifrado, y no incluirse en repositorios de código con acceso amplio. He visto reportes de red teaming publicados inadvertidamente en repos de GitHub, proporcionando a cualquiera con acceso el manual exacto para atacar el sistema.

La metodología de red teaming produce un hallazgo reproducible por cualquier miembro del equipo usando solo la documentación del reporte. Si un hallazgo no puede reproducirse con las instrucciones del reporte, no puede verificarse ni mitigarse, y el ejercicio que lo produjo no tiene valor de seguridad neto.
