# Módulo 7 – Capítulo 09 – Sección 05

## Escalabilidad horizontal de agentes: workers, colas y balanceo de carga

Un agente en producción de alto volumen es, desde el punto de vista de la infraestructura, un consumidor de recursos intensivo y de duración variable: cada tarea puede requerir múltiples llamadas a APIs externas con latencias de cientos de milisegundos cada una, ejecución de código en sandboxes, y ciclos de razonamiento del LLM que pueden tomar segundos por iteración, con una duración total por tarea que va de segundos a minutos. Estas características hacen que una arquitectura de servidor web convencional —donde cada request HTTP ocupa un hilo o coroutine durante la duración de la respuesta— sea ineficiente para escalar agentes: un servidor HTTP estándar con 20 workers concurrentes procesando tareas de 30 segundos cada una tiene un throughput máximo de 40 tareas por minuto, que es insuficiente para muchos sistemas de producción.

El patrón de escalabilidad correcto para agentes es el **sistema de colas con worker pools**. El flujo tiene tres componentes independientes: los **productores** (los clientes que envían tareas, típicamente instancias del API server), la **cola de mensajes** (que actúa como buffer elástico entre productores y workers, implementada con Redis, RabbitMQ, Amazon SQS o Apache Kafka), y los **workers** (instancias dedicadas del agente que consumen tareas de la cola y las ejecutan hasta completarlas). Este desacoplamiento entre la recepción de requests y su procesamiento tiene tres propiedades operativas fundamentales: los productores pueden aceptar tasks nuevas sin importar si hay workers disponibles en ese momento (resiliencia ante picos de demanda), el número de workers puede ajustarse independientemente del número de instancias del API server (escalabilidad diferenciada por capa), y un worker que falla durante el procesamiento devuelve la tarea a la cola para que otro worker la procese (resiliencia ante fallos de instancias).

**Celery con Redis o RabbitMQ** es el stack de worker queue más establecido en el ecosistema Python para este patrón. Un worker Celery para agentes puede configurarse para ejecutar múltiples agentes concurrentemente usando `asyncio` (apropiado para agentes I/O-bound, que pasan la mayor parte del tiempo esperando respuestas de APIs): `celery -A agent_tasks worker --concurrency=10 --pool=gevent` lanza un worker que procesa hasta 10 tareas concurrentemente usando greenlets, lo que es mucho más eficiente que 10 procesos Python separados para workloads I/O-bound. Para workloads CPU-intensivos (ejecución de código, procesamiento de imágenes), el modelo de procesos separados es más apropiado.

El **auto-scaling basado en métricas de cola** automatiza el ajuste del número de workers en función de la carga real. La señal más directa es la **profundidad de la cola** (número de tareas pendientes de procesamiento): cuando supera un umbral (p.ej., 50 tareas pendientes), el sistema de orquestación añade workers; cuando cae por debajo de otro umbral (p.ej., 5 tareas pendientes), reduce workers para minimizar el costo de infraestructura en períodos de baja demanda. En Kubernetes, este patrón se implementa con **KEDA** (Kubernetes Event-driven Autoscaling), que escala el número de réplicas de los Deployments de workers en función de métricas de colas externas (Redis, SQS, RabbitMQ) sin requerir programación adicional. La combinación de Kubernetes + KEDA + Celery o Dramatiq es un stack de producción probado para escalabilidad horizontal de agentes.

La **dead letter queue (DLQ)** es el mecanismo que previene que tareas irrecuperables bloqueen la cola principal. Cuando una tarea falla repetidamente (supera `max_retries`, típicamente 3), se mueve automáticamente a la DLQ. Allí, un operador humano puede revisar la tarea, diagnosticar la causa del fallo, y decidir si reintentar manualmente (si fue un fallo transitorio), descartar la tarea (si el input es inválido), o crear un ticket de bug (si es un fallo del agente que requiere corrección de código). La DLQ es esencial para la observabilidad de fallos sistémicos: si 50 tareas se acumulan en la DLQ en un período de 1 hora con el mismo mensaje de error, eso es una alerta de que hay un problema sistemático que requiere atención inmediata.

La **priorización de tareas** es una consideración de diseño que frecuentemente se omite hasta que hay un incidente. En un sistema con un único nivel de prioridad, una carga de trabajo batch —análisis nocturnos, generación de reportes periódicos— puede llenar la cola y producir latencias inaceptables para las tareas interactivas de usuario que llegan concurrentemente. Implementar dos colas separadas —una de alta prioridad para tareas interactivas, una de baja prioridad para tareas batch— con workers que priorizan la cola de alta prioridad, previene este problema. En Redis Sorted Sets, la prioridad puede representarse como el score del sorted set: las tareas con menor timestamp de encolamiento tienen mayor prioridad, con la opción de asignar scores artificialmente bajos a tareas marcadas como prioritarias por el sistema.

## Aspectos técnicos

- **Queue-based worker pool**: productores (API server) encolan tareas en Redis/SQS con task_id, input, configuración; workers consumen y procesan tareas hasta completarlas; desacoplamiento elástico entre recepción y procesamiento
- **Worker concurrency con asyncio**: para agentes I/O-bound, Celery con pool gevent o asyncio permite concurrencia de 5-20 agentes por worker sin overhead de múltiples procesos; para agentes CPU-bound (ejecución de código), pool de procesos separados
- **Auto-scaling con KEDA**: escala el número de réplicas de workers en Kubernetes basándose en métricas de cola (profundidad de cola en Redis/SQS); escala hacia arriba cuando la cola crece, hacia abajo cuando se vacía; reduce el costo de infraestructura en períodos de baja demanda
- **Dead letter queue (DLQ)**: tareas que superan `max_retries` se mueven a DLQ para revisión manual; acumulación anómala en DLQ es una señal de alerta de problema sistémico; revisar DLQ periódicamente como parte del proceso de operaciones
- **Priorización de tareas**: dos colas separadas (alta/baja prioridad) con workers que priorizan la cola de alta prioridad; previene que workloads batch produzcan latencias inaceptables para tareas interactivas

> **Nota del Arquitecto**: La métrica de monitoreo más valiosa para el sistema de colas de un agente no es el throughput (tareas procesadas por minuto) sino la **latencia de queue wait** (tiempo desde que una tarea es encolada hasta que un worker comienza a procesarla). Un throughput alto con latencia de queue wait creciente indica que los workers existentes no pueden absorber la demanda actual y que es necesario escalar antes de que los usuarios experimenten degradación. Esta métrica debe estar en el dashboard principal del equipo de operaciones, con una alerta cuando supera el P95 histórico.

## Buena práctica

Monitorear la profundidad de cola y la latencia de queue wait como SLIs primarios del sistema de agentes. Un aumento sostenido en la profundidad de cola sin aumento proporcional de workers es la señal más temprana de degradación de capacidad, y actuar sobre esta señal preventivamente —antes de que los usuarios experimenten latencias inaceptables— es la diferencia entre un sistema de producción robusto y uno reactivo.
