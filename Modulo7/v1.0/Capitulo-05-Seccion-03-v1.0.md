# Módulo 7 – Capítulo 05 – Sección 03

## CrewAI: orquestación de equipos de agentes con roles definidos

CrewAI representa el enfoque de mayor nivel de abstracción en la ingeniería de agentes: en lugar de programar grafos de estado (LangGraph) o configurar conversaciones entre agentes (AutoGen), el desarrollador declara un equipo con roles y tareas en lenguaje natural, y el framework gestiona la coordinación. Esta filosofía de diseño prioriza explícitamente la velocidad de desarrollo sobre el control de implementación: un equipo de agentes funcional puede construirse en pocas líneas de código, a costa de menor control sobre los detalles de la coordinación entre agentes.

La metáfora organizacional de CrewAI es directa: un **`Crew`** es un equipo de **`Agents`** con roles específicos que colaboran en **`Tasks`** para lograr un objetivo común. Un agente de investigación puede tener el rol de "Technical Research Specialist" con el objetivo de encontrar información técnica precisa y actualizada, acceso a herramientas de búsqueda web y lectura de documentos, y una `backstory` que contextualiza su expertise ("Especialista en investigación técnica con 10 años de experiencia en análisis de documentación de APIs y papers de ingeniería"). Una tarea puede ser "Investigar las características principales de LangGraph 0.2 y producir un resumen técnico de 500 palabras con ejemplos de código". La separación entre qué hace el agente (rol) y qué debe producir en esta instancia (tarea) permite reutilizar agentes en diferentes contextos con diferentes tareas.

Los dos modos de proceso de CrewAI capturan trade-offs fundamentales en la coordinación multi-agente. **`Process.sequential`** ejecuta las tareas en orden, con el output de cada tarea disponible como contexto para la siguiente: el investigador completa su tarea, el analista recibe ese output y produce el análisis, el redactor recibe el análisis y produce el informe final. La secuencia es predecible y fácil de depurar; el bottleneck es que la latencia total es la suma de las latencias individuales. **`Process.hierarchical`** introduce un agente manager que orquesta dinámicamente la distribución de tareas: el manager analiza el objetivo general, decide qué agente debe ejecutar qué subtarea, evalúa los resultados intermedios, y puede reasignar o ajustar tareas según los resultados. Este modo añade flexibilidad adaptativa pero el manager se convierte en un punto de fallo central cuya calidad de razonamiento determina el desempeño de todo el sistema.

La integración de memoria en CrewAI sigue un modelo de cuatro capas accesibles con la configuración `memory=True` en el `Crew`: **short-term memory** para el contexto de la conversación actual (implementado como buffer de mensajes), **long-term memory** para persistencia entre ejecuciones del crew (SQLite por defecto, configurable), **entity memory** para mantener información estructurada sobre entidades mencionadas a lo largo del trabajo (personas, empresas, conceptos clave), y **user memory** para preferencias y contexto específico del usuario. La activación de todos los tipos de memoria con una sola línea de configuración es un ejemplo de la filosofía de facilidad de uso de CrewAI, aunque con el trade-off de menor control sobre qué se almacena y cómo se recupera comparado con un sistema de memoria custom en LangGraph.

El **kickoff asíncrono** con `crew.kickoff_async()` permite ejecutar el crew sin bloquear el hilo principal, lo que es necesario en aplicaciones web que deben responder al usuario mientras el crew trabaja en background. `kickoff_for_each_async()` procesa múltiples inputs en paralelo sobre el mismo crew, lo que es especialmente útil para tareas de procesamiento batch: generar 50 reportes de análisis de competidores, procesar 100 artículos de noticias, o clasificar 200 tickets de soporte técnico de forma simultánea.

La integración nativa con el ecosistema de LangChain tools permite a CrewAI reutilizar el amplio catálogo de herramientas de LangChain sin reimplementación: las herramientas de búsqueda web, vectorstores, APIs, y utilidades de texto de LangChain se pueden pasar directamente como `tools=[]` en la definición de cada agente de CrewAI. Esta interoperabilidad reduce significativamente el tiempo de implementación cuando el proyecto ya usa herramientas de LangChain.

## Componentes principales

- **Agent definition**: cada agente se define con `role` (función en el equipo), `goal` (objetivo específico), `backstory` (contexto de expertise en lenguaje natural) y `tools` (lista de herramientas disponibles); la backstory influye en cómo el LLM interpreta su rol
- **Task definition**: cada tarea especifica `description` (qué debe producir), `expected_output` (formato y contenido esperado), `agent` (agente responsable), y opcionalmente `context` (resultados de otras tasks que deben considerarse como input)
- **Process.sequential vs hierarchical**: secuencial es predecible y trazable (latencia = suma de latencias individuales); jerárquico es flexible y adaptativo pero el manager LLM introduce no-determinismo en la asignación de tareas
- **Memory system**: short-term, long-term (SQLite), entity memory y user memory; activables con `memory=True`; más simple de activar que un sistema custom, con menos control sobre la implementación
- **Kickoff asíncrono**: `crew.kickoff_async()` para ejecución no bloqueante; `kickoff_for_each_async()` para procesamiento batch paralelo de múltiples inputs sobre el mismo crew

## Principio rector

CrewAI intercambia flexibilidad de bajo nivel por velocidad de desarrollo: su API declarativa permite construir un sistema multi-agente funcional en pocas líneas de código, a costa de menor control sobre la lógica de coordinación que LangGraph o AutoGen ofrecen. Es la elección correcta cuando la velocidad de prototipar importa más que el control de implementación, y cuando los flujos son suficientemente estándar para que las abstracciones de alto nivel de CrewAI sean una ventaja en lugar de una restricción.

La sección siguiente examina Pydantic AI, el framework que aborda un problema diferente: no la coordinación entre agentes ni el control del flujo, sino la garantía de tipos en las entradas y salidas del agente como mecanismo de confiabilidad en producción.
