# Módulo 7 – Capítulo 03 – Sección 02

## Function calling en APIs: OpenAI, Anthropic (tool_use) y Google

La capacidad de un agente de invocar herramientas depende de cómo el proveedor del LLM expone function calling en su API. Las tres plataformas principales —OpenAI, Anthropic y Google— implementan esta funcionalidad con la misma intención pero con diferencias concretas en nomenclatura, estructura de mensajes, y comportamiento de control de flujo que pueden producir bugs sutiles cuando se construye un agente que debe ser portable o cuando se cambia de proveedor. Conocer estas diferencias no es un detalle técnico menor: es el conocimiento que permite diagnosticar por qué un agente que funciona con GPT-4o no funciona directamente con Claude sin modificaciones, y cómo diseñar la capa de abstracción que hace el código verdaderamente portable.

**OpenAI** (GPT-4o, GPT-4 Turbo, GPT-3.5 Turbo con soporte limitado) implementa function calling mediante el campo `tools` en la request, que contiene un array de objetos con estructura `{"type": "function", "function": {"name": "...", "description": "...", "parameters": {...JSON Schema...}}}`. Cuando el modelo decide invocar una herramienta, devuelve en el mensaje del asistente un array `tool_calls` donde cada entrada contiene un `id` único, el `function.name`, y los `function.arguments` como string JSON. El desarrollador ejecuta la función con esos argumentos y devuelve el resultado como un mensaje adicional con `role: "tool"`, el `tool_call_id` correspondiente, y el `content` con el resultado serializado. El ciclo completa cuando el modelo decide que ya tiene suficiente información para responder sin invocar más herramientas.

**Anthropic** (Claude 3.5 Sonnet, Claude 3 Opus, Claude 3 Haiku) usa el mismo campo `tools` en la request, pero la estructura y el flujo de mensajes son diferentes. El modelo devuelve bloques `content` de tipo `tool_use` con `id`, `name`, e `input` como objeto JSON (no como string). Los resultados se devuelven no como mensajes separados sino como bloques `tool_result` dentro del siguiente mensaje de usuario, lo que significa que el formato de la conversación alterna entre mensajes de usuario y mensajes de asistente de forma estricta. Esta diferencia de formato —tool results en el mensaje de usuario en lugar de mensajes independientes— es la fuente más común de incompatibilidad cuando se portan agentes de OpenAI a Anthropic.

**Google** (Gemini 1.5 Pro, Gemini 1.5 Flash) usa `function_declarations` dentro del campo `tools`, y el modelo devuelve `Part` de tipo `functionCall` con nombre y argumentos como `Struct` protobuf. Las respuestas se envían como `Part` de tipo `functionResponse` en el siguiente turno. La principal diferencia operativa con OpenAI y Anthropic es el uso de types de protobuf en lugar de JSON nativo, lo que requiere adaptadores específicos cuando se trabaja con la librería de Python.

Las **llamadas paralelas a herramientas** (parallel tool use) son especialmente importantes para la eficiencia de los agentes. GPT-4o y Claude 3.5 Sonnet pueden invocar múltiples herramientas en una sola respuesta: en lugar de buscar en la web, esperar el resultado, y luego buscar en la base de datos, el agente puede iniciar ambas búsquedas simultáneamente. Esta capacidad puede reducir el número de iteraciones del ciclo en hasta un 50% para tareas donde múltiples acciones son independientes entre sí. El desarrollador debe estar preparado para manejar arrays de `tool_calls` en OpenAI y arrays de bloques `tool_use` en Anthropic, ejecutando cada invocación en paralelo con `asyncio.gather()` y retornando todos los resultados en el siguiente mensaje.

El parámetro **tool_choice** permite controlar el comportamiento de selección de herramientas: `tool_choice: "auto"` (el modelo decide si usar herramientas o responder directamente), `tool_choice: "none"` (el modelo debe responder sin herramientas), y `tool_choice: {"type": "tool", "name": "..."}` en Anthropic (forzar el uso de una herramienta específica). Esta última opción es útil para garantizar outputs estructurados en formato específico: si se necesita que el agente devuelva siempre un JSON validado, se puede definir una "herramienta de output" ficticia con el schema Pydantic del resultado esperado y forzar al modelo a usarla.

## Aspectos técnicos

- **OpenAI tool_calls**: el modelo devuelve un array `tool_calls` con id, nombre y argumentos como string JSON; los resultados se devuelven como mensajes con `role: "tool"` referenciando el `tool_call_id`
- **Anthropic tool_use**: el modelo devuelve bloques `content` de tipo `tool_use` con id, nombre e `input` como objeto JSON; los resultados se devuelven como bloques `tool_result` dentro del siguiente mensaje de `role: "user"`
- **Google functionCall**: el modelo devuelve `Part` de tipo `functionCall` con nombre y argumentos como `Struct`; la respuesta se envía como `Part` de tipo `functionResponse` en el siguiente turno de usuario
- **tool_choice / forced calling**: las tres APIs permiten forzar el uso de una herramienta específica o prohibir el uso de herramientas; útil para garantizar outputs estructurados o para implementar herramientas de output como alternativa a JSON mode
- **Parallel tool use**: GPT-4o y Claude 3.5 Sonnet pueden invocar múltiples herramientas en una sola respuesta; ejecutar las invocaciones paralelas con `asyncio.gather()` reduce la latencia total en tareas con acciones independientes

> **Nota del Arquitecto**: Cuando el proyecto requiere portabilidad entre proveedores, la solución correcta es una capa de abstracción delgada, no confiar en el que el framework lo resuelva automáticamente. LangChain y LangGraph abstraen estas diferencias razonablemente bien, pero a veces a costa de exponer menos control sobre los detalles de implementación específicos de cada proveedor. Para proyectos donde el costo de API es una variable crítica, trabajar directamente con las APIs nativas y construir una capa de abstracción propia es frecuentemente más eficiente.

## Para recordar

La portabilidad entre proveedores de function calling no es automática: las diferencias en estructura de respuesta, manejo de herramientas paralelas y control de tool_choice requieren una capa de abstracción explícita o el uso de un framework que la proporcione y que el equipo entiende suficientemente bien para depurar cuando hay comportamientos inesperados.

La sección siguiente examina por qué el diseño de la descripción de cada herramienta es tan importante como su implementación: una herramienta con implementación perfecta pero descripción ambigua producirá errores de selección que ninguna cantidad de debugging en la implementación podrá resolver.
