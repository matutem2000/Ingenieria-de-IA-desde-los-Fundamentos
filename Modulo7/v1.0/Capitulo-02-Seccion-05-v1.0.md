## Verificación y autocorrección: el agente evalúa sus propios pasos

Planificar bien y razonar bien no garantizan que cada paso del ciclo produzca el resultado correcto. Los LLMs cometen errores: alucinan datos, interpretan incorrectamente observaciones de herramientas, seleccionan herramientas inadecuadas para ciertos casos de borde, y generan código que no funciona. La autocorrección agéntica es el mecanismo que cierra ese gap: en lugar de propagar cada error al paso siguiente, el sistema detecta el problema, evalúa su gravedad, y toma la acción correctiva antes de continuar. La clave es que esta verificación ocurra dentro del ciclo de ejecución, sin requerir intervención humana para cada paso, pero también sin dejar al sistema ciego ante sus propios errores.

La forma más directa de autocorrección es la **verificación externa**: ejecutar el resultado del agente en el entorno real y observar si produce el efecto esperado. Un agente que genera código Python puede ejecutarlo en un sandbox E2B y verificar si compila y si los tests pasan. Un agente que genera una URL puede hacer una llamada HTTP y verificar que devuelve HTTP 200. Un agente que genera un JSON puede validarlo contra un schema Pydantic o JSON Schema. Esta verificación es binaria, programática, y no introduce la incertidumbre adicional de una segunda llamada al LLM. Siempre que los criterios de corrección sean formalizables, la verificación externa es la forma más confiable de autocorrección y debe preferirse sobre cualquier evaluación basada en LLM.

Cuando los criterios de corrección son semánticos y no formalizables, la autocorrección debe involucrar otro paso de inferencia. El **patrón de reflexión** (reflection pattern) es el más directo: el mismo agente que generó la respuesta recibe un prompt adicional que le pide identificar posibles errores y auto-corregirse. "Revisa tu respuesta anterior. ¿Hay afirmaciones que podrían ser incorrectas? ¿El razonamiento es consistente con las observaciones disponibles? Si encuentras errores, corrígelos." Estudios experimentales muestran que esta auto-revisión mejora los resultados en 10-30% en tareas de codificación y razonamiento matemático. La limitación es igualmente documentada: el modelo puede cometer el mismo error tanto en la generación como en la evaluación si el error proviene de un sesgo sistemático del modelo o de información incorrecta en el contexto.

El **patrón LLM-as-judge** mitiga esta limitación usando un segundo modelo o un segundo prompt radicalmente diferente para evaluar la respuesta del primer agente. El juez recibe la tarea original, la respuesta del agente, y un rubric de evaluación explícito, y devuelve un score más justificación textual de sus observaciones. Usar GPT-4o como juez para evaluar outputs de modelos menores, o usar Claude 3.5 Sonnet como juez para outputs generados por el mismo Claude con un prompt diferente, puede detectar errores que la auto-reflexión pierde. El costo es real: cada evaluación es una llamada adicional al LLM con toda la latencia y costo asociados.

La **self-consistency** es una técnica diferente que evita el problema de la evaluación: en lugar de evaluar una respuesta, genera múltiples respuestas independientes para el mismo problema y aplica voting para seleccionar la más frecuente. Generar k=5 respuestas y elegir por mayoría es efectivo para problemas con respuesta única discreta (clasificaciones, cálculos numéricos, selección de categorías) donde la varianza del modelo puede controlarse con temperatura moderada. Su limitación es el costo: k=5 respuestas significa 5 llamadas al LLM con el costo de tokens completo de cada una.

Para todos los patrones de autocorrección, la política de reintentos es tan importante como el mecanismo de verificación. Sin un límite de intentos, la autocorrección puede generar bucles donde el agente corrige indefinidamente sin mejorar, consumiendo tokens y latencia de forma proporcional. El diseño estándar es `max_retries=3` con escalado al humano si se supera ese límite. Cuando una herramienta falla repetidamente o el agente no puede producir un resultado válido después de tres intentos, la decisión correcta es comunicar el fallo explícitamente —con diagnóstico de qué fue lo que no funcionó— en lugar de degradar silenciosamente la calidad del resultado.

## Puntos críticos

- **Verificación externa como primera opción**: ejecutar el resultado y verificar el efecto real es siempre la forma más confiable de autocorrección; preferir sobre LLM-as-judge cuando los criterios de éxito son formalizables (el código compila, el JSON valida, la URL responde)
- **Reflection pattern**: el agente revisa su propia respuesta con un prompt de evaluación diferenciado; mejora resultados en 10-30% en tareas de codificación y razonamiento, pero falla ante sesgos sistemáticos del modelo
- **LLM-as-judge**: un segundo modelo o prompt radicalmente diferente evalúa la respuesta con un rubric explícito; más robusto que la auto-reflexión pero añade latencia y costo de una llamada adicional al LLM por cada paso evaluado
- **Self-consistency**: generar k respuestas independientes y seleccionar por majority voting; efectivo para respuestas discretas, costoso para respuestas de texto libre
- **max_retries con escalado**: limitar los intentos de autocorrección (max_retries=3) y escalar al humano cuando se supera; la autocorrección sin límite puede consumir más recursos que reiniciar la tarea desde el principio

> **Nota del Arquitecto**: La tentación de usar LLM-as-judge en cada paso del ciclo para garantizar calidad es real, pero el costo operativo puede volverse mayor que el beneficio. En producción, aplicar verificación por LLM-judge selectivamente: solo en los pasos donde el error tiene mayor impacto en el resultado final o donde la verificación programática no es factible. Para los demás pasos, confiar en la verificación programática y reservar los recursos de evaluación para donde más importan.

## Buena práctica

Priorizar verificación externa sobre autocorrección por LLM siempre que sea posible: ejecutar el resultado en un sandbox o verificarlo contra un schema es una verificación de verdad objetiva, mientras que la autocorrección por LLM es solo otra inferencia probabilística sujeta a los mismos sesgos y limitaciones del modelo que generó el resultado original.
