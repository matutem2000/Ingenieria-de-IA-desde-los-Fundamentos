## Vectorización de memorias: búsqueda semántica sobre el historial del agente

El valor de un sistema de memoria de largo plazo depende directamente de la calidad de su mecanismo de recuperación. Si el agente no puede encontrar la memoria relevante en el momento correcto, la memoria existe pero no tiene efecto sobre el comportamiento. La recuperación exacta por keyword —buscar "preferencia idioma" para encontrar memorias que mencionan "prefiere inglés" o "responder en inglés"— falla ante la riqueza semántica del lenguaje natural: la misma idea puede expresarse con vocabulario completamente diferente. La vectorización convierte unidades de texto en representaciones numéricas de alta dimensión que capturan el significado semántico, permitiendo recuperar memorias relevantes aunque usen terminología distinta a la query actual.

Los **modelos de embedding** son el componente que determina la calidad de esta representación semántica. Cada fragmento de texto —una memoria individual, un episodio de conversación, un hecho extraído— se convierte en un vector de dimensión fija mediante un modelo de embedding: 1536 dimensiones para `text-embedding-3-large` de OpenAI, 1024 para `voyage-3` de Anthropic, 768 para `multilingual-e5-large` de Microsoft. La elección del modelo de embedding debe basarse en el tipo de contenido del dominio: `text-embedding-3-large` es óptimo para texto técnico en inglés; `multilingual-e5-large` es necesario para sistemas que manejan múltiples idiomas; modelos especializados como `voyage-code-2` o `code2vec` son más precisos cuando la memoria incluye fragmentos de código. La calidad del embedding afecta directamente la calidad del retrieval; cambiar el modelo de embedding requiere re-vectorizar todo el store.

Las **plataformas de vectorstore** más usadas en producción para memoria agéntica tienen perfiles diferentes. **Pinecone** es el servicio SaaS más maduro: serverless, con índices HNSW para búsqueda ANN de baja latencia, filtrado por metadata integrado, y soporte para hybrid search (semántico + keyword). **Weaviate** es self-hosted o cloud, con soporte multimodal, hybrid search nativo con BM25, y módulos de reranking integrados. **Chroma** es embebido en proceso, sin infraestructura adicional, ideal para desarrollo local y pruebas; no escala a millones de vectores en producción sin un backend persistente. **pgvector** como extensión de PostgreSQL es la opción más atractiva cuando el sistema ya usa PostgreSQL: permite vectorstore en la misma base de datos relacional, lo que simplifica la gestión de infraestructura y permite joins entre datos estructurados y vectoriales en una sola query.

La **estrategia de chunking** determina la granularidad de las unidades de memoria vectorizadas. Memorias largas —transcripciones de sesiones completas, documentos extensos— deben dividirse en fragmentos de tamaño óptimo (256-512 tokens) con overlap (10-20%) para no perder contexto en los límites entre chunks. El tamaño óptimo depende del caso de uso: chunks más pequeños producen retrieval más preciso (cada chunk habla de un único tema) pero requieren más operaciones de búsqueda; chunks más grandes capturan más contexto pero pueden incluir información irrelevante que diluye la señal semántica.

El **filtrado por metadata antes del ANN search** es fundamental para la eficiencia y la privacidad. Filtrar por `user_id` antes de la búsqueda vectorial garantiza que el agente solo recupera memorias del usuario correcto; filtrar por `date_range` permite priorizar memorias recientes; filtrar por `type` permite buscar solo en categorías relevantes (solo preferencias, solo hechos, solo errores). La mayoría de los vectorstores soportan este filtrado pre-ANN: se aplica como restricción antes de ejecutar la búsqueda vectorial, reduciendo el espacio de búsqueda y mejorando tanto la eficiencia como la precisión.

El **re-ranking post-retrieval** con un cross-encoder puede mejorar significativamente la calidad del retrieval final. Los modelos ANN como HNSW optimizan la velocidad de búsqueda aproximada, no la precisión absoluta: el top-k recuperado puede incluir ítems semánticamente similares pero no los más relevantes para la query específica. Aplicar un cross-encoder —`cohere-rerank-3`, `bge-reranker-v2-m3`— sobre los top-20 candidatos para obtener el top-3 final mejora la precision@3 en 15-30% sobre el retrieval puro, a costa de una latencia adicional de 50-200ms para la operación de reranking.

## Aspectos técnicos

- **Modelos de embedding por dominio**: `text-embedding-3-large` para texto técnico en inglés, `multilingual-e5-large` para sistemas multilingüe, `voyage-code-2` para memorias que incluyen código; cambiar el modelo requiere re-vectorizar todo el store
- **Plataformas de vectorstore**: Pinecone (SaaS maduro, HNSW, hybrid search), Weaviate (self-hosted o cloud, multimodal), Chroma (embebido, desarrollo local), pgvector (PostgreSQL extension, gestión simplificada si ya se usa PostgreSQL)
- **Chunking strategy**: fragmentos de 256-512 tokens con 10-20% de overlap; chunks más pequeños para retrieval preciso, chunks más grandes para preservar contexto; el tamaño óptimo depende del caso de uso específico del dominio
- **Filtrado por metadata pre-ANN**: filtrar por user_id, date_range, y type antes del search vectorial; reduce el espacio de búsqueda y garantiza privacidad a nivel de query, no solo a nivel de aplicación
- **Re-ranking post-retrieval**: aplicar un cross-encoder (cohere-rerank-3, bge-reranker-v2-m3) sobre los top-k candidatos ANN para reordenar por relevancia real; mejora precision@3 en 15-30% a costa de 50-200ms de latencia adicional

## Buena práctica

Evaluar la calidad del retrieval de memorias con un conjunto de queries de test antes de desplegar en producción: medir precision@3 y recall@10 sobre un conjunto anotado de (query, memorias_relevantes). Un retrieval con precision@3 < 0.7 produce memorias irrelevantes en el contexto que confunden el razonamiento del agente tanto como o más de lo que lo ayudan. La evaluación del retrieval debe repetirse cuando se cambia el modelo de embedding, cuando el store crece significativamente, o cuando se modifican las estrategias de chunking.
