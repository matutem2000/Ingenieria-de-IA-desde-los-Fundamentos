# Qué es un agente: percepción, razonamiento, memoria, herramientas y acción

Si el Módulo 6 enseñó a construir sistemas que recuperan información relevante de un corpus de documentos, este módulo enseña a construir sistemas que actúan en el mundo usando esa información como uno de sus instrumentos. Un sistema RAG responde preguntas; un agente ejecuta objetivos. El salto conceptual es significativo, pero la continuidad técnica es real: la memoria semántica de un agente —su capacidad de recuperar conocimiento del dominio bajo demanda— es exactamente el mismo mecanismo de retrieval que construimos en el módulo anterior. Un agente que consulta una base vectorial de documentos internos antes de responder no es arquitectónicamente diferente a un pipeline RAG; la diferencia está en que ese retrieval es uno más entre los instrumentos disponibles para un sistema que razona y actúa de forma iterativa.

Un agente de IA es un sistema que percibe su entorno a través de entradas estructuradas —texto, JSON, resultados de API, contenido de archivos—, razona sobre esa percepción usando un modelo de lenguaje como motor de inferencia, y ejecuta acciones con efectos en el mundo real: llamadas HTTP, ejecución de código, escritura en bases de datos o interacción con sistemas externos. A diferencia de una función determinista, un agente opera en bucles iterativos donde cada acción puede modificar el estado del entorno y generar nueva percepción. Esta naturaleza cíclica es la diferencia fundamental entre un sistema de IA que responde y uno que actúa: el chatbot termina su trabajo al generar texto; el agente termina su trabajo cuando el objetivo está cumplido, lo que puede requerir docenas de pasos intermedios.

La arquitectura clásica de un agente —inspirada en los sistemas de agentes inteligentes descritos por Russell y Norvig en "Artificial Intelligence: A Modern Approach"— descompone el comportamiento en cinco componentes funcionales que operan de forma coordinada. La **percepción** es la entrada al agente en cada paso del ciclo: puede ser el mensaje inicial del usuario, los resultados de una herramienta invocada en el paso anterior, el contenido de un archivo leído, o la respuesta de una API externa. Todo este material se serializa en el contexto del LLM para que el modelo pueda razonar sobre él. El **razonamiento** es la función del LLM: dado el contexto acumulado, el modelo decide qué hacer a continuación. En GPT-4o, Claude 3.5 Sonnet o Gemini 1.5 Pro, esta decisión toma la forma de una elección entre llamar a una herramienta específica con determinados parámetros, continuar razonando sin invocar herramientas, o declarar que la tarea está completa.

La **memoria** es el mecanismo que permite al agente mantener estado entre pasos del ciclo. Se divide en dos categorías que se complementan: la memoria in-context es el historial activo de mensajes y observaciones que cabe dentro de la ventana de contexto del LLM; la memoria externa —vectorstores como Pinecone o Weaviate, bases de datos como PostgreSQL, cachés como Redis— almacena información que no cabe en el contexto activo y se recupera selectivamente cuando es relevante. Esta distinción es directamente heredera del Módulo 6: cuando un agente consulta un vectorstore con una query semántica para obtener fragmentos de documentación antes de responder, está usando un sistema RAG como componente de su memoria semántica. El retrieval es el mismo mecanismo; el uso es diferente.

Las **herramientas** son funciones con esquema JSON que el LLM puede invocar: desde búsqueda web con Tavily o SerpAPI hasta ejecución de código Python en un sandbox E2B, lectura de archivos del sistema o llamadas a APIs REST arbitrarias. Cada herramienta representa una forma de conectar el razonamiento del agente con el mundo real. La **acción** es la operación concreta que el agente ejecuta tras decidir: una llamada de herramienta, un mensaje al usuario, una escritura en base de datos, o la declaración de que la tarea está terminada. La acción cierra un ciclo y abre el siguiente: su resultado se convierte en la próxima percepción del agente.

## Componentes principales

- **Percepción**: entrada al agente en cada paso del ciclo; puede ser texto del usuario, resultados de herramientas, contenido de archivos o respuestas HTTP serializadas en el contexto
- **Razonamiento**: el LLM (GPT-4o, Claude 3.5 Sonnet, Gemini 1.5 Pro) actúa como motor de inferencia que decide qué hacer a continuación dado el contexto acumulado
- **Memoria in-context**: historial activo en la ventana de contexto del LLM; acceso inmediato sin latencia adicional, limitado por el tamaño de la ventana (128K tokens en GPT-4o, 200K en Claude 3.5 Sonnet)
- **Memoria semántica externa**: vectorstores como Pinecone o Weaviate con recuperación por similaridad semántica; es exactamente el mismo mecanismo RAG del Módulo 6 aplicado como componente de memoria del agente
- **Herramientas**: funciones con esquema JSON que el LLM puede invocar; desde búsqueda web (Tavily, SerpAPI) hasta ejecución de código (Python REPL, E2B sandbox) o llamadas a APIs REST
- **Acción**: la operación concreta que el agente ejecuta tras decidir; puede ser una llamada de herramienta, un mensaje al usuario, una escritura en base de datos o la finalización de la tarea

> **Nota del Arquitecto**: En producción, el error más frecuente de diseño es tratar el agente como un chatbot mejorado y no como un sistema con efectos en el mundo real. Un chatbot que falla produce una mala respuesta; un agente que falla puede borrar registros, enviar emails o modificar configuraciones de producción. Esta asimetría de consecuencias debe estar presente desde el primer día de diseño, no cuando el primer incidente ocurre.

## Principio rector

Un agente no es una secuencia fija de pasos sino un sistema que decide dinámicamente qué operación ejecutar a continuación, condicionado por el estado actual del entorno y su historial de percepción acumulado. Esta autonomía operativa —no la cantidad de herramientas disponibles— es la propiedad que define a un agente.

La sección siguiente examina en detalle el salto arquitectónico que separa un chatbot de un agente: no es una diferencia de prompt, sino una diferencia de infraestructura de control de flujo, gestión de estado y criterios de terminación.
