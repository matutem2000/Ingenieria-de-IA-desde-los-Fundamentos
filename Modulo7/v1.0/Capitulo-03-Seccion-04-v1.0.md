# Módulo 7 – Capítulo 03 – Sección 04

## Herramientas de sistema: shell, filesystem, navegador web y code interpreter

Las herramientas de sistema son las más potentes del arsenal de un agente y, por la misma razón, las que requieren el diseño de seguridad más riguroso. Mientras que una herramienta de búsqueda web que devuelve resultados incorrectos produce una mala respuesta, una herramienta de shell que ejecuta el comando incorrecto puede comprometer el sistema host, y una herramienta de base de datos que ejecuta el SQL incorrecto puede borrar datos de producción de forma irreversible. El poder de las herramientas de sistema es proporcional a la responsabilidad de su diseño: cada herramienta que da acceso al sistema operativo, el filesystem, la red o la ejecución de código debe incluir controles de seguridad que operen de forma independiente del razonamiento del LLM.

El **intérprete de código** (code interpreter) es la herramienta de mayor versatilidad: permite al agente escribir y ejecutar código Python para manipular datos, realizar cálculos, generar visualizaciones, o interactuar con librerías que no tienen una herramienta específica disponible. La implementación correcta en producción requiere un **sandbox aislado**: el código generado por el LLM no debe ejecutarse en el mismo proceso que el agente ni en el sistema host. Las plataformas especializadas en sandboxing de código para agentes incluyen **E2B** (e2b.dev), que provee microVMs Linux efímeras con API de Python (`sandbox = e2b.Sandbox(); sandbox.process.start_and_wait("python script.py")`), **Modal** (modal.com), que ofrece contenedores serverless con runtimes preconfigurados, y **Daytona**, orientado a entornos de desarrollo completos. Para implementaciones self-hosted, Docker con restricciones de red (`--network none`) y de filesystem (montaje read-only excepto el directorio de trabajo) es la opción más común. El timeout de ejecución debe ser explícito y proporcionado a la complejidad esperada de los scripts: 30 segundos para scripts de manipulación de datos, 5 minutos para pipelines más complejos.

La **herramienta de filesystem** da al agente acceso a leer y escribir archivos, lo que puede ser necesario para procesar documentos subidos por el usuario, guardar resultados intermedios, o interactuar con datos locales. El control de acceso es crítico: la herramienta debe restringirse a un directorio de trabajo definido y rechazar activamente rutas absolutas, path traversal (`../../../etc/passwd`), y symlinks que apunten fuera del directorio autorizado. Esta validación debe ocurrir en el código Python de la herramienta antes de cualquier operación de filesystem, no en el system prompt del agente. Un agente que confía en que el LLM "nunca pedirá acceso a rutas no autorizadas" está un prompt injection de distancia de un incidente de seguridad.

La **herramienta de shell** es la de mayor superficie de ataque de todas: ejecutar comandos arbitrarios del sistema operativo puede hacer prácticamente cualquier cosa que el usuario del proceso tenga permisos para hacer. Su uso en agentes de producción debería ser la excepción, no la regla, y cuando se justifica, debe implementarse con: una lista blanca de comandos permitidos (verificada antes de la ejecución), timeout estricto (máximo 30 segundos), ejecución como usuario sin privilegios (nunca como root), y logging inmutable de cada comando ejecutado con timestamp, usuario y output. El monto de comandos que pueden ejecutarse con seguridad absoluta en producción es pequeño; para la mayoría de las operaciones de sistema, es mejor diseñar herramientas Python específicas que encapsulen las operaciones necesarias en lugar de exponer un shell genérico.

Las **herramientas de navegador web** permiten al agente interactuar con páginas dinámicas que los scrapers HTTP simples no pueden acceder: formularios, páginas renderizadas por JavaScript, sistemas que requieren autenticación, o interfaces web que no tienen API pública. **Playwright** headless es la herramienta estándar de la industria para este propósito: permite navegar, hacer clic, rellenar formularios y extraer contenido de páginas web con una API Python de alto nivel. Para agentes que solo necesitan acceso a contenido indexable, las **APIs de búsqueda web** como Tavily Search, SerpAPI o la API de Bing son preferibles: devuelven resultados estructurados sin el overhead de renderizar páginas, con latencia de 1-3 segundos en lugar de los 5-15 segundos de una navegación con Playwright. La regla práctica es usar una API de búsqueda web cuando el agente necesita encontrar información, y usar Playwright solo cuando necesita interactuar con la interfaz de una página específica.

## Componentes principales

- **Python REPL / Code interpreter**: ejecución de código generado por el LLM en un sandbox aislado; E2B Sandbox, Modal y Daytona ofrecen entornos cloud con aislamiento de contenedor, timeout configurable y API de alto nivel; para self-hosted, Docker con `--network none` y usuario sin privilegios
- **Herramienta de filesystem**: operaciones de lectura/escritura de archivos; restringida a un directorio de trabajo definido; validar y rechazar path traversal y rutas absolutas en el código Python de la herramienta, no en el prompt del agente
- **Shell tool**: ejecución de comandos del sistema; la herramienta de mayor superficie de ataque; lista blanca de comandos permitidos, timeout máximo de 30 segundos, nunca ejecutar como root; preferir herramientas Python específicas sobre un shell genérico
- **Navegador web (Playwright)**: navegación de páginas dinámicas con JavaScript; bloquear recursos no necesarios (imágenes, fuentes, media) para reducir latencia; timeout de 10-30 segundos por página; preferir APIs de búsqueda cuando solo se necesita contenido indexado
- **APIs de búsqueda web (Tavily, SerpAPI, Bing)**: resultados estructurados sin overhead de renderizado; latencia de 1-3 segundos; opción preferida cuando el agente necesita información actualizada sin interacción con la interfaz de una página específica

> **Nota del Arquitecto**: La regla que más me ha servido en el diseño de herramientas de sistema es esta: cualquier herramienta que, si es comprometida por prompt injection, puede causar daño irreversible necesita una capa adicional de protección independiente del LLM. Esa protección puede ser confirmación humana explícita, verificación programática de los argumentos antes de ejecutar, o restricción del scope de la herramienta a un nivel donde el daño máximo posible sea aceptable. Diseñar esta restricción en la implementación, no en el prompt.

## Buena práctica

Aplicar el principio de mínimo privilegio a cada herramienta de sistema: si el agente solo necesita leer archivos CSV de un directorio específico, la herramienta debe rechazar cualquier operación fuera de ese scope antes de enviarse al ejecutor, no después. La validación de scope debe ser parte del código de la herramienta, no una restricción expresada solo en el system prompt del agente.
