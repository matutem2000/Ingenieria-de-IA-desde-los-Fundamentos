## Comunicación entre agentes: mensajes, handoffs y contratos de interfaz

La comunicación entre agentes es el talón de Aquiles más frecuente de los sistemas multiagente en producción. Mientras que la comunicación entre microservicios tiene décadas de patrones establecidos —REST, gRPC, mensajería asíncrona con Kafka—, la comunicación entre agentes de LLM enfrenta un desafío adicional: el receptor es un sistema probabilístico que interpreta el mensaje recibido en lenguaje natural, y una descripción ambigua o un formato inconsistente puede producir una interpretación diferente a la intención del emisor. Este problema es invisible en los demos donde el agente produce exactamente el texto que el desarrollador esperaba; se manifiesta en producción cuando el output del agente A se convierte en el input del agente B en condiciones que el desarrollador no anticipó durante el desarrollo.

La solución fundamental es tratar la comunicación entre agentes con el mismo rigor formal que la comunicación entre servicios: **contratos de interfaz** que especifican exactamente el formato de input y output de cada agente. En Python, esto se implementa con modelos Pydantic que definen la estructura de los mensajes que cada agente produce y consume. Un agente de análisis de sentimientos que recibe `TextAnalysisRequest` (texto a analizar, idioma, dominio) y produce `SentimentAnalysisResult` (score de sentimiento, entidades mencionadas, resumen) tiene una interfaz tan bien definida como una función de una librería pública. Pydantic AI hace esto nativo; en LangGraph y AutoGen requiere disciplina de diseño del equipo.

Los **mensajes estructurados** son la unidad de comunicación entre agentes. Un mensaje bien diseñado para sistemas multiagente incluye: el resultado principal del procesamiento del agente emisor, metadata de ejecución (`agent_id`, `task_id`, `timestamp`), un indicador de confianza (`confidence_score` entre 0 y 1), cualquier error parcial o advertencia (`warnings`), y estadísticas de consumo de recursos (`tokens_used`, `latency_ms`). Esta metadata permite al agente receptor o al orquestador tomar decisiones informadas: si el confidence_score es menor de 0.6, quizás el resultado debe ser revisado por otro agente antes de usarse; si `tokens_used` supera un umbral, quizás la subtarea fue más compleja de lo esperado y el plan debe ajustarse.

El **patrón de handoff** de Anthropic es el mecanismo más documentado para la transferencia de control entre agentes con contexto completo. En el flujo de Claude, un agente puede devolver una herramienta `handoff_to_agent(agent_id, context)` que transfiere el control al agente receptor junto con el historial de conversación completo hasta ese punto. El agente receptor no empieza desde cero: hereda el contexto acumulado del agente emisor, incluyendo las observaciones recopiladas, las decisiones tomadas, y el progreso hacia el objetivo. Este patrón garantiza continuidad de contexto pero puede producir contextos muy largos si el historial acumulado antes del handoff es extensivo.

El debate entre **message passing** y **shared state** como paradigmas de comunicación refleja un trade-off fundamental. Message passing —cada agente produce mensajes explícitos que se enrutan a los receptores apropiados— es más desacoplado y escalable: los agentes son independientes entre sí y pueden evolucionar sin afectar a los demás mientras respeten los contratos de interfaz. Shared state —un estado global accesible por todos los agentes, como el `StateGraph` de LangGraph— es más conveniente para agentes que colaboran estrechamente sobre el mismo problema: cualquier agente puede leer el estado actual completo sin esperar mensajes explícitos. Los sistemas de producción complejos frecuentemente combinan ambos: estado compartido para el contexto de la tarea actual, y mensajes explícitos para la transferencia de resultados entre etapas.

La **serialización** de los mensajes es un requisito operativo que se ignora en desarrollo local y produce bugs en producción. Los mensajes entre agentes que cruzan boundaries de proceso —diferentes workers, diferentes servicios— deben ser serializables a JSON: nunca usar `pickle` para serializar mensajes inter-agente porque `pickle` es inseguro (puede ejecutar código arbitrario durante la deserialización), no es compatible entre versiones de Python, y no es legible para debugging. Los modelos Pydantic se serializan trivialmente a JSON con `.model_dump_json()` y se deserializan con `Model.model_validate_json()`.

## Aspectos técnicos

- **Contratos de interfaz (Pydantic schemas)**: definir modelos de input y output de cada agente como clases Pydantic; validar el input antes de enviarlo y el output antes de procesarlo; la interfaz del agente es tan explícita como la de una función pública en una librería
- **Mensajes estructurados con metadata**: incluir resultado principal + `agent_id`, `task_id`, `confidence_score`, `warnings`, `tokens_used`; la metadata permite al orquestador tomar decisiones informadas sobre cómo proceder con el resultado
- **Handoff pattern**: transferencia de control entre agentes con el historial de contexto completo acumulado; garantiza continuidad pero puede producir contextos extensos si el historial previo al handoff es largo
- **Message passing vs shared state**: message passing para agentes desacoplados que pueden evolucionar independientemente; shared state (LangGraph StateGraph) para agentes que colaboran estrechamente y necesitan acceso al estado completo de la tarea
- **Serialización JSON**: todos los mensajes que cruzan boundaries de proceso deben ser JSON-serializable; nunca usar pickle; Pydantic provee serialización/deserialización JSON nativa con validación de tipos

## Principio rector

Los contratos de interfaz entre agentes son tan importantes como los contratos de API entre microservicios: la informalidad en la comunicación inter-agente produce bugs que son difíciles de atribuir a un agente específico porque el error es una propiedad emergente de la interacción, no de ningún agente individual.
