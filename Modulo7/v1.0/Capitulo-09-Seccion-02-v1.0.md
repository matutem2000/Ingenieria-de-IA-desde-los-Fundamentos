# Módulo 7 – Capítulo 09 – Sección 02

## Gestión del estado entre sesiones: persistencia y recuperación de contexto

Un agente en producción puede ser interrumpido en cualquier punto de su ejecución por razones que no tienen nada que ver con el agente en sí: el servidor puede ser reemplazado durante un rolling deployment mientras la tarea está en curso; el proceso puede terminar inesperadamente por agotamiento de memoria; el usuario puede cerrar la conexión en el paso 15 de 20, con intención de retomar la tarea más tarde; un operador puede pausar la ejecución para insertar una revisión humana. En todos estos casos, la pregunta crítica es: ¿el sistema puede reanudar desde donde quedó, o debe reiniciar desde cero? Para tareas cortas de segundos, el reinicio es aceptable. Para tareas de varios minutos o decenas de pasos, el reinicio completo ante cualquier interrupción no es una propiedad aceptable de un sistema de producción: desperdicia recursos, degrada la experiencia del usuario, y en algunos casos —tareas con efectos secundarios irreversibles ya ejecutados— puede ser directamente incorrecto reejecutar desde el principio.

El **checkpointing** resuelve este problema al serializar periódicamente el estado completo del agente a almacenamiento durable, de forma que una ejecución interrumpida pueda reanudarse desde el último checkpoint guardado en lugar de desde el inicio. En LangGraph, el mecanismo de checkpointing se configura al compilar el `StateGraph`: `graph = workflow.compile(checkpointer=PostgresSaver.from_conn_string(db_url))`. Con este checkpointer configurado, LangGraph serializa automáticamente el estado completo del grafo —el `AgentState` con todas sus variables, el historial de mensajes, los nodos ya ejecutados— a PostgreSQL después de completar cada nodo. Si la ejecución se interrumpe en cualquier punto, reanudar es tan simple como llamar `graph.invoke(None, config={"configurable": {"thread_id": "session-abc-123"}})`: LangGraph recupera el último estado guardado para ese `thread_id` y continúa desde el nodo siguiente al último completado, sin re-ejecutar los nodos ya completados.

El **granulo del checkpointing** determina cuánto trabajo puede perderse en el peor caso: con checkpointing por nodo —el comportamiento default de LangGraph— el agente nunca pierde más de un nodo de trabajo ante una interrupción, porque el estado se persiste después de completar cada nodo. Un granulo más grueso (p.ej., guardar el estado cada 5 nodos) reduce el overhead de escrituras a base de datos pero aumenta el trabajo que puede perderse. Para tareas largas, el checkpointing por nodo es el tradeoff correcto.

El **`AgentState` serializable** es un requisito de diseño que frecuentemente se ignora hasta que causa problemas. El estado que LangGraph serializa a PostgreSQL debe ser completamente representable en JSON o en tipos nativos de la base de datos: listas, diccionarios, strings, números. Objetos Python que no son serializables —conexiones de base de datos, file handles abiertos, objetos de configuración con estado, referencias a funciones— no pueden incluirse en el `AgentState` del checkpointer. La solución es separar el estado serializable del contexto de ejecución no serializable: el estado incluye los datos del agente (mensajes, observaciones, variables de tarea), mientras que el contexto de ejecución (conexiones de herramientas, credenciales) se reconstruye al reanudar la sesión a partir de la configuración del sistema, no del checkpoint.

El **`thread_id` como identificador de sesión** es la clave que une cada request de un usuario con su estado persistido. Al reanudar una sesión, el cliente proporciona el `thread_id` de la sesión original; LangGraph recupera el estado asociado a ese ID del checkpointer y continúa la ejecución. Este mecanismo permite múltiples sesiones concurrentes del mismo agente sin interferencia entre ellas: cada sesión tiene su propio `thread_id` y su propio espacio de estado en el checkpointer. La gestión de `thread_id` es responsabilidad del cliente o de la capa de API del sistema: puede usarse el ID de sesión del usuario, un UUID generado al inicio de cada tarea, o el ID de un ticket de soporte si el agente opera en ese contexto.

La **retención y limpieza de checkpoints** es una consideración operativa que los equipos frecuentemente posponen hasta que el almacenamiento crece de forma inesperada. Los checkpoints de sesiones ya completadas no son necesarios para la ejecución futura y pueden purgarse con un TTL corto (7 días). Las sesiones pausadas esperando revisión humana deben retenerse más tiempo (30 días es razonable para la mayoría de los contextos). Las sesiones activas en curso nunca deben purgarse automáticamente. Implementar un job de limpieza periódico que elimine checkpoints según su estado y antigüedad previene el crecimiento indefinido del almacenamiento sin impactar la funcionalidad.

## Aspectos técnicos

- **Checkpointing por nodo en LangGraph**: `compile(checkpointer=PostgresSaver(...))` serializa el `AgentState` completo a PostgreSQL después de cada nodo; `graph.invoke(None, config={"configurable": {"thread_id": "..."}})` reanuda desde el último estado guardado para ese thread_id
- **`MemorySaver` vs `SqliteSaver` vs `PostgresSaver`**: MemorySaver es en memoria (solo para tests, no sobrevive reinicios), SqliteSaver es en archivo local (adecuado para desarrollo y producción de baja escala), PostgresSaver es en PostgreSQL (producción de alta escala, soporta múltiples instancias concurrentes)
- **Estado serializable**: el AgentState debe contener solo tipos JSON-serializables; objetos no serializables (conexiones DB, file handles) se excluyen del estado y se reconstruyen al reanudar a partir de la configuración del sistema
- **Reanudación parcial correcta**: al reanudar, el agente identifica el último nodo completado via el checkpoint y continúa desde el nodo siguiente; no re-ejecuta nodos ya completados ni repite efectos secundarios (emails enviados, datos modificados) que ya ocurrieron en la ejecución anterior
- **Retención de checkpoints**: TTL diferenciado según estado de la sesión: 7 días para sesiones completadas (no necesarias para reanudación), 30 días para sesiones pausadas esperando revisión humana, indefinido para sesiones activas; job de limpieza periódico (cron diario) que aplica el TTL

> **Nota del Arquitecto**: El error de diseño más costoso en producción es asumir que el checkpointing es solo para alta disponibilidad y omitirlo en deployments "pequeños". El checkpointing también es necesario para el HITL: cuando el agente hace una pausa para solicitar revisión humana, el estado debe persistirse de forma que la aprobación o rechazo humano ocurra en una request completamente diferente, potencialmente horas después. Sin checkpointing, el HITL es arquitectónicamente imposible de implementar correctamente en producción.

## Para recordar

El checkpointing no es un lujo de sistemas de alta disponibilidad; es un requisito de correctitud para cualquier agente que ejecuta tareas largas o que implementa HITL. Una tarea de 20 minutos que falla en el minuto 18 sin checkpointing reinicia completamente; con checkpointing, reanuda desde el paso 17 de 20 y termina en 2 minutos adicionales.
