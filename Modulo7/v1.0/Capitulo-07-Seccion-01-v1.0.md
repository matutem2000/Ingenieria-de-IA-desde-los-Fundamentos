# Módulo 7 – Capítulo 07 – Sección 01

## El desafío de testear agentes: no-determinismo, cadenas largas y efectos secundarios

Este capítulo aborda el testing de agentes durante el desarrollo y en pipelines de CI/CD: cómo verificar que el comportamiento del agente es correcto antes de desplegarlo en producción, utilizando entornos controlados, inputs sintéticos y criterios de validación formalizados. Esta delimitación es importante porque existe un capítulo paralelo —el Capítulo 10— que aborda la evaluación continua en producción: métricas sobre tráfico real, ciclos de mejora basados en fallos reales, y comparación entre versiones sobre distribuciones de casos de uso auténticos. El testing del Capítulo 07 y la evaluación del Capítulo 10 son complementarios: el primero verifica correctitud antes del deploy, el segundo mide efectividad después del deploy.

Testear agentes de IA presenta desafíos cualitativamente distintos a los del testing de software tradicional. Las técnicas estándar de unit testing —dado un input X, el output es siempre Y— fallan ante tres propiedades de los sistemas agénticos. El **no-determinismo**: con temperatura mayor que cero, el mismo input puede producir diferentes trayectorias de acciones en diferentes ejecuciones, haciendo imposible la comparación exacta de outputs. Las **cadenas largas**: el espacio de estados intermedios crece exponencialmente con el número de pasos; con N herramientas y M pasos máximos, el número de trayectorias posibles es O(N^M), haciendo imposible la cobertura exhaustiva. Los **efectos secundarios reales**: el agente ejecuta acciones con consecuencias en el mundo —escritura en bases de datos, envío de emails, llamadas a APIs de pago— que no pueden "deshacerse" como se deshace una mutación de variable en un test.

El cambio de paradigma necesario para testear agentes correctamente es pasar de "¿produce el output correcto?" a "¿se comporta correctamente dado el contexto?". Esta reformulación tiene implicaciones prácticas concretas: en lugar de verificar que el agente produce exactamente el string X, se verifica que el agente usó la herramienta correcta, llegó al resultado correcto, no ejecutó acciones prohibidas, y se comportó de forma razonable ante adversidad. Esta evaluación de comportamiento es más tolerante al no-determinismo porque define propiedades que se pueden verificar independientemente de la trayectoria específica tomada para satisfacerlas.

El **no-determinismo controlado** es la primera herramienta práctica: configurar `temperature=0` durante los tests para reducir la variabilidad y hacer los resultados más reproducibles. Temperatura cero no elimina el no-determinismo completamente —el modelo puede cambiar entre versiones de la API, y diferentes versiones del mismo modelo pueden producir outputs diferentes— pero lo reduce a niveles manejables para comparaciones sistemáticas. Los tests con temperatura=0 son deterministas dado un modelo específico y una versión específica de la API; esta garantía es suficiente para CI/CD donde el modelo y la versión se fijan explícitamente.

El **mocking de herramientas** es el segundo requisito fundamental. Las herramientas con efectos secundarios reales —escritura en DB, envío de emails, llamadas a APIs externas— deben ser reemplazadas por mocks que registran las invocaciones sin ejecutarlas. En Python, `unittest.mock.patch` o `MagicMock` permiten interceptar las llamadas a herramientas, verificar que fueron invocadas con los argumentos correctos, y devolver respuestas predefinidas que simulan el comportamiento real. Los tests con herramientas mockeadas son rápidos (sin latencia de red), aislados (sin efectos en sistemas externos), y repetibles (el mock siempre devuelve la misma respuesta configurada).

La **idempotencia de tests** garantiza que los tests pueden ejecutarse múltiples veces en la misma suite sin efectos acumulados. El entorno de test debe resetearse a un estado limpio antes de cada ejecución: bases de datos de test en estado conocido, mocks reseteados, contadores de iteración en cero. En LangGraph, usar checkpointers de test (`MemorySaver` en lugar de `PostgresSaver`) garantiza que el estado del agente no persiste entre ejecuciones de test.

## Conceptos clave

- **Alcance de este capítulo**: testing en desarrollo y CI/CD con inputs sintéticos y entornos controlados, para verificar correctitud antes del deploy; distinto de la evaluación en producción (Capítulo 10) que mide efectividad sobre tráfico real
- **No-determinismo controlado**: `temperature=0` para reproducibilidad en tests; modelo y versión de API fijados explícitamente en CI/CD; elimina la variabilidad gestionable aunque no la variabilidad entre versiones del modelo
- **Evaluación de comportamiento**: verificar propiedades del comportamiento del agente (¿usó la herramienta correcta? ¿evitó acciones prohibidas?) en lugar de verificar outputs exactos (¿produjo exactamente este string?)
- **Mocking de herramientas**: reemplazar herramientas con efectos reales por mocks que registran invocaciones y devuelven respuestas predefinidas; prerequisito para tests rápidos, aislados y repetibles
- **Idempotencia de tests**: el entorno de test debe resetearse antes de cada ejecución; checkpointers de memoria (no de base de datos) para el estado del agente en tests; bases de datos de test en estado conocido al inicio de cada test

## Principio rector

Testear agentes requiere evaluar comportamiento (¿actuó el agente correctamente dadas las circunstancias?) en lugar de verificar outputs (¿produjo exactamente este string?). Este cambio de perspectiva es la diferencia entre encontrar bugs de comportamiento agéntico que importan en producción y perseguir diferencias de wording que no afectan la funcionalidad.

La sección siguiente examina el primer nivel de testing —el más tractable y más frecuentemente omitido—: el unit testing de herramientas individuales, que puede ejecutarse sin LLM y que detecta los bugs más comunes antes de que se enmasqaren en la complejidad del ciclo agéntico completo.
