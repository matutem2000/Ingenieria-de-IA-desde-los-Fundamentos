# Módulo 8 – Capítulo 08 – Sección 04

## Prompt caching en servidores locales: reutilización del KV cache entre peticiones

Flash Attention reduce el costo de computar el KV cache una vez para un prompt dado. El prefix caching elimina la necesidad de computar ese KV cache en absoluto cuando el mismo prompt ya fue procesado por una petición anterior: reutiliza los bloques de KV cache almacenados de peticiones previas que comparten el mismo prefijo, reduciendo el TTFT en el porcentaje del contexto que se puede cachear.

El caso de uso más directo y de mayor impacto es la aplicación multi-usuario con un system prompt estático largo. Considera un asistente corporativo donde el system prompt de 1.500 tokens describe las políticas de la empresa, los productos disponibles, el tono de comunicación y las restricciones de respuesta. Sin prefix caching, cada una de las 10.000 peticiones diarias del asistente debe procesar esos 1.500 tokens de system prompt en la fase de prefill, incluso cuando el contenido es idéntico en todas las peticiones. Con prefix caching activo en vLLM, la primera petición del día computa el KV cache del system prompt y lo almacena en el pool de PagedAttention. Todas las peticiones posteriores que comienzan con ese mismo system prompt detectan el cache hit y saltan directamente al prefill de los tokens exclusivos de cada petición (la pregunta del usuario), eliminando el 75% o más del trabajo de prefill si el system prompt representa esa fracción del prompt total.

vLLM implementa prefix caching con el flag `--enable-prefix-caching`. El mecanismo interno usa un **Radix Tree** para gestionar los bloques de KV cache compartibles: cada nodo del árbol representa un bloque de 16 tokens; peticiones con el mismo prefijo comparten los mismos nodos hasta el punto donde sus contenidos divergen. El cache hit solo ocurre cuando los primeros K tokens de la nueva petición son **byte-a-byte idénticos** a los de una petición previa, donde K es múltiplo del block_size de 16 tokens. Una diferencia de un espacio, una mayúscula distinta o un carácter de puntuación diferente en el system prompt produce un miss completo. Por esta razón, en aplicaciones con prefix caching activo, el system prompt debe ser gestionado como un artefacto versionado: una cadena exacta con su codificación UTF-8, no generada dinámicamente en cada petición.

El **cache warming** al inicio del servidor es una práctica que amplifica el beneficio del prefix caching en producción. Al iniciar el servidor de vLLM, enviar inmediatamente una petición de warmup con el system prompt completo pre-computa y almacena el KV cache de ese prefijo antes de que lleguen requests reales de usuarios. Sin warmup, las primeras N peticiones del día —donde N es el número de peticiones necesarias para llenar la capacidad del cache pool con el prefijo compartido— pagan el costo de prefill completo. Con warmup, la primera petición real ya tiene el cache del system prompt disponible.

llama.cpp también soporta un forma de caching de contexto orientada a sesiones: `--save-cache-kv ruta/cache.bin` serializa el estado del KV cache a disco después de procesar un prompt largo; `--load-cache-kv ruta/cache.bin` lo restaura en la siguiente sesión. Este mecanismo es especialmente útil para pipelines RAG donde el contexto de recuperación —10-50 documentos recuperados, posiblemente miles de tokens— se actualiza infrecuentemente (cada hora, cada día) pero se usa en todas las peticiones de ese periodo. Guardar el KV cache del contexto de recuperación evita recomputarlo en cada petición, reduciendo el TTFT de los segundos que podría tomar prefill de 4K-8K tokens de documentos a los milisegundos del decode de los tokens de la query.

## Implementaciones y consideraciones del prefix caching

- **Requisitos para el cache hit:** los primeros K tokens deben ser byte-a-byte idénticos, con K múltiplo del block_size de 16; cualquier diferencia (espacio, capitalización) produce miss completo.
- **Radix Tree de vLLM:** gestiona bloques de KV cache compartibles entre requests; compartición eficiente de prefijos de distintas longitudes; liberación de nodos cuando las requests completan.
- **LLM caching a nivel de aplicación:** semantic cache con Redis o GPTCache para queries semánticamente similares; complementario al prefix caching; opera a nivel de respuesta completa, no de KV cache.
- **Cache warming:** enviar request de warmup al iniciar el servidor; pre-computa el KV del system prompt antes de recibir requests reales; especialmente importante después de reinicios planificados.
- **llama.cpp KV cache persistence:** `--save-cache-kv` / `--load-cache-kv` para pipelines RAG con contextos de recuperación que se actualizan infrecuentemente.

> **Nota del Arquitecto:** El prefix caching es la optimización más fácil de implementar con el mayor retorno de inversión para aplicaciones enterprise: activar `--enable-prefix-caching` en vLLM y asegurar que el system prompt sea idéntico entre peticiones (sin timestamps, sin IDs de sesión dinámicos en el system prompt) puede reducir el costo de prefill en un 70-80% para aplicaciones donde el system prompt representa más del 50% del prompt total. El esfuerzo de implementación es literalmente un flag en el comando de inicio del servidor.
