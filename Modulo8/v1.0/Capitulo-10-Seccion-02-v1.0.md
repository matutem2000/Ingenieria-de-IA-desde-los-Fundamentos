# Módulo 8 – Capítulo 10 – Sección 02

## Patrón router: clasificar peticiones y dirigirlas al modelo correcto según complejidad

El patrón router —también denominado LLM routing o model routing— es la pieza arquitectónica central de cualquier sistema híbrido: una capa de clasificación intermedia que analiza cada petición entrante y la dirige al modelo más apropiado según criterios de complejidad, sensibilidad de datos, costo proyectado o latencia aceptable, sin que el cliente que realiza la petición necesite saber qué modelo la procesará. Desde la perspectiva del cliente, existe una única API OpenAI-compatible; desde dentro del sistema, esa API es una función de routing que optimiza continuamente la distribución de carga entre modelos locales y de nube basándose en políticas configurables. El router es la abstracción que convierte la decisión estática "¿local o nube?" en una decisión dinámica y por-petición que se toma en 5-20 ms de overhead adicional.

La implementación más simple del router usa heurísticas determinísticas basadas en características estructurales de la petición: longitud del prompt (prompts cortos a modelo local, prompts mayores de 4K tokens al modelo de nube con mayor ventana de contexto), tipo de endpoint (embeddings y clasificaciones siempre local, generación de código complejo siempre nube), y presencia de PII detectada por Presidio (cualquier petición con PII activa el routing a modelo local dentro del perímetro, independientemente del resto de criterios). Las heurísticas son rápidas —no añaden latencia de modelo al path de la petición— pero tienen precisión limitada: no pueden diferenciar entre una pregunta corta trivial y una pregunta corta que requiere razonamiento profundo.

El siguiente nivel de sofisticación es un **clasificador de complejidad entrenado**: un modelo BERT o DeBERTa fine-tuneado en un dataset de pares `(prompt, complejidad_etiquetada)` que predice en una categoría de dificultad (simple / intermedia / compleja) con una latencia de inferencia de 10-30 ms en CPU. RouteLLM, el proyecto open source de LMSYS, va un paso más allá: entrena un clasificador basado en matrices de preferencia humana que predice si dos modelos producirán respuestas de calidad equivalente para una petición dada, y solo enruta a la nube cuando predice una diferencia de calidad significativa. En sus benchmarks, RouteLLM puede mantener el 95% de la calidad de GPT-4o enrutando solo el 28% del tráfico a la nube —el 72% restante se sirve localmente con un modelo menor sin degradación perceptible por el usuario.

La **API unificada** es el requisito de diseño que hace que el router sea transparente: el router implementa exactamente el mismo contrato de interfaz que sus backends (el mismo schema de OpenAI Chat Completions API, los mismos campos en la respuesta, el mismo comportamiento de streaming). Los clientes no necesitan modificarse para soportar el routing; los headers de respuesta pueden opcionalmente incluir metadatos del modelo usado (`X-Model-Used: llama-3.1-8b-instruct`) para debugging y telemetría sin afectar la compatibilidad. La lógica de routing puede actualizarse sin modificar ningún cliente.

El router requiere su propio **ciclo de evaluación y mejora continua**. La política de routing (qué clasificador usar, qué umbrales de complejidad, qué modelos en cada capa) es un hiperparámetro del sistema que se optimiza basado en datos de producción: logs de feedback de usuarios (thumbs up/down), métricas de re-intentos (que señalan respuestas insatisfactorias), y el análisis de las peticiones que fueron roteadas a la nube y podrían haberse servido localmente con calidad equivalente. Un AB test que compara dos políticas de routing diferentes —umbral de complejidad más conservador vs más agresivo— con métricas de calidad y costo como variables de resultado es el método correcto para optimizar el punto de equilibrio.

## Componentes de implementación del patrón router

- **Clasificador de complejidad:** desde heurísticas de longitud y palabras clave hasta modelos de clasificación fine-tuneados (BERT/DeBERTa); las heurísticas son más rápidas (0 ms overhead de modelo) pero menos precisas; el clasificador entrenado añade 10-30 ms pero permite routing semántico.
- **Criterios multidimensionales:** complejidad de la tarea + presencia de PII + longitud de contexto + tipo de usuario (plan premium / estándar) + throughput actual del modelo local; el router combina estos criterios en una función de scoring configurable.
- **Fallback implícito:** si el modelo local produce error, timeout o respuesta de baja calidad, el router reencamina automáticamente a la nube sin intervención manual; el fallback es el safety net que hace que el sistema sea resiliente a degradaciones del modelo local.
- **API unificada OpenAI-compatible:** el cliente ve una única API; el router implementa el mismo schema que sus backends; los metadatos del modelo usado se exponen en headers opcionales para debugging y telemetría.
- **AB testing de políticas de routing:** comparar umbrales distintos con métricas de calidad y costo como variables de resultado; la política de routing es un hiperparámetro que requiere tuning basado en datos reales de producción.

> **Nota del Arquitecto:** El beneficio económico del router es no lineal respecto al volumen: con 1.000 peticiones al día el overhead de implementación del router no se amortiza; con 100.000 peticiones al día, rerouting del 70-80% a modelos locales puede reducir la factura de inferencia en nube en un 60-70% sin degradación perceptible de la calidad media. Calcular el volumen de break-even antes de invertir en el router.

La clave de la eficiencia económica de la arquitectura híbrida es que el router aprende con el tiempo: a medida que se acumulan datos de producción sobre qué peticiones se sirven bien localmente, la política de routing se afina y el porcentaje de tráfico local aumenta. El sistema se vuelve más eficiente con el uso, no a pesar del cambio sino como resultado directo de él.
