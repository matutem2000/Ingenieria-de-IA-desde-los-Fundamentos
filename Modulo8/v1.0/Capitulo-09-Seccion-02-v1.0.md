# Módulo 8 – Capítulo 09 – Sección 02

## Versionado de modelos: checkpoints, adaptadores LoRA y snapshots

El versionado de artefactos de modelo presenta complejidades que no existen en el versionado de software convencional: los archivos de pesos son de 2-80 GB, las diferencias entre versiones no son diffables con herramientas de texto como `git diff`, y el "artefacto" a versionar puede ser el modelo base completo, un adaptador LoRA de 50-300 MB, o la combinación de ambos fusionada en un snapshot. Tratar los tres con la misma estrategia de versionado produce confusion; cada uno tiene su estrategia óptima.

Los **checkpoints de entrenamiento** son capturas del estado completo del proceso de fine-tuning en un momento dado: incluyen los pesos del adaptador LoRA, el estado del optimizador Adam (los primeros y segundos momentos por parámetro), el step actual y la posición en el dataset. Su función es permitir reanudar el entrenamiento desde ese punto exacto si el proceso se interrumpe —por un fallo de hardware, una instancia Spot interrumpida o simplemente para evaluar el modelo a distintos puntos del entrenamiento. Hugging Face `Trainer` con `save_steps=100` guarda un checkpoint cada 100 pasos; `save_total_limit=3` mantiene solo los 3 más recientes para no saturar el almacenamiento. Los checkpoints son 2-3x más grandes que el adaptador LoRA solo (por el estado del optimizador incluido) y no deben confundirse con el artefacto de distribución final.

Los **adaptadores LoRA** son el artefacto de versionado más compacto y versátil: un archivo SafeTensors de 50-300 MB que contiene únicamente los pesos aprendidos por las matrices A y B de todas las capas de atención. Al ser independientes del modelo base, se versionan separadamente: el modelo base Llama 3.1 8B ocupa 16 GB y es idéntico para todos los proyectos que lo usan; el adaptador LoRA de 150 MB es específico de cada tarea y puede iterarse y versionarse frecuentemente sin replicar el modelo base. La convención de naming en Hugging Face Hub para adaptadores LoRA es `{org}/{modelo-base}-{tarea}-{versión}`, por ejemplo `acme/llama3-soporte-tecnico-v2`, con el modelo base referenciado en la `model_card` y el `adapter_config.json`. Descargar y usar el adaptador requiere solo el adaptador y el modelo base original: `PeftModel.from_pretrained(base_model, "acme/llama3-soporte-tecnico-v2")`.

Los **snapshots de producción** son modelos fusionados listos para despliegue: el resultado de `model.merge_and_unload()` que funde el adaptador LoRA con el modelo base en un único conjunto de pesos. Los snapshots representan el artefacto de producción final que se carga directamente en vLLM o se convierte a GGUF para distribución con Ollama. Se versionan con tags semánticos en el registry (`v1.0`, `v1.1-hotfix`, `v2.0`) y se almacenan en el object storage del registry como archivos SafeTensors. Solo los snapshots que han pasado todos los gates de validación (golden dataset + load test) se promueven a "Production" en el sistema de stages del registry; los que no pasan se marcan como "Rejected" con las razones del fallo documentadas.

La **metadata de linaje** es el componente que conecta el snapshot de producción con todos los artefactos que lo producen. Cada versión del modelo en el registry debe incluir: SHA del repositorio Git del código de entrenamiento en el commit exacto usado para ese run, SHA del archivo de dataset (o la versión del dataset en Hugging Face Datasets si es público), versión exacta del modelo base (incluyendo el commit SHA del repositorio de Hugging Face del modelo base), hiperparámetros completos del entrenamiento (rank de LoRA, learning rate, número de epochs), y métricas de evaluación en el golden dataset con el score obtenido. Esta información permite reconstruir completamente cómo se llegó a cada versión y es el fundamento del sistema de ML auditable.

## Estrategias de versionado por tipo de artefacto

- **Checkpoints:** guardar cada 100-500 steps; retener solo los N mejores según la métrica de validación; incluyen estado del optimizador (son 2-3x más grandes que el adaptador solo); para reanudación de entrenamiento, no para distribución.
- **Adaptadores LoRA:** convención `{org}/{base_model}-{tarea}-{versión}` en Hugging Face Hub; metadata con SHA del modelo base, dataset y hiperparámetros; versionado independiente del modelo base.
- **Snapshots de producción:** tags semánticos (`v1.0`, `v2.0`); solo snapshots que pasan los gates de validación; almacenados en object storage del registry como SafeTensors o GGUF.
- **Metadata de linaje:** SHA del código de entrenamiento, SHA del dataset, versión del modelo base, hiperparámetros, métricas en el golden set; permite reconstruir el historial completo de cada versión.
- **Git para configuraciones:** Modelfiles de Ollama, configs de Axolotl, scripts de evaluación y definiciones de datasets se versionan en Git normal; los archivos de pesos (grandes) en Git-LFS o en el registry de modelos.

> **Nota del Arquitecto:** La regla mínima de versionado de modelos es versionar siempre la tupla (modelo base + adaptador + dataset) como una unidad. Si cambias cualquiera de los tres —nuevo modelo base, nuevos datos de entrenamiento, mismos datos pero procesados de forma diferente— el resultado es una nueva versión, no una actualización de la versión anterior. Esta granularidad en el versionado es lo que permite comparar versiones de forma significativa y hacer rollback con confianza.
