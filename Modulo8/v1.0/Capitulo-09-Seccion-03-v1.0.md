# Módulo 8 – Capítulo 09 – Sección 03

## Validación antes del despliegue: benchmarks de calidad y de performance

Un nuevo modelo nunca se despliega directamente en producción sin pasar por un proceso de validación que verifica dos dimensiones independientes: la calidad funcional (¿el modelo genera las respuestas correctas?) y el rendimiento de infraestructura (¿el modelo cumple los SLOs de latencia y throughput bajo la carga de producción?). La validación de cualquiera de las dos dimensiones por separado es insuficiente: un modelo con calidad perfecta que no cumple los SLOs de latencia destruye la experiencia de usuario; un modelo que cumple los SLOs de latencia pero tiene regresión en calidad introduce errores silenciosos en el producto que pueden tardar días en detectarse.

El **golden dataset** es el componente central de la validación de calidad. Este conjunto de 100-1.000 ejemplos representativos de los casos de uso del producto —construido y mantenido con el mismo cuidado que los tests de integración de software— se evalúa en cada versión candidata del modelo antes del despliegue. Los ejemplos cubren los flujos más críticos del producto, los edge cases conocidos que han producido fallos en el pasado, y las categorías de uso más frecuentes según los logs de producción. Las métricas de evaluación varían según la tarea: exact match para respuestas de opción múltiple o clasificación, ROUGE-L o BERTScore para resúmenes, y LLM-as-judge para respuestas de forma libre donde la calidad no puede medirse con métricas automáticas. El score en el golden dataset es el gate de calidad: si la nueva versión del modelo tiene una degradación superior al umbral definido por el equipo de producto (típicamente 2-5%) respecto a la versión actual de producción, el despliegue se bloquea automáticamente.

La **evaluación LLM-as-judge** complementa las métricas automáticas para respuestas abiertas. El proceso usa un modelo más potente (GPT-4o, Claude Opus) como juez que evalúa pares `(input, expected_output, actual_output)` con un prompt de evaluación estructurado que define los criterios de calidad relevantes para la tarea (precisión, completitud, formato, tono) y produce un score numérico entre 0 y 1 con una justificación textual. Este proceso es automatizable en CI/CD con un umbral de score mínimo configurado: el pipeline de GitHub Actions puede ejecutar la evaluación LLM-as-judge en el golden dataset como parte del proceso de PR del adaptador LoRA o del snapshot de producción, fallando el PR si el score promedio cae del umbral. La clave es que el prompt de evaluación del juez sea específico para la tarea y validado manualmente antes de automatizarlo.

Los **benchmarks de rendimiento** pre-despliegue deben replicar el patrón de tráfico real de producción: longitud de prompts, distribución de output tokens, y número de requests concurrentes basados en los percentiles reales de producción, no en los mejores casos. El script `benchmark_throughput.py` de vLLM permite configurar estos parámetros y genera un reporte de TTFT P50/P95/P99 y throughput bajo distintos niveles de carga. Este benchmark debe ejecutarse en un entorno de staging con **hardware idéntico a producción** durante al menos 30 minutos bajo la carga P95 esperada: los problemas de degradación de rendimiento bajo carga sostenida (memory leaks, fragmentación del KV cache, scheduling degradation) solo aparecen en runs de duración suficiente.

Los **smoke tests de integración** completan el conjunto de validaciones pre-despliegue: 5-10 requests de ejemplo que cubren los flujos más críticos del producto, ejecutadas contra el modelo candidato en staging, verificando que el modelo responde al formato correcto de request, que el streaming funciona, que los stop tokens se procesan correctamente y que el model name en la respuesta es el esperado. Son la primera línea de defensa: si los smoke tests fallan, no hay razón para ejecutar el golden dataset completo.

## Componentes del pipeline de validación previa al despliegue

- **Golden dataset:** 100-1.000 ejemplos representativos de casos de uso reales; métricas exactas o LLM-as-judge según la tarea; gate de calidad con umbral de degradación máxima aceptable.
- **LLM-as-judge evaluation:** modelo más potente como árbitro de calidad para respuestas abiertas; score numérico 0-1 con justificación; automatizable en CI/CD con umbral configurado como gate de PR.
- **Load test pre-despliegue:** hardware idéntico a producción; parámetros de tráfico basados en percentiles reales (longitud de prompts, output, concurrencia); duración mínima de 30 minutos; verificar TTFT-P95 y TBT-P95 contra los SLOs definidos.
- **Smoke tests de integración:** 5-10 requests de flujos críticos; verificación de formato, streaming, stop tokens y model name en la respuesta; primera línea de defensa antes del golden dataset completo.
- **Canary validation:** 5-10% del tráfico real al modelo candidato durante 24-48 horas antes del despliegue completo; comparación de métricas de negocio (thumbs up/down, tasa de completación); el AB test en producción real no puede ser reemplazado por evaluación offline.

> **Nota del Arquitecto:** El golden dataset mantenido con cuidado y el load test representativo son los dos gates que previenen el 90% de los incidentes de producción relacionados con actualizaciones de modelos. El golden dataset detecta regresiones de calidad; el load test detecta problemas de rendimiento. Omitir cualquiera de los dos es aceptar riesgo de incidente que podría prevenirse con 2-4 horas de trabajo de validación.

La validación pre-despliegue rigurosa es lo que hace que las actualizaciones de modelos sean operaciones predecibles en lugar de eventos de riesgo. La sección siguiente detalla las estrategias de despliegue progresivo y rollback que completan el ciclo de actualización de modelos en producción.
