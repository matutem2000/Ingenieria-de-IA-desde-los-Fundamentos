## Fallback patterns: resiliencia cuando el modelo local falla o supera su capacidad

El fallback pattern en arquitecturas híbridas no es un plan de contingencia de última hora —es una característica de diseño de primera clase que define cómo el sistema responde cuando el modelo local no puede satisfacer una petición de forma satisfactoria. Un sistema que no tiene fallback definido falla ante el usuario cuando el modelo local tiene problemas; un sistema con fallback bien diseñado hace transparente esa degradación y entrega la mejor respuesta posible en todo momento. La diferencia entre los dos no es si los modelos locales pueden fallar —todos pueden— sino si el sistema está diseñado para manejar esos fallos con elegancia.

Los escenarios que deben activar el fallback cubren toda la gama de formas en que un modelo local puede no cumplir con lo requerido. El **fallo técnico** es el más obvio: error HTTP 5xx del servidor de inferencia, OOM (out of memory) por un prompt más largo de lo esperado que satura el KV cache, timeout por una respuesta que excede el tiempo máximo aceptable para el usuario. El **fallo de capacidad** es el más frecuente en sistemas en producción: el prompt tiene más tokens de los que el modelo local soporta en su `--ctx-size` (8.192 tokens para muchos modelos Ollama básicos vs 128K en modelos de frontera en la nube); la petición requiere conocimiento que el modelo local no tiene por ser demasiado especializado o demasiado reciente respecto a su fecha de corte de entrenamiento. El **fallo de calidad** es el más difícil de detectar: el modelo local produce una respuesta técnicamente válida (sin error, dentro del tiempo) pero de calidad insuficiente para el caso de uso. Detectar el fallo de calidad requiere un verificador post-procesamiento.

El **fallback basado en timeout** es la implementación más simple y la primera línea de defensa: se configura un tiempo máximo de espera para la primera respuesta del modelo local (por ejemplo, 5 segundos para el TTFT); si se supera, la petición se cancela y se reenvía a la nube. En Python, `asyncio.wait_for(local_inference_coroutine(), timeout=5.0)` implementa este comportamiento con manejo de `asyncio.TimeoutError` para activar el fallback. La elección del umbral de timeout es un trade-off: demasiado corto genera fallos innecesarios en peticiones legítimas que simplemente tienen prompts largos; demasiado largo degrada la experiencia de usuario en los fallos reales.

El **circuit breaker** es el mecanismo que previene el thundering herd de fallbacks cuando el modelo local está degradado de forma persistente. Si el modelo local falla N veces en una ventana de tiempo W (por ejemplo, 10 errores en 60 segundos), el circuit breaker "abre" y enruta todo el tráfico directamente a la nube durante un tiempo de recuperación T (por ejemplo, 60 segundos), sin intentar el modelo local. Después del tiempo de recuperación, el circuit breaker entra en estado "half-open" y permite un porcentaje pequeño de tráfico al modelo local para verificar si se ha recuperado antes de cerrar de nuevo. La librería `tenacity` de Python o `pybreaker` implementan este patrón con configuración declarativa.

El **cascading fallback** introduce una jerarquía de modelos en lugar de la dicotomía simple local/nube: modelo local 7B → modelo local 13B (si existe) → API de nube de costo intermedio → modelo de frontera en la nube. Cada nivel se activa solo si el anterior falla o no supera el umbral de calidad. Este patrón es especialmente útil en organizaciones con múltiples modelos locales de distintas capacidades disponibles: el 7B maneja el 70% del tráfico, el 13B maneja el 20% de mayor complejidad que el 7B no puede resolver bien, y solo el 10% restante va a la nube. El overhead de latencia del cascading fallback (intentar un modelo, verificar, intentar el siguiente) se mitiga ejecutando los pasos de verificación de calidad en paralelo con la generación, o usando un clasificador pre-generación que predice directamente el nivel de modelo necesario.

## Implementación de fallback patterns

- **Timeout-based fallback:** umbral estricto de TTFT para el modelo local; `asyncio.wait_for()` o timeouts HTTP en el proxy; cancelación limpia de la petición local antes de reenviar a la nube.
- **Circuit breaker:** N fallos en ventana W abren el circuito por T segundos; half-open para verificar recuperación; `pybreaker` o `tenacity` en Python; evita thundering herd cuando el modelo local está degradado.
- **Cascading fallback:** jerarquía 7B → 13B → cloud_económica → cloud_frontera; cada nivel activado por fallo o baja calidad del anterior; el clasificador pre-generación puede predecir el nivel necesario sin intentar los niveles inferiores.
- **Response quality gate:** clasificador binario ligero (DistilBERT o ONNX en CPU) que evalúa la respuesta del modelo local en menos de 50 ms; score bajo activa el fallback a la nube; entrenado en logs de feedback de producción (thumbs up/down).
- **Logging exhaustivo de fallbacks:** cada fallback registra el motivo (timeout / error / baja calidad / contexto largo), el modelo origen, el modelo destino y la latencia adicional; esta telemetría alimenta el ciclo de mejora del clasificador de calidad y del clasificador de routing.

> **Nota del Arquitecto:** El response quality gate es el componente más valioso y el más frecuentemente omitido. Sin él, el sistema enruta a la nube solo cuando hay fallos técnicos obvios, pero permite que respuestas de baja calidad del modelo local lleguen al usuario. Con el quality gate, el sistema puede detectar "el modelo respondió algo, pero es demasiado corto / está fuera de dominio / es incoherente" y activar el fallback silenciosamente. La inversión de implementar un verificador de calidad ligero se recupera en calidad media del sistema.

La telemetría de fallbacks es un activo de gestión del conocimiento: el análisis de los logs revela qué tipos de peticiones fallan más frecuentemente en el modelo local y proporciona exactamente el conjunto de datos necesario para una siguiente ronda de fine-tuning que reduzca la tasa de fallback. El sistema de fallback se convierte así en el mecanismo de recopilación de datos para mejorar el modelo local, cerrando el ciclo de mejora continua de la arquitectura híbrida.
