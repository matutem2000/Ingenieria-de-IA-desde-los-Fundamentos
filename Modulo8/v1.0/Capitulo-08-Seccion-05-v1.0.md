# Módulo 8 – Capítulo 08 – Sección 05

## Perfilado de inferencia: identificar cuellos de botella con herramientas de profiling

Conocer las técnicas de optimización disponibles no es suficiente si no se sabe cuál aplicar primero en un sistema específico. Un sistema con alta latencia de TTFT puede estar sufriendo de prompts largos sin chunked prefill, de un modelo draft incorrecto para el dominio que reduce la tasa de aceptación en speculative decoding, de un pool de KV cache subutilizado, o simplemente de que la GPU elegida no tiene suficiente ancho de banda para el throughput requerido. Aplicar la optimización incorrecta no solo no ayuda: puede empeorar la situación al añadir overhead sin abordar la causa raíz. El perfilado es el proceso de medir para saber dónde está realmente el cuello de botella.

El perfilado de inferencia de LLMs opera en múltiples niveles simultáneos con herramientas distintas para cada nivel. El nivel más alto —el más útil para el monitoreo continuo en producción— es el endpoint `/metrics` de vLLM, que expone métricas Prometheus actualizadas en tiempo real. Las métricas más importantes son: `vllm:num_requests_running` y `vllm:num_requests_waiting` (para ver si hay backpressure en la cola), `vllm:gpu_cache_usage_perc` (porcentaje de uso del pool de KV cache; si supera el 90% consistentemente, el pool está demasiado pequeño), `vllm:time_to_first_token_seconds` (histograma de TTFT), y `vllm:time_per_output_token_seconds` (histograma de TBT). Configurar un dashboard de Grafana con estas métricas y alertas sobre los P95 de TTFT y TBT es el primer paso del monitoreo de producción y debe estar disponible antes del primer despliegue, no después del primer incidente.

El nivel GPU del perfilado requiere herramientas de mayor resolución cuando el dashboard de Prometheus indica anomalías pero no revela la causa. **`nvidia-smi dmon -s puct -d 1`** proporciona monitoreo en tiempo real a 1 Hz de utilización de GPU (%), uso de VRAM (MB), temperatura (°C) y potencia (W): suficiente para detectar problemas estructurales como GPU constantemente al 30% de utilización (indica throttling por temperatura o instancia sobredimensionada) o VRAM al 95%+ (indica pool de KV cache al límite). Para diagnóstico más profundo, **NVIDIA Nsight Systems** (`nsys profile`) captura una traza temporal completa de todos los kernels CUDA, mostrando exactamente qué operaciones dominan el tiempo de ejecución y si hay periodos de GPU idle entre kernels que indican scheduling overhead.

Para diagnóstico de cuellos de botella en el código Python del motor de serving (tokenización, serialización de respuestas, middleware), **`py-spy`** proporciona profiling de CPU sin instrumentación del código: `py-spy top --pid <pid>` muestra en tiempo real las funciones Python con mayor uso de CPU, permitiendo identificar si el cuello de botella está en la GPU o en el procesamiento Python del servidor. Este diagnóstico es especialmente relevante cuando el `nvidia-smi` muestra utilización GPU baja pero las métricas de Prometheus muestran TTFT alto: indica que el tiempo se está gastando en Python (serialización del JSON, tokenización, lógica del servidor) en lugar de en la GPU.

Para benchmarking end-to-end antes del despliegue, los scripts `benchmark_throughput.py` y `benchmark_latency.py` incluidos en el repositorio de vLLM permiten generar workloads sintéticos configurables con longitudes de prompt y output variables, midiendo TTFT P50/P95/P99 y throughput bajo distintos niveles de carga concurrente. Este benchmarking pre-despliegue debe ejecutarse con parámetros que reflejen el percentil 95 del tráfico real de producción —longitudes de prompt, distribución de output lengths, número de requests concurrentes— no con los mejores casos.

## Herramientas de perfilado por nivel

- **Dashboard Prometheus + Grafana:** métricas en tiempo real de vLLM (`num_requests_running`, `gpu_cache_usage_perc`, `time_to_first_token_seconds`); primer nivel de monitoreo de producción; alertas sobre P95 de TTFT y TBT.
- **`nvidia-smi dmon`:** monitoreo a 1 Hz de GPU utilization, VRAM, temperatura y potencia; detección de throttling, subutilización y saturación de VRAM.
- **Nsight Systems:** traza completa de kernels CUDA con timeline visual; identifica GPU idle, solapamiento de kernels y operaciones dominantes; `nsys profile --trace=cuda,nvtx python -m vllm.entrypoints.openai.api_server`.
- **`py-spy`:** profiling de CPU Python sin instrumentación; `py-spy top --pid <pid>` muestra funciones Python con mayor uso de CPU; diagnóstica cuellos de botella en el servidor vs en la GPU.
- **Scripts de benchmark de vLLM:** `benchmark_throughput.py` y `benchmark_latency.py`; workloads sintéticos configurables; TTFT P50/P95/P99 y throughput bajo carga concurrente.

> **Nota del Arquitecto:** El orden correcto de perfilado es de afuera hacia adentro: primero el dashboard de Grafana con métricas de Prometheus para identificar el síntoma (TTFT alto, queue depth, baja utilización de GPU); luego `nvidia-smi` para ver el nivel de utilización real de la GPU; solo si el problema no está claro con esas dos herramientas, Nsight Systems o `py-spy` para el diagnóstico profundo. El 80% de los problemas de producción son visibles con las métricas de Prometheus y `nvidia-smi`; Nsight Systems es para el 20% restante.

El perfilado riguroso es la base del ciclo de mejora continua del rendimiento de inferencia. La sección de cierre sintetiza las técnicas de optimización del capítulo como una disciplina de sistemas que requiere comprensión de hardware además de modelos.
