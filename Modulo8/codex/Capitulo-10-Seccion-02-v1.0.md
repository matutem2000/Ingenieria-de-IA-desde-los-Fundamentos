# Patrón router: clasificar peticiones y dirigirlas al modelo local o de nube según complejidad

El patrón router (también llamado LLM routing o model routing) es una arquitectura donde una capa de clasificación intermedia analiza cada petición entrante y la dirige al modelo más apropiado según criterios de complejidad, sensibilidad, costo o latencia, sin que el cliente final necesite conocer qué modelo procesará su petición. La implementación más simple del router usa un clasificador de texto pequeño (BERT, DeBERTa, o incluso un modelo de ML clásico como logistic regression sobre embeddings) para categorizar cada petición en niveles de complejidad: peticiones simples (preguntas factoriales, reformateos, clasificaciones) se dirigen a un modelo local de 7B; peticiones medianas (resumen de documentos, respuestas con múltiples pasos) a un modelo local de 13B-34B o a una API económica; peticiones complejas (razonamiento multi-hop, análisis de código complejo, síntesis de información conflictiva) a un modelo de frontera en la nube. RouteLLM (proyecto open source de Lmsys) implementa un router basado en matrices de preferencia humana: entrena un clasificador de binarized preference que predice si un par de modelos (local vs nube) producirá respuestas de calidad equivalente para una petición dada, y solo enruta a la nube cuando el clasificador predice una diferencia de calidad significativa. El router debe ser cualitativamente invisible para el usuario: introduce una latencia adicional de 5-20ms en el path de la petición (el tiempo de clasificación) pero el beneficio de costo y eficiencia justifica este overhead para sistemas de alto volumen donde el 70-80% de las peticiones pueden ser servidas localmente.

## Componentes de implementación del patrón router

- Clasificador de complejidad: puede ser tan simple como un ensemble de reglas heurísticas (longitud del prompt, presencia de palabras clave de dominio, número de documentos adjuntos) o tan sofisticado como un modelo de clasificación fine-tuneado; las heurísticas son más rápidas pero menos precisas; el clasificador tiene su propio pipeline de evaluación y mejora continua
- Criterios de routing multidimensionales: la complejidad de la tarea es solo un criterio; otros incluyen: presencia de PII en el texto (routing obligatorio a local), coste previsto de tokens (prompts muy largos pueden ser más económicos en nube si el modelo local tarda demasiado), tipo de usuario (plan premium puede tener acceso preferente a modelos de nube)
- Fallback implícito: el router debe incluir lógica de fallback: si el modelo local produce un error, timeout o respuesta de baja confianza (detectable con un clasificador de calidad de respuesta), la petición se reencamina automáticamente al modelo de nube sin intervención manual
- API unificada: el router implementa la misma interfaz OpenAI-compatible que los backends; el cliente nunca ve dos APIs distintas sino una sola que abstrae la lógica de routing; los headers de respuesta pueden incluir metadatos del modelo usado para debugging
- A/B testing del router: comparar diferentes políticas de routing (umbral de complejidad más alto vs más bajo, diferentes clasificadores) contra métricas de calidad y costo para optimizar el punto de equilibrio; el routing policy es un hiperparámetro del sistema que requiere tuning basado en datos de producción

## Para recordar

El patrón router es la clave de la eficiencia económica en arquitecturas híbridas: enrutar el 80% del tráfico a modelos locales y solo el 20% más complejo a modelos de nube puede reducir el costo total de inferencia en un 60-70% sin degradación perceptible de la calidad promedio.
