# Actualizaciones y rollback: estrategias para reemplazar modelos en producción

El despliegue de una nueva versión de modelo en producción es una operación de mayor riesgo que un despliegue de software convencional: los modelos de lenguaje pueden exhibir regresiones de calidad sutiles que no se detectan en métricas de infraestructura (latencia, error rate) sino en métricas de comportamiento (calidad de respuesta, adherencia a instrucciones, tasa de rechazo de casos límite) que requieren tiempo de observación para manifestarse. La estrategia de despliegue canary es el estándar de la industria para actualizaciones de modelos: se configura un servidor de inferencia con el nuevo modelo y se enruta el X% del tráfico (comenzando con 1-5%) mientras se monitorean simultáneamente métricas de infraestructura (TTFT P95, error rate) y métricas de producto (engagement, conversión, feedback de usuario); el porcentaje se incrementa gradualmente (5% → 10% → 25% → 50% → 100%) con periodos de observación entre cada incremento. En Kubernetes, el canary deployment se implementa con dos Deployments del mismo servicio (uno con la versión actual, uno con la nueva) y un Service que distribuye el tráfico proporcionalmente usando labels; Argo Rollouts o Flagger automatizan el proceso de incremento gradual basado en análisis de métricas, con rollback automático si las métricas cruzan un umbral definido. El rollback de un modelo debe ser una operación que cualquier miembro del equipo pueda ejecutar en menos de 5 minutos: el modelo anterior sigue disponible en el registry, el Kubernetes Deployment tiene `kubectl rollout undo` como mecanismo de rollback inmediato, y el load balancer puede redirigir el tráfico completo al modelo anterior en segundos.

## Estrategias de actualización de modelos

- Blue-Green deployment: se mantienen dos entornos idénticos (blue=actual, green=nuevo); el tráfico se redirige completamente de blue a green una vez que green pasa todos los tests; rollback instantáneo redirigiendo de vuelta a blue; requiere 2x la capacidad de GPU durante el periodo de transición
- Canary progresivo: más económico que Blue-Green; el porcentaje de tráfico al nuevo modelo se incrementa gradualmente; el análisis automático de métricas (Argo Rollouts + Prometheus + Grafana) puede promover o hacer rollback automáticamente; la mayor parte de los deployments maduros de LLMs usan este patrón
- Shadow mode (dark launch): el nuevo modelo recibe una copia del tráfico de producción pero sus respuestas no se envían a los usuarios; permite evaluar la calidad y el rendimiento en tráfico real sin riesgo para el usuario; requiere un sistema de logging paralelo y herramientas de comparación offline; útil para validar modelos con cambios arquitectónicos significativos
- Feature flags para modelos: en arquitecturas con múltiples modelos, usar feature flags (LaunchDarkly, Unleash, o flags en base de datos) para controlar qué porcentaje de usuarios o qué segmentos de usuarios reciben cada versión del modelo; permite experimentos A/B con modelos de forma más granular que el canary a nivel de tráfico total
- Runbook de rollback: documentar el procedimiento exacto de rollback (qué comando ejecutar, quién tiene permisos, cómo verificar que el rollback fue exitoso) y mantenerlo actualizado; el runbook debe ser ejecutable por cualquier persona de guardia, no solo por el equipo de ML

## Para recordar

El rollback de un modelo no es un evento de emergencia sino una parte planeada del ciclo de despliegue: si el proceso de rollback no puede completarse en menos de 5 minutos con un único comando, la arquitectura de despliegue necesita ser rediseñada antes del siguiente release.
