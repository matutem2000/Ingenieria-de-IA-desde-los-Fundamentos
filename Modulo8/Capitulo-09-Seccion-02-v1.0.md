# Versionado de modelos: checkpoints, adaptadores LoRA y snapshots

El versionado de modelos de LLM presenta complejidades que no existen en el versionado de software tradicional: los archivos de pesos son de 2-80 GB, las diferencias entre versiones no son diffables con herramientas de texto, y el componente a versionar puede ser el modelo base completo, un adaptador LoRA de 50-300 MB, o la combinación de ambos; cada uno de estos casos requiere una estrategia de versionado distinta. Los checkpoints de entrenamiento son el mecanismo de versionado durante el proceso de fine-tuning: herramientas como Hugging Face `Trainer` y Axolotl guardan checkpoints cada N steps con los pesos del adaptador LoRA, el estado del optimizador y el paso actual del scheduler de learning rate, permitiendo reanudar el entrenamiento desde cualquier punto sin perder el estado completo; los checkpoints incluyen suficiente información para reproducir el resultado del training desde ese punto. Los adaptadores LoRA son el artefacto de versionado más compacto y versatil: un adaptador de rank 16 sobre un modelo de 7B ocupa 50-150 MB vs los 4-14 GB del modelo completo; se versionan independientemente del modelo base en Hugging Face Hub bajo la estructura `base_model/adapter_name`, y se cargan en tiempo de ejecución con `PeftModel.from_pretrained(base_model, adapter_path)` sin necesidad de replicar el modelo base por cada versión. Los snapshots son capturas completas del modelo fusionado (base + adapter mergeado) que se usan para distribución final: representan el artefacto de producción que se carga en vLLM o se convierte a GGUF para distribución.

## Estrategias de versionado por tipo de artefacto

- Checkpoints de entrenamiento: guardar con frecuencia (cada 100-500 steps) pero retener solo los N mejores según la métrica de validación; Hugging Face Trainer con `save_total_limit=3` mantiene solo los 3 checkpoints más recientes; los checkpoints completos (incluyen estado del optimizador) son 2-3x más grandes que el modelo solo
- Versionado de adaptadores LoRA: usar la estructura `{modelo_base}/{tarea}/{fecha}/{experimento}` como path en el registry; incluir en el README el sha del modelo base, el dataset de entrenamiento, los hiperparámetros y las métricas de evaluación; versionar el dataset junto con el adaptador cuando los datos son propietarios
- Snapshots de producción: los modelos fusionados listo para producción se versionan con tags semánticos (`v1.0`, `v1.1`, `v2.0`); se almacenan en el object storage del registry como SafeTensors o GGUF; solo los snapshots de producción validados deben almacenarse a largo plazo; los checkpoints de entrenamiento pueden archivarse o eliminarse
- Metadata de linaje: cada versión del modelo debe incluir: SHA del código de entrenamiento, SHA del dataset, hiperparámetros usados, métricas de evaluación en el golden set, nombre del modelo base y versión del modelo base; esto permite reconstruir el historial completo de cómo se llegó a cada versión
- Git para configuraciones: los Modelfiles de Ollama, las configuraciones de Axolotl, los scripts de evaluación y las definiciones de datasets se versionan en Git normal; los archivos de pesos (grandes) se gestionan con Git-LFS o directamente en el registry de modelos

## Para recordar

La regla mínima de versionado de modelos es: versionar siempre el modelo base + el adaptador + el dataset como una tupla; la capacidad de reproducir exactamente qué modelo está en producción y con qué datos fue entrenado es el fundamento de cualquier sistema de ML auditable.
